## 1. 이 수업을 왜 듣는가

스칼라(SKALA) 커리큘럼의 목표는 "AI 연구자"를 키우는 것이 아니라, **현장에서 이해관계자의 페인 포인트를 AI 서비스로 해결하는 실전 전문가**를 키우는 것이다.

- 우리는 구글 같은 빅테크와 범용 AI 성능으로 경쟁하지 않는다. SOTA(State of the Art) 모델은 그때그때 가져다 쓰면 된다.
- 우리가 경쟁력을 갖는 지점은 **특정 업무 도메인(버티컬)에 AI를 적용해 이해관계자에게 가치를 주는 것**이다. 빅테크는 전 세계를 대상으로 서비스하기 때문에 오히려 좁고 깊은 업무 도메인에는 들어오기 어렵다.
- 개발 역량 자체가 목적이 아니다. AI에게 개발을 맡기더라도 결과를 검증할 수 있는 최소한의 개발·아키텍처 이해가 필요하기 때문에 스프링, MSA 등을 함께 배우는 것이다. "개발자 양성과정"이 아니라 **AI 서비스를 설계·검증할 수 있는 사람을 키우는 과정**이다.

## 2. AI의 두 갈래: 예측형 AI vs 생성형 AI

### 2.1 예측형 AI (Predictive AI)
- 업무 A → 데이터 A, 업무 B → 데이터 B가 이어지는 구조에서, A·B 데이터로 아직 발생하지 않은 C를 예측/분류/추천하는 방식.
- 전통적인 머신러닝·딥러닝 기반 모델 서빙(추론 엔진)이 이 영역에 해당한다.
- 예: 설비 온도·모터 회전수 패턴으로 장애를 예지하는 예지보전(predictive maintenance).

### 2.2 생성형 AI (Generative AI)
- 사람처럼 "이해하고 말하는" AI. 대표 기술이 언어모델(LLM/SLM)이다.
- 왜 언어모델이 생성형 AI를 대표하는가? → **시장의 선택**. 인류가 축적해온 데이터의 절대다수가 텍스트(언어) 데이터이기 때문이다. 이미지 데이터는 상대적으로 늦게, 어렵게 구축되었다(예: ImageNet 구축 시기).

### 2.3 두 축의 결합
현장 AI 서비스는 예측형 AI(딥러닝 추론)와 생성형 AI(LLM)가 함께 동작하는 경우가 많다.
예) 설비 이상 예지(예측형 AI) → 알람 발생 → LLM이 보고서를 작성하고 사람(Human-in-the-loop)이 판단하거나 자동 처리 후 보고.

## 3. 컴퓨터·딥러닝의 역사적 맥락 (왜 지금 LLM인가)

1. **폰 노이만 구조**: 최초의 컴퓨터는 CPU(연산)·메모리(기억)·디스크(저장)가 분리되어 있었다.
2. **클라우드의 등장(2000년대 전후)**: 이 세 기능을 네트워크로 묶어(클러스터링) 하나처럼 동작시키는 기술이 등장 → 클라우드.
3. 이 변화는 사람의 뇌(뉴런에서 연산·기억·저장이 통합되어 있는 구조)를 흉내낼 수 있는 컴퓨팅 자원을 만들어주었고, 이것이 **딥러닝**의 실용화로 이어졌다.
   - 시각 정보 처리 → CNN (컨볼루션, 초점을 맞추고 시야를 확산하는 방식의 모사)
   - 시간적 순서 정보(말) 처리 → RNN (순차적으로 받아들이고 되짚어보는 방식의 모사)
4. RNN의 한계: 사람처럼 "전체 맥락을 한 번에 삼키고" 문법을 습득하는 방식이 아니라, 앞의 내용을 순서대로 기억해야 해서 오래된 정보를 잊는 문제가 있었다.
5. **2017년 "Attention is All You Need" (Transformer)**: 전체 문장을 한 번에 바라보고, 그 안에서 무엇에 집중(attention)할지 스스로 찾아내는 방식. 사람이 두세 살 때 언어 습득 장치가 열려 문장을 통째로 흡수하며 문법을 체득하는 과정과 유사한 발상.

## 4. Transformer 구조: 인코더 vs 디코더

Transformer는 원래 영어-프랑스어 번역(통번역) 문제를 풀기 위해 제안된 구조로, **인코더(이해)** 와 **디코더(생성)** 로 구성된다.

| 구분 | 역할 | 대표 모델 | 용도 |
|---|---|---|---|
| 인코더 (Encoder-only) | 입력을 깊이 이해 | BERT (2018) | 분류, 검색, 개체명 인식 등 "이해만 하면 되는" 업무 |
| 디코더 (Decoder-only) | 다음 단어를 순차적으로 생성 | GPT 계열 (2018~) | 챗봇, 질의응답 등 "말을 잘해야 하는" 업무 |

- 통역팀에 비유하면 **청취 담당(인코더)** 과 **발화 담당(디코더)** 이 나뉘어 있는 것과 같다.
- BERT 이후 인코더 전용 연구는 어느 정도 정체된 반면, GPT 계열(디코더 전용)은 계속 발전하고 있다. 이는 시장이 "이해"보다 "적절한 생성(답변)"을 더 필요로 하기 때문이다.
- **우리가 SLM을 Fine-tuning하는 목적은 "질의응답을 잘하는 것"이므로, 파인튜닝은 디코더 쪽에 집중한다.**

### 4.1 MLM vs CLM

| 구분 | 전체 명칭 | 특징 |
|---|---|---|
| MLM | Masked Language Model | 입력을 받을 때부터 일부를 마스킹. 전체 문맥(양방향)을 보되 정답을 가려서 학습 → 인코더 계열 |
| CLM | Causal Language Model | 현재까지의 문맥을 바탕으로 다음 토큰을 단방향·순차적으로 예측 → 디코더 계열 |

우리가 파인튜닝하는 대상은 **CLM(디코더)** 이다.

## 5. LLM → SLM으로: 왜 작은 모델을 쓰는가

- LLM(Large Language Model)은 파라미터가 많을수록(예: GPT-5급 약 900억 개 수준으로 언급) 성능이 좋아지지만, 학습·운영에 막대한 자원과 시간이 든다.
- 우리 목적은 "내부 도메인 지식에 대해 잘 답변하는 것"이지, 백과사전적 범용 지식이 아니다. → 굳이 큰 모델이 필요 없다.
- **SLM(Small Language Model)** 은 오픈소스로 공개된 베이스 모델(오픈웨이트 LLM)을 가져와, 우리 도메인에 맞게 파인튜닝해서 쓰는 방식이다.
- Hugging Face: 오픈소스 모델·데이터셋을 공유하는 대표 저장소. 빅테크들이 후원사로 참여하고 있다.
  - Meta → LLaMA 계열 (상용 서비스 대신 전부 오픈소스로 생태계 확보 전략)
  - Google → Gemma 계열
  - 이번 수업에서 사용하는 모델: **Qwen(알리바바)** — 한국어·영어·한자가 섞이는 국내 업무 환경에서 다국어 지원이 상대적으로 우수함. 실습은 Qwen2.5 1.5B(파라미터 15억 개) 모델로 진행.

### 왜 오픈소스로 푸는가 (기업 관점)
- 상용 LLM을 직접 만들어 서비스하려면 비용·인력·책임이 크다.
- 반대로 베이스 모델을 오픈소스로 풀면, 전 세계 개발자들이 그 생태계 위에서 서비스를 만들게 되어 **시장 점유(에코시스템) 확보**에 유리하다.
- 예: 구글이 온디바이스 통번역이 가능한 경량 LLM(Gemma 기반)을 오픈소스로 공개 → 통번역 시장 자체의 진입장벽을 낮춰 생태계를 자기 것으로 만드는 전략.

## 6. SLM을 내부망에 쓰는 이유 — 데이터 주권

### 6.1 상용 LLM(외부 API)의 한계
- 상용 LLM에 사내 영업비밀·개인정보를 연결하면 데이터가 벤더사 인프라로 전송된다.
- 벤더사가 "프라이빗하게 처리하겠다"고 해도, **모델 운영 정책의 결정권은 벤더사에 있다.** 규제·정부 요청 등에 따라 언제든 접근 가능한 구조다.
- 특히 의료, 국방/외교안보 등 규제 산업은 데이터가 외부로 나가는 것 자체가 금지된다.

### 6.2 SLM(내부 구축)의 장점
- 내부망 안에 SLM을 직접 배치 → 인프라·로그를 전부 감사(audit)할 수 있고, 직접 파인튜닝도 가능.
- 상용 LLM은 내부 파라미터를 들여다볼 수 없어(블랙박스) 파인튜닝이 불가능하다.
- 데이터 주권 확보 + 좁지만 깊은(버티컬) 도메인 성능 확보라는 두 가지 목적을 동시에 달성.

### 6.3 내부 파이프라인 vs 외부 파이프라인
| 구분 | 설명 | 적합한 경우 |
|---|---|---|
| 외부 파이프라인 | 상용 LLM API 호출 | 범용 지식, 이미 공개된 방대한 자료(예: 법령/판례) 분석처럼 자체 운영 리소스 투입이 비효율적인 경우 |
| 내부 파이프라인 | 사내망에 SLM을 직접 배치·운영 | 절대 외부로 나가면 안 되는 업무 비밀, 개인정보, DBMS 핵심 정보 |

- 내부 파이프라인 운영에는 서버 자원, 24시간 365일 운영 프로세스, 관리 인력·비용이 필요하다는 트레이드오프가 있다. 실무에서는 보통 **내부·외부 파이프라인을 함께 사용**한다.

## 7. Knowledge Asset(지식 자산) — 왜 이 과정이 중요한가

- 조직이 업무에 AI를 연결하면, 그 업무 처리 결과가 데이터로 축적되고 AI가 이를 사람이 할 수 없는 수준으로 구조화·연결한다. 이것이 조직의 **Knowledge Asset**이다.
- 이 자산은 상용 LLM에 연결하는 순간 외부로 유출될 위험이 있으므로, SLM(내부 파이프라인)과 연결해 축적해야 한다.
- 코드/알고리즘 자체는 대부분 공개되어 있어 개인의 경쟁력이 되기 어렵다. 진짜 경쟁력은:
  1. AI에게 업무를 지시하고, 그 결과를 검증할 수 있는 역량
  2. 현장 이해관계자와 협업하며 그 결과가 실제 가치를 주는지 판단할 수 있는 역량
  3. 이 과정에서 쌓이는 **도메인 지식**

## 8. RAG (Retrieval-Augmented Generation) 맛보기

파인튜닝만으로는 최신 정보나 방대한 사내 지식을 모두 담을 수 없다. 이때 사용하는 것이 RAG다.

1. 사내 문서를 여러 조각(chunk)으로 나눈다.
2. 각 조각을 **임베딩**(embedding) — 사람이 이해하는 정보를 AI(컴퓨터)가 이해할 수 있는 벡터(0과 1의 수치 표현)로 변환.
3. 벡터를 **Vector DB**(실습에서는 Meta의 오픈소스 라이브러리 **FAISS** 사용)에 저장.
4. 사용자가 질문하면, 질문도 동일한 방식으로 임베딩한 뒤 Vector DB에서 **유사도 검색**으로 가장 관련 있는 조각(top-k)을 가져온다.
5. 가져온 조각(context)과 질문을 함께 LLM/SLM에 넣어 답변을 생성한다.
6. 관련 정보가 없을 때는 "모른다"고 답하도록 프롬프트에 명시할 수 있다(할루시네이션 방지의 가장 단순한 형태).

- 추천 임베딩 모델: **BGE-M3** (BAAI 제공, Hugging Face 공개, 다국어 임베딩에 특화).
- 심화 주제(이번 수업 범위 밖, 추후 학습): 청킹 전략, 메타데이터 필터링, 하이브리드 서치(의미 기반 + 키워드 기반), 리랭킹.

## 9. 파인튜닝 전략 개요

### 9.1 Full Fine-Tuning vs PEFT
- **Full Fine-Tuning**: 전체 파라미터를 재학습. 성능은 좋을 수 있으나 시간·비용이 크다.
- **PEFT (Parameter-Efficient Fine-Tuning)**: 전체 파라미터 중 일부만 효율적으로 조정. 실전에서 널리 쓰이는 방식.

### 9.2 대표 PEFT 기법 비유
공장에 비유하면:
- **어댑터(LoRA 등)**: 원본 설비(베이스 모델)는 그대로 두고, 그 옆에 작은 우회 보정 장치를 병렬로 붙여서 학습시키는 방식. "핵심 기계 원본 가동치는 건드리지 않고 병렬로 작은 보정 장치(아답터)를 붙인다" → **LoRA (Low-Rank Adapter)** 가 대표적.
- **Prefix Tuning**: 각 작업 라인 앞에 참고할 메모를 끼워 넣는 것에 비유. 어댑터보다 가벼운 방식.
- **Prompt Tuning**: 공장 정문에 오늘의 작업 지시서를 붙여두는 것에 비유. Prefix Tuning보다 더 가벼움.

가벼운 방식일수록 나쁜 것이 아니라, **가장 적은 비용으로 원하는 성능을 얻는 것이 최선**이라는 관점에서 선택한다.

### 9.3 왜 LoRA인가
- 실전(현업)에서 가장 널리 쓰이는 PEFT 기법.
- 원본 파라미터를 동결(freeze)하고, 일부 레이어 옆에 저랭크(low-rank) 행렬(어댑터)만 학습시킨다.
- 학습된 어댑터는 붙였다 뗐다 할 수 있어 관리가 용이하다.

### 9.4 SFT vs CPT
| 구분 | 전체 명칭 | 특징 |
|---|---|---|
| SFT | Supervised Fine-Tuning | 질문-정답 쌍을 주고 "이렇게 답하라"는 형식으로 지도 학습. 이번 실습의 핵심 방식. |
| CPT | Continued Pre-Training | 라벨 없는 대량의 도메인 텍스트를 계속 학습시키는 방식. 목적에 딱 맞는 답변 형식을 만들기보다는 방대한 지식 주입에 가까움. |

### 9.5 RLHF / DPO (참고, 심화)
- **RLHF (Reinforcement Learning from Human Feedback)**: 사람이 모든 응답을 채점할 수 없으므로 "보상 모델(reward model)"을 만들어 대신 채점하게 하고, 이 피드백으로 강화학습을 진행. 효과적이지만 모델이 "보상 모델의 눈치만 보는" 부작용(reward hacking)이 생길 수 있다.
- **DPO (Direct Preference Optimization)**: 별도의 보상 모델·채점 과정 없이, "이 답이 더 낫다"는 선호(preference) 데이터로 직접 최적화. RLHF의 부작용을 피하기 위한 대안적 접근.

### 9.6 지식 증류 (Knowledge Distillation, 참고)
- 크고 성능이 뛰어난 "교사 모델"(상용 LLM 또는 자체 대형 모델)에게 대량의 원천 데이터를 넣어 고품질 질문-답변 데이터를 생성하게 하고, 이를 정제해 작은 "학생 모델(SLM)"의 학습 데이터로 활용하는 방식. 특히 도메인 학습 데이터가 부족할 때 유용하다.

## 1. Pretraining → Fine-Tuning 개념 재정리

- **Pretrained Model(사전학습 모델)**: 처음 학습시킨 베이스 모델. 이 단계도 "풀 트레이닝(Full Training)" 방식이다.
- 이후 특정 목적으로 **재학습**시키는 모든 과정을 **Fine-Tuning(파인튜닝)** 이라 부른다.
  - 전체 파라미터를 다시 학습 → **Full Fine-Tuning**
  - 일부 파라미터만 효율적으로 학습 → **PEFT (Parameter-Efficient Fine-Tuning)**

### 왜 "일부만 업데이트"가 어려운가 — Catastrophic Forgetting
- 딥러닝은 뉴런처럼 레이어와 가중치가 서로 연결되어 학습(전파)된다.
- 학습된 가중치 중 일부만 수정하려고 해도, 그 수정이 연결된 가중치 전체로 전파되어 **기존에 학습된 내용 전체가 무너지는 현상**이 발생한다. 이를 **Catastrophic Forgetting(재앙적 망각)** 이라 한다.
- 그래서 "일부만 콕 집어 업데이트"하는 것이 딥러닝 구조상 원천적으로 어렵다. → 이 문제를 우회하기 위해 나온 것이 PEFT/LoRA다.

### 책 출판 비유
- Full Fine-Tuning = 책 전체를 다시 써서 재출간하는 것 (비용·시간 큼)
- PEFT/LoRA = 이미 출간된 책에 포스트잇으로 업데이트할 내용만 붙이는 것 (가볍고 빠름)

## 2. LoRA (Low-Rank Adaptation) 심화

### 2.1 개념 — 물감 팔레트 비유
- 원본 모델(베이스 모델)의 파라미터를 전부 **동결(freeze)** 한다.
- 전체 그림(모델이 표현할 수 있는 모든 것)을 다시 그리는 대신, **지금 필요한 그림을 그리는 데 필요한 물감만 뽑아낸 팔레트**를 별도로 만든다고 생각하면 된다. 이 "팔레트"가 바로 LoRA가 추가하는 **저랭크(low-rank) 파라미터**다.
- "Low-Rank"의 의미: 저용량. 전체 파라미터(예: Qwen2.5-1.5B 기준 약 15억 개)를 다 학습하는 게 아니라, 그중 극히 일부(실습 기준 약 1,000여 개 수준)만 추가로 학습한다.
- 이 추가 파라미터(어댑터)는 원본과 **병렬(parallel)** 로 붙는다. 원본 가중치(W)는 건드리지 않고, 별도의 경로를 만들었다가 나중에 합쳐지는 구조다.

### 2.2 왜 여러 개의 LoRA 어댑터를 동시에 붙이지 않는가
- 언어모델(LLM)에서는 서로 다른 문체·규칙·도메인 지식을 학습한 어댑터를 동시에 얹으면 **어댑터 간 간섭(충돌)** 이 발생할 수 있다. 그래서 실전에서는 LLM에 여러 LoRA 어댑터를 동시에 붙이지 않는다.
- 반면 이미지 생성 모델(예: Stable Diffusion)은 병렬 처리 특성상 여러 어댑터를 동시에 붙여도 혼선이 적어, 그런 경우에는 다중 어댑터를 쓰기도 한다. (언어모델과 이미지모델의 차이)

### 2.3 동일 조건으로 학습해도 결과가 완전히 같지 않은 이유
- 같은 베이스 모델, 같은 초기값(seed), 같은 LoRA Config로 학습해도 **이론적으로는 동일할 수 있지만 실제로는 미세하게 달라진다.** 학습 과정의 여러 요인이 완전히 결정론적으로 통제되지 않기 때문이다.

### 2.4 LoRA를 어디에 붙이는가 — QKV
- Transformer의 핵심 연산은 **Query(Q), Key(K), Value(V)** 조합으로 "지금 어디에 주의(attention)를 집중할지" 계산하는 것이다.
- LoRA 어댑터는 이 Q/K/V 관련 레이어 등 특정 위치에 붙일 수 있다.
- 모든 위치에 다 붙이면 이론적으로 성능은 좋아질 수 있지만 학습 시간이 오래 걸린다. 이번 실습 예제에서는 **위치를 2곳만 선택**해 빠르게 결과를 확인할 수 있도록 구성했다(실전에서는 더 많은 위치를 선택하기도 하며, 이는 시간과 성능 사이의 트레이드오프다).

### 2.5 성능을 좌우하는 것은 결국 "데이터"
- 알고리즘(LoRA) 자체는 이미 논문으로 공개되어 있고 가벼운 구조라서, 알고리즘 자체의 차이로 성능이 크게 갈리지 않는다.
- **실전에서 성능을 좌우하는 것은 도메인 지식을 담은 질문-답변 데이터를 어떻게 구성하느냐**이다. (강사가 강조한 핵심 포인트)
- 첨단 파운데이션 모델을 처음부터 새로 학습시키는 영역(사전학습, 초거대 아키텍처 설계)은 국내 유수 대학원조차 따라가기 어려운 자원 경쟁의 영역이다. 우리가 다루는 영역은 **이미 공개된 베이스 모델을 현장에 특화시키는 실전 적용 영역**이며, 여기서의 승부처는 **현장 도메인 지식과 데이터 설계 역량**이다.

## 3. SFT 데이터셋 설계

### 3.1 설계 원칙
같은 원천 문서(규정집)라도 다음에 따라 학습 결과가 달라진다:
- 문서를 **어떻게 쪼개는지**(섹션 단위 등)
- 각 섹션이 **어떤 비율로 노출되는지** (특정 섹션에 치우치면 편향)
- 정답을 **어떤 형식으로 통일하는지**
- "정보가 없을 때"에 대한 대응까지 데이터에 반영되어 있는지 (없으면 모델이 **환각(hallucination)** 을 일으키기 쉬움)

> SFT는 모델이 이미 학습한 지식 자체를 바꾸는 것이 아니라, **어떤 형식·태도로 답할지를 예시로 각인시키는 과정**이다.

### 3.2 실습 데이터 구성 예시 (가상의 HR 사내 규정집 기반)
- 인사 규정 문서를 **섹션 단위로 분할**, 섹션마다 **6개의 질의응답**을 균형 있게 생성 (총 582건).
- 필드 구조: `id`, `source`, `section_id`, `source_title`, `message` 등
- 대화 형식: `System`(역할·답변 원칙 제시) → `User`(질문) → `Assistant`(답변)
- 답변 스타일: **결론을 먼저 제시(두괄식)** 하고 이어서 절차/조건/예외를 안내하는 구조로 통일.
- "정보가 없는 질문"에 대해서는 **모르면 지어내지 말고 모른다고 답하라**는 유형의 데이터도 포함 → 할루시네이션 억제.
- 질문 유형 예: 일반 규정 문의, 절차·조건 문의, 등급/조건이 섞인 복합 질문, 답이 없는 경우 등을 균형 있게 배치.

### 3.3 평가용 별도 데이터
- 강사가 임의로 만든 "가상 회사 휴먼 AI 전용 정책 코드"처럼, **베이스 모델이 절대 알 수 없는 정보**를 5개 정도 질문으로 뽑아 파인튜닝 전/후 성능을 비교할 수 있게 구성.
- RAG를 붙였을 때의 참조 데이터도 별도로 준비하여, **① 베이스 모델만 ② 파인튜닝 모델만 ③ 파인튜닝 + RAG** 세 가지 조건의 답변 품질을 비교할 수 있도록 설계.

## 4. 모델 학습 vs RAG — 언제 무엇을 쓰는가

| 상황 | 방법 |
|---|---|
| 자주 바뀌지 않는 지식(정책, 규정 등) | 모델 자체에 **LoRA 파인튜닝**으로 학습 |
| 자주 갱신되는 정보(최신 공지, 변동성 있는 데이터) | **RAG**(Vector DB에 임베딩만 갱신하면 됨, 재학습 불필요) |

- RAG는 파이프라인이 늘어나는 만큼(검색 → 컨텍스트 결합 → 생성) 응답 시간이 더 걸릴 수 있다. 다만 최신성 유지 측면에서 유리하다.
- 실전에서는 두 방식을 함께 쓰는 경우가 많다: 안정적인 지식은 파인튜닝, 변동성 있는 지식은 RAG.

## 5. 실습 환경 및 학습 실행 개요

- 하드웨어 호환성: NVIDIA GPU(CUDA), Apple Silicon(MPS), CPU 환경 모두에서 동작하도록 코드가 구성되어 있다. 코드가 실행 환경을 자동 감지해 적절한 디바이스를 선택한다.
- 데이터 구조: `train`(학습용) / `validation`(파인튜닝 전후 성능 비교·평가용)으로 분리.
- **베이스 모델 캐시**: 별도 경로를 지정하지 않으면 Hugging Face가 자동으로 로컬 캐시 경로에 베이스 모델을 다운로드·관리한다. 직접 관리하려면 경로를 하드코딩해야 하므로, 특별한 이유가 없다면 자동 캐시 방식을 권장.
  - 상용 LLM(API 방식)은 모델이 벤더사 서버에 있고 API 호출로만 사용 가능하지만, 이번 실습은 **모델을 로컬 PC/서버에 직접 다운로드**해서 사용하는 방식이라는 차이를 이해할 것.
- **학습 산출물**: LoRA 어댑터가 지정된 출력 경로(예: `models/hr_qwen_lora`)에 생성된다.
  - 재학습 시 동일 경로에 다시 실행하면 기존 어댑터가 덮어써진다.
  - 결과가 만족스러우면 해당 폴더를 복사해 별도 디렉토리에 보관하고, 이후 그 경로를 지정해 사용하면 된다.
- **학습 시간**: 예제 기준 평균 약 10분. (강사가 수업 진행상 시간을 의도적으로 맞춰 구성한 값이며, 너무 짧으면 품질이 부족하고 너무 길면 실습 진행이 어려워 이 정도로 설정)
- 코드 구조를 볼 때는 **`main` 함수 중심**으로 어떤 순서로 로드·구성·실행되는지 따라가는 것이 이해에 도움이 된다.
- 주요 하이퍼파라미터: 배치 크기, gradient accumulation, LoRA rank(r) 등 메모리·연산량과 관련된 설정들. 로컬 사양(예: 16GB 메모리 맥북)에 맞춰 값이 조정되어 있다.

## 6. 언어모델 중심 전략에 대한 보충 설명 (질의응답 정리)

**Q. 텍스트 분석(Text Analytics) 중심으로 가는데, 이미지 분석은 나중 순위인가?**

- 지금까지 인류가 축적한 데이터의 절대다수가 텍스트이기 때문에 생성형 AI가 언어모델 중심으로 먼저 발전한 것.
- 다만 AI가 물리 세계로 확장되는 **피지컬 AI(Physical AI)** 방향으로 갈수록 공간·시공간·이미지 데이터의 비중이 커질 것이며, 텍스트와 이미지 분석은 결국 **멀티모달**로 함께 융합되어 갈 전망이다.

**Q. 같은 도구(Transformer, PEFT 등)를 누구나 쓸 수 있는데, 그럼 승부는 어디서 나는가?**

- Transformer 구조, PEFT 기법, 학습 도구는 이미 논문으로 공개되어 누구나 같은 도구를 쓸 수 있다.
- (엔비디아 CUDA 생태계처럼) 도구 자체보다, **그 위에 무엇을 쌓느냐(현장 도메인 지식과 데이터 구성)** 가 실질적인 경쟁력을 좌우한다는 것이 강사의 결론.

## 7. 핵심 용어 정리 (Day 2 추가/보강)

| 용어 | 의미 |
|---|---|
| Catastrophic Forgetting | 딥러닝 특성상 일부 가중치만 업데이트해도 학습된 전체 표현이 무너지는 현상 |
| Full Fine-Tuning | 전체 파라미터를 재학습하는 방식 |
| PEFT | 파라미터 효율적 미세조정. 원본 동결 + 일부만 추가 학습 |
| LoRA (Low-Rank Adaptation) | 원본 가중치를 동결하고 저랭크 어댑터를 병렬로 추가해 학습하는 PEFT 대표 기법 |
| Q, K, V | Transformer Attention의 Query/Key/Value — LoRA 적용 위치 후보 |
| Rank(r) / LoRA Alpha | LoRA 어댑터의 크기(용량)와 스케일링을 결정하는 하이퍼파라미터 |
| Reward Hacking | RLHF에서 모델이 실제 목적보다 보상 모델의 채점 기준에만 맞추려는 부작용 |
| Hallucination(환각) | 근거 없는 정보를 사실처럼 생성하는 현상. 데이터 설계(정답 없음 처리 등)로 완화 가능 |
| Physical AI | AI가 물리 세계(공간, 이미지, 센서 등)로 확장되는 방향성 |
| Multimodal | 텍스트, 이미지, 음성 등 여러 형태의 데이터를 함께 다루는 모델 특성 |
