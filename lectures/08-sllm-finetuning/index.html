1. LLM 서빙 파이프라인 개요

요청 처리 5단계 흐름 · 외부 API 기반 파이프라인 · 내부(자체 호스팅) sLLM 파이프라인 · 선택 기준(비용·보안·지연시간·커스터마이징)

💡
쉽게 말하면: 사용자가 챗봇에 메시지를 보내고 답을 받기까지, 서버 안에서는 "받고 → 다듬고 → 모델에 묻고 → 다시 다듬고 → 돌려주는" 5단계 파이프라인이 돌아가요. 이 파이프라인의 "모델에 묻는" 부분을 OpenAI/Anthropic 같은 외부 API로 채울 수도 있고, 직접 서빙하는 내부 sLLM으로 채울 수도 있어요. 이번 장은 두 구조의 차이와, 어떤 상황에 어느 쪽을 선택해야 하는지를 정리합니다.

1) 요청 처리 전체 흐름 — 5단계

AI 서비스의 백엔드가 사용자 요청 하나를 처리하는 과정은 대체로 다음 5단계로 구성돼요. 이 흐름은 외부 API를 쓰든 내부 sLLM을 쓰든 공통적으로 적용되는 큰 틀이에요.

① 요청 수신 → ② 전처리(Preprocessing) → ③ 모델 추론(Inference) → ④ 후처리(Postprocessing) → ⑤ 응답 반환
③ 모델 추론 단계를 "외부 API 호출"로 채우는지 "내부 sLLM 서버 호출"로 채우는지가 이번 장의 핵심 분기점
  • ① 요청 수신 — 웹/앱 클라이언트가 보낸 사용자 메시지, 세션·인증 정보를 API 서버가 받는다.
  • ② 전처리 — 프롬프트 템플릿 적용, 이전 대화 이력 삽입, 토큰 길이 검증/트리밍, 민감정보(개인정보 등) 마스킹을 수행한다.
  • ③ 모델 추론 — 완성된 프롬프트를 LLM에 전달해 응답을 생성한다. 외부 API 호출이거나, 자체 GPU 서버의 sLLM 호출이다.
  • ④ 후처리 — 생성된 텍스트를 다듬는다(포맷팅, 금칙어·오남용 필터링, JSON 등 구조화, 로깅·모니터링).
  • ⑤ 응답 반환 — 최종 결과를 클라이언트에 전달한다.
🔑 전처리·후처리는 종종 "모델보다 덜 중요하다"고 생각하기 쉽지만, 실서비스 품질을 좌우하는 건 오히려 이 두 단계인 경우가 많아요. 프롬프트를 얼마나 잘 구성하느냐, 생성 결과를 얼마나 안전하게 걸러내느냐가 서비스 신뢰도를 결정합니다.

2) 외부 API 기반 파이프라인 — OpenAI/Anthropic 호출

가장 빠르게 서비스를 시작하는 방법은 OpenAI, Anthropic 같은 상용 LLM API를 그대로 호출하는 거예요. 인프라 구축·모델 학습 없이 API 키만 있으면 바로 고성능 모델을 쓸 수 있어요.

pseudo-code — 외부 API 기반 파이프라인
def handle_request(user_message, history):
    # ② 전처리
    prompt = build_prompt(template="cs_chatbot", history=history, message=user_message)

    # ③ 모델 추론 — 외부 API 호출 (네트워크 밖으로 프롬프트가 나감)
    response = external_llm_api.chat.completions.create(
        model="gpt-4o-mini",       # 또는 claude-*, 예시용 모델명
        messages=prompt,
        max_tokens=512,
    )

    # ④ 후처리
    answer = postprocess(response.text)
    return answer

이 구조는 토큰 사용량만큼 비용이 청구되고, 서버 인프라(GPU) 운영 부담이 없다는 장점이 있어요. 다만 프롬프트와 사용자 데이터가 외부 서비스로 전송된다는 점, 트래픽이 많아질수록 API 비용이 선형적으로 늘어난다는 점을 감안해야 해요.

3) 내부(자체 호스팅) sLLM 파이프라인

반대로 자체적으로 GPU 서버를 두고 sLLM(작은 규모의 LLM)을 직접 호스팅해 추론을 처리할 수도 있어요. 이때는 회사 내부 네트워크(온프레미스 또는 사설 클라우드) 안에서 모든 처리가 끝나요.

pseudo-code — 내부 sLLM 서빙 파이프라인
def handle_request(user_message, history):
    # ② 전처리 (동일)
    prompt = build_prompt(template="cs_chatbot", history=history, message=user_message)

    # ③ 모델 추론 — 내부망의 추론 서버 호출 (데이터가 외부로 나가지 않음)
    response = internal_inference_server.generate(
        model="cs-chatbot-sllm-7b-lora",   # 도메인 특화로 Fine-Tuning된 sLLM
        prompt=prompt,
        max_new_tokens=512,
    )

    # ④ 후처리 (동일)
    answer = postprocess(response.text)
    return answer

내부 sLLM은 초기 인프라 투자(GPU)와 운영 역량이 필요하지만, 일단 구축하고 나면 트래픽이 늘어도 추가 API 비용이 발생하지 않고, 도메인 데이터로 자유롭게 Fine-Tuning해 응답 품질을 계속 개선할 수 있어요.

4) 두 파이프라인의 선택 기준

기준외부 API 기반내부(자체 호스팅) sLLM
비용 구조토큰 사용량 기반 종량제 — 트래픽에 비례해 증가초기 GPU·인프라 투자 후 고정비 중심 — 트래픽이 많을수록 유리
데이터 보안프롬프트·사용자 데이터가 외부로 전송됨내부망 안에서 처리 — 민감 데이터 외부 유출 우려 없음
응답 지연시간외부 네트워크 왕복 지연 포함내부망 직결로 지연시간 최소화·예측 가능
커스터마이징 자유도제한적(프롬프트 엔지니어링 수준)Fine-Tuning으로 도메인 특화·화법 최적화 가능
운영 부담거의 없음(API 호출만 관리)모델 서빙·GPU·스케일링을 직접 운영해야 함
🔎 심화 — "둘 중 하나"가 아니라 "혼합"도 흔하다

실제 서비스에서는 두 구조를 함께 쓰는 경우도 많아요. 예를 들어 일반적인 문의에는 저비용의 내부 sLLM을 우선 사용하고, sLLM이 처리하기 어려운 복잡한 질문만 외부 API로 라우팅하는 하이브리드 파이프라인을 구성하기도 해요. 이는 비용과 품질 사이의 균형을 맞추는 실전 전략입니다.

⚠️ "프라이빗하게 처리하겠다"는 약속만으로는 데이터 주권이 확보되지 않는다

외부 API 벤더가 "고객 데이터를 학습에 쓰지 않겠다"고 약속하더라도, 데이터가 일단 벤더사 인프라로 전송되는 순간 그 운영 정책의 최종 결정권은 벤더사에 있다는 사실은 바뀌지 않아요. 규제 대응이나 정부 요청 등에 따라 벤더가 데이터를 열람·보관해야 하는 상황이 생길 수도 있고요. 의료·국방/외교안보처럼 데이터가 외부로 나가는 것 자체가 금지된 규제 산업에서 내부 sLLM을 선택하는 이유가 바로 이 데이터 주권(Data Sovereignty) — 단순히 "돈을 아낀다"가 아니라 "통제권을 남에게 넘기지 않는다"는 관점이에요.

5) 예측형 AI와 생성형 AI — 이 파이프라인이 다루는 것은 어느 쪽인가

AI 서비스는 크게 두 갈래로 나눌 수 있어요. 이 강의에서 다루는 sLLM·Fine-Tuning은 그중 생성형 AI 쪽에 속해요.

구분예측형 AI(Predictive AI)생성형 AI(Generative AI)
하는 일이미 가진 데이터로 아직 일어나지 않은 것을 예측·분류·추천사람처럼 이해하고 새로운 텍스트를 만들어냄
대표 예시설비 센서 패턴으로 고장을 미리 감지하는 예지보전(predictive maintenance)질문에 답하는 챗봇, 문서 요약·작성
기반 기술전통적인 머신러닝·딥러닝 추론 엔진LLM/sLLM(언어모델)

실제 현장에서는 두 축이 함께 동작하는 경우가 많아요. 예를 들어 설비 이상을 예측형 AI가 먼저 감지하면, 그 결과를 바탕으로 생성형 AI(LLM)가 보고서를 작성하고 사람이 최종 판단하거나 자동으로 후속 조치를 진행하는 식으로 두 기술이 이어지기도 해요.

✔ 1장 핵심 요약
  • LLM 서빙 파이프라인은 "요청 수신 → 전처리 → 모델 추론 → 후처리 → 응답 반환"의 5단계로 구성된다.
  • 외부 API 기반은 빠른 구축·낮은 운영 부담이 장점이지만, 데이터가 외부로 전송되고 종량제 비용이 든다.
  • 내부 sLLM은 초기 투자와 운영 역량이 필요하지만, 데이터 보안·지연시간·커스터마이징 면에서 유리하다.
  • 실전에서는 두 구조를 혼합해 비용과 품질의 균형을 맞추기도 한다.

2. MLM vs CLM — 언어모델 학습 방식

Masked LM(BERT류) vs Causal LM(GPT류) · 양방향 vs 단방향 학습 · 생성형 AI가 CLM 중심으로 발전한 이유

💡
쉽게 말하면: MLM은 문장 중간에 빈칸을 뚫어놓고 "양쪽 문맥을 다 보면서" 빈칸을 채우도록 학습하는 방식이고(BERT류), CLM은 "왼쪽에서 오른쪽으로, 이전 단어들만 보면서" 다음 단어를 예측하도록 학습하는 방식이에요(GPT류). 오늘날 우리가 쓰는 ChatGPT·Claude 같은 생성형 AI는 대부분 CLM 계열이에요 — 그 이유를 이번 장에서 살펴봐요.

1) MLM(Masked Language Model) — 양방향 이해 학습

MLM은 문장의 일부 토큰을 [MASK]로 가려놓고, 모델이 앞뒤 문맥을 모두 활용해 가려진 토큰을 맞히도록 학습해요. BERT가 대표적이고, 이런 방식으로 학습된 모델은 문장 전체를 "이해"하는 데 강점이 있어요.

MLM 학습 예시 — 양방향 문맥 활용
입력: "이 상품은 [MASK] 이내에 무료로 반품할 수 있습니다."
목표: [MASK] → "7일" 예측

- 모델은 "[MASK]" 앞의 "이 상품은"뿐 아니라
  뒤의 "이내에 무료로 반품할 수 있습니다"까지 동시에 참고해서 예측한다.

이런 양방향(bidirectional) 구조 덕분에 MLM 계열 모델은 문장 분류, 감성 분석, 개체명 인식(NER) 같은 이해(Understanding) 중심 태스크에 특히 강해요.

2) CLM(Causal Language Model) — 단방향 생성 학습

CLM은 이전 토큰들만 보고 다음 토큰을 순차적으로 예측하도록 학습해요. 미래 시점의 토큰은 절대 미리 볼 수 없다는 뜻에서 "Causal(인과적)"이라는 이름이 붙었어요. GPT 계열이 대표적이에요.

P(x₁, x₂, ..., xₙ) = ∏ P(xₔ | x₁, ..., xₔ₋₁)
t번째 토큰을 예측할 때, 오직 그 이전 토큰(1 ~ t-1)들만 조건으로 사용한다 — 이것이 CLM의 핵심 제약
CLM 학습 예시 — 단방향 다음 토큰 예측
입력: "이 상품은 7일 이내에 무료로"
목표: 다음 토큰 → "반품" 예측

- 모델은 "반품" 뒤에 어떤 단어가 오는지는 전혀 볼 수 없고,
  오직 왼쪽(과거) 문맥만으로 다음 단어를 순차적으로 생성한다.

3) 구조 비교 — MLM vs CLM

구분MLM(예: BERT)CLM(예: GPT)
문맥 활용 방향양방향(앞+뒤 모두 참고)단방향(이전 토큰만 참고)
학습 목표가려진 토큰(빈칸) 맞히기다음 토큰 순차 예측
주요 아키텍처Transformer EncoderTransformer Decoder
강점 태스크분류·NER·문장 이해텍스트 생성·대화·요약·코드 작성
텍스트 생성구조상 자유로운 생성에 부적합태생적으로 생성에 최적화

4) 왜 오늘날 생성형 AI는 CLM 중심으로 발전했는가

MLM은 "빈칸을 채우는" 방식이라 애초에 정해진 위치의 토큰만 예측할 수 있어요. 반면 우리가 챗봇에 기대하는 건 "질문에 대해 임의 길이의 답변을 처음부터 끝까지 자연스럽게 만들어내는 것"이에요. 이건 다음 토큰을 계속 이어 붙여 나가는 CLM의 생성 방식과 구조적으로 딱 맞아요.

  • CLM은 "다음 토큰 예측"을 반복하는 것만으로 임의 길이의 문장을 끝까지 생성할 수 있다.
  • 대화형 챗봇, 코드 자동완성, 요약·번역 등 대부분의 생성 태스크는 본질적으로 "앞 내용을 보고 다음 내용을 이어가는" 구조다.
  • Fine-Tuning(특히 SFT)도 "주어진 대화 맥락에서 적절한 다음 응답을 생성하도록" 튜닝하는 것이므로 CLM 구조와 자연스럽게 맞물린다.
⚠️ MLM이 "구식"이라거나 "틀렸다"는 뜻은 아니다

MLM 계열이 여전히 검색 랭킹, 문서 분류, 임베딩 생성 등 이해 중심 태스크에서는 폭넓게 쓰여요. 다만 "자유로운 텍스트 생성"이 핵심 목표인 오늘날의 생성형 AI·챗봇 서비스에서는 CLM 계열이 사실상 표준이 됐다는 것이 산업 동향이에요.

5) 산업 동향 — 상용 LLM 대부분이 디코더 기반 CLM

GPT 시리즈, LLaMA 계열, Claude, Gemini 등 오늘날 널리 쓰이는 상용/오픈소스 LLM은 대부분 디코더(Decoder-only) 구조의 CLM 기반이에요. 이는 "범용적으로 무엇이든 생성할 수 있는 모델"을 만드는 데 CLM 구조가 가장 확장성 있게 검증되었기 때문이에요.

✔ 2장 핵심 요약
  • MLM은 양방향 문맥으로 빈칸을 채우는 학습(BERT류) — 이해 태스크에 강하다.
  • CLM은 이전 토큰만으로 다음 토큰을 순차 예측하는 학습(GPT류) — 생성 태스크에 강하다.
  • 생성형 AI·챗봇은 "임의 길이 텍스트를 처음부터 만들어내는" 태스크라 CLM 구조와 본질적으로 맞물린다.
  • 오늘날 상용 LLM 대부분이 디코더 기반 CLM 구조를 채택하고 있다.

3. LLM vs sLLM — 언제 sLLM을 쓰는가

파라미터 규모·비용·지연시간·온프레미스 배포 비교 · 버티컬(도메인 특화) sLLM 요건 · Fine-Tuning의 다리 역할

💡
쉽게 말하면: LLM은 수천억 개 파라미터를 가진 "모든 걸 다 아는 대형 모델"이고, sLLM(small LLM)은 수십억 개 이하의 "특정 목적에 맞게 다듬어 쓰는 작은 모델"이에요. sLLM은 혼자서는 LLM만큼 똑똑하지 않지만, Fine-Tuning으로 특정 도메인에 특화시키면 오히려 그 영역에서는 더 실용적인 선택이 될 수 있어요.

1) 파라미터 규모로 보는 LLM vs sLLM

명확히 정해진 기준선은 없지만, 실무에서는 대략 다음과 같은 감각으로 구분해요.

  • LLM — 대체로 수백억~수천억 개 파라미터. GPU 클러스터 단위의 대규모 인프라에서 서빙된다.
  • sLLM — 대체로 수십억 개(1B~수십B) 이하 파라미터. 1~수 대의 GPU로도 서빙 가능한 규모다.

2) 비교표 — LLM vs sLLM

기준LLM (대형)sLLM (소형)

🔑 sLLM이 LLM보다 "무조건 열등한 대체재"는 아니에요. 범용 지식이 넓게 필요한 상황이 아니라 특정 도메인 안에서 정확하고 빠르게 답하는 것이 목표라면, 잘 튜닝된 sLLM이 오히려 비용·속도·보안 면에서 더 나은 선택일 수 있습니다.

3) 버티컬(도메인 특화) sLLM의 요건

특정 산업·업무 영역에 특화된 sLLM을 버티컬(Vertical) sLLM이라고 불러요. 범용 sLLM을 그대로 쓰는 것과 달리, 버티컬 sLLM이 되려면 다음 요건을 충족해야 실전에서 쓸모가 있어요.

✔ 버티컬 sLLM에 필요한 요건
  • 도메인 용어 이해 — 예: 쇼핑몰 CS라면 "교환/반품/환불/배송지연/부분환불" 등 업무 용어와 그 관계를 정확히 구분해야 한다.
  • 업무 프로세스 이해 — 단순 지식 응답이 아니라, "반품 요청 시 먼저 주문번호를 확인하고 사유를 분류한다" 같은 실제 업무 절차를 반영해야 한다.
  • 일관된 화법·톤 — 조직이 원하는 응대 어조(정중함, 간결함 등)를 일관되게 유지해야 한다.
  • 범용 모델이 흔히 놓치는 예외 케이스 대응 — 도메인 특유의 예외 상황(예: 해외 배송 반품 규정)을 학습해야 한다.

이런 요건은 사전학습(Pre-training)만으로는 충분히 채워지지 않아요. 사전학습 모델은 "일반적인 언어 능력"은 갖췄지만, 특정 조직의 업무 맥락까지는 알지 못하기 때문이에요.

4) Fine-Tuning — 범용 모델을 버티컬 sLLM으로 완성시키는 다리

여기서 Fine-Tuning의 역할이 명확해져요. 사전학습된 범용 sLLM은 언어를 이해하고 생성하는 기본기는 갖췄지만, 특정 도메인의 용어·프로세스·화법까지는 모릅니다. Fine-Tuning은 이 범용 모델에 도메인 데이터를 추가로 학습시켜, "일반적으로 말은 잘하지만 우리 업무는 모르는 모델"을 "우리 업무를 아는 모델"로 완성시키는 다리 역할을 해요.

사전학습(범용 언어 능력) + Fine-Tuning(도메인 데이터) = 버티컬 sLLM(도메인 특화 실무 모델)
사전학습은 "언어를 다루는 법"을, Fine-Tuning은 "우리 업무를 다루는 법"을 가르친다
🔎 심화 — sLLM 선택이 "타협"이 아닌 "전략"이 되는 지점

많은 조직이 처음엔 "더 똑똑한 모델이 무조건 좋다"고 생각해 대형 LLM API부터 검토해요. 하지만 반복적으로 발생하는 특정 업무(예: 정형화된 CS 응대)라면, 그 업무만 정확히 처리하도록 Fine-Tuning된 sLLM이 비용·지연시간·데이터 보안 모든 면에서 더 합리적인 선택이 되는 경우가 많습니다. 이는 "타협"이 아니라 목적에 맞춘 전략적 선택이에요.

✔ 3장 핵심 요약
  • LLM은 넓은 범용 지식이 강점, sLLM은 낮은 비용·빠른 응답·온프레미스 배포 가능성이 강점이다.
  • 버티컬 sLLM이 되려면 도메인 용어·업무 프로세스·화법·예외 케이스까지 이해해야 한다.
  • 이런 도메인 특화는 사전학습만으로는 부족하며, Fine-Tuning이 그 간극을 메우는 다리 역할을 한다.

4. sLLM Use Case — 실전 활용 시나리오

상용 API의 제약 상황 · sLLM이 유리한 활용 사례 3가지 · 고객지원(CS) 챗봇 구현 방향 개요

💡
쉽게 말하면: 상용 LLM API가 항상 정답은 아니에요. 민감한 데이터를 다루거나, 아주 빠른 응답이 필요하거나, 특정 업무 화법을 지켜야 하는 상황에서는 sLLM이 더 실용적인 선택이 될 수 있어요. 이번 장은 그런 상황을 정리하고, 대표 사례로 고객지원(CS) 챗봇을 어떻게 구현할지 큰 그림을 그려봐요.

1) 상용 LLM API를 그대로 쓰기 어려운 제약 상황

제약 상황구체적 이유
민감 데이터 외부 전송 불가고객 개인정보, 주문 내역, 사내 정책 등이 프롬프트에 포함되면 외부 서버로 전송돼야 하는데, 보안·컴플라이언스 상 허용되지 않는 경우가 많다.
매우 낮은 응답 지연 요구실시간 상담 보조, 콜센터 음성 응대처럼 밀리초 단위 응답이 필요한 경우 외부 API의 네트워크 왕복 지연이 부담이 된다.
특정 도메인 전문 용어·화법 필요범용 모델은 특정 업무 맥락(예: 반품/교환 정책의 세부 조건)을 정확히 모르고, 일관된 응대 톤을 유지하기도 어렵다.
높은 API 비용대량 트래픽(초당 수천 건 문의 등) 환경에서는 종량제 API 비용이 누적되어 자체 호스팅보다 비싸질 수 있다.

2) sLLM이 유리한 활용 사례 3가지

✔ 사례 1 — 사내 문서 기반 Q&A
  • 사내 규정, 매뉴얼, 위키 등 외부에 공개할 수 없는 문서를 기반으로 임직원 질의에 답하는 어시스턴트.
  • 문서가 외부로 나가지 않아야 하므로 내부 sLLM(+ RAG 결합)이 적합하다.
✔ 사례 2 — 특정 업무 프로세스 자동 응답
  • 예: 사내 IT 헬프데스크에서 "비밀번호 초기화 절차"처럼 정형화된 절차를 안내하는 봇.
  • 같은 유형의 질문이 반복되므로, 그 범위 안에서 Fine-Tuning된 sLLM만으로도 충분히 높은 정확도를 낼 수 있다.
✔ 사례 3 — 특화 분류/추출 태스크
  • 예: 고객 문의를 "배송/반품/결제/기타"로 자동 분류하거나, 문의 텍스트에서 주문번호·상품명 등을 추출하는 태스크.
  • 생성형 대화보다 태스크 범위가 좁고 명확해, 작은 sLLM으로도 빠르고 저렴하게 처리 가능하다.

3) 대표 시나리오 — 고객지원(CS) 챗봇 구현 방향

이 강의에서는 쇼핑몰 CS 챗봇(반품·교환·배송 문의에 응답하는 챗봇)을 예시 도메인으로 삼아요. 왜 이 시나리오가 sLLM에 적합한지, 구현 방향을 큰 그림으로 살펴봐요.

  • 왜 sLLM인가 — 문의 내용에 주문번호·연락처 등 개인정보가 포함되는 경우가 많아 외부 전송이 부담스럽고, 문의 유형(반품/교환/배송지연/환불)이 어느 정도 정형화되어 있어 sLLM으로도 충분히 커버 가능하다.
  • 데이터 준비 — 실제(혹은 유사) CS 상담 이력을 "고객 질문 → 상담원 응답" 쌍으로 정리해 Fine-Tuning용 학습 데이터로 구성한다(7장에서 구체적인 데이터 구조를 다룬다).
  • 모델 선택과 튜닝 — 수십억 파라미터급 오픈소스 sLLM을 기반으로, PEFT 기법(5·6장)을 적용해 CS 도메인에 특화시킨다.
  • 서비스 배치 — 사내 GPU 서버에 추론 서버를 띄우고, 기존 CS 상담 시스템(또는 챗봇 UI)과 연동한다(11·12장에서 아키텍처를 다룬다).
CS 챗봇 문의-응답 예시 (Fine-Tuning 학습 데이터 개념 미리보기)
{
  "instruction": "고객 문의: 어제 주문한 신발이 사이즈가 안 맞아서 교환하고 싶어요. 어떻게 해야 하나요?",
  "response": "안녕하세요, 고객님. 상품 수령일로부터 7일 이내에는 사이즈 교환이 가능합니다. 주문 내역에서 '교환 신청'을 선택하신 뒤 원하시는 사이즈를 입력해 주시면, 접수 후 1~2일 내 새 상품을 발송해 드립니다."
}
🔑 위 데이터 형식은 7장 "SFT 학습 데이터 구조 설계"에서 더 자세히 다뤄요. 이번 장에서는 "왜 이 도메인에 sLLM이 적합한지"에 집중해요.
✔ 4장 핵심 요약
  • 민감 데이터·낮은 지연시간·도메인 화법·높은 API 비용은 상용 API 사용을 어렵게 만드는 대표 제약이다.
  • 사내 문서 Q&A, 정형화된 업무 자동응답, 분류/추출 태스크는 sLLM이 특히 유리한 영역이다.
  • CS 챗봇은 개인정보 민감성과 정형화된 문의 유형을 동시에 갖춰 sLLM Fine-Tuning의 대표적인 활용 사례다.

5. Fine-Tuning 전략과 PEFT 기법 개요

Full Fine-Tuning vs PEFT · LoRA·Prompt Tuning·Prefix Tuning·Adapter 비교 · 시나리오별 기법 선택 기준

💡
쉽게 말하면: Full Fine-Tuning은 모델의 모든 파라미터를 다시 학습시키는 "풀 리모델링"이고, PEFT(Parameter-Efficient Fine-Tuning)는 일부 파라미터만 학습시키는 "부분 인테리어"예요. PEFT는 훨씬 적은 비용·시간으로 비슷한 효과를 낼 수 있어서, 오늘날 sLLM Fine-Tuning의 사실상 표준 접근법이 됐어요.

1) Full Fine-Tuning — 모델 전체를 재학습

Full Fine-Tuning은 사전학습된 모델의 모든 파라미터를 도메인 데이터로 다시 업데이트하는 방식이에요. 이론적으로는 가장 높은 성능을 낼 잠재력이 있지만, 현실적인 제약이 커요.

  • 모델 전체 파라미터만큼의 GPU 메모리가 필요하다(옵티마이저 상태까지 포함하면 파라미터 수의 몇 배 메모리가 필요).
  • 학습 시간·컴퓨팅 비용이 매우 크다 — 수십억 파라미터 모델이면 고성능 GPU 여러 대로도 오랜 시간이 걸린다.
  • 학습된 모델 전체를 별도로 저장해야 해서, 여러 용도의 모델을 각각 만들면 저장 공간 부담도 커진다.

2) 왜 "일부만 콕 집어 업데이트"가 어려운가 — Catastrophic Forgetting

PEFT가 필요한 진짜 이유를 이해하려면 먼저 짚어야 할 문제가 있어요. 딥러닝 모델은 뉴런처럼 레이어와 가중치가 서로 촘촘하게 연결되어 학습(전파)돼요. 그래서 "이 부분만 살짝 고치자"고 의도해도, 그 수정이 연결된 가중치 전체로 퍼져나가면서 기존에 학습해둔 능력 전체가 무너지는 현상이 생길 수 있어요. 이를 Catastrophic Forgetting(재앙적 망각)이라고 불러요.

🔑 그래서 "전체 파라미터 중 필요한 일부만 딱 골라 업데이트"하는 건 딥러닝 구조상 원천적으로 까다로운 문제예요. 원본 가중치를 아예 건드리지 않고 옆에 작은 어댑터만 새로 붙이는 PEFT(다음 절 및 6장의 LoRA)는, 바로 이 Catastrophic Forgetting을 원천적으로 피해가기 위한 접근이라고 이해하면 전체 그림이 잡혀요.

3) PEFT — 일부 파라미터만 효율적으로 학습

PEFT(Parameter-Efficient Fine-Tuning)는 원본 모델 파라미터는 대부분 고정(freeze)한 채, 작은 규모의 추가 파라미터만 학습시켜 모델을 원하는 방향으로 조정하는 접근법이에요.

Full Fine-Tuning: 전체 파라미터 θ 를 갱신  |  PEFT: 원본 θ 고정 + 소수의 추가 파라미터 Δθ만 갱신
PEFT는 Δθ의 크기를 원본 대비 1% 미만 수준으로 줄이는 것이 일반적인 목표
  • 학습해야 할 파라미터 수가 크게 줄어 GPU 메모리·학습 시간이 절약된다.
  • 원본 모델은 그대로 두고 "작은 조각(어댑터)"만 저장하면 되므로, 여러 도메인용 버전을 가볍게 관리할 수 있다.
  • 대신 Full Fine-Tuning만큼의 근본적인 모델 변화를 만들기는 어려워, 데이터가 매우 많고 근본적인 성능 개선이 필요한 경우엔 한계가 있을 수 있다.

6. LoRA 파라미터 구조 이해

저랭크 행렬 A·B의 원리 · rank(r)·alpha 하이퍼파라미터 · target_modules · 파라미터 절감 수치 예시

💡
쉽게 말하면: LoRA는 원본 가중치는 그대로 얼려두고(freeze), 그 옆에 아주 작은 두 개의 행렬 A·B를 붙여서 그 둘의 곱만 학습시키는 방법이에요. 원본 모델은 건드리지 않으니 안전하고, 학습해야 할 파라미터 수는 원본의 1% 미만으로 줄어드는 경우가 많아요.

1) LoRA 핵심 원리 — 저랭크 행렬 A·B

원본 Transformer의 가중치 행렬을 W₀(크기 d×k)라고 할 때, LoRA는 W₀를 직접 업데이트하지 않고, 그 옆에 훨씬 작은 두 행렬 A(r×k)와 B(d×r)를 새로 추가해요. 이때 r(rank)은 원본 차원(d, k)보다 훨씬 작은 값이에요.

h = W₀x + ΔWx = W₀x + BAx
W₀(원본, 고정) + B·A(저랭크 행렬 곱, 학습 대상) — 추론 시엔 W₀+BA로 병합해 원본과 동일한 구조로 사용 가능
  • W₀(원본 가중치)는 학습 과정 내내 고정(freeze)되어 전혀 업데이트되지 않는다.
  • A, B라는 두 개의 작은 행렬만 새로 추가되어 이 둘만 학습된다.
  • 학습이 끝나면 ΔW = BA를 원본 W₀에 더해 하나의 행렬로 병합(merge)할 수 있어, 추론 시 별도의 연산 구조 변경 없이 기존 모델과 동일한 속도로 서빙할 수 있다.
🔎 심화 — 왜 "저랭크"로 충분한가

LoRA는 "Fine-Tuning으로 만들어지는 가중치 변화량(ΔW)은 실제로 매우 낮은 랭크(rank)를 갖는 경향이 있다"는 관찰에서 출발해요. 즉 모델을 도메인에 맞게 조정하는 데 필요한 정보량 자체가 원본 가중치 전체 공간에 비해 작기 때문에, 굳이 ΔW 전체(d×k 크기)를 다 학습하지 않고 훨씬 작은 저랭크 근사(B×A)만으로도 충분히 그 변화를 표현할 수 있다는 아이디어입니다.

2) rank(r)와 alpha 하이퍼파라미터

하이퍼파라미터의미영향
r (rank)A·B 행렬의 저랭크 차원 수. 학습 가능한 파라미터 양을 직접 결정한다.r이 클수록 표현력은 커지지만 학습 파라미터·메모리도 늘어난다. 보통 4~64 사이 값을 많이 쓴다.
alphaΔW = BA에 곱해지는 스케일링 계수(보통 alpha/r 비율로 적용).alpha가 클수록 LoRA로 학습된 변화가 원본 출력에 더 강하게 반영된다. r과의 비율로 학습 강도를 조절하는 용도로 쓰인다.
🔑 실무에서는 흔히 alpha를 r의 2배 전후로 설정하는 경우가 많지만(예: r=8, alpha=16), 정답은 없고 데이터·태스크에 따라 실험적으로 조정해요.

3) target_modules — 어느 레이어에 LoRA를 적용할까

LoRA는 모델의 모든 가중치 행렬에 적용할 필요가 없어요. target_modules는 LoRA를 적용할 대상 레이어를 지정하는 설정이에요. 가장 흔한 선택은 Self-Attention의 Query(Q)·Value(V) 투영 행렬이에요.

  • Query, Value(Q, V) — Attention이 "무엇에 주목할지"를 결정하는 핵심 부분. 가장 흔히 LoRA를 적용하는 대상.
  • Key(K), Output projection — 필요에 따라 추가로 포함시켜 표현력을 늘릴 수 있다.
  • Feed-Forward(MLP) 레이어 — 더 강한 적응이 필요할 때 함께 적용하기도 하지만, 그만큼 학습 파라미터가 늘어난다.

4) 코드로 보는 LoRA 설정 (PEFT 라이브러리 스타일)

pseudo-code — LoRA Config 정의 (Hugging Face PEFT 스타일)
from peft import LoraConfig, get_peft_model

lora_config = LoraConfig(
    r=8,                                  # rank — 저랭크 행렬의 차원
    lora_alpha=16,                        # 스케일링 계수 (보통 r의 약 2배)
    target_modules=["q_proj", "v_proj"],  # Attention의 Query·Value 투영 행렬에만 적용
    lora_dropout=0.05,                    # 과적합 방지용 드롭아웃
    bias="none",
    task_type="CAUSAL_LM",                # CLM 계열 sLLM Fine-Tuning
)

# 원본 sLLM 위에 LoRA 어댑터를 부착
model = get_peft_model(base_model, lora_config)
model.print_trainable_parameters()
# 예: trainable params: 4,194,304 || all params: 7,004,193,792 || trainable%: 0.0599

5) 파라미터 절감 수치 예시

70억(7B) 파라미터 규모의 sLLM에 위와 같이 Q·V 프로젝션에만 r=8 LoRA를 적용하면, 학습 대상 파라미터가 전체의 1% 미만으로 줄어드는 경우가 흔해요.

구분파라미터 수(예시)비율
원본 모델 전체 파라미터약 70억 개100%
LoRA 학습 대상 파라미터(A+B, target_modules=Q,V)약 400만~1,000만 개 내외0.1% 이하 ~ 1% 미만
⚠️ "파라미터가 적으니 성능도 그만큼 떨어진다"는 오해

학습 파라미터 수가 적다고 해서 최종 성능이 비례해서 낮아지는 건 아니에요. LoRA는 "모델을 통째로 다시 만드는 것"이 아니라 "이미 잘 학습된 원본 위에 도메인에 맞는 작은 보정을 얹는 것"이라, 목적에 맞게 잘 설계하면 Full Fine-Tuning에 근접한 성능을 훨씬 적은 자원으로 달성할 수 있어요.

6) 여러 LoRA 어댑터를 동시에 붙이지 않는 이유

"도메인마다 어댑터를 하나씩 만들어서 여러 개를 한 모델에 동시에 얹으면 안 되나?"라는 질문이 자주 나와요. 언어모델에서는 서로 다른 문체·규칙·도메인 지식을 학습한 어댑터를 동시에 얹으면 어댑터끼리 간섭(충돌)이 생기기 쉬워서, 실전에서는 LLM에 여러 LoRA 어댑터를 한 번에 동시 적용하지 않는 것이 일반적이에요.

🔑 반대로 이미지 생성 모델(예: Stable Diffusion 계열)은 처리 방식의 특성상 여러 어댑터를 동시에 붙여도 상대적으로 혼선이 적어, 스타일 어댑터를 여러 개 조합해 쓰는 경우가 흔해요. 언어모델과 이미지모델에서 LoRA 어댑터를 다루는 관행이 다르다는 점을 기억해두면 좋아요.

7) 같은 설정으로 다시 학습해도 결과가 완전히 같지 않은 이유

동일한 베이스 모델·같은 초기값(seed)·같은 LoRA Config로 다시 학습시켜도, 결과 어댑터의 가중치나 응답이 미세하게 달라지는 경우가 있어요. 이론적으로는 완전히 같아야 할 것 같지만, GPU 연산의 병렬 처리 순서 같은 여러 요인이 실제로는 완전히 결정론적으로 통제되지 않기 때문이에요. 그래서 파인튜닝 결과를 평가할 때는 "한 번 돌린 결과"만 보고 성급히 판단하기보다, 약간의 변동성이 있을 수 있다는 점을 감안하는 것이 좋아요.

🎯 결국 성능을 좌우하는 것은 "데이터"

LoRA 알고리즘 자체는 이미 논문으로 공개되어 있고 구조도 비교적 단순해서, 알고리즘을 얼마나 잘 아는지로 최종 성능이 크게 갈리지는 않아요. 실전에서 결과 품질을 실질적으로 좌우하는 건 도메인 지식을 담은 질문-답변 데이터를 어떻게 구성하느냐예요(7장에서 자세히 다룹니다). 처음부터 초거대 모델을 새로 사전학습시키는 영역은 막대한 자원이 필요한 별개의 경쟁 영역이고, 우리가 다루는 "공개된 베이스 모델을 현장에 특화시키는" 영역에서는 현장 도메인 지식과 데이터 설계 역량이 진짜 승부처예요.

7. SFT 학습 데이터 구조 설계

SFT의 목적 · instruction/output 및 messages 형식 jsonl · 토픽 균형과 일관된 포맷의 중요성 · 애매한 정답 대응 · CS 챗봇 데이터 샘플

💡
쉽게 말하면: SFT(Supervised Fine-Tuning)는 모델에게 "이런 질문엔 이런 형식·태도로 답해야 해"라는 걸 소수의 정답 예시로 각인시키는 과정이에요. 모델은 이미 말하는 법을 알고 있으니, SFT의 진짜 일은 새로운 지식을 넣는 것보다 "정답의 모양"을 가르치는 것에 가까워요. 그래서 데이터를 어떻게 구조화하고 균형 있게 구성하느냐가 결과 품질을 크게 좌우해요.

1) SFT의 목적 — "정답의 형식·태도"를 각인시키는 과정

사전학습(Pre-training)된 모델은 이미 방대한 텍스트로부터 언어 구사 능력과 일반 지식을 갖추고 있어요. 하지만 "질문을 받으면 정중하게, 이 회사의 정책에 맞게, 이 포맷으로 답하라"는 것까지는 몰라요. SFT(Supervised Fine-Tuning)는 "질문(입력) → 정답(출력)" 쌍으로 이루어진 소수의 예시 데이터를 모델에 보여주면서, 원하는 응답 형식·어조·판단 기준을 학습시키는 과정이에요.

  • SFT는 모델에게 없던 지식을 대량으로 주입하는 단계라기보다, 이미 아는 것을 "우리가 원하는 방식으로" 꺼내 쓰도록 조정하는 단계에 가깝다.
  • 그래서 데이터 양보다 데이터 품질과 일관성이 훨씬 중요하다 — 수십만 건의 뒤죽박죽 데이터보다 수백~수천 건의 정제된 예시가 더 나은 결과를 낼 수 있다.
  • CS 챗봇이라면 "반품 문의엔 이런 순서로, 이런 어조로 답한다"는 패턴을 소수의 고품질 예시로 각인시키는 것이 SFT의 목표다.

SFT 데이터는 보통 한 줄에 하나의 학습 예시를 담는 jsonl(JSON Lines) 형식으로 준비해요. 대표적으로 두 가지 스키마가 널리 쓰여요.

3) 토픽별 노출 균형과 일관된 정답 포맷이 중요한 이유

SFT 데이터를 구성할 때 흔히 놓치는 부분이 토픽 간 균형과 포맷 일관성이에요. 이 두 가지가 무너지면 학습이 잘 되어도 실제 서비스에서 응답이 불안정해져요.

  • 토픽별 노출 균형 — CS 챗봇이라면 반품·교환·배송·환불·기타 문의가 골고루 포함돼야 한다. 특정 토픽(예: 반품)이 데이터의 80%를 차지하면, 모델은 배송지연 문의에도 반품 응대 패턴을 섞어 답하는 등 토픽 편향이 생기기 쉽다.
  • 일관된 정답 포맷 — 같은 유형의 질문에는 항상 비슷한 구조(인사 → 상황 확인 → 처리 방법 → 다음 안내)로 답하도록 데이터를 통일해야 한다. 예시마다 형식이 들쭉날쭉하면 모델도 어떤 형식이 "정답"인지 확신하지 못해 응답이 불안정해진다.
  • 이 두 가지가 흔들리면 응답 안정성이 떨어지고 환각(hallucination) 발생률이 높아진다 — 모델이 배운 패턴이 일관되지 않으면, 모르는 상황에서 그럴듯하지만 근거 없는 답을 지어내는 경향이 강해진다.
🔎 심화 — 데이터 양보다 "분포"가 먼저다

데이터를 추가로 더 모으기 전에, 지금 가진 데이터의 토픽별 분포와 포맷 일관성부터 점검하는 게 우선이에요. 예를 들어 문의 500건 중 반품이 400건, 배송지연이 20건뿐이라면, 배송지연 응답 품질은 데이터를 더 모아도 개선되지 않고 오히려 반품 패턴에 계속 끌려갈 수 있어요.

4) 정답이 애매하거나 없는 경우의 데이터 설계

실제 CS 상황에서는 명확한 정답이 없는 문의도 많아요(예: 회사 정책에 없는 특수 사례, 추가 확인이 필요한 애매한 요청). 이런 케이스를 데이터에서 빼버리면, 모델은 실제 서비스에서 비슷한 상황을 만났을 때 근거 없이 지어내는(환각) 답을 내놓기 쉬워요.

  • "모른다"고 답하는 예시를 의도적으로 포함 — "죄송하지만 해당 사안은 담당자 확인이 필요합니다. 상담원 연결을 도와드릴까요?" 같은, 확답 대신 안전하게 에스컬레이션하는 응답 패턴을 학습 데이터에 넣어둔다.
  • 추가 정보 요청 패턴 포함 — 문의만으로 정확한 답을 줄 수 없을 때 "주문번호를 알려주시면 확인해 드리겠습니다"처럼 되묻는 예시를 넣어, 모델이 불충분한 정보로 단정 짓지 않도록 유도한다.
  • 정책 범위 밖 질문에 대한 거절 예시 — 회사 정책에 없는 요구(예: 정책 외 특별 할인)에는 정중히 안내 범위를 밝히는 예시를 넣는다.
⚠️ "정답 데이터만 모으면 된다"는 오해

SFT 데이터를 "질문 → 확실한 정답"의 쌍으로만 구성하면, 모델은 모든 질문에는 확신에 찬 답이 있어야 한다고 착각하게 돼요. 애매하거나 정보가 부족한 상황에서도 그럴듯한 문장을 지어내는 습관이 들 수 있어요. "모르면 되묻거나 안전하게 넘긴다"는 것 자체도 SFT로 가르쳐야 할 중요한 행동 패턴이에요.

8. sLLM·PEFT 최신 트렌드

성능·효율 향상 연구의 3대 축 — 파라미터 효율화 · Context/Reasoning 확장 · 추론 효율화

💡
쉽게 말하면: sLLM과 PEFT 관련 연구는 대체로 세 방향으로 발전하고 있어요. ① 더 적은 파라미터로 더 잘 학습되게(파라미터 효율화), ② 더 긴 문맥과 더 깊은 추론이 가능하게(Context/Reasoning 확장), ③ 서빙을 더 빠르고 싸게(추론 효율화). 이 세 축을 알아두면 새로운 논문·기술이 나왔을 때 "이건 어느 축의 개선인가"를 빠르게 파악할 수 있어요.

1) 축 ① — 파라미터 효율화: 더 적은 파라미터로 더 잘 학습되게

6장에서 다룬 LoRA도 이 축에 속해요. 목표는 "학습해야 할 파라미터 수를 최소화하면서도 Full Fine-Tuning에 가까운 성능을 내는 것"이에요.

  • 양자화 결합형 PEFT — 원본 모델 가중치를 4비트 등으로 양자화(quantization)해 메모리를 더 줄이면서 그 위에 LoRA 어댑터를 학습하는 방식이 널리 쓰인다. 소비자용 GPU 한 대로도 수십억 파라미터 모델을 Fine-Tuning할 수 있게 해준 핵심 흐름이다.
  • LoRA의 변형 기법들 — 랭크를 레이어마다 다르게 자동 배분하거나, 가중치 초기화 방식을 개선해 더 적은 스텝으로 수렴하도록 하는 등, LoRA 자체를 더 효율적으로 다듬는 연구가 꾸준히 이어지고 있다.
  • 어댑터 조합·전환 — 여러 도메인용 어댑터를 하나의 베이스 모델 위에서 상황에 맞게 갈아 끼우거나 조합해 쓰는 멀티 어댑터 운용 방식도 실무에서 자리잡고 있다.

2) 축 ② — Context/Reasoning 확장: 더 긴 문맥, 더 깊은 추론

모델이 한 번에 참고할 수 있는 입력 길이(컨텍스트 길이)를 늘리고, 복잡한 문제를 단계적으로 풀어내는 추론 능력을 강화하는 방향이에요.

  • 긴 컨텍스트 지원 확대 — 초창기 모델은 수천 토큰 수준이었지만, 최근에는 수만~수십만 토큰 규모의 문서를 한 번에 참고할 수 있는 모델이 늘고 있다. 긴 상담 이력, 방대한 사내 문서를 통째로 프롬프트에 넣는 활용이 가능해진다.
  • 추론(Reasoning) 능력 강화 — 답을 바로 내놓기보다 중간 사고 과정을 거쳐 단계적으로 결론에 도달하도록 학습·유도하는 흐름이 확산되고 있다. 복잡한 정책 판단이 필요한 CS 문의(예: 여러 조건이 얽힌 환불 가능 여부 판단)에서 특히 유용하다.
  • sLLM 관점에서는 무작정 컨텍스트를 늘리기보다, RAG로 필요한 부분만 압축해 넣어주는 방식과 병행하는 것이 비용·속도 면에서 현실적인 경우가 많다(9장에서 자세히 다룬다).

3) 축 ③ — 추론 효율화: 서빙 속도·비용 최적화

학습이 아무리 잘 되어도, 실제 서비스에서 응답이 느리거나 GPU 비용이 크면 실용성이 떨어져요. 이 축은 이미 학습된 모델을 얼마나 빠르고 저렴하게 서빙할 것인가에 집중해요.

  • 추론 전용 양자화 — 서빙 시점에 모델 가중치를 더 낮은 비트로 압축해 메모리 사용량과 연산량을 줄인다.
  • 배치 처리·캐싱 최적화 — 여러 사용자의 요청을 효율적으로 묶어 처리하거나(배치), 반복되는 문맥의 중간 계산 결과를 재사용(KV 캐시 등)해 처리량을 늘린다.
  • LoRA 어댑터 병합 — 6장에서 본 것처럼 학습이 끝난 LoRA는 원본 가중치에 병합할 수 있어, 추론 단계에서 별도의 구조 변경 없이 원본과 같은 속도로 서빙할 수 있다.
  • 경량 서빙 프레임워크 — 다수의 동시 요청을 효율적으로 스케줄링하는 전용 추론 서버 프레임워크를 도입해 처리량과 지연시간을 함께 개선하는 것도 최근 실무의 표준 흐름이다.

9. RAG vs Fine-Tuning — 목적별 기법 선택

RAG(검색 증강 생성)의 원리 · Fine-Tuning과의 근본적 차이 · 선택 기준 비교표 · 임베딩 모델·벡터DB 선정 개요

💡
쉽게 말하면: RAG는 모델은 그대로 두고 "질문에 관련된 문서를 검색해서 프롬프트에 끼워 넣는" 방식이고, Fine-Tuning은 "모델 자체를 다시 학습시켜 내부에 지식·화법을 새기는" 방식이에요. 둘은 경쟁 관계가 아니라 서로 다른 문제를 푸는 도구예요 — "정보가 최신이어야 하는가"와 "모델의 말투·판단 방식을 바꾸고 싶은가"가 핵심 분기점이에요.

1) RAG(Retrieval-Augmented Generation)의 원리

RAG는 사용자 질문이 들어오면, 모델이 답하기 전에 관련 문서를 벡터DB에서 검색해 그 내용을 프롬프트에 함께 넣어주는 방식이에요. 모델 파라미터는 전혀 바뀌지 않고, "참고 자료"만 매 요청마다 새로 제공돼요.

① 질문 임베딩 → ② 벡터DB에서 유사 문서 검색(top-k) → ③ 검색된 문서 + 질문을 프롬프트에 결합 → ④ LLM이 그 내용을 바탕으로 답변 생성
모델 자체는 학습되지 않는다 — "이번 질문에 필요한 지식"을 매번 프롬프트로 주입하는 방식
pseudo-code — RAG 파이프라인 (CS 챗봇, 정책 문서 검색)
def rag_answer(user_question):
    # ① 질문을 임베딩 벡터로 변환
    query_vec = embedding_model.encode(user_question)

    # ② 벡터DB에서 관련 정책 문서 top-k 검색
    docs = vector_db.search(query_vec, top_k=3)
    # 예: ["교환/반품 정책 v3", "해외배송 반품 규정", "환불 처리 절차"]

    # ③ 검색된 문서를 프롬프트에 결합
    prompt = f"""아래 정책 문서를 참고해 고객 문의에 답하세요.
[참고 문서]
{format_docs(docs)}

[고객 문의]
{user_question}"""

    # ④ LLM 추론 (모델 자체는 변경되지 않음)
    return llm.generate(prompt)

2) RAG vs Fine-Tuning — 근본적인 차이

  • RAG — 모델의 "머릿속 지식"은 그대로 두고, 매 요청마다 필요한 정보를 외부에서 검색해 넣어주는 방식. 지식을 업데이트하려면 벡터DB의 문서만 바꾸면 된다.
  • Fine-Tuning — 모델 자체(가중치)를 재학습시켜, 지식·화법·판단 기준을 모델 내부에 새기는 방식. 지식을 바꾸려면 다시 학습 데이터를 만들고 재학습해야 한다.
  • 즉 RAG는 "책을 옆에 두고 찾아보며 답하는 것", Fine-Tuning은 "책의 내용을 아예 외워버리는 것"에 가까운 차이예요.

3) 선택 기준 비교표

4) 임베딩 모델·벡터DB 선정 시 고려사항

RAG를 구현하려면 질문·문서를 벡터로 바꾸는 임베딩 모델과, 그 벡터를 저장·검색하는 벡터DB가 필요해요. 선정 시 아래를 고려해요.

  • 임베딩 모델 — 도메인 언어(한국어, 전문 용어)를 얼마나 잘 반영하는가, 임베딩 차원 수(검색 정확도와 저장·연산 비용의 트레이드오프), 문서 길이 제한을 고려한다.
  • 벡터DB — 검색 속도 — 근사 최근접 이웃(ANN) 검색 알고리즘의 지원 여부와 대규모 데이터에서의 검색 지연시간을 확인한다.
  • 벡터DB — 스케일 — 문서 수가 앞으로 얼마나 늘어날지, 그에 따라 인덱스 재구축·샤딩이 얼마나 수월한지를 본다.
  • 벡터DB — 관리 편의성 — 자체 호스팅이 필요한지, 관리형 서비스가 있는지, 기존 인프라(내부망 배포 등)와의 호환성도 함께 고려한다.
🔑 RAG는 "검색이 얼마나 정확한가"에 품질이 크게 좌우돼요. 아무리 좋은 LLM을 붙여도 엉뚱한 문서가 검색되면 답변도 부정확해지므로, 임베딩 모델·검색 파라미터(top-k, 유사도 임계값 등) 튜닝에 충분한 시간을 투자해야 해요.
✔ 실습·소규모 서비스에서 자주 쓰는 오픈소스 조합 예시
  • 벡터DB — Meta가 공개한 오픈소스 벡터 검색 라이브러리 FAISS는 별도 서버 없이 로컬 환경에서 빠르게 유사도 검색을 실습·검증해볼 수 있어 학습·소규모 배포 단계에서 자주 쓰인다.
  • 임베딩 모델 — BGE-M3(BAAI 공개, Hugging Face에서 이용 가능)처럼 다국어·다양한 문서 길이를 지원하는 임베딩 모델은 한국어가 섞인 사내 문서를 다룰 때 특히 유용하다.
🔑 여기서 소개한 청킹·검색 조합은 RAG의 가장 기본적인 형태예요. 실전에서는 문서를 어떻게 쪼갤지(청킹 전략), 검색 결과를 메타데이터로 한 번 더 거르는지(메타데이터 필터링), 의미 기반 검색과 키워드 검색을 함께 쓰는지(하이브리드 서치), 검색 결과 순위를 한 번 더 다듬는지(리랭킹) 같은 심화 주제가 이어지지만, 이 강의에서는 RAG의 기본 원리와 Fine-Tuning과의 선택 기준까지만 다뤄요.
✔ 9장 핵심 요약
  • RAG는 관련 문서를 검색해 프롬프트에 넣어주는 방식으로, 모델 자체는 재학습하지 않는다.
  • Fine-Tuning은 모델 가중치를 재학습해 지식·화법을 모델 내부에 각인시킨다.
  • 정보가 자주 바뀌고 즉시 반영이 필요하면 RAG, 말투·형식·판단 패턴을 안정적으로 고정하고 싶으면 Fine-Tuning이 유리하다.
  • RAG 품질은 임베딩 모델과 벡터DB(검색 속도·스케일·관리 편의성) 선정에 크게 좌우된다.

10. PEFT 시나리오 설계

RAG + Fine-Tuning 하이브리드 시나리오 · "RAG로 풀지, Fine-Tuning으로 풀지, 둘 다 쓸지" 판단 프레임워크

💡
쉽게 말하면: 실전 서비스에서는 RAG와 Fine-Tuning 중 하나만 고르기보다 둘을 함께 쓰는 경우가 훨씬 많아요. 예를 들어 "말투·응대 형식은 Fine-Tuning으로 고정하고, 최신 정책·재고 정보는 RAG로 보강"하는 식이에요. 이번 장은 이 둘을 결합하는 대표 패턴과, 요구사항이 들어왔을 때 무엇을 선택할지 판단하는 흐름을 정리해요.

1) 왜 하이브리드가 필요한가

9장에서 봤듯, RAG와 Fine-Tuning은 각자 잘하는 영역이 달라요. RAG는 최신 정보 반영에 강하고, Fine-Tuning은 일관된 화법·판단 로직을 각인시키는 데 강해요. CS 챗봇처럼 "항상 정중하게 답해야 하면서, 동시에 최신 배송·재고 정보도 반영해야 하는" 서비스는 둘 중 하나만으로는 완전히 커버되지 않아요.

Fine-Tuning(고정 — 화법·형식·판단 프로세스) + RAG(가변 — 최신 정책·재고·이벤트 정보) = 안정적이면서 최신 정보에 강한 CS 챗봇
"변하지 않는 것"은 모델에 각인시키고, "자주 변하는 것"은 검색으로 보강한다

2) 하이브리드 시나리오 예시 — CS 챗봇

pseudo-code — Fine-Tuned sLLM + RAG 결합 파이프라인
def hybrid_answer(user_question, history):
    # ① 전처리 — 대화 이력 결합
    prompt_context = build_context(history, user_question)

    # ② RAG — 최신 정책/재고/이벤트 정보 검색 (가변 정보 보강)
    query_vec = embedding_model.encode(user_question)
    retrieved_docs = vector_db.search(query_vec, top_k=3)

    # ③ Fine-Tuned sLLM 호출 — 화법·판단 프로세스는 모델에 이미 각인됨
    #    검색된 문서는 참고자료로만 프롬프트에 추가
    prompt = f"""{prompt_context}
[참고 — 최신 정책/재고 정보]
{format_docs(retrieved_docs)}"""

    response = cs_finetuned_sllm.generate(prompt)   # 말투·응대 순서는 Fine-Tuning으로 이미 학습됨
    return postprocess(response)
  • Fine-Tuning이 담당하는 부분 — "인사 → 상황 확인 → 처리 방법 안내 → 다음 단계 안내"라는 응대 프로세스, 정중하고 간결한 어조, "모르면 되묻는다"는 태도(7장에서 다룬 패턴).
  • RAG가 담당하는 부분 — 이번 주 진행 중인 프로모션 조건, 특정 상품의 실시간 재고, 최근 업데이트된 반품 정책 예외 조항처럼 자주 바뀌는 사실 정보.

3) "RAG로 풀지, Fine-Tuning으로 풀지, 둘 다 쓸지" 판단 프레임워크

새로운 요구사항이 들어왔을 때, 아래 흐름으로 판단하면 어느 기법을 써야 할지 빠르게 방향을 잡을 수 있어요.

Q1. 이 요구사항이 다루는 정보가 자주 바뀌는가?
  ├─ YES → Q2. 모델의 말투·판단 로직도 함께 바뀌어야 하는가?
  │    ├─ YES → RAG + Fine-Tuning 하이브리드
  │    └─ NO  → RAG만으로 충분
  └─ NO  → Q3. 응답의 형식·어조·판단 패턴을 일관되게 고정하고 싶은가?
      ├─ YES → Fine-Tuning만으로 충분
      └─ NO  → 프롬프트 엔지니어링만으로 우선 시도
정보의 변동성(Q1)과 화법·판단 고정 필요성(Q2·Q3)이라는 두 축으로 기법을 결정한다
요구사항 예시정보 변동성화법 고정 필요선택
반품 접수 응대 어조·순서 통일낮음높음Fine-Tuning
이번 달 프로모션 할인 조건 안내높음낮음RAG
정중한 어조 유지 + 실시간 재고 기반 교환 가능 여부 안내높음높음RAG + Fine-Tuning
간단한 인사말 응답낮음낮음프롬프트 엔지니어링
🔎 심화 — 처음부터 Fine-Tuning으로 시작하지 않는다

실무에서는 보통 프롬프트 엔지니어링 → RAG → Fine-Tuning 순서로 복잡도를 높여가며 접근해요. 프롬프트만으로 해결되는 요구사항에 굳이 학습 데이터를 만들고 재학습할 필요는 없어요. Fine-Tuning은 프롬프트·RAG로도 안정적인 품질이 나오지 않을 때, 혹은 화법·판단 로직을 구조적으로 고정해야 할 때 투입하는 것이 비용 효율적이에요.

✔ 10장 핵심 요약
  • 실전 서비스는 RAG와 Fine-Tuning 중 하나만 쓰기보다, 고정된 화법은 Fine-Tuning으로 최신 정보는 RAG로 보강하는 하이브리드 구조가 흔하다.
  • 요구사항을 판단할 때는 "정보가 자주 바뀌는가"와 "말투·판단 패턴을 일관되게 고정하고 싶은가" 두 축을 함께 본다.
  • 실무에서는 보통 프롬프트 엔지니어링 → RAG → Fine-Tuning 순으로 복잡도를 높여가며 접근하는 것이 효율적이다.

11. sLLM 서비스 아키텍처 설계

전체 파이프라인(요청 → 라우팅/전처리 → RAG 검색 or Fine-Tuned 추론 → 후처리 → 응답) · 벡터DB 선정 기준 · 시스템 구성요소

💡
쉽게 말하면: 지금까지 배운 SFT, PEFT, RAG를 실제 서비스로 조립하면 어떤 그림이 될까요? 사용자 요청이 들어오면 어디로 보낼지 판단(라우팅)하고, RAG 검색 또는 Fine-Tuned 모델 추론을 거쳐, 후처리를 마친 뒤 응답하는 하나의 파이프라인으로 이어져요. 이번 장은 그 전체 그림과 각 구성요소를 정리해요.

1) 전체 서비스 파이프라인

① 사용자 요청 → ② 라우팅/전처리 → ③ RAG 검색 and/or Fine-Tuned 모델 추론 → ④ 후처리 → ⑤ 응답
10장의 판단 프레임워크(RAG/Fine-Tuning/하이브리드)가 ③ 단계에서 실제 분기 로직으로 구현된다
  • ① 사용자 요청 — 챗봇 UI, 앱, 콜센터 상담 보조 도구 등에서 들어오는 고객 문의 텍스트와 세션 정보.
  • ② 라우팅/전처리 — 문의 유형 분류(배송/반품/교환/기타), 개인정보 마스킹, 대화 이력 결합, 프롬프트 템플릿 적용을 수행한다. 문의 유형에 따라 다음 단계에서 RAG를 탈지, Fine-Tuned 모델만 탈지 결정한다.
  • ③ RAG 검색 and/or Fine-Tuned 모델 추론 — 10장의 판단 기준에 따라, 최신 정보가 필요하면 벡터DB 검색을 거치고, 항상 도메인 특화 Fine-Tuned sLLM이 최종 응답을 생성한다.
  • ④ 후처리 — 생성된 응답의 포맷 정리, 금칙어·오남용 필터링, 필요시 JSON 구조화(예: 상담 시스템 연동용 필드 추출), 로깅.
  • ⑤ 응답 — 최종 답변을 클라이언트(챗봇 UI 등)에 반환하고, 필요하면 사람 상담원에게 에스컬레이션한다.

스케일문서 수가 늘어날 때(예: 정책 문서, 과거 상담 이력 누적) 인덱스 재구축·확장이 수월한가.

내부망 배포 가능 여부CS 문의에 개인정보가 포함될 수 있으므로, 내부망(온프레미스/사설 클라우드) 배포가 가능한지도 중요한 선정 기준이다.
메타데이터 필터링검색 시 "카테고리=배송" 같은 조건으로 사전 필터링할 수 있는지 — 문의 유형별 라우팅과 결합하면 검색 정확도를 높일 수 있다.
🔑 벡터DB 하나만 잘 고른다고 검색 품질이 보장되진 않아요. 문서를 얼마나 적절한 단위(청크)로 쪼개서 저장하는지, 임베딩 모델이 도메인 용어를 얼마나 잘 반영하는지가 함께 맞아떨어져야 실제 검색 정확도가 나와요.

4) 라우팅 단계의 역할 — RAG/Fine-Tuning 분기

10장에서 세운 판단 프레임워크는 이 아키텍처의 라우팅/전처리 단계에서 실제로 구현돼요. 예를 들어 문의가 "프로모션 조건"으로 분류되면 RAG 검색을 거치도록, "환불 처리 순서 안내"로 분류되면 RAG 없이 Fine-Tuned 모델만으로 응답하도록 분기할 수 있어요.

🔎 심화 — 라우팅도 결국 작은 분류 모델의 일이다

이 라우팅(문의 유형 분류) 자체도 4장에서 다룬 "특화 분류 태스크"의 한 예시예요. 별도의 경량 분류기(작은 sLLM 또는 전통적 분류 모델)를 두어 라우팅을 처리하면, 무거운 생성형 모델을 매 요청마다 라우팅 판단에까지 쓰지 않아도 되어 전체 파이프라인의 지연시간과 비용을 줄일 수 있어요.

✔ 11장 핵심 요약
  • sLLM 서비스는 "요청 → 라우팅/전처리 → RAG 검색 and/or Fine-Tuned 추론 → 후처리 → 응답"의 파이프라인으로 구성된다.
  • 벡터DB는 검색 속도·스케일·관리 편의성·내부망 배포 가능 여부·메타데이터 필터링을 기준으로 선정한다.
  • 라우팅/전처리 단계에서 10장의 판단 프레임워크(RAG/Fine-Tuning/하이브리드)가 실제 분기 로직으로 구현된다.

12. sLLM 서비스 구현과 배포

Fine-Tuning이 꼭 필요한 카테고리 판단 기준 · 전처리/추론/후처리 모듈 분리 이유 · 배포 전 체크리스트

💡
쉽게 말하면: 이 강의의 마지막 장이에요. 지금까지 배운 SFT·PEFT·RAG·아키텍처 설계를 실제로 구현하고 배포하는 단계에서 확인해야 할 것들을 정리해요 — 어떤 기능이 Fine-Tuning까지 필요한지, 코드를 왜 모듈로 나눠야 하는지, 배포 전에 무엇을 점검해야 하는지예요.

1) 어떤 기능이 Fine-Tuning이 꼭 필요한 카테고리인가

모든 기능에 Fine-Tuning이 필요한 건 아니에요. 아래 기준에 해당할수록 Fine-Tuning 투자가 정당화돼요.

판단 기준Fine-Tuning 필요성 높음Fine-Tuning 필요성 낮음
반복 빈도매우 자주 발생하는 문의 유형(예: 반품/교환 응대)드물게 발생하는 예외적 문의
응답 일관성 요구정해진 화법·순서를 반드시 지켜야 함자유로운 형식이어도 무방함
프롬프트만으로 재현 가능성프롬프트로 유도해도 형식이 자주 흔들림프롬프트 지시만으로 안정적으로 재현됨
도메인 특수성일반 모델이 잘 모르는 용어·프로세스가 많음일반 상식 수준으로 충분히 처리됨
🎯 CS 챗봇 예시

"반품/교환 접수 응대"는 반복 빈도가 매우 높고, 회사가 원하는 화법·절차를 일관되게 지켜야 하므로 Fine-Tuning이 필요한 대표 카테고리예요. 반면 "이번 주 이벤트가 뭐예요?" 같은 단순 정보 안내는 RAG만으로 충분히 처리되는 경우가 많아, 굳이 Fine-Tuning 대상으로 삼지 않아도 돼요.

2) 코드 모듈 구조 — 전처리/추론/후처리를 분리하는 이유

11장의 파이프라인을 실제 코드로 옮길 때는 전처리(preprocess) / 추론(infer) / 후처리(postprocess)를 명확히 분리된 모듈로 구현하는 것이 중요해요.

모듈 구조 예시 — CS 챗봇 서비스
cs_chatbot_service/
├── preprocess/
│   ├── mask_pii.py          # 개인정보(연락처, 주소 등) 마스킹
│   ├── classify_intent.py   # 문의 유형 분류(배송/반품/교환/기타) → 라우팅
│   └── build_prompt.py      # 대화 이력 + (필요시) RAG 검색 결과 결합
├── retrieval/
│   ├── embed.py              # 질문 임베딩
│   └── vector_search.py      # 벡터DB 검색
├── infer/
│   └── sllm_client.py        # Fine-Tuned sLLM 추론 서버 호출
└── postprocess/
    ├── filter_content.py     # 금칙어·오남용 필터링
    ├── format_response.py    # 응답 포맷 정리, 구조화
    └── log_interaction.py    # 로깅·모니터링
  • 독립적인 교체·개선이 가능하다 — 예를 들어 임베딩 모델을 바꾸거나 필터링 규칙을 추가할 때, 추론 모듈이나 다른 단계를 건드릴 필요가 없다.
  • 테스트가 쉬워진다 — 각 모듈을 독립적으로 단위 테스트할 수 있어, "전처리에서 개인정보가 잘 마스킹되는가"를 모델 추론과 무관하게 검증할 수 있다.
  • 장애 지점을 빠르게 좁힐 수 있다 — 응답 품질에 문제가 생겼을 때, 전처리·검색·추론·후처리 중 어느 단계의 문제인지 로그로 구분해 원인을 빠르게 찾을 수 있다.
  • 모델 교체에 강하다 — Fine-Tuned 모델을 새 버전으로 교체하거나, 특정 기능만 다른 모델로 바꿔도 나머지 파이프라인은 그대로 유지할 수 있다.

3) 배포 전 체크리스트

✔ 배포 전 최종 점검 항목
  • 성능 검증 — 토픽별(반품/교환/배송/환불/기타) 평가셋으로 응답 정확도·형식 일관성을 확인했는가. 특정 토픽에 편중된 성능 저하는 없는가(7장의 토픽 균형 문제와 연결).
  • 응답 시간 — 실제 트래픽 부하 상황에서도 목표 응답 지연시간(예: 2초 이내)을 만족하는가. 동시 요청이 몰릴 때의 큐잉 지연도 측정했는가.
  • 환각(hallucination) 모니터링 — 정책에 없는 내용을 지어내는 응답이 없는지 샘플링 검수했는가. RAG 검색 실패 시 "모른다"고 안전하게 답하는지 확인했는가(7장의 애매한 케이스 대응과 연결).
  • 안전장치 — 금칙어·오남용 필터링이 정상 동작하는가. 정책 범위를 벗어난 요구(예: 규정 외 환불)에 안전하게 거절하는가.
  • 에스컬레이션 경로 — 챗봇이 처리하기 어려운 문의를 사람 상담원에게 자연스럽게 넘기는 흐름이 마련되어 있는가.
  • 롤백 계획 — 새 버전(모델·RAG 인덱스 포함) 배포 후 문제가 발견되면 즉시 이전 버전으로 되돌릴 수 있는가. 모델·어댑터 버전 관리가 되어 있는가.
  • 모니터링·로깅 — 배포 이후에도 응답 품질·지연시간·오류율을 지속적으로 관측할 대시보드와 알림이 준비되어 있는가.
⚠️ "학습이 끝나면 배포는 형식적인 절차"라는 오해

Fine-Tuning으로 좋은 평가 지표를 얻었다고 해서 실서비스에서도 항상 안전한 건 아니에요. 실제 사용자 질문은 학습 데이터보다 훨씬 다양하고 예측 불가능한 표현으로 들어와요. 배포 전 체크리스트는 "형식적 절차"가 아니라, 학습 단계에서 미처 걸러지지 않은 위험을 마지막으로 점검하는 실질적인 안전망이에요.
