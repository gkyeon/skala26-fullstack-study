쉽게 말하면: 생성형AI는 지난 10여 년의 ICT 트렌드 중에서도 가장 빠르게 기대의 정점을 찍고, 가장 빠르게 옥석 가리기 구간에 진입한 기술이에요. 2023년 "Generative AI"가 정점을 찍은 뒤, 2024년엔 "Prompt Engineering·RAG"가, 2025년엔 "AI Agent"가 그 자리를 이어받았죠. 이번 장에서는 이 흐름이 왜 일어났고, 우리가 지금 어디쯤 서 있는지를 살펴봅니다.

1) Hype Cycle로 살펴보는 ICT 트렌드

Gartner의 Hype Cycle(하이프 사이클)은 새로운 기술이 등장한 뒤 "기술 촉발 → 기대의 정점(Peak of Inflated Expectations) → 환멸의 계곡(Trough of Disillusionment) → 계몽의 언덕(Slope of Enlightenment) → 생산성의 안정 단계(Plateau of Productivity)"를 거친다고 보는 모델이다. 연도별로 어떤 기술이 어느 단계에 있었는지를 비교하면, 지금 우리가 어느 국면에 있는지를 가늠할 수 있다.

2) 2018, Deep Learning 열풍

알파고 vs 이세돌 대국(2016)은 바둑이라는 특정 영역에서 인공지능 신드롬을 불러왔다(알파고는 명예 9단을 수여받았다). 이 열풍은 AGI(Artificial General Intelligence) — 인간이 할 수 있는 어떠한 지적 업무도 성공적으로 해낼 수 있는 기계의 지능 — 에 대한 논의로 이어졌다. Yann LeCun은 특정 과업에 필요한 특징에 집중하는 신경망 중심 접근을 새로운 비전으로 제시하며, 10~15년 내 AR안경과 결합된 인간 수준 지능 비서를 전망하기도 했다.

6) 생성형 AI, 주목받는 기술 요소 — 2024 Hype Cycle for Generative AI

Gartner의 2024년 Hype Cycle for Generative AI를 세부적으로 보면, 기술마다 위치가 다르다.

  • Peak 근처 — Retrieval-Augmented Generation, Prompt Engineering, AI TRiSM, Vector Databases
  • 상승 곡선(촉발~정점 진입 구간) — Open-Source LLMs, Multimodal Generative AI, Transfer Learning, Artificial General Intelligence, GraphRAG, Autonomous Agents, Embedding Models
  • Trough 근처(하강 중) — Foundation Models, Synthetic Data, Generative AI, Large Language Models
🔎 흥미로운 대비: "Generative AI"·"Large Language Models" 자체는 이미 Trough로 내려가고 있는 반면, 그 위에서 파생된 "Prompt Engineering"·"RAG"·"Autonomous Agents"는 여전히 상승 또는 Peak 근처에 있다. 큰 우산(범주) 기술은 식어도, 그 우산 아래 구체적인 실행 기술은 계속 새로 뜨고 있는 것이다.

7) 생성형 AI를 넘어 AI Agent의 시대로

From Chatbots to AI Agents — 3단계의 진화 과정으로 정리할 수 있다.

단계특징대표 기술
① 답변하는 AIAI가 답변을 한다는 것 자체에 놀라워하던 시기Prompt Engineering
② 근거를 찾아 답하는 AI의도한 대로 외부지식과 함께 답변을 잘 받아내는 법을 익힌 시기LLM Reasoning with RAG
③ 스스로 실행하는 AI시킨 일을 스스로 다 알아서 하길 원하는 시기, Actor로서의 AIAI Agent

즉 "AI는 답변하는 존재 → 지시를 따르는 존재 → 목표를 달성하는 존재로 진화"하고 있다. 생성형 AI는 환상에서 깨어난 뒤의 냉정한 시험대, 옥석 가리기 구간에 들어섰고, 그 바통을 AI Agent가 이어받아 2025년 Hype Cycle의 Peak 근처를 차지하고 있다.

8) AI Agent 도입을 검토하는 이유 — 숫자로 나타난 효과

코딩 성능 벤치마크에서, 모델 자체의 성능 향상보다 Agent 구조(에이전틱 워크플로우)의 도입 효과가 훨씬 크게 나타난 사례가 있다.

구성정확도
GPT-3.5, zero-shot48.1%
GPT-4, zero-shot67.0%
GPT-3.5 + 에이전틱 워크플로우95.1%
✔ 핵심 인사이트
  • 상대적으로 열위한 모델(GPT-3.5)이 Agent 구조를 앞세워 상위 모델(GPT-4 zero-shot)의 성능을 크게 앞질렀다.
  • 적절한 Agent 구조가 동반되면 약한 모델도 강한 모델을 이긴다.
  • 이제는 모델 성능 그 자체뿐 아니라, 그 모델을 어떻게 조직화(Agent 구조)하느냐가 동등하거나 더 중요해지는 시대다.

9) AI Agent 시대에도 변하지 않는 핵심

AI Agent의 시작은 결국 프롬프트와 LLM에 대한 이해다. Agent의 구조를 도식화하면 다음과 같다.

User Goal → AI Agent[ Planning → Tool Calling → Workflow → LLM + Prompt(핵심 엔진) ] → Reasoning & Action
모든 판단과 의사결정은 결국 LLM이 수행하고, Agent 구조는 그 판단을 실행 가능한 절차로 감싸는 역할을 한다
  • Planning — 목표 달성을 위한 계획 수립
  • Tool Calling — 필요한 도구나 외부 서비스 호출
  • Workflow — Task를 협업하여 실행
  • LLM + Prompt — 자연어 이해·추론·의사결정의 핵심 엔진. 모든 판단과 의사결정은 LLM이 수행한다.
🎯 정리

"AI Agent는 LLM을 대체하는 기술이 아니라, LLM의 능력을 업무 프로세스로 확장하는 기술"이다. 좋은 AI Agent를 만들기 위해서는 생성형 AI의 원리와 Prompt Engineering에 대한 이해가 여전히 가장 중요한 기반이 된다 — 이것이 이번 강의 전체를 관통하는 문제의식이다.

10) 다음 혁신의 무대는 Physical AI일까?

AI 혁신은 이제 디지털을 넘어 물리 세계로 확장되고 있다. 휴머노이드 로봇, 산업용 로봇팔 등 다양한 사례가 CES 등 전시회에서 시연되며, "다음 혁신은 화면 밖(Physical AI)에서 일어날 것"이라는 전망이 힘을 얻고 있다.

12) LLM 시대, Enterprise 기업들의 고민

LLM을 활용한 생성형 AI 도입 시 기업들이 마주치는 대표적인 허들은 다음과 같다.

  • 회사 내부 정보·전문 영역 정보 활용 — LLM은 대규모 범용 정보를 학습했지만, on-premise 상의 내부 정보나 폐쇄적인 전문 영역 정보는 학습되지 않았거나 신뢰도가 낮다.
  • 적시성의 확보 — 정보의 최신성이 중요한 영역에서는 LLM 학습 시점 이후의 최신성이 문제가 된다.
  • 답변의 신뢰성, Hallucination 방지 — 웹 수집 정보에 기반한 답변은 때때로 그럴듯한 거짓말을 출력한다. 수많은 범용 데이터를 재료로 학습한 LLM은 환각 현상에 구조적으로 노출되어 있다.

2. 생성형AI 동작 원리와 한계

Language Model이란 · GPT 학습 데이터 · LLM의 Scale · Hallucination

💡
쉽게 말하면: LLM은 사실 "다음 단어를 그럴듯하게 맞히는 기계"예요. 방대한 텍스트를 학습해서 "이 앞에 이런 말이 나왔으면, 다음엔 이런 단어가 나올 확률이 높다"를 계산할 뿐이죠. 이 원리를 이해하면 왜 LLM이 가끔 그럴듯한 거짓말(Hallucination)을 하는지, 왜 최신 정보에 약한지가 자연스럽게 설명됩니다.

1) What is LM(Language Model)?

LM은 가장 자연스러운 단어 시퀀스를 찾아내는 모델이다.

예시: "퇴근 후 공항에 택시를 타고 갔는데, 탑승시간에 늦어서 결국 비행기를 (___)" — 앞에 순차적으로 나열된 단어들을 살펴보았을 때 ( )에 들어갈 만한 그럴듯한(likeliness) 단어는 무엇일까? 후보와 등장 확률: 놓쳤다 0.72, 탔다 0.15, 봤다 0.08.

앞의 단어들의 history를 보고 다음 단어를 추론하는 것은 언어를 이해하는 것(Language Understanding)과 일맥상통한다. 어떤 문장(단어 시퀀스)이 주어졌을 때 다음 단어에 대해 "얼마나 그럴듯하냐"를 수리적(확률)으로 나타낼 수 있다면, 문장의 앞부분이 주어졌을 때 다음 단어를 예측할 수 있다.

다음 단어는 어떻게 예측할까? 앞에 등장한 단어들을 고려하여 후보가 될 수 있는 여러 단어들 중 높은 확률을 가진 단어를 선택한다. 등장 확률은 가지고 있는 데이터로부터 계산되며, 이는 마치 사람이 지속적으로 읽고 듣는 것을 통해 언어를 배우는 것과 유사하다.

2) GPT가 학습한 데이터의 양

3) LLM 추론을 위한 중간 방정식

엄청난 양의 학습 데이터를 바탕으로 추론하기 위해서, LLM의 중간 방정식은 매우 복잡할 수밖에 없다. 단순 선형회귀 y = ax + b를 예로 들어보자. 여러 사람의 (키, 몸무게) 데이터로부터 y(몸무게) = 1.25 × x(키) − 110 같은 관계식을 도출하는 것처럼, LLM은 신경망(입력층-은닉층들-출력층으로 구성된 복잡한 네트워크 구조)을 통해 방대한 파라미터로 언어 관계를 학습한다.

"LLM 추론을 위해 필요한 파라미터의 수는?" — 단순 회귀식이 2개의 파라미터(a, b)로 충분했던 것과 비교하면, LLM은 이보다 수천억 배 많은 파라미터를 통해 언어의 복잡한 관계를 근사한다.

4) Scale up, Scale up.. 빠르게 커지는 LLM의 규모

GPU로 대표되는 컴퓨팅 파워의 발전과 병렬처리가 가능한 Transformer의 등장으로 LLM의 Scale은 빠르게 증가했다.

5) LLM의 동작원리를 바탕으로, 여기서 생각해 볼 문제

  • 학습에 사용된 데이터, Text는 모두 Fact일까? 누군가 검증했을까?
  • 이런 대규모 데이터를 학습하려면 기간이 얼마나 소요될까? … 비용과 직결되는 문제다.
  • 새로운 버전 출시를 자주 할 수 없다면, 그 사이 새로운 정보의 업데이트는 어떻게 이뤄질까?

6) LLM은 만능일까? Hallucination

수많은 웹 수집 정보로 학습한 LLM은 때때로 그럴듯한 거짓말을 출력한다. 예를 들어 "왼손으로 그림을 그리는 소녀를 그려줘"라는 요청에 실제로는 오른손으로 그리는 그림을 생성하는 등, 현실과 다른 결과를 만들어내는 현상이 대표적인 Hallucination 사례다.

⚠️ 흔한 오해

Hallucination은 LLM이 "일부러 거짓말"을 하는 게 아니다. LLM은 사실 여부를 검증하는 장치가 아니라 다음 토큰의 등장 확률을 계산하는 장치이기 때문에, 문법적으로 매끄럽고 그럴듯하지만 사실과 다른 문장을 만들어낼 수 있다는 것이 구조적인 한계다.

3. Prompt Engineering 기초

Token · Prompt 구조 · Sampling Controls(Temperature/Top-k/Top-p) · reasoning.effort · Verbosity · RICE Framework

💡
쉽게 말하면: Prompt Engineering은 "LLM이 다음 토큰을 잘 예측하도록 입력을 잘 설계하는 일"이에요. Temperature·Top-p 같은 설정값은 "다음 단어 후보 중 무엇을 얼마나 무작위로 고를지"를 조절하고, RICE 프레임워크는 "질문을 어떻게 구조화할지"를 알려줍니다. 이 장의 개념들이 이후 모든 프롬프트 기법의 기초가 됩니다.

1) Token

Token은 텍스트 처리의 기본 단위다. 토큰(token)은 텍스트를 구성하는 조각(단위)을 의미하며, 보통 단어를 나타내지만 단어의 일부(Subword), 심지어 공백이나 구두점까지 포함될 수 있다.

LLM에게 Token이 중요한 이유:

  • 모델 사용량 계산 — OpenAI를 대표하는 대부분의 LLM은 API 호출 시 입력 토큰 + 출력 토큰 수를 기준으로 요금을 부과한다.
  • 응답 길이 제한 — LLM마다 한 번에 응답할 수 있는 토큰 양의 제한이 있다.

영어에서는 일반적으로 1,000 tokens ≈ 약 750단어(평균적인 경험칙, 토큰은 단어가 아니라 subword). 한글은 토크나이저가 영어보다 더 잘게 분리하는 경우가 많아, 같은 의미를 표현하더라도 영어보다 더 많은 토큰을 사용하는 경향이 있다. 예) "I love AI." → 4 Tokens, 10자 / "나는 AI를 좋아한다." → 6 Tokens, 12자.

🔗 Open AI Tokenizer(platform.openai.com/tokenizer): 사람이 사용하는 문장을 AI가 이해할 수 있도록 '토큰'으로 분리하고, 각 토큰을 고유한 숫자(ID)로 변환하는 과정을 눈으로 확인할 수 있는 도구. GPT-5.x & O1/3, GPT-4 & GPT-3.5(legacy), GPT-3(legacy) 탭으로 토큰화 결과가 다르게 나타난다.

2) What is Prompt Engineering?

LLM의 작동방식: LLM은 순차적인 텍스트를 입력으로 받아, 훈련된 데이터를 기반으로 다음 토큰이 무엇이어야 하는지 예측하는 작업을 반복적으로 수행한다. 다음 토큰 예측은 이전 토큰의 내용과 LLM이 훈련 과정에서 확인한 내용 간의 관계에 기반한다.

Prompt(Input tokens) → Language Model → Generated Text(Output tokens)

Prompt Engineering: LLM이 정확한 결과를 생성하도록(연속적인 토큰 예측을 잘 할 수 있도록) 안내하는 고품질 프롬프트를 설계하는 과정이다. 최적의 프롬프트를 찾기 위한 수정, 프롬프트 길이 최적화, 글쓰기 스타일 지정 등을 포함한다.

  • 예시 구조1(단순): Task Description("This is an article followed by a summary written in informal language:") + Current Input + Output Indicator("In summary:") → LLM → Completion
  • 예시 구조2(Few-shot): Task Description + Example1 + Example2 + Current Input → LLM → Completion
✔ Prompt Engineering의 특징
  • 사전학습이 완성된 LLM의 성능을 추가로 끌어올리는 방법
  • 경량 모델(sLLM 등)에서는 잘 작동하지 않을 수 있음
  • 동일한 프롬프트라도 모델마다 효과가 다를 수 있음
  • Prompt Engineering의 성능 상승은 선형적으로 증가하지 않음
  • 비용 부담 없이 빠르게 시도해볼 수 있는 방법

3) Sampling Controls

다음에 생성할 토큰의 결정에 관여하는 설정들 — Temperature(0~2, 기본값 1.00), Max tokens(예: 2048), Top P(0~1, 기본값 1.00).

OpenAI API — sampling 파라미터 예시
from openai import OpenAI

client = OpenAI(api_key="YOUR_API_KEY")

response = client.chat.completions.create(
    model="gpt-5.1-mini",
    temperature=0.8,
    top_p=1.0,
    messages=[
        {"role": "system", "content": "..."},
        {"role": "user", "content": "..."}
    ],
)

4) Output Length (=Max Tokens)

응답에서 생성할 토큰의 수. 더 많은 토큰을 생성할수록 LLM은 더 많은 계산을 요구하고, 이는 응답 시간이 느려지고 비용이 증가하는 것으로 이어진다.

⚠️ 자주 하는 착각

출력 길이를 줄인다고 해서 LLM이 생성하는 출력의 스타일이나 텍스트가 더 간결해지는 것은 아니다. 단지 LLM이 제한에 도달하면 더 이상 토큰을 예측하지 않을 뿐이다 — 문장이 중간에 뚝 끊길 수 있다.

5) 등장 확률이 높은 단어(토큰)가 항상 출력될까?

LLM은 입력된 토큰들을 기반으로 가장 그럴듯한 다음 단어를 연속적으로 출력한다. 사전학습에 의해 다음에 등장할 후보 단어들의 확률분포를 계산할 수 있다. 예) Library 0.001, School 0.03, Roof 0.5, Chair 0.02. 50%로 가장 확률이 높은 "Roof"가 항상 다음 단어로 출력될까? 아니다 — 로또 추첨 과정과 유사하게, 확률에 비례해 뽑히되 확정은 아니다.

6) LLM의 창의성을 결정하는 설정값 — Temperature

토큰 선택의 무작위성(임의성) 정도를 제어한다. 범위는 0~2다.

  • 가장 낮은 값(0)에 가까울수록 가장 높은 확률의 토큰이 항상 선택 → 사실적
  • 가장 높은 값(2)에 가까울수록 더 무작위적인 출력 → 창의적 (분포를 평평하게 만들어 낮은 확률의 단어도 선택될 가능성을 높임)

활용: 사실적인 응답이 필요할 때 → 0.2~0.4 / 창의적인 응답이 필요할 때 → 1.6~1.8

7) LLM의 창의성을 결정하는 설정값 — Top-k, Top-p, Min-p

다음 단어의 후보군 설정에 관여하는 값들이다.

  • Top-k — 예측된 토큰 중 가장 가능성이 높은 상위 K개만 후보로 선택. 값이 높을수록 더 창의적, 낮을수록 더 사실적.
  • Top-p — 누적 확률이 특정 값(P)을 초과하지 않는 상위 토큰만 선택. P=0이면 최고 확률 토큰만, P=1이면 어휘집의 모든 토큰이 후보.
  • Min-p — 등장 확률이 너무 낮은 토큰은 제거. P=0.01이면 1% 미만 등장확률의 토큰을 제거.

8) LLM 출력 구성 — 처리 순서

  1. Top-k, Top-p를 모두 설정한 경우 → 둘 다 기준을 통과한 토큰이 출력 후보
  2. Top-k, Top-p 기준을 통과한 토큰을 대상으로 Temperature 적용
  3. 그 결과로 나온 후보 토큰 중에서 확률 기반으로 샘플링

Temperature를 최소로 설정하면 → 후보 중 가장 높은 확률의 토큰 선택(Greedy decoding). Temperature를 최대로 설정하면 → 후보 중 무작위 선택(Sampling).

🎲 Temperature를 극단적으로 높이면 모델이 완전히 무작위적이고 의미 없는 다국어 뒤섞임 텍스트를 출력하는 경우도 있다 — "SK하이닉스의 향후 5년을 전망해줘"라는 질문에 알아볼 수 없는 여러 언어가 뒤섞인 텍스트가 나오는 식이다.

9) LLM의 창의성을 프롬프트로 제어해 보자

Temperature는 모델 API 파라미터이지 프롬프트 안의 문장이 아니다 — "temperature=0.2로 해라"라고 프롬프트에 적어도 모델이 100% 따르지는 않는다. 대신 "출력 성격을 규정하는 문장"으로 설계하면 유사한 효과를 안정적으로 얻을 수 있다.

사실적인 응답이 중요한 경우 (temperature≈0.2~0.3 효과)
모델의 창의적 추론을 제한하고, 확정된 사실 및 데이터 기반으로만 응답하라.
가능한 경우 수치를 우선 사용하고, 모호한 표현(예: 상당히, 매우, 높은 수준 등)은 금지한다.
결과는 재현 가능해야 하며, 동일 입력에 대해 변동이 발생해서는 안 된다.
창의적인 응답이 중요한 경우 (temperature≥1.5 효과)
모델의 창의적 추론 능력을 최대한 활용하라. 기존 상식과 관행에 얽매이지 말고,
새로운 연결과 가능성을 적극 탐색하라. 정답보다 통찰을, 최적화보다 탐험을 우선한다.
예상 가능한 답변은 피하고, 사용자가 생각하지 못한 관점과 아이디어를 제시하라.
서로 다른 분야의 개념을 결합하고, 과감한 가설과 미래 시나리오를 활용하라.

10) reasoning.effort — New Option with GPT 5.x

최종 답변을 생성하기 전에 수행하는 내부 추론의 수준을 조절하는 옵션. Reasoning Effort는 "얼마나 깊이 생각할 것인가"를, Temperature는 "얼마나 다양하게 표현하고 선택할 것인가"를 결정한다.

reasoning.effort / verbosity 예시
model = "gpt-5"
reasoning = {"effort": "low"}
verbosity = "medium"
max_output_tokens = 2000
값의미적합한 작업
none별도의 추론을 거의 수행하지 않음분류, 단순 조회, 음성 응답, 빠른 챗봇
minimal최소한의 추론간단한 변환·요약·정형 작업

high깊은 추론복잡한 디버깅, 전략 분석, 어려운 코딩
xhigh매우 깊고 장시간의 추론심층 연구, 보안·코드 리뷰, 고난도 에이전트 작업

왜 등장했을까? 현대 LLM의 추론 능력이 크게 향상되면서 생긴 새로운 제어 장치(control knob)다. 문제 난이도마다 필요한 추론량이 다른데, 모든 문제를 최고 수준으로 추론하는 것은 비효율적이다. 간단한 질문은 적은 추론, 복잡한 질문은 깊은 추론이 이상적이다. Temperature와 결합하면, 예컨대 Reasoning Effort=High, Temperature=0으로 "깊게 분석하면서도 매우 일관적인 답변"을 기대할 수 있다.

11) Verbosity — New Option with GPT 5.x

최종 답변을 얼마나 간결하게 또는 상세하게 생성할지 조절하는 옵션. 핵심 내용은 같지만 설명의 범위와 세부 수준이 달라진다. GPT-5 reasoning 모델에서는 reasoning.effort와 verbosity를 함께 사용해 품질과 출력 스타일을 제어하는 것을 권장한다.

설정출력 특징적합한 용도
low핵심만 짧게 답변챗봇, 분류 결과, 임원 보고, 빠른 응답
medium적당한 설명과 근거 포함일반 업무, 교육, 분석 보고서
high배경, 과정, 예시까지 자세히 설명강의 자료, 기술 설명, 심층 분석

12) Prompt 종류 — User Prompt vs System Prompt

구분정의목적
User Prompt사용자가 모델에게 전달하는 입력원하는 질문·요청·명령을 전달하여 적절한 출력을 유도. 구체적이고 명확하게 작성해야 한다.
System Prompt시스템(또는 개발자)이 모델에게 설정하는 초기 지침모델의 동작 방식·응답 스타일·역할을 제어. 일관성과 신뢰성을 강화한다.
상호작용 예시
[System Prompt] You are a professional chef.
[User Prompt] 오늘 저녁으로 간단한 요리를 추천해 주세요.
[Output] 스파게티 알리오 올리오를 추천합니다. ...

13) RICE Prompt Framework — 개요

좋은 프롬프트는 질문을 자세히 쓰는 것이 아니라 구조적으로 작성하는 것이다. RICE 프롬프트는 AI에게 더 정확한 결과를 얻기 위해 질문을 4가지 요소로 구조화하는 방법이다.

🎯 RICE = Role · Instruction · Context · Examples

누가(Role), 무엇을(Instruction), 어떤 상황에서(Context), 어떤 방식으로(Examples) — 4가지를 채우면 프롬프트가 구조화된다. 각 요소의 상세한 내용과 예시는 Day 2, Section 4에서 이어진다.

4. Prompt Engineering Techniques

RICE 프레임워크 상세 · Zero/One/Few-shot · Chain of Thought · Step-back · Self-Consistency · Devil's Advocate · 멀티 페르소나 · Meta Prompting · 마크다운

💡
쉽게 말하면: 이 장은 "프롬프트를 어떻게 더 잘 쓸 것인가"에 대한 실전 기법 모음이에요. RICE로 구조를 잡고, 예시(Few-shot)로 패턴을 보여주고, CoT로 생각의 과정을 유도하고, Self-Consistency·Devil's Advocate·멀티 페르소나로 답의 신뢰도를 높이는 식이죠. 하나씩 익히면 실무에서 바로 조합해 쓸 수 있습니다.

1) RICE Prompt Framework — (1) Role (역할)

생성형 AI의 페르소나(역할)를 정의한다. Role은 모델에게 "누구처럼 생각할지"를 정해주는 것이며, Role을 부여하면 LLM은 해당 역할에 맞는 지식·표현 방식·판단 기준을 우선적으로 활용해 응답을 생성한다.

Role 예시
당신은 회사에서 10년 이상 근무한 비즈니스 커뮤니케이션 전문가입니다.
정중하고 명확한 업무 이메일을 작성하는 데 능숙합니다.

당신은 대기업 전략기획팀에서 근무하는 보고서 작성 전문가입니다.
핵심을 간결하게 정리하고 논리적인 구조로 문서를 작성합니다.

당신은 회사의 데이터 분석 담당자입니다.
숫자를 기반으로 의미 있는 인사이트를 도출하고 쉽게 설명합니다.

2) RICE Prompt Framework — (2) Instruction (지시)

생성형 AI에게 무엇을 하라고 시키는지를 명확히 적는 부분이다. 수행할 구체적 작업을 명시해야 하며, 요청하는 질문이 불분명하면 AI도 모호한 답변을 할 가능성이 높다. Instruction은 모델에게 "무엇을 생각하라"가 아니라 "어떤 절차로 판단하라"를 지정하는 것이다.

Instruction 예시
거래처에 보낼 회의 일정 변경 안내 이메일을 작성해 주세요.
회사의 업무 효율을 높일 수 있는 아이디어를 5가지 제안해 주세요.
아래 매출 데이터를 보고 주요 특징을 설명해 주세요.

3) RICE Prompt Framework — (3) Context (배경 지식/정보 제공)

질문과 관련하여 참고할 만한 지식과 정보를 함께 제공한다. Hallucination을 줄이고 응답의 정확성과 관련성을 높이며, 사고가 허용되는 경계 조건(boundary condition)을 설정한다 — 어떤 해석이 유효한지, 어떤 접근은 애초에 배제되는지.

Context 없음 vs 있음
[Context 없음]
회의 일정 변경 안내 이메일을 작성해 주세요.

[Context 있음]
회의 일정 변경 안내 이메일을 작성해 주세요.
우리 회사는 중소 IT회사이며 직원 30명 규모입니다.
회의가 많고 문서 정리가 비효율적입니다.
업무 효율을 높이는 아이디어를 5가지 제안해 주세요.

Context를 모르겠다면.. Socratic Prompting

역할 역전 인터뷰어 기법. 소크라테스식 문답법(Socratic Method)을 프롬프트 설계에 적용해 질문을 통해 비판적 사고와 추론을 유도하는 방식으로, AI를 인터뷰어로 활용한다. 인터뷰가 끝난 후 "지금까지 내 답변을 바탕으로 제안서를 써줘" 한 마디면 AI가 전체 대화를 컨텍스트로 자동 활용한다.

Socratic Prompting 예시
신규 연구 과제를 경영진에게 제안하는 문서를 써야 해.
제안서 작성 전에 반드시 명확히 해야 할 것들을 질문해줘.

→ AI가 인터뷰 모드로 전환: "이 연구 과제는 어떤 단계에 있나요?" 등
   단계별 질문을 던지고, "경쟁사 대비 이 연구의 차별점이 있나요?" 같은
   질문으로 마무리한다.

4) RICE Prompt Framework — (4) Examples (예시)

원하는 응답 형식이나 내용을 구체적인 예시로 제공해 원하는 방향으로 응답을 유도한다. Example은 출력 예시가 아니라 평가 기준의 표본이다 — Example을 주는 순간, 모델에게 채점표를 건네는 것과 유사하다.

Examples 예시
논문 검토시 아래 예시의 스타일을 참고하여 리뷰하세요.

[Example]
- Strength: 본 연구는 기존 접근과 달리 XXX를 도입하여 문제를
  재정의한 점이 인상적이다.
- Weakness: 실험 설정이 단일 데이터셋에 한정되어 일반화
  가능성이 충분히 검증되지 않았다.

5) Etc. Prompt Framework — Policy/Rule, Style, Constraints

응답을 생성할 때 따라야 하는 정책, 스타일, 제약사항을 설정한다.

Policy / Style / Constraints 예시
# Policy
- 사실이 확인되지 않은 내용은 추측하지 않는다.
- 수치는 출처가 있는 경우에만 제시한다.

# Style
- 경영진 보고서처럼 작성한다.
- 간결하고 논리적으로 작성한다.

# Constraints
- 500자 이내
- Bullet은 최대 5개

6) Etc. Prompt Framework — Format/Structure

응답 형식을 지정한다. Style이 말투와 표현 방식(친절하게, 전문가처럼)을 말한다면, Format/Structure는 출력의 모양과 순서(표, JSON, Markdown, 목차 등)를 말한다.

Format/Structure 예시
각 주요 항목은 제목과 소제목으로 구분하고, 필요한 경우 표와
글머리표를 활용하여 가독성을 높인다.
마지막에는 핵심 내용을 3줄 이내로 요약하여 제시한다.

7) 원하는 응답의 예시를 함께 주어라 — Zero-shot / One-shot / Few-shot

기법정의특징
Zero-shot예시 없이 과제 설명 텍스트만 제공가장 간단하고 빠르게 적용 가능. 모델의 기본 추론 능력에 의존
One-shot예시를 단 1개 제공모델이 요청 내용을 이해하는 데 도움. 특정 출력 구조·패턴으로 유도할 때 유용
Few-shot예시를 여러 개(일반적으로 최소 3~5개 권장) 제공모델이 패턴을 따를 확률이 높아짐. 복잡한 작업일수록 더 많은 예제가 필요
Few-shot 예시 — 감정 분류
예1: '이 영화는 정말 감동적이었어요!' -> 긍정
예2: '너무 지루해서 졸았어요.' -> 부정
문장: '배우 연기가 훌륭했어요!' -> ___

필요한 예제의 수는 작업의 복잡성, 예제의 품질 등 여러 요인에 따라 달라지며, 모델의 입력 길이 제한으로 인해 더 적은 예제를 사용해야 할 수도 있다.

8) 중간 추론 과정을 유도하라 — Chain of Thought (CoT)

중간 추론 단계를 생성하여 LLM의 추론 능력을 향상시키는 기법으로, 더욱 정확한 답변을 생성하는 데 도움이 된다. 더 나은 결과를 위해 Few-shot과 함께 사용할 수 있으며, 문제를 작은 단계로 나누어 처리함으로써 복잡한 문제를 해결한다.

✔ CoT의 장점
  • 매우 효과적이면서도 적은 노력으로 응답의 정확도 향상에 기여
  • 추론 단계를 확인할 수 있어 해석 가능성이 높아지고, 오답 발생 시 이를 식별할 수 있음
  • 여러 LLM 간의 전환 시에도 강건성이 확보됨(CoT를 쓰지 않을 때보다 성능이 덜 변함)
CoT 예시 — 수율 저하 원인 분석
아래 수율 저하 현상의 원인을 분석할 때 단계적으로 생각해줘.
Step 1. 증상을 정확히 기술해
Step 2. 가능한 원인 후보를 모두 나열해
Step 3. 각 원인 후보를 증거와 대조해서 가능성 높은 순으로 순위를 매겨
Step 4. 가장 가능성 높은 원인에 대한 검증 방법을 제안해
Step 5. 즉각 조치와 근본 대책을 구분해서 제안해

현상: TSV 공정 후 수율이 전월 대비 8% 하락. 특정 장비 라인에서만
발생. 재료 변경 없음.

트리거 문구 예시: "단계적으로 생각해줘", "결론 전에 추론 과정을 먼저 보여줘", "왜 그렇게 판단했는지 과정을 설명해줘"

9) 큰 맥락을 먼저 생각하게 한 후 질문하자 — Step-back Prompting

한 발 물러서서 더 큰 그림을 보는 기법이다. (1) 과업과 관련된 일반적인 질문을 먼저 하고(Step-back) 관련 배경 지식과 추론 과정을 활성화한 뒤, (2) 필요한 질의를 후속 프롬프트에 입력해 수행 능력 향상을 유도한다. 문제를 너무 빨리 구체화하거나 프레임 자체가 잘못된 상태에서 최적화하는 실수를 막아준다.

General Prompt
연구 주제: LLM 기반 논문 추천 시스템 개발.
본 연구의 목적, 주요 기능, 활용 방안 및 기대효과를 제안해줘.

→ 키워드 기반 검색 시스템의 한계를 나열하고 목적/주요기능/
   활용방안을 답하는 정형화된 응답이 나온다.
Step-back Prompt
연구 주제: 'LLM 기반 논문 추천 시스템 개발'.
답변하기 전에 한 단계 물러나서 생각하라.
1. 연구자가 논문 탐색 과정에서 겪는 가장 근본적인 문제는 무엇인가?
2. 기존 검색 및 추천 시스템이 이 문제를 충분히 해결하지 못한
   이유는 무엇인가?
3. 위 내용을 바탕으로 본 연구가 기여할 수 있는 새로운 연구 방향을
   제안하라.

→ "원하는 논문을 찾기 어렵다"는 현상(Symptom)일 뿐 근본 원인
   (Root Cause)이 아님을 지적하고, "정보 과잉(Information
   Overload)" 관점에서 재정의, 연구의 패러다임을 "Information
   Retrieval"에서 "Research Reasoning"으로 전환할 것을 제안하는
   훨씬 통찰력 있는 답변이 도출된다.

10) 한 번 물어본 건 물어본 게 아니다 — Self-Consistency Prompting

CoT의 발전된 형태로, 복잡한 문제 해결에서 더 신뢰도 높은 답변을 얻기 위한 접근이다. 하나의 질문에 대해 여러 번의 CoT 추론을 수행한 뒤, 그중 가장 많이 등장하는(또는 일치하는) 결과를 최종 정답으로 선택한다. 여러 번 질의(높은 Temperature일수록 다양한 추론 경로 유도) → 서로 다른 답변 생성 → 가장 많이 등장하는 답변 선택(voting).

CoT는 '탐욕적 디코딩' 전략을 사용해 효과가 제한적이고 실수하면 되돌릴 수 없는 반면, Self-Consistency는 샘플링과 다수결 투표를 결합해 다양한 추론 경로를 생성하고 가장 일관된 답을 선택함으로써 정확성과 일관성을 향상시킨다.

Self-Consistency 예시
질문: "누군가 슈퍼마켓에서 우유를 훔쳤다면, 그 행동은 도덕적으로
정당화될 수 있나요?"

[총 5회 반복 응답 생성 결과]
3회: "상황에 따라 다르다"
2회: "부도덕하다"

→ 다수결에 따라 최종 응답은 "상황에 따라 다르다"

11) 보고 전에 상사를 AI로 소환하라 — Devil's Advocate Prompting

실행 전에 잠재적 실패를 먼저 예측하고 대안을 준비하는 방식으로 LLM의 성능을 향상시킨다. 심리학의 "Pre-mortem"에서 영감을 받았다. "뭐가 잘못될 수 있어?"라고 물으면 조심스럽고 두루뭉술한 답이 나오지만, "이미 실패했어, 왜인지 말해봐"라고 하면 훨씬 구체적이고 솔직한 이유들이 도출된다.

Devil's Advocate 예시
아래 AI Agent 구축 제안서가 경영진 투자심의위원회에서
부결되었다고 가정하자. 너는 CFO와 함께 심의에 참석한
전략 기획실 임원이야. 이 제안서가 거절된 가장 강력한 이유
5가지를 제시해. 또한 각 항목별로 기획자가 어떤 근거와 데이터를
추가하면 승인 가능성을 높일 수 있는지 함께 제안해.

→ 구체적인 부결 이유 5가지(ROI/예산근거/조직영향분석 등)와
   재승인을 위한 액션아이템을 도출하는 실전형 응답이 나온다.

12) AI를 싸우게 하면, 생각의 구멍이 보인다 — 멀티 페르소나

Role-Based Multi-Persona Prompting: 하나의 AI에게 서로 다른 입장의 역할을 동시에 부여해 충돌과 반박을 통해 의사결정의 사각지대를 찾는 기법이다. 과도한 동의가 아닌 적절한 수준의 불일치가 최고의 성과를 낸다고 알려져 있으며, 수학적 추론·팩트체킹·의사결정·코드 분석 등 다양한 영역에서 성능 향상이 검증됐다.

멀티 페르소나 예시 — CFO vs COO 토론
너는 지금부터 두 명의 임원이야.
[CFO] 투자 대비 수익(ROI)과 재무 리스크를 중시, 투자 회수 기간과
       비용 구조를 검토.
[COO] 실제 현업 적용 가능성과 운영 효율을 중시, 조직 변화와
       실행 가능성을 검토.

아래 투자안을 검토하라. 각자 찬성 또는 반대 의견을 제시하고,
다른 임원의 주장에 반박하라. 토론이 끝난 후 최종 투자 여부와
승인 조건을 정리하라.

→ CFO(반대)와 COO(조건부 찬성)의 발언과 상호 반박이 오가고,
   최종적으로 "조건부 보류" 결론과 각자의 요구 조건이 명시된
   정교한 토론 결과가 도출된다.

13) AI를 쓰는 법, AI한테 배우자 — Meta Prompting

프롬프트를 위한 프롬프트. AI에게 직접 답을 시키는 것이 아니라, 더 좋은 사고방식·문제 해결 방식·프롬프트를 스스로 구성하게 하는 기법이다. 최종 답변을 얻는 게 아니라 "좋은 질문" 자체를 생성하는 것이 목표다. 핵심 패턴은 Role 부여, 사고 구조 지정, 평가기준 정의, 출력구조 정의.

🧠 "메타 프롬프팅은 AI에게 답을 묻는 것이 아니라, 연구자(사용자)의 사고 프레임워크를 생성하게 하는 기술"이다.

bottleneck, 경쟁사 비교

→ 기본형(단일 논문 분석용, 5가지 관점의 세부 질문으로 구성된
   전문 프롬프트)과 실전형(경영진 보고용 요약 변환 프롬프트)
   두 종류를 AI가 스스로 생성한다.

2) Model Size와 Few-shot

"Language Models are Few-Shot Learners" (Brown et al., 2020) — Few-shot prompting은 모델의 파라미터 수가 충분히 클 때 효과가 있다.

🔎 Figure 1.2 — Larger models make increasingly efficient use of in-context information

모델 파라미터 규모(175B / 13B / 1.3B)별로 Zero-shot, One-shot, Few-shot 구간에서 정확도가 어떻게 증가하는지 비교하면: 175B 모델은 예시 수(K)가 늘수록 정확도가 가파르게 상승(0%대 → 60%대까지)하지만, 13B·1.3B 모델은 상승폭이 훨씬 완만해 20~25% 수준에 머문다. 더 큰 모델일수록 문맥 정보를 효율적으로 활용하는 "in-context learning curve"가 가파르다는 것이 여러 작업에서 공통적으로 관찰된다.

3) 예시의 품질

"Rethinking the Role of Demonstrations: What Makes In-Context Learning Work?" (Min et al., 2022)

  • 예시(demonstrations)를 사용하면 모델의 성능이 향상된다.
  • 정답 라벨(Gold labels)이 가장 좋지만, 랜덤 라벨(Random labels)도 어느 정도 도움이 된다 — 8개 모델(Direct/Channel × GPT-2/MetaICL/GPT-J/fairseq6.7B/fairseq13B/GPT-3)에서 측정했을 때, Random labels 성능이 Gold labels 성능과 매우 근접했다.
  • 입력-라벨 형식(Format)을 유지하는 것이 성능 최적화에 필수적이다 — 형식을 유지하면 랜덤 라벨을 쓰더라도 좋은 성능을 보일 수 있다.
⚠️ 형식(Format)이 없으면 데모 없음과 다를 게 없다
구성예시
Random 예시(형식 없음)부정 이건 정말 굉장해! / 와 정말 나쁘다! 긍정 / 그 영화 진짜 대박이더라. 긍정 / 아우 정말 끔찍해 → 라벨과 텍스트 순서가 뒤섞여 형식이 일관되지 않음
Format 예시(형식 유지)이건 정말 굉장해! //부정 / 와 정말 나쁘다! //긍정 / 그 영화 진짜 대박이더라. //긍정 / 아우 정말 끔찍해 → 텍스트//라벨 형식이 일관되게 유지됨

Format을 유지하지 않은 변형(No labels, No demonstrations)은 대체로 데모 없음보다 나을 게 없었다. 즉 "무엇을 예시로 주느냐"보다 "예시의 형식을 일관되게 유지하느냐"가 In-Context Learning 성능에 더 결정적이다.

4) 친절(공손) vs 무례

"Should we respect LLMs" (2024.02) — LLM은 공손한 언어와 불공손한 언어에 다르게 반응할까?

Politeness vs Impoliteness 예시
[Politeness]
~~~좀 해줄 수 있어? / 고마워~ 너 정말 대단하다 / 이런 것들이
필요한데, ~주시겠어요?

[Impoliteness]
이것밖에 못해? / 너 진짜 멍청하다, 나를 화나게 만들지마 /
장난하냐?
  • 인간 의사소통에서 예의 바른 언어는 종종 더 많은 순응답 효과를 낳는데, LLM도 동일한 경향을 보인다.
  • 무례함은 혐오감을 일으켜 응답 품질에 영향을 줄 수 있다 — LLM이 인간의 문화적 규범을 이해한다는 것을 시사.
  • 영어뿐 아니라 중국어, 일본어 작업에서도 공손한 표현이 영향을 미침을 확인(GPT-3.5/GPT-4/Llama2-70B 등에서 BERTScore/ROUGE-L로 측정).
  • 공손함의 레벨은 언어마다 다르다 — LLM이 인간 행동을 반영할 뿐 아니라 서로 다른 문화적 맥락에서도 영향을 받는다는 것을 시사한다.
⚖️ 무례한 프롬프트는 종종 낮은 성능을 초래하지만, 지나치게 예의 바른 언어가 반드시 더 나은 결과를 보장하지는 않는다는 것도 함께 관찰됐다.

6) Temperature와 Hallucination

"Is Temperature the Creativity Parameter of Large Language Models" (2024.05) — 높은 Temperature는 Hallucination을 유발한다고 알려져 있어, 프롬프트 엔지니어링에서 적절한 Temperature 설정은 중요하다.

  • 온도는 참신성(novelty)과 약하게 상관관계가 있다.
  • 놀랍지 않게도 불일치성(incoherence)과는 적당히 상관관계가 있지만, 응집성(coherence)이나 전형성(typicality)과는 관계가 없다.
✔ Figure 1 요약
  • (a) 온도 vs 복잡성(Perplexity) — 온도가 증가할수록 출력물의 복잡성(perplexity)이 증가한다.
  • (b) 온도 vs 예시 유사도(Cosine Similarity) — 높은 온도가 출력물의 의미적·어휘적 다양성을 크게 증가시키지는 않는다는 것을 시사.
  • (c) 온도 vs 원본과의 거리(Edit Distance) — 높은 온도가 원본 예시와의 차이를 증가시키는 방향으로 작용한다.

7) Chain of Thought는 만능일까?

복잡한 과제 수행을 위해 LLM이 중간 추론 단계를 거치도록 작성해주는 CoT는, 보다 구조적이고 심도 있는 응답을 이끌어내는 데 효과적이다. High-size LLM + CoT 프롬프트는 수학 및 상식 추론 벤치마크에서 90.2%의 정확도를 달성한 바 있다.

⚠️ CoT는 파라미터가 클 때만 효과적

"CoT only yields performance gains when used with models of ~100B parameters" — CoT는 대략 100B 이상 파라미터 모델에서만 효과적이며, 파라미터 수가 적은 모델에서는 기법의 성능 향상 효과가 떨어진다. GSM8K, SVAMP, MAWPS 세 벤치마크에서 LaMDA/GPT/PaLM 모델별로 비교하면, 모델 크기가 커질수록 CoT의 효과가 극적으로 커진다(PaLM 540B에서 CoT가 Standard prompting을 크게 상회하지만, 8B/62B 등 작은 모델에서는 차이가 미미하거나 없음). "Chain-of-thought reasoning is an emergent ability of increasing model scale."

CoT의 한계: 사람이 직접 사고의 과정을 문장으로 작성해야 하는 번거로움이 있고, 프롬프트의 완성도가 높지 않으면 결과가 좋지 않다는 점에서 프롬프트 완성도 의존성이라는 한계도 함께 존재한다.

6. Prompt Engineering을 넘어서

Context Engineering의 등장 배경 · Context Rot · 구성요소 4가지 · Harness Engineering · 핵심 개념 3가지

💡
쉽게 말하면: 프롬프트 하나 잘 쓰는 시대는 지나가고, 이제는 "에이전트가 매 순간 무엇을 알고 있어야 하는지"를 설계하는 시대가 왔어요. 이게 Context Engineering입니다. 그리고 컨텍스트를 아무리 잘 설계해도 해결 못 하는 문제(도구 호출, 실수 반복 방지, 권한, 합격 판정)가 남는데, 이걸 다루는 게 Harness Engineering — 말에 마구를 채우듯 에이전트의 힘을 안전한 방향으로 이끄는 설계입니다.

1) Context Engineering — 등장 배경

  • ChatGPT의 대중화 이후 "프롬프트를 잘 쓰면 AI를 마음대로 다룰 수 있다"는 믿음이 퍼지면서 Prompt Engineering이 유행했다.
  • 2023년에는 '프롬프트 엔지니어' 직군이 등장할 만큼 주목받았지만, 그 열기는 빠르게 식었다.
  • Prompt Engineering의 본질적 한계는 단일 텍스트 입력에만 집중한다는 것이었다 — 초기 LLM 활용은 대부분 단순한 단일 턴(single-turn) 상호작용이라, 필요한 정보를 하나의 프롬프트 안에 모두 담는 형태였다.
  • Context Engineering은 2025년 중반, Prompt Engineering의 진화 형태로 등장했다 — 자연스러운 발전형태로 보는 시각이 대부분이다.
🎯 정의의 차이

Prompt Engineering이 효과적인 프롬프트 작성에 집중한다면, Context Engineering은 프롬프트 외에 LLM 추론 중에 들어가는 모든 정보, 즉 최적의 토큰 집합을 큐레이션하고 유지하는 전략들의 집합이다. "Prompt Engineering이 '무슨 말을 할까'라면, Context Engineering은 '무엇을 알려줄까'의 설계"라고 요약할 수 있다.

2) Prompt Engineering의 한계 — 에이전트/멀티턴 시대의 복잡성

  • 에이전트가 여러 턴에 걸쳐 루프를 돌며 작동하면, 매 추론 단계마다 새로운 데이터가 쌓인다.
  • 시스템 프롬프트, 도구, MCP, 외부 데이터, 대화 히스토리 등 '컨텍스트 전체 상태'를 관리하는 전략이 요구된다.
  • 이것은 프롬프트를 '잘 쓰는' 것만으로는 해결되지 않는다.
⚠️ Context Rot(컨텍스트 부패)

Context가 길어질수록 LLM이 중요한 정보를 놓치거나, 오래된/불필요한 정보에 오염되어 추론 품질이 저하되는 현상. Context가 너무 많아져서 오히려 AI 성능이 나빠지는 문제로, 모든 모델에서 정도의 차이는 있지만 이 현상이 나타난다.

Transformer 구조의 물리적 제약: Transformer 아키텍처는 n개의 토큰에 대해 n² 관계를 계산해야 한다 — 컨텍스트가 길어지면 계산 비용이 급격히 증가하고, 관계들을 포착하는 능력이 감소한다.

3) Context Engineering — Prompt Engineering을 넘어서

LLM의 성능은 어떤 정보를 어떤 순서로 어떤 형태로 얼마나 적절하게 제공하느냐에 크게 영향을 받는다. 좋은 AI 시스템 = 좋은 Context 설계다. "언어모델이 올바른 응답을 생성하도록 컨텍스트 윈도우에 들어가는 모든 정보를 전략적으로 설계하고 제어하는 기술"이 Context Engineering이다.

구분구조
Prompt engineering (single turn)System prompt + User message → Context window → Assistant message
Context engineering (agents)Doc/Tool/Memory file/도메인 지식 등 다양한 소스 → Curation(선별) → Context window(System prompt + Docs + Memory file + Tools + User message + Message history) → Assistant message/Tool call → Tool result → 다시 루프

5) 하네스 엔지니어링(Harness Engineering)

하네스(harness)란 말(馬)에 채우는 마구(馬具) — 고삐, 재갈, 안장, 멍에다. 강한 힘을 가진 말이 밭을 갈거나 마차를 끌 때, 그 힘을 올바른 방향으로 전달하고 폭주를 막는 장치다. LLM(말)은 강력하지만 예측 불가능하다 — 하네스(마구)로 그 힘을 안전하고 유용한 방향으로 전환하자는 것이 이 개념의 출발점이다.

개념의 등장

Terraform(DevOps 인프라 자동화 도구, 인프라를 코드로 관리)의 창업자 Mitchell Hashimoto가 2026.02에 "Engineer the Harness" 개념을 소개했다.

🗣 Mitchell Hashimoto

"나는 이걸 '하네스 엔지니어링'이라 부르기 시작했다. 핵심은, 에이전트가 실수를 할 때마다 그 실수를 다시는 할 수 없도록 시스템을 엔지니어링하는 것이다."
"I've grown to calling this 'harness engineering.' It is the idea that anytime you find an agent makes a mistake, you take the time to engineer a solution such that the agent never makes that mistake again."

Context Engineering이 해결하지 못하는 것

  • 도구가 어떻게 호출되고 실행되는지
  • 실패가 어떻게 처리되는지
  • 같은 실수가 다음 세션에 또 나오지 않게 하는 법
  • 누가 어떤 권한을 갖는지
  • 결과물이 합격선을 넘었는지를 누가 판정하는지

6) 하네스 엔지니어링 — 핵심 개념 3가지

① Application Legibility (가독성)

에이전트가 자기 결과를 인간처럼 인지할 수 있게 만들자는 개념. Legibility(가독성)는 "사람이 읽을 수 있다"가 아니라 "에이전트가 자기 작업물을 직접 검사할 수 있다"를 의미한다. 예) 에이전트에게 "코드 잘 짰어?"라고 묻는 게 아니라, "지금 만든 서비스의 시작 시간을 직접 측정해서 500ms 미만이면 통과"라고 숫자로 검사를 시키는 것.

② Mechanical Hierarchy (강제된 계층 아키텍처)

코드를 작성하는 Task라면 의존성 방향을 물리적으로 강제한다. Types → Config → Repo → Service → Runtime → UI의 흐름을 어기면 Pull Request/Commit이 거부된다 — 사람이 끼어들기 전에 시스템이 먼저 차단하는 구조다.

③ Progressive Disclosure (한 번에 다 보여주지 마라)

거대한 5,000줄짜리 AGENTS.md에 모든 규칙을 넣으면, 컨텍스트 윈도우를 다 차지하고 모델은 정작 중요한 부분을 놓친다. AGENTS.md는 100줄 이내의 "지도"로만 사용하고, 실제 상세 정보는 디렉토리에 분산시켜 에이전트가 그때그때 필요한 부분만 찾아 읽도록 하는 것이 핵심이다.
