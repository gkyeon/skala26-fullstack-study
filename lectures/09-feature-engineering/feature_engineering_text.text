# 데이터 분석 강의 노트 — Feature Engineering (2026-08-14)

> 데이터 분석 과정 2강: Feature Engineering
> 웹사이트 보충 설명용으로 핵심 개념 위주로 재구성한 노트입니다.

---

## 1. 이 수업을 대하는 태도 — "운전자"가 되어라

- 기업이 필요로 하는 데이터 분석 역량은 **엔진을 잘 아는 사람**이 아니라 **운전을 잘하는 사람**이다. 상황에 맞게 빠르고 안전하게 운전할 수 있는 능력, 즉 **활용 역량**이 핵심이다.
- 요소 기술(알고리즘, 통계 이론 등) 하나하나를 깊이 파고드는 것도 좋지만, 거기에 매몰되면 정작 더 중요한 **"데이터 분석 프로세스에 대한 이해"** 를 놓치게 된다.
- 데이터 분석·사이언스 하면 가장 먼저 떠올려야 할 단어는 패턴, 머신러닝, 통계가 아니라 **프로세스(Process)** 다.
  - 기업이 데이터 분석을 하는 근본 목적: **데이터 기반 의사결정 지원**
  - 큰 흐름: 데이터 수집 → 처리 → 분석 → 의사결정 반영
  - 이 안에 다시 여러 세부 프로세스가 있으며, 어떤 문제에 대해 **어떤 프로세스로 설계하고 적용할지**가 하나의 기술을 깊이 아는 것보다 더 중요하다.
- 도구(파이썬, R, SAS 등)는 시대에 따라 계속 바뀐다. 코드는 수단일 뿐이며, AI가 코드를 대신 작성해주는 시대이므로 **분석 코드 작성 자체보다 컨셉·프로세스 이해가 우선**이다.

---

## 2. Feature Engineering이란

> **원본 데이터를 모델 성능에 도움이 되는 형태로 가공하는 모든 과정**

- 원본 데이터를 그대로 모델에 넣는 경우는 거의 없다. 최종적으로 모델에 들어가는 입력값이 바로 **Feature(피처)** 다.
- 예시: 은행 고객 이탈 예측 모델
  - `생년월일` 그 자체는 피처로 쓸 수 없다 → **나이, 연령대, 세대**로 가공(피처 생성)
  - `가입일자` 그 자체는 의미가 없다 → **가입기간**(가입 시점 ~ 분석 기준 시점)으로 가공해야 유의미한 피처가 된다.

### 2.1 용어 정리: Target vs Feature

| 용어 | 통계학 용어 | 의미 |
|---|---|---|
| Target | Y 변수, 종속 변수, 라벨, 정답지 | 맞춰야 할 대상. 보통 1개 |
| Feature | X 변수, 설명 변수, 독립 변수 | Target을 맞추기 위한 입력값. 여러 개 |

- 예: 아파트 가격 예측 모델 → Target = 아파트 가격, Feature = 평수, 방 개수, 지하철 거리 등
- 모델(통계 분석, 머신러닝, 딥러닝)은 결국 **Feature(X)와 Target(Y)의 관계를 표현한 것**이다.
  - 통계/회귀 분석: `Y = aX + b` 같은 함수식으로 관계를 설명 가능(화이트박스)
  - 머신러닝/딥러닝: 대부분 **블랙박스** — 왜 그런 결과가 나오는지 직접 설명하기 어려워, 이를 해석하는 후속 알고리즘(XAI 등)이 별도로 필요.

---

## 3. 데이터 분석 파이프라인에서 FE의 위치

일반적인 흐름 (표준은 아니며 상황에 따라 달라질 수 있음):

```
비즈니스 문제 정의 → 분석 요건화 → 데이터 수집 → 데이터 탐색(EDA)
→ Feature Engineering → 모델링 → 모델 평가
```

- **데이터 전처리(Data Preprocessing)** 와 **Feature Engineering**은 실무에서 혼용되지만, 엄밀히는:
  - 데이터 전처리: 모델 성능과 무관하더라도 분석 입력으로 쓸 수 있게 형태를 바꾸는 모든 작업(더 큰 개념)
  - Feature Engineering: 그중에서도 **모델 성능에 도움이 되는 방향**으로 가공하는 작업
- Feature Engineering과 모델링은 **성능 개선을 위해 계속 반복(iterative)** 된다.

### 3.1 EDA(데이터 탐색)를 하는 이유
- 목적 없이 하는 게 아니다. **데이터를 이해해서 어떤 피처를 남기고, 바꾸고, 제거할지 판단하기 위한 후속 작업(Feature Engineering)** 을 잘 하기 위해 한다.
- 결국 모든 작업의 최종 판단 기준은 **모델 성능(평가 결과)** 이다. → "개발보다 평가가 더 중요하다"는 것이 강사의 관점.

### 3.2 왜 Feature Engineering이 가장 중요한가
- 초심자들은 보통 모델링(어떤 알고리즘을 쓸지)에 관심을 쏟지만, 실제로 모델 성능에 영향을 미치는 요인 중 **Feature Engineering의 비중이 가장 크다**는 조사 결과가 있다(강사 언급: 전체 성능 기여 요인 중 약 25% 수준, 개인적으로는 이보다 더 크게 본다고 강조).
- 하이퍼파라미터 튜닝, 모델 알고리즘 선택으로 얻을 수 있는 성능 개선은 한계가 있다. **더 크게 성능을 끌어올리려면 데이터 처리·Feature Engineering·데이터 설계**를 건드려야 한다.

---

## 4. Feature Engineering의 3대 작업 유형

| 유형 | 설명 |
|---|---|
| **Feature Transformation (변환)** | 기존 피처의 형태를 변경 (결측치·이상치 처리, 스케일링, 구간화 등) |
| **Feature Creation (생성)** | 기존 피처를 조합해 새로운 피처(파생변수)를 만듦 |
| **Feature Selection (선택)** | 불필요한 피처를 제거하고 중요한 피처만 남김 |

---

## 5. Feature Transformation ①: 결측치(Missing Value) 처리

### 5.1 왜 처리해야 하는가
- 일부 알고리즘은 결측치가 있으면 아예 실행되지 않는다(요즘 트리 계열 모델은 결측치가 있어도 돌아가는 경우가 많지만 예외는 존재).
- 평균, 상관계수 등 통계량 계산이 왜곡될 수 있다.
- **단순 삭제는 거의 하지 않는다** — 정보 손실과 데이터 건수 감소 문제 때문.

### 5.2 결측치의 종류(발생 원인 기준)
| 종류 | 설명 | 예시 | 처리 방식 |
|---|---|---|---|
| 완전 무작위 결측 (MCAR) | 패턴 없이 랜덤하게 발생 | 입력 실수로 값 누락 | 대표값(평균/중앙값) 대체 또는 삭제 |
| 조건부 무작위 결측 (MAR) | 다른 변수와 관련되어 발생 | 남성이 체중 응답을 잘 누락 | 관련 변수로 그룹핑 후 그룹별 대표값 대체 |
| 비무작위 결측 (MNAR) | 결측 자체가 정보를 담고 있음 | 고소득자가 일부러 소득을 미기재 | **결측 여부 자체를 새로운 피처로 활용** |

### 5.3 결측이 "소중한 정보"가 되는 사례
- 실제 사례(가전제품 구매 예측 모델): 전화번호가 결측인 고객(약 50% 이상)일수록 구매율이 낮은 패턴이 발견됨 → **결측 자체가 유의미한 피처**가 되어, "전화번호 없음" 여부를 하나의 카테고리로 만들어 활용.
- **결론: 결측치를 함부로 버리지 말 것.** 결측 정보 자체가 소중한 신호일 수 있다.

### 5.4 수치형 변수의 "0"을 조심하라
- 실제로는 결측인데 시스템에서 편의상 0으로 채워놓는 경우가 흔하다.
- 0값을 만나면 항상 "정말 0이 맞는가?"를 의심해야 하며, 결측으로 재분류한 뒤 처리하는 것이 안전하다.

### 5.5 대체(Imputation) 방법
| 변수 유형 | 대표 방법 |
|---|---|
| 연속형 | 평균(이상치에 민감), **중앙값(주로 사용)**, 최빈값 |
| 시계열 | 직전값(과거→현재 방향으로만, 미래값 사용 금지), 보간(선형 등) |
| 범주형 | 최빈값 대체, 새로운 범주(new/unknown)로 대체(가장 흔히 씀), 그룹별 최빈값 대체 |

> 어떤 방법이 "정답"인지는 없다. **최종 판단 기준은 항상 모델 성능(평가)** 이다.

## 6. Feature Transformation ②: 이상치(Outlier) 처리

### 6.1 이상치 발생 원인
- 입력 오류(예: 나이에 999 입력)
- 측정 오류(센서 오작동 등)
- 실제 발생한 극단값(초고액자산가, 비정상거래/사기 등)

### 6.2 이상치가 문제가 되는 이유
- 평균 등 통계량을 왜곡시킨다.
- 모델이 이상치에 과도하게 맞춰져(overfit) 성능이 저하될 수 있다.
- **결국 문제의 핵심도 "모델 성능"이다.** 왜곡·저하가 없다면 굳이 처리할 필요가 없다.

### 6.3 이상치 탐지 방법
| 방법 | 설명 |
|---|---|
| IQR (사분위 범위) | Q3-Q1을 IQR로 정의, 상·하한선을 벗어나면 이상치 후보 (박스플롯 시각화와 연결) |
| Z-score (표준점수) | (값-평균)/표준편차. 절대값이 보통 3을 넘으면 이상치 후보 |
| 머신러닝 기법 (예: Isolation Forest) | 정상 데이터만으로 분포를 학습하는 비지도학습, 경계를 벗어나는 것을 이상치로 판정 |
| 시각화 | 산점도 등으로 육안 확인 |
| 분위수 분석 | 상/하위 1%, 5% 등 특정 백분위 범위를 벗어나는 값 |
| 휴리스틱/비즈니스 경험 기준 | 도메인 지식 기반 경계값 설정 (예: 하이닉스 제조공정 사례 — 최종적으로 "과거 평균 대비 100% 이상"이라는 단순 기준으로 고객·분석팀이 합의) |

> **복잡한 알고리즘이 항상 더 좋은 것은 아니다.** 운영·자동화 관점에서는 단순하고 이해하기 쉬운 방법이 더 실전적인 경우가 많다.

### 6.4 이상치 처리 방법
- **유지(강사가 가장 많이 씀)**: 명백한 입력 오류가 아닌 이상 함부로 손대지 않는다. 이상치의 명확한 경계 기준 자체가 존재하지 않기 때문.
- **경계값(Winsorizing) 대체**: 특정 분위수(예: 95%) 값으로 상한을 잘라서 대체.
- **변환(로그, 제곱근 등)**: 분포를 완화. 단, 회귀분석의 정규성 가정 때문에 전통적으로 많이 썼던 방법이며, 머신러닝/딥러닝 위주인 요즘은 정규성 가정 자체가 필요 없는 경우가 많아 **성능에 실질적 도움이 될 때만 사용**.

> 반복되는 원칙: **"이게 맞나?" 고민하지 말고 해보고 성능으로 판단하라.** (Missing 대체 방법, 이상치 기준, 스케일링 방법, 인코딩 방법 선택 모두 동일한 원칙)

## 7. Feature Transformation ③: 스케일링(Scaling)

- 단위·범위가 다른 데이터를 동일 기준으로 비교하기 위한 작업.
- **거리 기반 모델**(KNN, K-Means, PCA, 신경망 등)에서 중요 — 단위가 큰 피처(예: 소득)에 학습이 쏠리는 문제를 방지.
- **트리 기반 모델**(랜덤포레스트, XGBoost 등)은 분기점 기반으로 학습하므로 스케일링 효과가 크지 않음.

| 방법 | 설명 |
|---|---|
| Z-score (Standard Scaling) | 평균 0, 표준편차 1로 변환 |
| Min-Max Scaling | 최소값 0, 최대값 1 범위로 변환 |

## 8. Feature Transformation ④: 연속형 변수의 구간화(Binning)

- 예: 연령 → 연령대. 설문조사·리포팅에서 흔히 사용.
- **구간화의 효과**
  1. 해석이 용이해짐
  2. 이상치의 영향을 완화(극단값이 하나의 구간 안에 묶임)
  3. **선형 모델에서도 비선형(U자형 등) 관계를 반영**할 수 있게 됨 — 예: 나이와 이탈률이 U자형 관계일 때, 회귀분석은 원래 직선 관계만 잡아내지만 구간화하면 이런 패턴도 포착 가능.

### 구간화 방법
| 방법 | 설명 |
|---|---|
| 등빈도(Equal Frequency) | 각 구간에 속하는 데이터 개수를 동일하게 맞춤 |
| 등간격(Equal Width) | 구간의 폭(간격)을 동일하게 맞춤 |

- 범주(구간) 개수는 경험적으로 **4~10개 정도**가 안정적. 너무 많으면 구간별 데이터 건수가 줄어 모델이 불안정해지고, 너무 적으면 변별력이 떨어진다.

---

## 9. Feature Transformation ⑤: 범주형 변수 인코딩

머신러닝 알고리즘은 대부분 숫자 기반으로 계산하므로 범주형 데이터를 수치로 변환해야 한다.

### 9.1 원-핫 인코딩 (One-Hot Encoding)
- 각 범주를 0/1 값을 갖는 별도 컬럼(더미 변수)으로 분리.
- **회귀분석에서는 다중공선성 문제** 발생 가능 → 범주 중 하나를 기준값으로 제외한 **k-1개 더미 변수**를 사용(`drop_first`).
- 트리 기반 모델에서는 다중공선성 문제가 없어 굳이 뺄 필요는 없지만, 관례적으로 k-1개를 많이 사용.
- **범주 개수가 너무 많을 때(예: 우편번호, 상품코드) 문제**: 컬럼 수 폭증 → 메모리/연산 문제, **차원의 저주(Curse of Dimensionality)** 로 모델 성능 저하 가능.

### 9.2 레이블 인코딩 (Label Encoding)
- 범주에 순서대로 정수를 부여. **범주 순서에 의미가 있을 때**(예: 학점 A/B/C, 등급 1등급/2등급) 적합.
- 순서 의미가 없어도, 트리 기반 모델에서는 성능 차이가 크지 않은 경우가 많음(단, 항상 검증 필요).

### 9.3 타겟 인코딩 (Target Encoding)
- 범주 개수가 매우 많을 때, 각 범주를 **Target의 평균값**으로 대체(예: 지역별 평균 집값).
- ⚠️ **데이터 리키지(Data Leakage) 주의**: 반드시 Train set 안에서만 평균을 계산해야 한다. Train/Test 전체 데이터로 평균을 내면 미래(테스트) 정보가 학습에 유입되는 문제(Data Leakage/Target Leakage)가 발생해 평가 성능이 부풀려진다.

### 9.4 범주 개수를 줄이는 방법 (그룹핑)
- **의미 기반 그룹핑**: 계층 구조가 있으면 상위 레벨로 묶기(우편번호 → 군/구 단위)
- **빈도 기반 그룹핑**: 빈도가 낮은 범주들을 "기타(Other)" 하나로 묶기

### 9.5 인코딩 선택 로직 (요약)
1. 범주 순서에 의미가 있는가? → 있으면 Label Encoding 우선 검토
2. 순서 없고 범주 개수가 적은가? → One-Hot Encoding
3. 순서 없고 범주 개수가 많은가? → Target Encoding / 의미·빈도 기반 그룹핑 후 인코딩

> 여기서도 최종 판단 기준은 **모델 성능(평가)** 이다.

### 9.6 타겟 클래스가 너무 많은 경우 (Multi-class 문제)
- 예: 상품 추천 모델의 상품 코드가 1,000개 → 그대로 분류 모델을 만들면 연산·메모리 문제 + 클래스별 데이터 부족으로 성능 저하.
- **잘못된 대안**: 목표(Target)가 있는데 비지도학습(클러스터링)으로 우회하는 것은 부적절 — 지도학습(Classification) 문제와 비지도학습(Clustering)은 목적 자체가 다르다.
- **올바른 접근**: 빈도 기반 혹은 의미(계층) 기반으로 클래스 수를 줄여서 **Classification 문제로 그대로 풀어야 한다.**

## 10. Feature Creation (파생변수 생성) — 가장 중요한 작업

> Feature Transformation은 상대적으로 "기계적인" 작업(자동화 여지가 있음)인 반면, **Feature Creation(파생변수 생성)은 창의력이 필요한 영역**이며 AI가 대신하기 어려운 부분이다. 강사는 이 부분을 데이터 분석에서 **가장 중요한 과정**으로 꼽는다.

### 10.1 파생변수를 만드는 이유
- 오직 하나: **모델 성능 향상.**

### 10.2 생성 방법 예시

**① 산술 조합(더하기/빼기/곱하기/나누기)**
| 연산 | 예시 |
|---|---|
| 더하기 | 카테고리별 구매액 합산 → 총 구매액 |
| 빼기 | 이번달-지난달 매출 → 매출 증감 |
| 곱하기 | 단가 × 수량 → 총매출 |
| 나누기 (특히 유용) | 체중/키² → BMI, 순이익/투자금 → ROE, 클릭수/노출수 → CTR, 매출/부채 → 부채비율, 거리/연료 → 연비 |

> 나누기(비율) 기반 파생변수는 단순 정보 두 개를 조합해 **훨씬 풍부한 정보(비율·효율)** 를 담아낸다는 점에서 특히 효과가 크다는 게 강사의 경험적 관찰.

**② 날짜/시간 분해**
- 1차 파생: 연도, 월, 분기, 일, 요일, 주차, 시간
- 2차 파생: 시간대(새벽/오전/오후/저녁), 러시아워 여부, 심야 여부, 근무시간 여부, 주말 여부, 월초/월말 여부, 분기말 여부, 공휴일/연휴 여부
- 시간 차이: 가입 시점 대비 현재 시점 → 가입기간(충성도 피처)
- 예: "금요일 오후 + 월말 + 공휴일 직전"과 같은 복합 조건 → 외식 매출 급증 예측 등에 활용 가능

**③ 텍스트 데이터 기반 파생변수**
- 단순 통계: 글자 수, 단어 수, 문장 수, 평균 단어 길이, 이모지/기호 사용 여부
- 키워드 기반: 긍정/부정 키워드 포함 여부, 특정 주제(배송, 품질 등) 언급 여부
- NLP 기법: TF-IDF(단어 중요도 벡터화), 임베딩(문장 벡터화), 감성분석(긍/부정 점수)

**④ 도메인 지식 기반 파생변수 (현업 협업 필요 영역)**
- 예: "광고비 효과는 시차를 두고 나타난다", "12월 매출은 항상 높다"는 도메인 지식이 있다면 → 지난달 광고비 대비 이번달 광고비 비율, 12월 여부 등의 피처를 설계.
- 이 영역은 데이터만 봐서는 알 수 없고 **업무 전문가와의 협업이 필수**.

**⑤ RFM (이커머스/CRM 대표 지표)**
- Recency(최근성): 마지막 구매로부터 경과 일수
- Frequency(빈도): 총 구매 횟수
- Monetary(금액): 총/평균 구매 금액

**⑥ 집계 변수 + 2차 파생변수**
- 고객 단위 집계: 평균, 중앙값, 합계, 최소/최대 구매금액 등
- 2차 파생: 최근 구매금액 대비 본인 평균 대비 비율, 본인이 속한 그룹 평균 대비 위치, **본인 과거 최대 구매금액 대비 현재 금액** → **사기(Fraud) 탐지에 특히 유용** (평소 소비 패턴과 급격히 다른 거래 포착)

**⑦ 시계열(Lag/Rolling) 변수**
- 예: 주가 데이터(시가/고가/저가/종가/거래량 5~6개)만으로도 수백 개의 파생변수 생성 가능.
- Lag 변수: 1일 전/7일 전 종가(단기 변동 포착)
- Rolling(이동평균) 변수: 5일/20일/60일 이동평균(트렌드 포착)
- **관찰 기간은 예측 기간(Horizon)에 맞춰 설계** — 단기 예측이면 단기 변동 지표, 장기 예측(예: 6개월 후)이면 장기 트렌드까지 반영해야 함.
- 참고: 실전에서는 복잡하게 조합한 기술적 지표보다 **단순한 지표가 오히려 더 좋은 성능**을 내는 경우가 흔하다.

### 10.3 데이터가 부족할 때 — 비정상거래(사기) 탐지 사례
- 실제 사례: 증권사 직원 횡령사고 예측 — 발생 건수가 극소수(5건 미만)라 지도학습(Classification)이 사실상 불가능.
- 잘못된 시도: "타겟이 없으니 비지도학습(클러스터링)으로 풀자" → **지도학습의 Classification과 비지도학습의 Clustering은 목적 자체가 완전히 다르므로 대체재가 아니다.**
- 실제 접근: 룰베이스/휴리스틱(전문가 판단 + AHP 같은 가중치 산정 기법), 현업과의 협업을 통한 피처 발굴(예: "최근 통화량이 급증했는가") → 정성적 판단 기반으로라도 모델(도구)을 구성.
- **결론: "딥러닝/머신러닝으로 풀 수 없다고 해서 과제를 못 하는 것이 아니다."** 분석가는 폭넓은 시각으로 대안적 방법론을 갖추고 있어야 한다.

### 10.4 데이터 자체를 관찰해서 만든 파생변수의 힘
- 제조 공정 품질 불량 예측 사례: 공정 간 **이동시간**에 대한 데이터가 관리되지 않고 있다는 것을 발견 → 도메인 지식 없이 데이터 구조만 보고 파생변수로 만들었는데, 실제로 모델에서 매우 중요한 변수로 확인됨.
- 시사점: 현업 전문가조차 당연하게 여겨 놓쳤던 정보가, 데이터를 유심히 살펴본 분석가에 의해 발견될 수 있다.

## 11. Feature Selection (선택)

### 11.1 왜 필요한가 — 차원의 저주(Curse of Dimensionality)
- 피처(차원) 수가 늘어나면 동일한 데이터 건수 대비 데이터 공간의 밀도가 급격히 낮아진다.
- 빈 공간까지 모델이 학습해야 하므로, 학습 데이터에는 잘 맞지만(Train 성능↑) 새로운 데이터에는 성능이 떨어지는 **과적합(Overfitting)** 이 발생하기 쉽다.
- 차원이 늘어날수록 이를 충분히 학습하려면 데이터도 기하급수적으로 많아야 하는데, 실전에서는 그렇지 않은 경우가 대부분.
- 데이터 건수가 적을수록 피처 수의 영향을 크게 받는다. (반대로 데이터가 매우 많으면 변수를 줄이는 것이 오히려 성능을 해칠 수 있음)

### 11.2 Feature Selection의 3단계

| 단계 | 내용 | 판단 주체 |
|---|---|---|
| ① 신뢰성 검증 | 데이터 품질 문제 여부 확인(결측률, 편향성/밀집도, 범위(min/max) 확인, 중복 여부) | 사람의 판단 |
| ② 중요도 검증 | 피처와 타겟 간 관계·패턴이 있는지 통계적/머신러닝 방법으로 확인 | 기계적으로 가능 |
| ③ 논리성 검증 | 통계적으로 유의해도 업무적으로 말이 되는 관계인지 확인 | 사람의 판단(업무 논리) |

**① 신뢰성 검증 세부사항**
- 결측률이 지나치게 높거나 낮은지
- 하나의 값에 데이터가 지나치게 몰려있는지(밀집도) — 단, 90~99%가 하나의 값이라도 100%가 아니라면 "일단 넣어보고 성능으로 판단"하는 것이 강사의 원칙
- min/max 범위가 상식적으로 타당한지
- 중복 데이터 여부

**② 중요도 검증 방법**
- 통계적 방법: 상관분석(단, **비선형 관계는 잘 못 잡아냄**이 한계), 카이제곱 검증(실무에서는 잘 안 씀)
- 머신러닝 방법: **Feature Importance**(트리 기반 모델), Permutation Importance — 실무에서 더 많이 사용

**③ 논리성 검증**
- 피처와 타겟의 관계를 단순 산점도/트렌드 차트로 시각화해서 확인.
- 기울기가 가파르면 강한 관계, 완만하면 약한 관계.
- **시간에 따른 안정성(Stability)** 도 함께 봐야 한다 — 같은 기울기라도 시간에 따라 안정적인 피처가 더 신뢰할 수 있는 피처.
- 업무적으로 말이 되는 방향인지(예: 온도·압력이 오르면 불량률도 오른다는 관계가 실제 업무 로직과 맞는지) 확인.
- 단순한 차트 하나로 모델의 예측력을 어느 정도 사전에 가늠할 수 있다.

### 11.3 상관성 기반 제거
- 피처 간 상관이 매우 높으면(다중공선성 유발) 하나를 제거하는 것이 일반적.
- **"상관이 몇 % 이상이면 높다"는 절대 기준은 없다.** 과제·데이터에 따라 다르므로, 여러 임계값(80%, 90%, 99% 등)으로 실제 성능을 비교해서 결정해야 한다.

> **반복되는 원칙**: 결측 대체, 이상치 기준, 스케일링, 구간화, 인코딩, 상관 제거 기준 — 이 모든 선택의 최종 기준은 이론적 정답이 아니라 **실제 성능 평가**다. 다만 방법 자체는 알고 있어야 무엇을 시도해볼지 판단할 수 있다.

## 12. Feature Store (참고)

- 피처를 팀·프로젝트 간 **중앙 집중식으로 저장·관리·재사용**할 수 있게 하는 시스템.
- Feature Store가 없을 때 생기는 문제
  - 여러 팀이 동일한 피처(예: 최근 30일 평균)를 각자 다시 만들면서 계산 로직이 미묘하게 달라져 결과가 달라짐.
  - **학습-서빙 불일치(Train-Serving Skew)**: 학습 시에는 파이썬, 운영 시에는 자바 등 다른 언어로 피처를 계산하면 로직 차이로 결과가 달라질 수 있음.
  - 피처 개발에는 분석가의 시간이 가장 많이 들어가는데(하루 종일 걸릴 수 있음), 이를 재사용하지 못하면 조직 전체에 큰 비효율이 발생.
- 국내에서는 아직 일부 금융기관 외에는 도입 사례가 드물지만, 팀 간 사일로(silo)를 줄이고 **분야 간 피처를 통합(융합 분석)** 하는 것이 데이터 분석 조직 성숙도의 중요한 다음 단계로 언급됨. (예: 리스크 관점의 피처가 마케팅 관점에서도 유효할 수 있음)

## 13. 데이터 분석에서 생성형 AI의 역할

### 13.1 두 가지 활용 방식

| 방식 | 설명 | 장점 | 단점 |
|---|---|---|---|
| **All-in-LLM** (Code Execution까지 전부 위임) | 프롬프트 + 데이터를 통째로 LLM에 맡겨 모델링·해석까지 전부 위임 | 코드/ML 지식 없이도 가능, 빠른 프로토타이핑 | 데이터 보안 이슈, 대용량 데이터 처리 한계, **재현성(reproducibility) 문제**(같은 데이터를 다시 넣어도 같은 결과가 보장 안 됨 — 신용평가 등 규제 산업에서는 치명적), 커스터마이징 어려움 |
| **Code Generation** (코드만 요청, 로컬에서 실행) | 프롬프트를 주고 코드만 받아 로컬 환경에서 직접 실행·검증·커스터마이징 | 보안 준수, 대용량 처리 가능, 재현성 확보, 세밀한 커스터마이징 가능 | 최소한의 코드/ML 이해가 필요(단, 최근 에이전트가 코드 검증도 지원) |

- POC, 교육, 탐색적/일회성 분석, 빠른 의사결정이 필요한 경우 → All-in-LLM 방식도 유효.
- 실제 기업 운영 환경에서 자동화·대규모 운영이 필요한 경우 → Code Generation 방식이 기본.

### 13.2 코드를 어느 수준까지 이해해야 하는가
- 판단 기준: **내가 앞으로 무엇을 커스터마이징할 것인가 / 어떤 부분에서 오류 대응이 필요한가**
- 커스터마이징할 계획이 없는 영역(예: 차트 디자인, 하이퍼파라미터 튜닝을 직접 할 계획이 없다면)은 코드를 라인 단위로 이해할 필요가 없다.
- 반대로 자주 손댈 영역(예: 스케일링 방식 변경, 임계값 조정)은 그 정도 수준까지는 이해하고 있어야 한다.
- 이를 판단하려면 결국 **전체 프로세스와 각 블록의 역할을 개념적으로 이해**하고 있어야 한다 — "동일한 비중으로 모든 코드를 이해할 필요는 없다"가 핵심 메시지.

### 13.3 실제 파이프라인에서의 역할 분담

```
문제 정의 → 모델 설계(생성형 AI 지원 가능)
→ 데이터 준비/피처 생성(생성형 AI가 코드/파생변수 아이디어 지원)
→ 모델 학습(전통적 ML/DL 파이프라인)
→ 운영/서빙
    ├─ 배치 예측: 사전 계산된 예측 스코어를 자연어 질의로 조회 (생성형 AI가 SQL 변환·에이전트 역할)
    └─ 실시간 예측: 실시간 데이터로 ML 모델 API 호출 → 결과를 자연어로 응답 (생성형 AI는 인터페이스 역할)
```

- 생성형 AI의 역할: **설계 지원 + 코드 생성 + 사용자 인터페이스(자연어 질의응답)**.
- 모델 학습·운영의 핵심 파이프라인 자체는 여전히 **전통적인 MLOps 방식**으로 구축·운영해야 한다.

## 14. 실습 개요 (Titanic 데이터셋)

- 데이터: 1912년 타이타닉호 침몰 사고의 승객 정보(891건, 12개 컬럼)
- Target: 생존 여부(0=사망, 1=생존) → **이진 분류(Binary Classification) 문제**
- Feature: 객실 등급, 이름, 성별, 나이, 형제/배우자 수, 부모/자녀 수, 티켓번호, 운임, 객실번호, 승선항구 등
- 연속형·범주형 피처가 골고루 섞여 있어 실습용으로 널리 사용되는 데이터셋.

### 실습 흐름
1. 불필요한 변수 제거 (ID, 티켓번호 등 — 의미 있는 정보를 담지 않은 식별자)
2. **파생변수 생성**
   - 가족 크기 = 형제/배우자 수 + 부모/자녀 수 + 1(본인)
   - 이름에서 정규표현식으로 **호칭(Mr., Mrs., Miss 등)** 추출 → 빈도 낮은 호칭은 그룹핑(Other) 및 유사 호칭 통합(Mlle→Miss 등)
   - (Self-Practice 예시) 어린이 여부(나이 기준) — 어린이 생존율이 성인 대비 뚜렷하게 높은 패턴 확인
3. **EDA**: 연속형 변수는 분포로 확인 — 이상값(음수/0), 결측 비율, min/max 범위, 밀집도(하나의 값에 쏠려있는지) 등을 한 번에 스캔
4. **데이터 파티션(Train/Test 분할)**: 통계량 계산이 필요한 변환(스케일링, 타겟 인코딩 등)은 Train 기준으로만 계산해야 하므로, 보통 파티션을 먼저 수행
5. **Feature Transformation**: 스케일링(Z-score, Min-Max), 범주형 인코딩(One-Hot/Label/빈도 기반 그룹핑)
6. **Feature Selection**: 신뢰성 → 중요도 → 논리성 순으로 검토

### 참고 Q&A: 작업 순서가 꼭 고정되어야 하는가?
- 파생변수 생성을 앞쪽에 배치한 이유: 뒤에서 스케일링·결측 처리 등 변환을 한 번에 일괄 적용하기 위함.
- 만약 파생변수에 별도 변환(스케일링, 결측 처리)이 필요 없다면 순서를 뒤로 옮겨도 무방.
- 데이터 파티션(Train/Test 분할)을 앞쪽에 두는 이유도 마찬가지: 통계량 계산이 필요한 변환에서 데이터 리키지를 막기 위함. **통계량 계산이 필요 없는 단순 변환이라면 파티션 전후 상관없다.**
- 결론: **프로세스 순서에는 이유가 있지만 절대적인 규칙은 아니다. 왜 그 순서로 하는지 이해하는 것이 중요하다.**

## 15. 핵심 용어 정리

| 용어 | 의미 |
|---|---|
| Feature / Target | 입력 변수(X) / 목표 변수(Y) |
| Feature Transformation | 기존 피처의 형태를 변경 (결측·이상치 처리, 스케일링, 구간화, 인코딩 등) |
| Feature Creation | 파생변수를 새로 만드는 작업 |
| Feature Selection | 불필요한 피처 제거, 중요 피처 선택 |
| 파생변수 | 기존 피처를 조합·가공해 만든 새로운 피처 |
| MCAR / MAR / MNAR | 결측치 발생 패턴 분류 (완전 무작위 / 조건부 무작위 / 비무작위) |
| IQR / Z-score | 대표적인 이상치 탐지 통계량 |
| One-Hot / Label / Target Encoding | 범주형 변수를 수치로 변환하는 대표 방법 |
| Data Leakage | 미래(테스트) 정보가 학습 과정에 유입되어 평가 성능이 부풀려지는 문제 |
| 차원의 저주 | 피처(차원) 수가 늘어날수록 데이터 밀도가 낮아져 모델 성능이 저하되는 현상 |
| Feature Store | 피처를 팀 간 공유·재사용할 수 있게 중앙 관리하는 시스템 |
| RFM | Recency(최근성)·Frequency(빈도)·Monetary(금액) 기반 고객 분석 피처 |
| Feature Importance / Permutation Importance | 머신러닝 기반 피처 중요도 산출 방법 |
