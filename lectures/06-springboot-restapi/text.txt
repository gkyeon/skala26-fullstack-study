## 1. Spring 컴포넌트 스캔 & 어노테이션 체계 상세

### 2.1 `@SpringBootApplication`의 실체
`@SpringBootApplication`은 다음 3개 어노테이션의 조합:
1. **`@SpringBootConfiguration`**
2. **`@EnableAutoConfiguration`** — Spring Boot 자동 설정을 활성화하는 핵심.
3. **`@ComponentScan`** — 아래 설명할 8가지 대상 어노테이션을 스캔.

### 2.2 컴포넌트 스캔 대상 어노테이션 (약 8개)
`@Component`, `@Controller`, `@RestController`, `@Service`, `@Repository`, `@Configuration`, `@ConfigurationProperties` 등 — 이 어노테이션이 붙은 클래스를 자동으로 탐색해 **빈(Bean)으로 등록**.
- **`@Component`**: 공통 유틸성 기능(어디에도 속하지 않는 공통 기능)에 사용.
- **`@Controller` / `@RestController`**: MVC 패턴의 프론트 진입점. `@RestController` = `@Controller` + `@ResponseBody` 조합 — **JSON 응답이 기본인 REST API 개발에서는 `@RestController`를 쓰는 게 표준**.
- **`@Service`**: 비즈니스 로직 담당 계층.
- **`@Repository`**: 데이터 접근(DAO) 계층.
- **`@Configuration`**: 설정 클래스.
- **`@ConfigurationProperties`**: 외부 설정값 바인딩용.
- **동작 원리**: `@SpringBootApplication`이 있는 패키지를 시작점으로 **하위 패키지를 모두 스캔**하는 게 기본 동작. (범위 제한도 가능하지만 실무에서 잘 안 씀.)

## 2. Lombok 심화

### 3.1 Getter/Setter가 왜 필요했는지 (역사적 배경)
- 캡슐화 원칙상 상태 변수(필드)는 무조건 `private`으로 선언해야 함 → 외부에서 값을 얻거나 수정하려면 `public` 메서드가 필요 → 그래서 각 필드마다 **기계적으로 getter/setter를 만들어야 했던 것**이 전통적인 방식.
- 이런 "본질적인 비즈니스 로직과는 무관하지만 반드시 작성해야 하는 코드"를 **보일러플레이트 코드(boilerplate code)**라고 부름 — Lombok은 이걸 어노테이션 하나로 자동 생성해 없애주는 라이브러리.

### 3.2 주요 Lombok 어노테이션
| 어노테이션 | 역할 |
|---|---|
| `@Getter` / `@Setter` | 각각 getter/setter 메서드 자동 생성 |
| `@ToString` | `toString()` 자동 생성 |
| `@EqualsAndHashCode` | `equals()`, `hashCode()` 자동 생성 |
| `@NoArgsConstructor` | 파라미터 없는 기본 생성자 |
| `@AllArgsConstructor` | 모든 필드를 파라미터로 받는 생성자 |
| `@RequiredArgsConstructor` | `final`이거나 `@NonNull`인 필드만 파라미터로 받는 생성자 |
| **`@Data`** | 위의 Getter, Setter, ToString, EqualsAndHashCode, RequiredArgsConstructor **5개를 한번에 적용** — 가장 많이 씀 |
| **`@Value`** | 모든 필드를 `private final`로 만들어 **불변(immutable) 객체**를 생성. Setter는 없고 Getter만 생성됨 — 데이터 신뢰성(중간 변조 방지) 확보에 중요 |
| `@Builder` | 빌더 패턴 자동 생성 |
| **`@Slf4j`** | 로그 객체(`log`)를 별도 선언 없이 자동 주입 — 로깅 처리가 매우 편해짐 |

- 실무 팁: 프로젝트 생성 시 **Lombok은 무조건 필수 의존성으로 선택**하는 걸 추천.

### 3.3 로그 레벨 기준 (실무 팁)
| 레벨 | 용도 |
|---|---|
| **TRACE** | 가장 상세, 변수값 변화 등 세밀한 추적 (개발 단계) |
| **DEBUG** | 개발 단계에서 메서드 파라미터/반환값/내부 변수 확인. **특히 JPA 사용 시 실제 변환된 쿼리를 확인하기 위해 필수적으로 찍어봐야 함** |
| **INFO** | 어떤 요청/작업이 있었는지 |
| **ERROR** | 운영 환경에서는 로그 레벨을 상세하게 하지 않고, 법적으로 필요한 것(감사 로그 등)과 에러 위주로만 남김 |
- 운영 환경에서 로그를 과도하게 남기면 **스토리지를 잡아먹는 주요 원인**이 되고 오히려 부하가 발생 — 개발/테스트/운영 환경별로 로그 레벨을 다르게 설정하는 게 원칙(Profile과 연결됨).
- **민감정보 마스킹**: 로그 안에도 개인정보가 노출될 수 있으므로 반드시 마스킹 처리(`*` 등)해야 함 — 컨트롤러 계층 로깅은 INFO(요청 URI/IP 등), DEBUG(파라미터/RequestBody 내용, 단 민감정보는 마스킹) 두 레벨로 나눠 관리하는 게 일반적.

### 3.4 DTO vs Entity — Lombok 관점에서 다시 강조
- **DTO(Data Transfer Object)**: 계층 간(Controller-Service-Repository) 데이터 전달 **전용** 객체. **절대 비즈니스 로직을 포함하지 않음**. 예전엔 "Value Object"라는 용어로도 불렸음(동일한 개념).
- **Entity를 DTO처럼 그대로 쓰지 말 것** — 이유:
  1. Entity를 클라이언트에 직접 노출하면 **원치 않는 민감 필드까지 외부에 노출**될 위험.
  2. UI 요구사항이 바뀔 때마다 DB 설계에 영향을 줘서 유연성이 떨어짐.
  3. 양방향 연관관계가 설정된 Entity를 그대로 JSON 직렬화하면 **무한 루프에 빠져 StackOverflow 에러**가 발생할 수 있음.
- **DTO 네이밍 컨벤션 권고**: 요청용은 `UserCreateRequest`, `ProductUpdateRequest`처럼, 응답용은 `~Response`처럼 **역할을 이름에 명시**해서 가독성을 높이는 걸 권장. 하나의 DTO를 요청/응답 모두에 재사용하면 용도가 다른 필드가 섞여 혼란을 줄 수 있음.
- **입력값 검증(Validation) 어노테이션은 DTO에 적용**하는 것이 표준 아키텍처 패턴 — 유효하지 않은 데이터가 서비스 계층까지 넘어가지 않도록 **컨트롤러 단에서 미리 필터링**해야 함(서비스 계층은 검증이 아니라 비즈니스 로직 처리에 집중).

## 3. Singleton 패턴 & Spring Bean 관리

### 4.1 왜 싱글턴인가
- 메모리는 **유한한 자원** — 개발자가 `new` 키워드로 매번 새 객체를 만들면 메모리를 낭비함.
- **Spring 컨테이너는 기본적으로 모든 빈(Bean)을 싱글턴으로 관리** — 애플리케이션 전체에서 객체를 하나만 생성해서 공유.
- 장점: **메모리 절약**, **데이터 일관성**(모든 사용자가 동일 객체 사용), **객체 생성 비용 감소**.
- 참고 비유: 프로세스는 독립적인 메모리를 갖지만, Java의 스레드는 **공유 메모리**를 사용 — 그래서 메모리 컨트롤(오너십)을 개발자가 직접 갖는 게 아니라 **가비지 컬렉터(GC)**가 안 쓰는 객체를 정리하고 자주 쓰는 객체를 유지해주는 역할을 함.

### 4.2 빈(Bean) 관련 핵심 정리
- **빈**: 스프링 컨테이너가 관리하는 객체 인스턴스.
- **싱글턴 스코프**: 하나의 인스턴스를 애플리케이션 전체가 공유해서 쓰는 방식 — 예: 커넥션 풀도 비슷한 개념(몇 개만 미리 만들어놓고 대여해서 재사용).
- 빈 생명주기 콜백: `@PostConstruct`(생성 직후 1회), `@PreDestroy`(소멸 직전 1회) — 이전 노트에서 다룬 내용과 동일.
- **`@Autowired`(필드 주입)는 실무에서 거의 안 씀** — **생성자를 통한 의존성 주입**이 표준.

## 4. Spring MVC ↔ Spring Boot의 관계 (구조 상세)

### 5.1 관계 정리
- **Spring MVC**는 Spring Framework의 **웹 계층 모듈**(MVC 패턴으로 HTTP 요청을 처리하는 웹 프레임워크) — Spring Boot보다 먼저 존재했던 기술.
- **Spring Boot는 내부적으로 Spring MVC를 그대로 활용**하면서, 그 위에 **자동 설정(Auto-Configuration) + 내장 톰캣**을 얹어 "손쉽게 구동"할 수 있게 감싸주는 **실행 플랫폼**.
- 예전 Spring MVC(Spring Boot 이전)는 `DispatcherServlet`, `ViewResolver` 등을 **수동으로 XML에 설정**해야 했고, 톰캣도 별도 설치가 필요했음. Spring Boot는 이걸 다 자동화(`spring-boot-starter-web` 하나 추가로 끝).

### 5.2 요청 처리 전체 흐름 (컴포넌트별 역할)
```
클라이언트 요청
  → DispatcherServlet (프론트 컨트롤러, 모든 요청의 단일 진입점)
  → HandlerMapping (URL/HTTP Method 등으로 "어느 핸들러로 갈지" 찾는 역할)
  → HandlerAdapter (찾은 Controller/RestController를 실제로 실행할 수 있는 적합한 어댑터 선택)
  → Controller (비즈니스 로직 호출, 요청 파라미터 바인딩, 응답 데이터 생성)
  → HttpMessageConverter (RequestBody ↔ Java 객체, Java 객체 ↔ ResponseBody 변환 = 직렬화/역직렬화)
  → 응답(JSON) 반환
```
- **DispatcherServlet**: Spring Boot에서는 **자동으로 등록**되어 있어 별도 설정 불필요.
- **HandlerMapping**: `@RequestMapping`, `@GetMapping` 등 매핑 정보로 "어디로 갈지"를 찾음.
- **HandlerAdapter**: `@Controller`/`@RestController`를 실제로 실행할 수 있게 함.
- **HttpMessageConverter**: `@RequestBody`, `@ResponseBody` 처리(JSON↔객체 변환).

### 5.3 Spring 어노테이션 전체 분류 체계
강사가 정리한 큰 6개 카테고리:
1. **컴포넌트 식별**: `@Component`, `@Controller`, `@Service`, `@Repository`, `@RestController`
2. **의존성 주입**: 생성자 주입이 표준 (`@Autowired`는 거의 안 씀)
3. **환경 설정**: `@Value`, `@ConfigurationProperties` (실무에서 잘 안 씀)
4. **웹 계층**: `@RequestMapping`, `@GetMapping`/`@PostMapping`/`@PutMapping`/`@PatchMapping`/`@DeleteMapping`, `@PathVariable`, `@RequestParam`, `@RequestBody`/`@ResponseBody`, `@RequestHeader`
5. **데이터 접근**: `@Entity`, `@Id`, `@GeneratedValue`, `@Repository`, `@Transactional`
6. **예외 및 검증**: `@ControllerAdvice`/`@RestControllerAdvice`, `@ExceptionHandler`, `@Valid`/`@Validated`

**어노테이션이 붙는 위치도 각기 다름** — 헷갈리기 쉬운 부분이라 강사가 강조:
- **클래스 위에만**: `@Entity`, `@Table`, `@Repository`(인터페이스 위)
- **메서드 위에만**: `@GetMapping`/`@PostMapping` 등
- **필드 위에**: `@Id`, `@GeneratedValue`
- **파라미터 위에**: `@PathVariable`, `@RequestParam`, `@RequestBody`
- **클래스 또는 메서드 둘 다 가능**: `@RequestMapping`, `@Transactional` (트랜잭션을 클래스 전체로 묶을지, 특정 메서드만 묶을지에 따라 위치가 달라짐)

### 5.4 Validation 재확인
- `@Valid`(Java/Bean Validation 표준) vs `@Validated`(Spring 확장 어노테이션) — **실무에서는 `@Valid`를 훨씬 더 많이 사용**함 (신기하게도 Spring 자체 확장 버전보다 표준 버전을 더 많이 씀).
- 역할 분리:
  - **컨트롤러 계층**: 데이터 **형식(format)** 검증 — 이메일 형식인지, null이 아닌지 등.
  - **서비스 계층**: **비즈니스 규칙** 검증 — 예를 들어 "1~5 중 하나여야 하는데 8이 들어옴"처럼 형식은 맞지만 값 자체가 비즈니스 규칙에 안 맞는 경우. 이건 컨트롤러가 알 수 없는 영역(도메인 지식 필요)이라 서비스 계층에서 처리.
- **Fail-Fast 원칙**: 잘못된 데이터는 가능한 한 **가장 바깥(컨트롤러)에서 빨리 차단**하는 것이 효율적 — 서비스 계층까지 넘어가서 검증하면 비즈니스 예외와 입력 검증 예외가 섞여 코드가 복잡해짐.

## 5. AOP (Aspect-Oriented Programming, 관점 지향 프로그래밍)

### 6.1 Spring Boot의 3대 핵심 요소
강사가 강조하는 정리: **IOC, DI, AOP** — 이 셋이 Spring Boot를 구성하는 3대 핵심.

### 6.2 AOP가 필요한 이유 — 횡단 관심사(Cross-Cutting Concern)
- OOP(객체지향)는 A기능, B기능, C기능처럼 **기능 단위(클래스)로 세로로 구현**하는데, 이 A, B, C 클래스 모두가 **공통으로 필요한 기능**(로깅, 트랜잭션 처리, 보안, 성능 측정 등)이 존재함 — 이를 **"공통 관심사(Common Concern)" = "횡단 관심사(Cross-Cutting Concern)"**라고 부름.
- SRP(단일 책임 원칙) 관점에서 보면 각 클래스는 자기 기능에만 집중해야 하는데, 그렇다고 공통 기능을 A, B, C 클래스에 일일이 다 손으로 넣으면(수정하면) 유지보수가 엄청나게 힘들어짐.
- **AOP의 핵심 아이디어**: 해당 클래스들을 **건드리지 않고(수정 없이)** 공통 기능을 별도로 분리해서 적용하는 것.
- `spring-boot-starter-aop` 의존성만 추가하면 별도 설정 없이 바로 사용 가능.

### 6.3 AOP 핵심 용어 — 가장 중요한 건 **Advice**(언제)와 **Pointcut**(어디에)
| 용어 | 의미 |
|---|---|
| **Aspect** | 공통 관심사를 모아둔 클래스. `@Aspect` 어노테이션 사용 (단, `@Aspect` 단독으로는 빈 등록이 안 되므로 `@Component`와 함께 써야 함) |
| **Advice** | **"언제"** 공통 로직을 실행할지 — `@Before`(메서드 실행 전), `@After`(실행 후), `@AfterReturning`(정상 실행 후), `@AfterThrowing`(예외 발생 후), **`@Around`(전후 모두, 실무에서 가장 많이 쓰임)** |
| **Pointcut** | **"어디에"** 적용할지 — 특정 패키지/클래스/메서드를 표현식으로 지정 (예: `execution(* com.example.service..*Service.find*(..))` 같은 형태) |
| **JoinPoint** | Advice가 적용될 수 있는 지점(Spring AOP에서는 메서드 실행 시점만 지원) |

### 6.4 Spring Proxy 개념
- 스프링 컨테이너는 AOP나 트랜잭션 대상이 되는 빈에 대해서는, **원본 객체 대신 프록시(Proxy) 객체를 생성**해서 컨테이너에 등록.
- 클라이언트가 빈을 호출하면 **프록시가 먼저 실행**되어 전처리(예: 로깅 시작) → 실제 원본 메서드 호출 → 후처리(예: 로깅 종료) → 결과 반환 순으로 동작.
- **트랜잭션(`@Transactional`)도 AOP와 같은 프록시 메커니즘**을 사용 — 일반적인 빈과 다르게 "특별 관리"가 필요한 대상.

### 6.5 Java Reflection과의 관계
- Java Reflection = 실행 중(런타임)에 클래스/메서드 정보를 읽거나 조작할 수 있게 해주는 기술.
- Spring의 빈 생성, DI, AOP, 컨트롤러 매핑 등 핵심 기능 대부분이 **내부적으로 Reflection을 적극 활용**함.

### 6.6 실무에서의 AOP 사용
- 공통 모듈(인증/인가, 로깅, 대외 연계 인터페이스 등)에 AOP가 많이 쓰임 — 프로젝트 현장에서는 보통 **공통개발팀**이 업무개발팀보다 먼저 투입되어 아키텍처 설계 + 공통 기능(AOP 포함) + 코드 템플릿을 미리 만들어놓고, 업무개발팀이 이를 가져다 씀.

## 6. JPA 심화

### 7.1 JPA vs JDBC vs MyBatis — 3자 비교
| 구분 | JDBC | JPA | MyBatis(SQL Mapper) |
|---|---|---|---|
| 방식 | SQL 직접 실행, Connection/Statement/ResultSet 개발자가 직접 관리 | 객체 지향(Entity/Repository), SQL 자동 생성 | SQL 직접 작성 + 파라미터 바인딩/결과 매핑만 프레임워크가 담당 |
| 표준/구현체 | - | **JPA는 인터페이스/어노테이션 표준 규격**, 실제 구현체는 **Hibernate** | **MyBatis 자체가 구현체** |
| DB 종속성 | - | 낮음 (Hibernate가 DB에 맞게 SQL 변환) | 높음 (SQL을 DB에 맞춰 직접 관리) |
| 성능 튜닝 | 직접 가능 | 생성된 SQL을 간접 제어(로그로 확인 필요) — 어려움 | SQL을 직접 보고 튜닝 가능 |
| 적합한 경우 | (레거시) | 도메인 중심 신규 개발, 단순 CRUD, DB 이식성 필요 시 | 복잡한 조인/집계, 튜닝된 SQL, 레거시 DB, 리포트/통계성 조회 |

- **JPA는 "SQL을 안 써도 된다"가 기본 사상** — 메서드 **네이밍만으로 Hibernate가 SQL을 자동 생성·변환**해서 JDBC를 통해 실행.
- 하지만 **실제로 예상한 SQL로 잘 변환됐는지는 로그를 찍어서 반드시 확인해야 함** — 이게 JPA 개발 시 빠뜨리기 쉬운 중요 습관.
- **한국/중국은 전 세계에서 JPA를 가장 적게 쓰는 나라 중 하나**라는 강사의 체감 — 이유: 우리나라 실무 쿼리는 서브쿼리/인라인뷰 등 복잡도가 매우 높은 경우가 많아, 복잡한 SQL을 JPA 메서드 네이밍만으로 표현하기 어렵기 때문. (SK텔레콤 백엔드 코드 중에는 수백 줄짜리 쿼리도 있다고 언급.)
- **결론(실무 전략)**: JPA와 SQL Mapper(MyBatis)는 **대체 관계가 아니라 선택지(역할 분담)** — 한 프로젝트 안에서 **등록/수정 등 단순 CRUD는 JPA로, 복잡한 조회/통계는 MyBatis로** 병행하는 경우가 대부분.

### 7.2 JPA 주요 어노테이션 (ORM 매핑)
| 어노테이션 | 역할 |
|---|---|
| `@Entity` | 해당 클래스가 DB 테이블과 매핑되는 JPA 엔티티임을 선언. 기본 생성자가 필요하며, `final`/`abstract`/`interface`/이너클래스에는 사용 불가 |
| `@Table(name=...)` | 매핑될 실제 테이블명을 명시 (생략 시 클래스명이 그대로 테이블명이 됨) |
| `@Id` | 기본키(Primary Key) 지정 |
| `@GeneratedValue` | 기본키 값 자동 생성 전략 지정 |
| `@Column` | 필드-DB 컬럼 매핑 (name, nullable, length, unique, insertable, updatable 등 속성 지정). **DB는 언더바(`_`) 네이밍, Java는 카멜케이스**를 쓰기 때문에 이 매핑이 특히 중요함 |
| `@Enumerated` | enum 타입 필드를 DB에 문자열/숫자로 매핑 |
| `@Lob` | 대용량 데이터(CLOB - Character Large Object, BLOB - Binary Large Object) 저장 |
| `@Transient` | DB 컬럼과 매핑되지 않는(저장 안 되는) 임시 필드 선언 |
| `@Embedded` / `@Embeddable` | 값 타입 객체를 필드로 포함(복합키 등에 사용). `@Embeddable`로 선언된 별도 클래스를 다른 엔티티에서 `@Embedded`로 포함시키는 짝 개념 — 주로 **복합키(composite key)** 구현에 사용 |
| `@OneToOne`, `@OneToMany`, `@ManyToOne`, `@ManyToMany` | 테이블 간 연관관계(릴레이션) 매핑. `@ManyToMany`는 보통 중간(조인) 테이블이 필요 |
| `@JoinColumn` | 외래키(FK) 컬럼 지정 |
| `mappedBy` | 연관관계의 **주인이 아닌 쪽**을 명시 (연관관계 주인은 보통 N쪽 — 예: 하나의 User가 여러 Transaction을 가지면 Transaction이 주인) |

- **`Update-Only` 컬럼 예시**: 생성일시/생성자/수정일시/수정자 4개 필수 컬럼은 `updatable=false` 등으로 "생성 후 절대 수정 불가"를 강제하기도 함(감사 추적성 확보).

### 7.3 시퀀스(Sequence) vs Auto Increment — 실무 팁
- 강사에게 자주 들어오는 질문: "PK 생성할 때 애플리케이션에서 `+1, +1` 하는 것과 DB 시퀀스를 쓰는 것 중 뭐가 나은가?" → **오더링 보장이 필요 없다면 무조건 시퀀스를 써라**는 게 강사의 답.
- **시퀀스는 오더링(순서, 1→2→3→4 연속성)을 100% 보장하지 않음** — 만약 업무상 "반드시 4 다음엔 5여야 한다"는 요건이 있으면(예: 회계 전표 번호), `SELECT FOR UPDATE`로 락을 걸고 애플리케이션에서 +1 처리해야 함.
- DB마다 지원 방식이 다름: MySQL/MariaDB 계열은 **Auto Increment**를 주로 지원, Oracle/PostgreSQL은 **Sequence**를 지원 — 기능이 비슷해 보여도 미묘하게 다르므로 프로젝트 초반에 DB 선택 시 확인 필요.

### 7.4 JpaRepository 계층 구조
```
Repository (최상위, 아무 메서드도 정의 안 된 마커 인터페이스)
  └─ CrudRepository (기본 CRUD 메서드 제공: save, findById, findAll, delete 등)
       └─ PagingAndSortingRepository (페이징 + 정렬 기능 추가)
            └─ JpaRepository (JPA 특화 기능 추가 — 실무에서 이걸 상속받아 씀)
```
- **페이징은 선택이 아니라 필수** — 페이징 처리 없이 몇만~몇십만 건을 그대로 SELECT하면 **OutOfMemory 장애**로 직결됨. 웹 화면에서 "다음 페이지" 버튼이든 무한 스크롤이든, 모두 내부적으로는 페이징 처리를 하고 있는 것.

### 7.5 자주 쓰는 JpaRepository 메서드
- `save(entity)`: 저장/수정.
- `saveAndFlush(entity)`: 저장 후 **즉시 플러시(flush)** — 영속성 컨텍스트 변경 내용을 DB에 바로 반영.
- `findById(id)`: 단건 조회 (반환 타입 `Optional<T>` — **값이 없을 수도 있음을 타입으로 표현**).
- `findAll()`: 다건 조회.
- `deleteById(id)`: 삭제.
- 메서드 삭제/조회 등도 나름의 명명 규칙(키워드 조합)을 따라야 Hibernate가 이를 인식해 SQL로 변환함.

### 7.6 Flush(플러시)의 의미
- **쓰기 지연(write-behind)**: `save()`를 호출해도 즉시 물리적 DB에 쓰는 게 아니라, 일단 **영속성 컨텍스트(1차 캐시/작업 공간)에 저장**되고, 실행할 SQL은 **"쓰기 지연 SQL 저장소"**에 쌓임 — 트랜잭션이 커밋되는 시점에 한꺼번에 DB에 반영됨.
- **명시적으로 flush를 호출해야 하는 대표적 상황**: insert/update 직후 바로 그 결과를 조회(select)해야 하는 경우 — 커밋 전이라 아직 DB에 반영이 안 된 상태에서 조회하면 "분명히 넣었는데 왜 안 보이지?" 하는 문제가 생길 수 있음.

### 7.7 Query Method / @Query
세 가지 방식이 있음:
1. **쿼리 메서드(네이밍 기반)**: `findByStatusAndEmail(...)`, `findByNameContaining(...)`처럼 **메서드 이름 자체가 규칙**이 되어 Hibernate가 SQL로 변환. 간단·빠르지만 복잡한 조건/조인에는 한계가 있고, 메서드명이 매우 길어질 수 있음(우리나라 실무 요건에는 잘 안 맞는 경우가 많음).
2. **`@Query` + JPQL**: **엔티티(객체) 기준**으로 쿼리 작성 — Table/Column이 아니라 **Entity/Field** 기준이라는 게 핵심 차이. DB에 독립적(ANSI SQL 관점)이지만, 결국 Hibernate가 다시 SQL로 변환해야 하므로 "JPQL 쓸 바에 그냥 네이티브 SQL 쓰는 게 낫다"는 의견도 실무에 존재.
3. **`@Query(nativeQuery = true)`**: 실제 DB의 **네이티브 SQL**을 그대로 사용 — DB에 종속적이지만 DB 고유 함수까지 활용 가능.

### 7.8 트랜잭션(Transaction) 상세

**ACID 원칙**
| 속성 | 의미 |
|---|---|
| **원자성(Atomicity)** | 모두 반영되거나 모두 반영되지 않거나 (**All or Nothing**) |
| **일관성(Consistency)** | 트랜잭션 전후로 데이터가 일관된 상태를 유지 |
| **격리성(Isolation)** | 동시에 실행되는 여러 트랜잭션이 서로 영향을 주지 않음 |
| **지속성(Durability)** | 커밋된 결과는 영구적으로 저장됨 |

**트랜잭션 시작/커밋 시점**
- `@Transactional`은 **서비스 계층에서만** 적용(컨트롤러/레포지토리에는 안 씀).
- `@Transactional`이 붙은 메서드가 예외 없이 정상 종료되는 시점에 **커밋**이 발생.
- 트랜잭션 대상 빈은 AOP처럼 **프록시 객체**로 등록되어, 실제 서비스 메서드 호출 전에 프록시가 먼저 개입.

**트랜잭션 범위(바운더리)는 최대한 좁게**
- 트랜잭션 범위를 너무 넓게 잡으면(예: 웹 API 호출/파일 IO 같은 장시간 작업까지 포함) **DB 동시성 저하 등 성능 문제**가 생길 수 있음 — 트랜잭션 범위는 **DB 오퍼레이션만 포함하도록 최대한 좁혀야 함**.

**전파(Propagation)**
- 기본값(`REQUIRED`): 기존 트랜잭션이 있으면 참여, 없으면 새로 생성.
- `REQUIRES_NEW`: 항상 새로운 트랜잭션 생성(기존 트랜잭션은 잠시 중단/서스펜드) — 로그 기록, 감사(audit) 처리 등에 활용.

**자기 호출(Self-Invocation) 문제 — 실무에서 자주 걸리는 함정**
- 하나의 클래스 내에서, `@Transactional`이 붙은 메서드가 **같은 클래스의 다른 `@Transactional` 메서드를 내부에서 직접 호출**하면 **전파 설정이 적용되지 않음**.
- 이유: 트랜잭션은 프록시(AOP)를 거쳐야 적용되는데, **내부 메서드 호출은 프록시를 거치지 않고 `this`를 통해 직접 호출**되기 때문.
- **해결책**: 트랜잭션을 분리해야 하는 메서드는 아예 **별도의 클래스로 분리**해서 호출해야 함.

**동시성 제어 — 낙관적 락 vs 비관적 락**
| 구분 | 특징 |
|---|---|
| **낙관적 락(Optimistic Lock)** | 읽기(SELECT)가 많은 환경에 유리. **DB에 직접 락을 걸지 않음**. 충돌이 발생하면 개발자가 직접 예외 처리 및 재시도 로직을 구현해야 함 |
| **비관적 락(Pessimistic Lock)** | CUD(Create/Update/Delete)가 많은 경우 유리. **DB에 실제로 락을 건다** — "화장실 문을 잠그는 것"처럼, 먼저 들어간 트랜잭션이 완료될 때까지 다른 요청은 대기(웨이팅). 데이터 정확성을 확실하게 보장하지만 성능 저하(대기 시간 증가) 가능성 있음 |
- 실무에서는 **데이터의 읽기 일관성(정합성)을 확실히 보장하고 싶을 때 비관적 락을 쓰는 경우가 많다**는 것이 강사의 체감.

## 7. MyBatis (SQL Mapper)

### 8.1 개념
- **SQL Mapper**: SQL을 직접 작성하고, 그 결과를 Java 객체에 매핑해주는 방식의 데이터 접근 기술 — **개발자가 SQL을 직접 관리(쥐고 감)**, 파라미터 바인딩과 결과 매핑만 프레임워크(MyBatis)가 담당.
- **JPA(Hibernate)는 "SQL을 만들어주는 쪽"**, **MyBatis는 "SQL을 직접 쥐고 가는 쪽"** — 강사의 한 줄 비교.
- 실행 흐름: `Mapper Interface` 호출 → `Mapper XML`의 SQL 조립 → JDBC 실행 → 결과 반환. (JPA도 결국 Hibernate를 거쳐 JDBC로 귀결되는 것과 마찬가지로, MyBatis도 결국 JDBC로 처리됨 — **모든 데이터 접근 기술은 종국에 JDBC를 거친다**.)

### 8.2 구성 요소
- **Mapper Interface**: 인터페이스만 정의 (JPA Repository와 비슷한 역할).
- **Mapper XML**: 실제 SQL 문을 작성하는 곳 — `namespace`로 어떤 Mapper Interface와 연결되는지 지정.
- 컬럼명/필드명이 다를 경우 **ResultMap**을 사용해 매핑하거나, `mapUnderscoreToCamelCase` 설정으로 자동 변환(`product_name` ↔ `productName`) 가능.

### 8.3 파라미터 바인딩 — `#{}` vs `${}` (보안 필수 지식)
- **`#{}` (샵 중괄호)**: PreparedStatement의 `?`(물음표)로 안전하게 바인딩됨 — **SQL Injection에 안전**.
- **`${}` (달러 중괄호)**: 문자열을 그대로 이어붙이는 방식 — **SQL Injection에 취약**하므로 매우 조심해서 사용해야 함.

### 8.4 동적 SQL (Dynamic SQL)
- 조건에 따라 SQL 문 자체가 달라지는 기능 — MyBatis를 쓰는 큰 이유 중 하나.
- `<if test="category != null"> ... </if>`처럼 조건부로 SQL 조각을 붙이는 방식, `<foreach>`로 컬렉션 순회(IN 절 등) 처리.
- 실무 팁: **동적 SQL은 매번 SQL 문이 바뀌기 때문에 SQL 캐싱 효율이 떨어질 수 있어**, 조회 조건이 다양한 경우 불가피하게 쓰긴 하지만 남발하지 않도록 주의.

### 8.5 페이징 (MyBatis는 자동 지원 안 함)
- JPA와 달리 MyBatis는 페이징을 자동으로 만들어주지 않으므로, **SQL에 직접 `LIMIT`/`OFFSET`을 작성**해야 함 (예: `LIMIT 20 OFFSET 40`).
- 전체를 다 읽어서 메모리에서 자르는 방식은 대용량 데이터에서 매우 위험 — 반드시 SQL 레벨에서 LIMIT 처리.

### 8.6 어노테이션 방식 vs XML 방식
- SQL이 짧으면 `@Select`, `@Insert` 등 어노테이션으로 간단히 처리 가능.
- 하지만 **실무에서는 SQL이 길거나 동적 SQL이 필요한 경우가 대부분이라 거의 XML 방식을 씀** — 강사는 "실제 프로젝트 현장에서 (MyBatis) 어노테이션 방식을 쓰는 걸 거의 못 봤다"고 언급.

### 8.7 실무에서 프로젝트 하나에 JPA + MyBatis를 같이 쓰는 이유
- **JPA가 유리한 경우**: 도메인 중심 신규 설계/개발, 단순 CRUD가 많은 경우, DB 이식성이 필요한 경우(DB 교체 가능성이 있는 경우).
- **MyBatis가 유리한 경우**: 복잡한 조인/집계, 통계·리포트성 대량 조회, 레거시 DB 대응, SQL 튜닝이 중요한 경우.
- **결론: 대체 관계가 아니라 선택지(역할 분담) — 등록/수정은 JPA로, 복잡한 통계/조회는 MyBatis로 나눠서 함께 쓰는 경우가 실무의 대부분.**
- 주의사항: MyBatis의 데이터 변경은 JPA(영속성 컨텍스트)가 인지하지 못하므로, **같은 트랜잭션 안에서 JPA와 MyBatis를 함께 쓸 때는 플러시(flush) 순서를 신경 써야 함**.

## 8. 데이터베이스 실무 배경지식 (강의 중 곁들여진 심화 내용)

### 9.1 DB 물리적 구조 — 왜 백엔드 개발자도 알아야 하는가
- 모든 컴퓨팅 자원(노트북, 서버, 데이터센터)은 **CPU > 메모리 > 스토리지** 순으로 속도가 빠르고, 스토리지가 가장 느림.
- **DBMS 튜닝의 핵심 컨셉**: 스토리지에 있는 물리적 데이터를 어떻게 하면 **메모리에 최대한 캐싱**해서 빠르게 서비스할 수 있을까 — 이게 모든 DB 제품(오라클의 SGA/PGA 등)이 신경 쓰는 핵심.
- **증권/트레이딩 데이터는 메모리 전용 DB(In-Memory DB)를 씀** — 스토리지에서 긁어오는 시간조차 허용 안 될 만큼 초저지연이 요구되기 때문.

### 9.2 인덱스는 원칙적으로 DBA의 역할
- 백엔드 개발자가 쿼리 성능 문제를 겪으면, 직접 인덱스를 만드는 게 아니라 **DBA에게 "어떤 테이블의 어떤 컬럼 순서로 인덱스를 만들어달라"고 요청**하는 것이 원칙적인 프로세스.
- **테이블스페이스(Tablespace)** 개념: 물리적 데이터 파일과 논리적 구성을 분리 — 실 데이터가 담긴 테이블스페이스와 인덱스 전용 테이블스페이스를 분리 관리하는 등 DBA가 정책을 갖고 운영.

### 9.3 이력 관리 / 감사 추적 (실무 패턴)
- 대부분의 테이블에는 **4개의 필수 컬럼**이 있음: **생성자, 생성일시, 수정자, 수정일시**.
- 추적성이 특히 중요한 마스터 데이터(고객정보, 상품정보 등)는 **별도의 히스토리(이력) 테이블**을 만들어 **변경 전(before)/변경 후(after)** 값을 모두 남기는 경우가 많음 — 단순 UPDATE만 치면 "왜 바뀌었는지" 추적이 불가능해지기 때문.
- **상용 서비스에서는 DB에 직접 접속(DB 툴로 UPDATE/INSERT/DELETE)하는 것을 원천 차단**하는 경우가 많음 — 데이터 변경은 반드시 **애플리케이션/서비스를 통해서만** 이루어지도록 통제.

### 9.4 개인정보/보안 관련 로깅 원칙
- 개인정보 등 민감 데이터에 접근한 이력은 **감사 로그(Audit Log)**로 반드시 남겨야 함 — 업무와 무관하게 접근한 경우 소명 절차가 필요할 만큼 엄격하게 관리됨. (보안사고의 대부분은 외부 침투가 아니라 **내부자에 의한 것**이라는 통계.)
- 애플리케이션 개발/구축 완료 후 서비스 오픈 전에는 **3가지 보안 진단**을 통과해야 함: ① 애플리케이션 보안 진단(코드), ② 인프라 보안 진단(클라우드 환경), ③ 모의해킹.

## 9. 헷갈리기 쉬운 개념 재확인 (Q&A)

**Q1. `@Valid`와 `@Validated`, 실무에선 뭘 더 쓰나?**
→ `@Valid`가 Java(Bean Validation) 표준이고 `@Validated`가 Spring 확장 버전인데, 신기하게도 **실무에서는 표준인 `@Valid`를 더 많이 씀**.

**Q2. Entity 클래스를 그냥 DTO로 써도 되지 않나?**
→ 안 됨. Entity는 DB 테이블과 1:1 매핑되는 클래스라 **민감 필드가 그대로 노출될 위험**, UI 요구사항 변경 시 DB 설계에 영향, 양방향 연관관계 직렬화 시 **무한루프(StackOverflow)** 위험이 있음. 계층 간 전달은 반드시 별도 DTO로.

**Q3. JPA를 쓰는데 왜 SQL 로그를 계속 찍어봐야 하나?**
→ JPA는 메서드 네이밍/JPQL을 **Hibernate가 실제 SQL로 변환**하는 구조라, 개발자가 예상한 SQL과 실제 변환된 SQL이 다를 수 있음. 특히 성능(인덱스 활용 여부, 풀스캔 여부)까지 확인하려면 **실제 실행되는 SQL을 로그로 반드시 확인**해야 함.

**Q4. 같은 클래스 안에서 `@Transactional` 메서드를 호출했는데 왜 트랜잭션이 안 걸리지?**
→ **자기 호출(Self-Invocation) 문제** — 내부 메서드 호출은 프록시(AOP)를 거치지 않고 `this`로 직접 호출되기 때문에 트랜잭션 전파(Propagation) 설정이 무시됨. 트랜잭션을 분리하려면 **별도 클래스**로 빼야 함.

**Q5. JPA와 MyBatis 중 뭘 써야 하나?**
→ 대체 관계가 아니라 **역할 분담**. 도메인 중심의 단순 CRUD는 JPA, 복잡한 조인·통계·리포트는 MyBatis — 한 프로젝트 안에서 **혼용하는 게 실무의 표준**.

**Q6. 낙관적 락과 비관적 락, 언제 뭘 쓰나?**
→ 조회(SELECT)가 많고 충돌이 드물게 예상되면 **낙관적 락**(락을 안 걸고, 충돌 시 개발자가 직접 처리). 수정(CUD)이 많고 데이터 정합성을 확실히 보장해야 하면 **비관적 락**(DB에 실제 락을 걸어 순차 처리).
