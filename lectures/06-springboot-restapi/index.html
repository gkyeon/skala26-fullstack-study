1. Java 실행 구조와 개발 환경

JVM·JRE·JDK 관계 · 소스코드에서 실행까지 · IDE 세팅 · Gradle·Maven 빌드 도구

💡
쉽게 말하면: 자바 코드는 컴퓨터가 바로 이해할 수 없어요. .java → 바이트코드(.class) → JVM이 실행이라는 3단계를 거치죠. 이번 장에서는 이 흐름을 만드는 JDK/JRE/JVM이 각각 뭘 하는 도구인지, 그리고 실무에서는 어떤 환경(IDE, 빌드 도구)으로 개발하는지를 정리해요.

1) JVM · JRE · JDK — 셋의 관계

자바 생태계를 처음 접하면 이 세 약어부터 헷갈리기 쉬워요. 포함 관계로 이해하면 간단해요: JDK ⊃ JRE ⊃ JVM.

  • JVM(Java Virtual Machine) — 바이트코드(.class 파일)를 실제로 한 줄씩 해석·실행하는 가상 컴퓨터. 운영체제마다 JVM 구현체가 다르기 때문에, 같은 바이트코드가 Windows든 macOS든 리눅스든 동일하게 동작한다("Write Once, Run Anywhere").
  • JRE(Java Runtime Environment) — JVM + 자바 표준 라이브러리(java.lang, java.util 등) + 실행에 필요한 파일들의 묶음. "이미 만들어진 자바 프로그램을 실행만 하고 싶다"면 JRE로 충분하다.
  • JDK(Java Development Kit) — JRE + 컴파일러(javac), 디버거, 문서화 도구(javadoc) 등 개발에 필요한 도구 일체. 자바로 코드를 "작성하고 빌드"하려면 JDK가 필요하다.
🔑 요즘은 JRE를 따로 설치하는 경우가 드물어요. 개발자는 물론 실행만 하는 환경에서도 보통 JDK를 설치해서 쓰는 게 일반적이에요(버전 관리 도구인 sdkman, jenv 등으로 여러 JDK 버전을 바꿔가며 씁니다).

2) 소스코드가 실행되기까지

자바는 "컴파일 언어이면서 동시에 인터프리터 언어"라는 독특한 위치에 있어요. 흐름을 순서대로 따라가 볼게요.

.java → .class → 실행 흐름
1. Hello.java 작성 (사람이 읽을 수 있는 소스코드)
2. javac Hello.java 실행 → Hello.class 생성 (바이트코드로 컴파일)
3. java Hello 실행 → JVM이 Hello.class를 읽어들여 한 줄씩 해석·실행
   (내부적으로는 JIT 컴파일러가 자주 실행되는 부분을 기계어로 즉석 변환해 최적화한다)

즉, 자바는 한 번 javac로 플랫폼에 독립적인 바이트코드로 컴파일해두면, 이후에는 어떤 OS에서든 그 OS에 맞는 JVM만 있으면 똑같이 실행할 수 있어요. C언어처럼 OS별로 다시 컴파일할 필요가 없다는 게 핵심 장점이에요.

3) 개발 환경 세팅 — IDE

실무에서는 메모장이 아니라 IDE(통합 개발 환경)를 써요. 자동완성, 오류 표시, 디버깅, 리팩토링 도구가 한데 묶여 있어 생산성이 크게 올라가기 때문이에요.

IDE특징
IntelliJ IDEA자바·스프링 개발에서 가장 널리 쓰이는 IDE. 강력한 리팩토링·디버깅 기능, Spring Boot 프로젝트 생성 마법사 내장.
VS Code가벼운 에디터에 자바 확장팩(Extension Pack for Java)을 설치해서 사용. 다양한 언어를 함께 다루는 풀스택 개발에 유리하다.
Eclipse오래된 오픈소스 자바 IDE. 여전히 많은 레거시 프로젝트와 교육 현장에서 쓰인다.

4) 프로젝트 빌드 도구 — Gradle과 Maven

실무 프로젝트는 파일 하나로 끝나지 않아요. 여러 클래스, 외부 라이브러리(의존성), 컴파일·테스트·패키징 과정을 관리해야 하는데, 이걸 자동화해주는 게 빌드 도구예요.

  • Maven — XML 기반(pom.xml)으로 의존성과 빌드 과정을 정의. 역사가 길고 규칙이 엄격해 예측 가능하다.
  • Gradle — Groovy 또는 Kotlin DSL 기반(build.gradle)으로 더 유연하고 간결하게 작성 가능. 빌드 속도 최적화(캐싱, 증분 빌드)에 강점이 있어 최근 Spring Boot 프로젝트에서 기본값으로 많이 쓰인다.
build.gradle 예시 — 의존성 선언
plugins {
    id 'org.springframework.boot' version '3.3.0'
    id 'java'
}

dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}
✔ 1장 핵심 요약
  • JDK(개발) ⊃ JRE(실행) ⊃ JVM(바이트코드 실행기) 포함 관계로 기억하자.
  • 자바는 .java → .class(바이트코드) → JVM 실행이라는 흐름 덕분에 "한 번 작성하면 어디서든 실행"된다.
  • 빌드 도구(Gradle/Maven)는 의존성 관리와 빌드 자동화를 담당하며, Spring Boot는 둘 다 지원한다.

2. 객체지향 프로그래밍과 SOLID

클래스·객체·필드·메서드·생성자 · 캡슐화·상속·다형성·추상화 · SOLID 5원칙

💡
쉽게 말하면: 객체지향은 "세상을 객체(물건)들의 상호작용으로 표현하자"는 프로그래밍 패러다임이에요. 클래스는 객체의 설계도이고, 캡슐화·상속·다형성·추상화는 그 설계도를 잘 쓰기 위한 4가지 원칙이죠. SOLID는 여기서 한 걸음 더 나아가 "변경에 강하고 유지보수하기 좋은" 클래스 설계를 위한 5가지 실전 가이드예요.

1) 클래스와 객체 — 필드·메서드·생성자

클래스(Class)는 객체를 만들기 위한 설계도이고, 객체(Object)는 그 설계도로 실제 메모리에 찍어낸 실체(인스턴스)예요. 클래스 안에는 상태를 담는 필드(field), 동작을 정의하는 메서드(method), 객체 생성 시 초기화를 담당하는 생성자(constructor)가 들어간다.

Book.java — 클래스 기본 구조
public class Book {
    // 필드 (상태)
    private String title;
    private String author;
    private int price;

    // 생성자
    public Book(String title, String author, int price) {
        this.title = title;
        this.author = author;
        this.price = price;
    }

    // 메서드 (동작)
    public String getTitle() {
        return title;
    }

    public void applyDiscount(int percent) {
        this.price = this.price - (this.price * percent / 100);
    }
}

2) 객체지향의 4대 특성

  • 캡슐화(Encapsulation) — 필드를 private으로 감추고 getter/setter 같은 메서드로만 접근을 허용해, 내부 구현이 바뀌어도 외부 코드에 영향이 적도록 하는 것.
  • 상속(Inheritance) — 기존 클래스(부모)의 필드·메서드를 새로운 클래스(자식)가 물려받아 재사용하는 것. extends 키워드로 표현한다.
  • 다형성(Polymorphism) — 같은 이름의 메서드가 객체 타입에 따라 다르게 동작하는 것. 오버라이딩(재정의)과 오버로딩(같은 이름, 다른 파라미터)이 대표적이다.
  • 추상화(Abstraction) — 공통적인 특징만 뽑아 인터페이스나 추상 클래스로 표현하고, 세부 구현은 감추는 것.
상속과 다형성 예시
abstract class Shape {
    abstract double area(); // 추상 메서드 — 구현은 자식에게 위임
}

class Circle extends Shape {
    private double radius;
    Circle(double radius) { this.radius = radius; }

    @Override
    double area() { return Math.PI * radius * radius; }
}

class Rectangle extends Shape {
    private double w, h;
    Rectangle(double w, double h) { this.w = w; this.h = h; }

    @Override
    double area() { return w * h; }
}

// 다형성: Shape 타입 변수로 실제 객체 종류에 상관없이 처리
List<Shape> shapes = List.of(new Circle(3), new Rectangle(4, 5));
for (Shape s : shapes) {
    System.out.println(s.area()); // 실제 객체 타입에 맞는 area()가 호출된다
}

3) SOLID 원칙 — 왜 필요한가

SOLID는 객체지향 설계에서 지켜야 할 5가지 원칙의 앞글자를 딴 것으로, Robert C. Martin이 정리한 개념이에요. 코드가 커질수록 "하나 고쳤더니 다른 데가 깨지는" 문제가 자주 생기는데, SOLID를 지키면 변경에 유연하고 테스트하기 쉬운 구조를 만들 수 있어요.

원칙이름한 줄 설명
S단일 책임 원칙 (SRP)클래스는 하나의 책임(변경 이유)만 가져야 한다.
O개방-폐쇄 원칙 (OCP)확장에는 열려 있고, 변경에는 닫혀 있어야 한다.
L리스코프 치환 원칙 (LSP)자식 클래스는 부모 클래스를 대체할 수 있어야 한다.
I인터페이스 분리 원칙 (ISP)클라이언트가 쓰지 않는 메서드에 의존하지 않아야 한다.
D의존관계 역전 원칙 (DIP)구체적인 구현이 아니라 추상화(인터페이스)에 의존해야 한다.

4) SRP·OCP 코드로 보기

SRP 위반 → 개선
// 나쁜 예: 도서 저장과 이메일 발송이라는 2가지 책임을 한 클래스가 담당
class BookService {
    void save(Book book) { /* DB 저장 로직 */ }
    void sendNotificationEmail(Book book) { /* 이메일 발송 로직 */ }
}

// 개선: 책임을 클래스 단위로 분리
class BookRepository {
    void save(Book book) { /* DB 저장 로직 */ }
}
class NotificationService {
    void sendNotificationEmail(Book book) { /* 이메일 발송 로직 */ }
}
OCP 적용 — 할인 정책 확장
interface DiscountPolicy {
    int discount(int price);
}

class FixedDiscountPolicy implements DiscountPolicy {
    public int discount(int price) { return price - 1000; }
}

class RateDiscountPolicy implements DiscountPolicy {
    public int discount(int price) { return price - (price * 10 / 100); }
}
// 새로운 할인 정책이 필요하면 클래스만 추가하면 된다 — 기존 코드는 손대지 않는다(확장에 열려있음)

5) LSP·ISP·DIP 코드로 보기

DIP — 인터페이스에 의존하기
// 나쁜 예: 구체 클래스(MySqlBookRepository)에 직접 의존
class BookService {
    private MySqlBookRepository repository = new MySqlBookRepository();
}

// 개선: 추상화(인터페이스)에 의존하고, 실제 구현은 외부에서 주입받는다
interface BookRepository {
    void save(Book book);
}

class BookService {
    private final BookRepository repository; // 구체 타입이 아닌 인터페이스 타입

    BookService(BookRepository repository) { // 생성자로 구현체를 주입받음
        this.repository = repository;
    }
}

LSP는 "자식 클래스 객체를 부모 타입 변수에 넣어 써도 프로그램이 정상 동작해야 한다"는 뜻이에요. 예를 들어 Rectangle을 상속한 Square가 부모의 setWidth/setHeight 동작 규약을 깨버리면 LSP 위반이 된다. ISP는 하나의 거대한 인터페이스보다, 클라이언트별로 필요한 메서드만 모은 작은 인터페이스 여러 개로 쪼개는 게 낫다는 원칙이에요(예: Readable, Writable을 분리).

🔑 DIP는 이후 배울 Spring의 DI(의존성 주입)와 IoC 컨테이너의 이론적 배경이 되는 원칙이에요. Day2에서 다시 만나게 됩니다.
✔ 2장 핵심 요약
  • 클래스=설계도, 객체=인스턴스, 필드=상태, 메서드=행동, 생성자=초기화.
  • 캡슐화·상속·다형성·추상화는 객체지향의 4대 특성.
  • SOLID는 "변경에 강한 설계"를 위한 5원칙 — 특히 DIP는 Spring DI의 뿌리가 된다.

3. Java 기초 문법 — 제어문·배열·메서드

if·switch·for·while 제어문 · 배열 선언과 활용 · 메서드 오버로딩과 가변인자

💡
쉽게 말하면: 아무리 객체지향이 화려해도, 결국 코드 한 줄 한 줄은 조건 분기(if)와 반복(for/while)으로 이루어져요. 이번 장은 자바 문법의 가장 기초 체력에 해당하는 제어문·배열·메서드를 다시 짚어봅니다.

1) 조건문 — if / switch

if-else와 switch 예시
int price = 32000;

if (price >= 30000) {
    System.out.println("무료 배송 대상");
} else if (price >= 10000) {
    System.out.println("배송비 2500원");
} else {
    System.out.println("배송비 5000원");
}

// Java 14+ switch expression (더 간결한 문법)
String grade = switch (price / 10000) {
    case 0, 1 -> "저가";
    case 2, 3 -> "중가";
    default -> "고가";
};

2) 반복문 — for / while

for, 향상된 for, while
int[] prices = {32000, 28000, 22000};

// 기본 for문 — 인덱스가 필요할 때
for (int i = 0; i < prices.length; i++) {
    System.out.println(i + "번째 가격: " + prices[i]);
}

// 향상된 for문(for-each) — 인덱스가 필요 없을 때 더 간결
for (int price : prices) {
    System.out.println(price);
}

// while문 — 조건 기반 반복
int sum = 0, idx = 0;
while (idx < prices.length) {
    sum += prices[idx];
    idx++;
}
🔑 for는 "몇 번 반복할지 알 때", while은 "조건이 언제 끝날지 모를 때(예: 사용자 입력을 계속 받는 경우)" 쓰는 게 일반적인 관례예요.

3) 배열

배열은 같은 타입의 값을 고정된 크기로 연속된 메모리에 저장하는 자료구조예요. 크기를 한 번 정하면 바꿀 수 없다는 게 다음 장에서 배울 List와 가장 큰 차이점이에요.

배열 선언과 2차원 배열
// 1차원 배열
String[] titles = new String[3];
titles[0] = "이펙티브 자바";
titles[1] = "클린 코드";

String[] titles2 = {"이펙티브 자바", "클린 코드", "객체지향의 사실과 오해"}; // 선언과 동시에 초기화

// 2차원 배열 (표 형태 데이터)
int[][] grid = new int[2][3]; // 2행 3열
grid[0][0] = 1;

4) 메서드 — 오버로딩과 가변인자

메서드 오버로딩(Overloading)은 이름은 같지만 매개변수의 개수나 타입이 다른 메서드를 여러 개 정의하는 것이에요. 가변인자(Varargs)는 매개변수 개수를 미리 정하지 않고 여러 개를 넘길 수 있게 하는 문법이다.

오버로딩과 가변인자 예시
class Calculator {
    // 오버로딩: 매개변수 타입/개수가 다른 여러 add 메서드
    int add(int a, int b) {
        return a + b;
    }
    double add(double a, double b) {
        return a + b;
    }
    int add(int a, int b, int c) {
        return a + b + c;
    }

    // 가변인자: 개수 제한 없이 넘길 수 있음 (내부적으로는 배열)
    int addAll(int... numbers) {
        int sum = 0;
        for (int n : numbers) {
            sum += n;
        }
        return sum;
    }
}

// 호출: addAll(1, 2), addAll(1, 2, 3, 4, 5) 모두 가능
✔ 3장 핵심 요약
  • if/switch는 조건 분기, for/while은 반복 — for는 횟수가 정해진 경우, while은 조건 기반 반복에 적합.
  • 배열은 크기 고정, 같은 타입만 저장 가능.
  • 오버로딩은 "같은 이름, 다른 시그니처", 가변인자는 인자 개수를 유연하게 받는 문법.

4. 컬렉션·제네릭·람다와 스트림

List·Set·Map 차이 · 제네릭 기초 · 람다식 문법 · Stream API(filter·map·collect)

💡
쉽게 말하면: 배열은 크기가 고정이라 불편했죠? 컬렉션(List/Set/Map)은 크기가 자유롭게 늘어나는 "똑똑한 배열"이에요. 여기에 제네릭으로 타입 안전성을 더하고, 람다·스트림으로 "무엇을 할지"만 선언하는 함수형 스타일까지 익히면 실무 자바 코드의 8할은 이 장의 내용이라고 봐도 돼요.

1) List / Set / Map — 언제 뭘 쓸까

컬렉션특징대표 구현체
List순서 있음, 중복 허용 — 인덱스로 접근 가능ArrayList, LinkedList
Set순서 없음(구현체에 따라 다름), 중복 불허 — "유일한 값들의 모음"HashSet, LinkedHashSet, TreeSet
MapKey-Value 쌍으로 저장, Key는 중복 불허HashMap, LinkedHashMap, TreeMap
List / Set / Map 기본 사용
List<String> titles = new ArrayList<>();
titles.add("이펙티브 자바");
titles.add("이펙티브 자바"); // 중복 저장 가능 → 크기 2

Set<String> authors = new HashSet<>();
authors.add("조슈아 블로크");
authors.add("조슈아 블로크"); // 중복 무시 → 크기 1

Map<String, Integer> priceByTitle = new HashMap<>();
priceByTitle.put("이펙티브 자바", 32000);
priceByTitle.put("클린 코드", 28000);
int price = priceByTitle.get("클린 코드"); // 28000

2) 제네릭(Generics) 기초

제네릭은 클래스나 메서드가 다룰 데이터 타입을 사용하는 시점에 지정할 수 있게 하는 문법이에요. 컴파일 시점에 타입을 체크해주기 때문에, Object를 쓰고 매번 형변환하던 방식보다 훨씬 안전하다.

제네릭 클래스 예시
class Box<T> {
    private T content;
    void set(T content) { this.content = content; }
    T get() { return content; }
}

Box<String> stringBox = new Box<>();
stringBox.set("이펙티브 자바");
String value = stringBox.get(); // 형변환 없이 바로 String으로 꺼낼 수 있음

// List<Book>처럼 컬렉션에서도 항상 제네릭을 함께 씀
List<Book> books = new ArrayList<>();

3) 람다식(Lambda Expression) 문법

람다식은 "이름 없는 함수"를 간결하게 표현하는 문법이에요. 인터페이스에 추상 메서드가 딱 하나만 있는 함수형 인터페이스(예: Runnable, Comparator)를 구현할 때 익명 클래스 대신 쓸 수 있다.

람다식으로 정렬 기준 지정하기
List<Book> books = new ArrayList<>(List.of(
    new Book("이펙티브 자바", "조슈아 블로크", 32000),
    new Book("클린 코드", "로버트 마틴", 28000)
));

// 익명 클래스 방식 (예전 스타일)
books.sort(new Comparator<Book>() {
    @Override
    public int compare(Book a, Book b) {
        return a.getPrice() - b.getPrice();
    }
});

// 람다식 방식 (간결)
books.sort((a, b) -> a.getPrice() - b.getPrice());

// 메서드 참조로 더 간결하게
books.sort(Comparator.comparingInt(Book::getPrice));

4) Stream API — filter / map / collect

Stream은 컬렉션의 데이터를 선언형(무엇을 할지)으로 가공하는 API예요. "필터링 → 변환 → 수집"의 파이프라인을 체이닝으로 표현할 수 있어, for문을 여러 겹 중첩하는 것보다 읽기 쉬운 코드가 된다.

filter → map → collect 파이프라인
List<Book> books = List.of(
    new Book("이펙티브 자바", "조슈아 블로크", 32000),
    new Book("클린 코드", "로버트 마틴", 28000),
    new Book("객체지향의 사실과 오해", "조영호", 22000)
);

// 3만원 이상인 책의 제목만 뽑아서 리스트로 만들기
List<String> expensiveTitles = books.stream()
    .filter(book -> book.getPrice() >= 30000)  // 조건에 맞는 요소만 통과
    .map(Book::getTitle)                        // Book -> String 변환
    .collect(Collectors.toList());              // 다시 List로 수집

// 전체 가격 합계 구하기
int total = books.stream()
    .mapToInt(Book::getPrice)
    .sum();
🔑 Stream은 원본 컬렉션을 변경하지 않아요(불변성). filter/map처럼 다른 스트림을 반환하는 연산을 "중간 연산", collect/sum처럼 최종 결과를 만드는 연산을 "종단 연산"이라고 부른다.
🔎 심화 — List/Set/Map, 언제 어떤 걸 고를까?

순서가 중요하고 같은 값이 여러 번 있을 수 있으면 List, "중복 없는 집합"이 필요하면 Set, "이름으로 빠르게 찾기"가 필요하면 Map을 고르면 돼요. 실무에서는 대부분 ArrayList와 HashMap이 기본 선택지가 됩니다.

✔ 4장 핵심 요약
  • List(순서·중복 허용), Set(중복 불허), Map(Key-Value) — 용도에 맞게 선택.
  • 제네릭은 컴파일 시점에 타입 안전성을 보장해준다.
  • 람다식 + Stream(filter/map/collect)으로 컬렉션을 선언형으로 가공할 수 있다.

5. RESTful API 설계 원칙

REST 아키텍처 제약조건 · HTTP 메서드와 멱등성 · 상태 코드 · 좋은 리소스 URI 설계

💡
쉽게 말하면: REST는 "자원(Resource)을 URI로 표현하고, HTTP 메서드로 행위를 표현하자"는 웹 API 설계 스타일이에요. URI에는 동사(get, delete 같은)를 넣지 않고, 대신 GET/POST/PUT/DELETE 같은 HTTP 메서드로 "무엇을 할지"를 표현하는 게 핵심 규칙이에요. 실습장에서 만져본 /api/books API가 바로 이 원칙을 따른 예시입니다.

1) REST란 — 아키텍처 제약조건

REST(REpresentational State Transfer)는 2000년 로이 필딩(Roy Fielding)의 박사 논문에서 제시된 아키텍처 스타일이에요. 몇 가지 제약조건을 지키는 API를 흔히 "RESTful하다"고 표현한다.

  • 자원 중심(Resource-based) — 모든 것을 "자원"으로 보고, 각 자원은 고유한 URI로 식별된다(예: /api/books/1).
  • 무상태성(Stateless) — 서버는 클라이언트의 이전 요청 상태를 기억하지 않는다. 매 요청에 필요한 정보가 모두 담겨 있어야 한다.
  • 클라이언트-서버 분리 — 클라이언트(화면)와 서버(데이터·로직)의 관심사를 분리해 독립적으로 발전할 수 있게 한다.
  • Uniform Interface(일관된 인터페이스) — HTTP 메서드, 상태 코드 등 표준화된 방식으로 자원을 다룬다.
  • Cacheable(캐시 가능) — 응답이 캐시 가능한지 여부를 명시해 성능을 높일 수 있어야 한다.

2) HTTP 메서드와 멱등성

멱등성(Idempotency)이란 같은 요청을 여러 번 보내도 결과(서버 상태)가 한 번 보낸 것과 동일한 성질을 말해요. 멱등하다고 해서 응답까지 항상 똑같은 건 아니라는 점에 주의하세요(예: DELETE는 두 번째부터 404가 될 수 있지만, "삭제된 상태"라는 결과는 동일).

메서드의미멱등성요청 바디
GET자원 조회O없음
POST자원 생성X (보낼 때마다 새로 생성됨)있음
PUT자원 전체 교체O있음
PATCH자원 부분 수정일반적으로 X있음
DELETE자원 삭제O보통 없음
🔑 PUT과 PATCH의 차이: PUT은 리소스 전체를 통째로 교체(빠진 필드는 null/기본값 처리될 수 있음), PATCH는 전달한 필드만 부분적으로 수정한다는 관례가 있어요. REST API 연습장의 PUT 예제가 일부 필드만 보내는 이유도 실무에서는 이 구분이 엄격하지 않게 쓰이는 경우가 많기 때문이에요.

3) 주요 HTTP 상태 코드

코드의미주로 쓰이는 상황
200 OK요청 성공GET, PUT 성공 시 일반적인 응답
201 Created자원 생성 성공POST로 새 자원을 만들었을 때
204 No Content성공했지만 응답 바디 없음DELETE 성공 시 흔히 사용

4) 좋은 리소스 URI 설계

URI는 명사(자원)를 표현하고, 행위는 HTTP 메서드가 담당해야 해요. 아래 예시로 비교해볼게요.

나쁜 URI vs 좋은 URI
[나쁜 예 — URI에 동사가 들어감]
GET  /getBookList
POST /createBook
POST /deleteBook?id=1

[좋은 예 — 자원(명사) 중심, 메서드로 행위 표현]
GET    /api/books          → 도서 목록 조회
POST   /api/books          → 도서 생성
GET    /api/books/{id}     → 특정 도서 조회
PUT    /api/books/{id}     → 특정 도서 전체 수정
PATCH  /api/books/{id}     → 특정 도서 부분 수정
DELETE /api/books/{id}     → 특정 도서 삭제

[계층 관계 표현 — 특정 도서의 리뷰 목록]
GET  /api/books/{bookId}/reviews
✔ 좋은 URI 설계 체크리스트
  • URI는 복수형 명사를 사용한다(/books, /users).
  • URI에 동사를 쓰지 않는다 — 행위는 HTTP 메서드로 표현한다.
  • 계층 관계는 /부모/{id}/자식 형태로 표현한다.
  • 대소문자는 소문자로 통일하고, 구분자는 하이픈(-)을 사용한다.

6. Spring과 Spring Boot 개요

Spring Framework 핵심 모듈(IoC/AOP) · Spring Boot 자동설정·내장 톰캣·starter · 설정 지옥 해소

💡
쉽게 말하면: Spring은 자바 엔터프라이즈 개발을 위한 커다란 프레임워크이고, Spring Boot는 그 Spring을 "설정 없이 빠르게 시작할 수 있게" 감싸놓은 도구예요. Spring만 쓰면 XML 설정을 산더미처럼 써야 했지만, Spring Boot는 "관례(convention)"로 대부분을 자동 설정해줘서 개발자가 비즈니스 로직에만 집중할 수 있게 해줍니다.

1) Spring Framework — 핵심 모듈

Spring Framework는 2003년경 등장한 자바 엔터프라이즈 애플리케이션 프레임워크예요. 여러 모듈로 구성되어 있는데, 그중 핵심은 다음 두 가지예요.

  • IoC(Inversion of Control) / DI(Dependency Injection) — 객체 생성과 의존관계 관리를 개발자 대신 컨테이너가 담당한다. 다음 장에서 자세히 다룬다.
  • AOP(Aspect Oriented Programming) — 로깅, 트랜잭션, 보안 검사처럼 여러 곳에 반복적으로 필요한 "횡단 관심사(cross-cutting concern)"를 핵심 로직과 분리해서 다룰 수 있게 해준다.
  • 이 외에도 데이터 접근(Spring Data), 웹(Spring MVC), 보안(Spring Security) 등 다양한 하위 프로젝트들이 Spring 생태계를 이루고 있다.

2) Spring Boot가 해결한 문제 — "설정 지옥"

전통적인 Spring 프로젝트는 시작 전에 해야 할 일이 많았어요. 톰캣 같은 웹 서버를 별도로 설치·설정하고, DispatcherServlet·데이터소스·트랜잭션 매니저 등을 XML이나 Java Config로 일일이 등록해야 했죠. 이렇게 "본 개발을 시작하기도 전에" 방대한 설정 작업이 필요했던 상황을 흔히 설정 지옥(configuration hell)이라고 불렀다.

Spring Boot(2014년 첫 출시)는 이 문제를 "관례 기반 자동 설정"으로 해결했어요. 프로젝트에 어떤 라이브러리가 있는지를 감지해서, 적절한 기본 설정을 자동으로 채워주는 방식이에요.

3) Spring Boot 핵심 기능

  • 자동 설정(Auto Configuration) — classpath에 어떤 라이브러리가 있는지 보고 필요한 Bean들을 자동으로 등록해준다(@SpringBootApplication이 이를 활성화하는 핵심 애노테이션).
  • 내장 톰캣(Embedded Tomcat) — 별도로 웹 서버를 설치하지 않아도, 애플리케이션 자체에 톰캣 서버가 내장되어 있어 main() 메서드 실행만으로 웹 서버가 뜬다.
  • Starter 의존성 — spring-boot-starter-web처럼 관련된 라이브러리들을 한 묶음으로 제공하는 의존성 패키지. 버전 호환성 걱정 없이 필요한 기능을 한 줄로 추가할 수 있다.
Spring Boot 애플리케이션 최소 구성
@SpringBootApplication // 자동설정 + 컴포넌트 스캔 + 설정 클래스 선언을 한 번에
public class BookApplication {
    public static void main(String[] args) {
        SpringApplication.run(BookApplication.class, args);
        // 이 한 줄로 내장 톰캣이 뜨고, 애플리케이션 컨텍스트가 초기화된다
    }
}

7. Spring Boot 핵심 — IoC·DI·Bean

IoC 컨테이너 개념 · 생성자·필드·세터 주입 비교 · Bean 등록 방법 · Bean 라이프사이클

💡
쉽게 말하면: 원래는 객체가 필요한 다른 객체를 직접 new로 만들어서 썼어요. IoC(제어의 역전)는 이 "객체를 만들고 연결하는 책임"을 개발자가 아니라 Spring 컨테이너에게 넘기는 것이고, DI(의존성 주입)는 그 컨테이너가 필요한 객체를 "대신 조립해서 넣어주는" 구체적인 방법이에요. 2장에서 배운 DIP 원칙이 여기서 실제로 구현되는 거죠.

1) IoC(제어의 역전) 컨테이너

전통적인 방식에서는 BookService가 필요한 BookRepository를 자기 손으로 new해서 만들었어요. IoC는 이 순서를 뒤집어요 — 객체(Bean)를 생성하고, 그 사이의 의존관계를 연결하는 일을 Spring 컨테이너(ApplicationContext)가 대신 해준다.

🔑 "제어의 역전"이라는 이름이 붙은 이유: 원래는 내 코드가 흐름을 제어했는데(내가 직접 객체를 생성), 이제는 프레임워크(컨테이너)가 흐름을 제어하고 내 코드는 그 안에서 호출당하는 입장이 되기 때문이에요.

2) DI(의존성 주입) 3가지 방식

Bean이 필요로 하는 다른 Bean(의존 객체)을 컨테이너가 "주입"해주는 방법에는 3가지가 있어요.

생성자 주입 vs 필드 주입 vs 세터 주입
// ① 생성자 주입 (권장 방식)
@Service
public class BookService {
    private final BookRepository bookRepository; // final로 선언 가능 → 불변성 보장

    public BookService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }
}

// ② 필드 주입 (간편하지만 비권장)
@Service
public class BookService {
    @Autowired
    private BookRepository bookRepository; // final 불가, 테스트 시 주입이 번거로움
}

// ③ 세터 주입 (선택적 의존관계에 사용)
@Service
public class BookService {
    private BookRepository bookRepository;

    @Autowired
    public void setBookRepository(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }
}
방식장점단점
생성자 주입불변(final) 보장, 누락 시 컴파일 오류로 조기 발견, 순환 참조를 컴파일/구동 시점에 감지하기 쉬움생성자 인자가 많아지면 코드가 길어짐(→ 오히려 설계 신호로 활용)
필드 주입코드가 짧음외부에서 변경 불가한 순수 자바 객체로 테스트하기 어려움, final 불가
세터 주입주입 대상을 나중에 바꿀 수 있음필수 의존관계인데 주입을 빠뜨려도 컴파일 오류가 안 남
🔑 Spring 공식 문서와 커뮤니티 모두 생성자 주입을 기본으로 권장해요. 필드 하나뿐이면 @Autowired도 생략 가능하다(생성자가 하나면 자동으로 주입 대상이 된다).

3) Bean 등록 방법

Spring이 관리하는 객체를 Bean이라고 불러요. Bean을 등록하는 방법은 크게 두 가지예요.

컴포넌트 스캔 방식 vs 자바 코드로 직접 등록
// 방법 1: 스테레오타입 애노테이션 (컴포넌트 스캔 대상)
@Component      // 범용 Bean
@Service        // 비즈니스 로직 계층
@Repository     // 데이터 접근 계층 (예외 변환 기능도 함께 제공)
@Controller     // 웹 요청 처리 계층

@Service
public class BookService { ... }

// 방법 2: 자바 설정 클래스에서 직접 등록 (외부 라이브러리 등에 사용)
@Configuration
public class AppConfig {
    @Bean
    public BookRepository bookRepository() {
        return new InMemoryBookRepository();
    }
}

@Component 계열 애노테이션은 클래스 위에 붙여두면 컴포넌트 스캔이 자동으로 찾아서 Bean으로 등록해줘요. 반면 @Configuration + @Bean은 내가 소스코드를 수정할 수 없는 외부 라이브러리 클래스를 Bean으로 등록하거나, 생성 과정을 세밀하게 제어하고 싶을 때 사용한다.

4) Bean 라이프사이클 개요

컨테이너 생성 → Bean 생성 → 의존관계 주입 → 초기화 콜백 → 사용 → 소멸 전 콜백 → 컨테이너 종료

Spring Bean은 기본적으로 싱글톤(singleton) 스코프로 관리돼요 — 컨테이너 안에 딱 하나의 인스턴스만 생성되고, 여러 곳에서 공유해서 사용한다. 초기화·소멸 시점에 특정 로직을 실행하고 싶다면 @PostConstruct, @PreDestroy 애노테이션을 사용할 수 있다.

✔ 7장 핵심 요약
  • IoC: 객체 생성·연결의 주도권을 개발자에서 컨테이너로 넘기는 것.
  • DI 3가지 방식 중 생성자 주입이 기본 권장(불변성, 조기 오류 발견).
  • Bean 등록은 컴포넌트 스캔(@Component 계열) 또는 @Configuration+@Bean으로.
  • Bean은 기본적으로 싱글톤 스코프로 관리된다.

8. Configuration과 Profile 관리

application.yml/properties · @Value 값 주입 · @ConfigurationProperties · Profile(dev/prod)별 설정 분리

💡
쉽게 말하면: DB 주소, 포트 번호 같은 값들을 코드에 하드코딩하면 개발 환경과 운영 환경마다 코드를 고쳐야 해서 위험해요. Spring Boot는 application.yml 같은 설정 파일에 값을 분리해두고, Profile로 "개발용/운영용" 설정을 나눠서 관리할 수 있게 해줘요.

1) application.yml / application.properties

Spring Boot 프로젝트는 src/main/resources 아래에 있는 application.yml(또는 application.properties) 파일을 실행 시점에 자동으로 읽어들여요. 같은 내용을 두 형식으로 비교해볼게요.

application.properties vs application.yml
## application.properties (key=value 방식)
server.port=8080
spring.application.name=book-api
book.default-page-size=20
book.support-email=support@example.com

# application.yml (계층 구조, 들여쓰기로 표현 — 실무에서 더 선호됨)
server:
  port: 8080
spring:
  application:
    name: book-api
book:
  default-page-size: 20
  support-email: support@example.com

같은 접두어(spring.*, server.*)가 반복되는 properties 방식보다, 계층 구조를 그대로 들여쓰기로 표현하는 yml 방식이 가독성이 좋아 최근에는 더 널리 쓰인다.

2) @Value로 값 주입하기

설정 파일의 값 하나를 필드에 바로 꽂아 넣고 싶을 때는 @Value 애노테이션을 사용해요. ${key} 형식으로 프로퍼티 키를 참조한다.

@Value 사용 예시
@Component
public class BookProperties {

    @Value("${book.default-page-size}")
    private int defaultPageSize;

    @Value("${book.support-email}")
    private String supportEmail;

    @Value("${book.discount-rate:0}") // 콜론 뒤 값 = 기본값 (설정이 없을 때 사용)
    private int discountRate;
}
⚠️ @Value는 값 하나하나를 개별적으로 가져오기 때문에, 관련 설정이 여러 개면 필드가 계속 늘어나요. 설정이 많아질수록 다음에 배울 @ConfigurationProperties가 더 낫다.

3) @ConfigurationProperties — 묶음으로 관리하기

관련된 설정값들을 하나의 클래스로 묶어서 타입 안전하게 관리하고 싶을 때 사용해요. 접두어(prefix)만 지정하면, 그 아래 있는 모든 값이 필드에 자동으로 매핑된다.

@ConfigurationProperties 예시
@Component
@ConfigurationProperties(prefix = "book")
public class BookProperties {
    private int defaultPageSize;
    private String supportEmail;
    private int discountRate;

    // getter/setter 필요 (또는 Lombok @Getter @Setter, 혹은 record + 생성자 바인딩)
    public int getDefaultPageSize() { return defaultPageSize; }
    public void setDefaultPageSize(int defaultPageSize) { this.defaultPageSize = defaultPageSize; }
    // ... 나머지 getter/setter 생략
}

// 사용하는 쪽 — Bean 하나로 관련 설정을 묶어서 주입받는다
@Service
public class BookService {
    private final BookProperties bookProperties;

    public BookService(BookProperties bookProperties) {
        this.bookProperties = bookProperties;
    }
}

4) Profile로 환경별 설정 분리

Profile은 "개발(dev)/운영(prod)/테스트(test)"처럼 환경에 따라 다른 설정을 적용할 수 있게 해주는 기능이에요. 파일을 application-{profile}.yml 형식으로 나눠서 관리한다.

환경별 설정 파일 분리
# application.yml (공통 설정 + 활성 프로필 지정)
spring:
  profiles:
    active: dev

---
# application-dev.yml (개발 환경)
spring:
  config:
    activate:
      on-profile: dev
  datasource:
    url: jdbc:h2:mem:devdb

---
# application-prod.yml (운영 환경)
spring:
  config:
    activate:
      on-profile: prod
  datasource:
    url: jdbc:mysql://prod-db:3306/bookdb

특정 Bean을 특정 Profile에서만 활성화하고 싶다면 @Profile 애노테이션을 클래스나 @Bean 메서드에 붙이면 돼요.

@Profile 애노테이션
@Configuration
public class MailConfig {

    @Bean
    @Profile("dev")
    public MailSender devMailSender() {
        return new ConsoleMailSender(); // 개발 환경 — 콘솔에 로그만 출력
    }

    @Bean
    @Profile("prod")
    public MailSender prodMailSender() {
        return new SmtpMailSender(); // 운영 환경 — 실제 SMTP 서버로 발송
    }
}
✔ 8장 핵심 요약
  • application.yml/properties에 설정값을 분리해두고 코드에서 참조한다.
  • 값 하나는 @Value, 관련된 값 묶음은 @ConfigurationProperties.
  • Profile(dev/prod)로 환경별 설정 파일과 Bean을 분리해 관리할 수 있다.

9. Spring Boot MVC와 Actuator

DispatcherServlet 기반 요청 처리 흐름(Front Controller 패턴) · MVC 구성요소 · Spring Boot Actuator 모니터링

💡
쉽게 말하면: 브라우저가 GET /api/books/1을 보내면, 그 요청이 곧바로 내가 만든 컨트롤러로 가는 게 아니에요. DispatcherServlet이라는 "문지기"가 모든 요청을 먼저 받아서, 어느 컨트롤러의 어느 메서드로 보낼지 결정한 다음 전달해줘요. 이렇게 요청을 받는 창구를 하나로 통일하는 설계를 Front Controller 패턴이라고 하고, MVC는 그 뒤에서 "요청 처리(Controller) · 데이터(Model) · 화면(View)"의 역할을 나누는 설계예요.

1) MVC 패턴 — 역할을 나누는 이유

MVC는 애플리케이션을 세 가지 역할로 나누는 설계 패턴이에요. 역할을 분리하면 한 부분(예: 화면)을 바꿔도 다른 부분(예: 비즈니스 로직)에 영향을 주지 않는다.

구성요소역할REST API에서의 대응
Model데이터와 비즈니스 로직Entity, Service, Repository
View사용자에게 보여줄 화면REST API에서는 화면 대신 JSON 응답 자체가 View 역할을 대신한다(@RestController)
Controller요청을 받아 Model을 호출하고 View를 결정BookController 같은 @RestController 클래스
🔑 전통적인 MVC(화면을 반환하는 웹앱)에서는 Controller가 View 이름을 반환하고 서버가 HTML을 렌더링해요. 반면 REST API는 @RestController를 사용해서 View 렌더링 과정 없이 Model(데이터)을 JSON으로 바로 직렬화해서 응답한다.

2) DispatcherServlet과 요청 처리 흐름 (Front Controller 패턴)

Spring MVC의 핵심은 DispatcherServlet이에요. 모든 HTTP 요청이 각 컨트롤러로 직접 가지 않고, 반드시 이 하나의 서블릿을 거치도록 설계되어 있다 — 이런 구조를 Front Controller 패턴이라고 불러요. Spring Boot는 내장 톰캣을 띄울 때 이 DispatcherServlet을 자동으로 등록해준다.

Client 요청 → DispatcherServlet → Handler Mapping(어느 메서드?) → Controller 실행 → Service/Repository 호출 → (View Resolver 또는 메시지 컨버터) → Client 응답
모든 요청의 단일 진입점 = DispatcherServlet (Front Controller 패턴)
  • Handler Mapping — 요청 URL·HTTP 메서드를 보고 어떤 컨트롤러의 어떤 메서드가 처리할지 찾는다(@GetMapping("/api/books/{id}") 같은 매핑 정보를 참조).
  • Handler Adapter — 찾아낸 메서드를 실제로 호출한다.
  • 메시지 컨버터(HttpMessageConverter) — @RestController에서는 반환값을 JSON으로 변환해서 응답 바디에 담아준다(기본적으로 Jackson 라이브러리 사용).
✔ Front Controller 패턴을 쓰는 이유
  • 공통 처리(인코딩 설정, 로깅, 예외 처리 진입점 등)를 한 곳에 모을 수 있다.
  • 요청 처리 흐름이 일관되어, 새 API를 추가할 때 컨트롤러 매핑만 신경 쓰면 된다.
  • 개발자는 DispatcherServlet의 존재를 거의 의식하지 않고 @RestController만 작성하면 되도록 추상화되어 있다.

3) Spring Boot Actuator란

Actuator는 운영 중인 Spring Boot 애플리케이션의 상태를 들여다볼 수 있게 해주는 모니터링·관리 기능 모음이에요. spring-boot-starter-actuator 의존성만 추가하면, 애플리케이션의 헬스 상태·메트릭·환경 설정 같은 정보를 HTTP 엔드포인트로 바로 확인할 수 있게 돼요. "애플리케이션에 계기판(actuator)을 달아준다"고 생각하면 쉽다.

build.gradle 의존성 추가
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-actuator'
}

4) 주요 Actuator 엔드포인트

엔드포인트제공 정보
/actuator/health애플리케이션의 헬스 상태(UP/DOWN). DB, 디스크 등 연결된 컴포넌트 상태도 함께 확인 가능
/actuator/metricsJVM 메모리, CPU 사용량, HTTP 요청 처리 시간 등 각종 지표
/actuator/info애플리케이션 버전 등 개발자가 직접 등록한 커스텀 정보
/actuator/beans현재 컨테이너에 등록된 모든 Bean 목록
/actuator/env현재 적용된 환경 변수·설정 프로퍼티 목록
⚠️ Actuator 엔드포인트 중 /health 외 대부분은 기본적으로 비활성화되어 있고, 민감한 정보(/env, /beans 등)를 담고 있는 경우가 많아요. 운영 환경에서는 management.endpoints.web.exposure.include 설정으로 노출할 엔드포인트를 신중하게 선택하고, 접근 권한도 별도로 제어해야 한다.
🔎 심화 — Actuator가 실무에서 쓰이는 곳

쿠버네티스 같은 오케스트레이션 환경에서는 /actuator/health를 컨테이너의 liveness/readiness probe로 등록해서, "이 인스턴스가 요청을 받아도 되는 상태인지"를 주기적으로 체크하는 데 흔히 활용해요. /actuator/metrics는 Prometheus 같은 모니터링 도구와 연동해서 대시보드를 구성하는 데 쓰인다.

✔ 9장 핵심 요약
  • MVC는 Model(데이터·로직)·View(화면)·Controller(요청 처리)로 역할을 나누는 패턴이다.
  • DispatcherServlet이 모든 요청의 단일 진입점 역할을 하는 것이 Front Controller 패턴.
  • Actuator는 /actuator/health, /actuator/metrics 등으로 애플리케이션 상태를 모니터링하게 해준다.

10. 컴포넌트 스캔과 Spring 컨테이너

@ComponentScan 동작 원리 · ApplicationContext가 Bean을 찾고 등록하는 과정 · @Autowired의 주입 원리

💡
쉽게 말하면: 7장에서 @Service, @Repository를 붙이면 Bean이 등록된다고 배웠는데, 그게 어떻게 가능한 걸까요? Spring 컨테이너(ApplicationContext)가 애플리케이션 실행 시점에 지정된 패키지를 훑어보면서(scan) 스테레오타입 애노테이션이 붙은 클래스를 찾아 Bean으로 등록하는데, 이 과정을 컴포넌트 스캔이라고 해요. 이번 장에서는 그 내부 동작을 조금 더 들여다본다.

1) @ComponentScan은 어디서 시작되는가

Spring Boot 프로젝트의 시작점인 @SpringBootApplication 애노테이션 안에는 사실 @ComponentScan이 포함되어 있어요. 별도 설정이 없으면, 메인 클래스가 위치한 패키지와 그 하위 패키지를 기본 스캔 범위로 삼는다.

패키지 구조 예시
com.example.bookapi
 ├─ BookApplication.java        // @SpringBootApplication — 여기가 스캔 시작점
 ├─ controller/BookController.java   // @RestController
 ├─ service/BookService.java         // @Service
 └─ repository/BookRepository.java   // @Repository
🔑 그래서 실무에서는 메인 클래스를 프로젝트 최상위 패키지(예: com.example.bookapi)에 두는 게 관례예요. 메인 클래스를 하위 패키지로 옮기면, 그보다 상위 패키지에 있는 컴포넌트는 스캔 대상에서 빠져 Bean으로 등록되지 않는다.

2) ApplicationContext가 Bean을 찾고 등록하는 과정

ApplicationContext는 Spring의 IoC 컨테이너 구현체예요. 애플리케이션이 시작되면 대략 다음 순서로 동작한다.

① 스캔 범위 내 클래스 탐색 → ② @Component 계열 애노테이션이 붙은 클래스 식별 → ③ 각 클래스를 Bean 정의(BeanDefinition)로 등록 → ④ 의존관계를 분석해 Bean 생성 순서 결정 → ⑤ 생성자/필드에 필요한 Bean을 주입하며 인스턴스 생성 → ⑥ 컨테이너 내부(싱글톤 레지스트리)에 보관
  • BeanDefinition — Bean의 클래스 정보, 스코프, 의존관계 등을 담은 "설계도" 같은 메타데이터. 컨테이너는 실제 객체를 만들기 전에 이 정의부터 모두 등록한다.
  • Bean 사이에 의존관계가 있으면(BookService가 BookRepository를 필요로 함), 컨테이너는 의존 대상을 먼저 생성한 뒤 필요한 곳에 주입한다.
  • 기본 스코프가 싱글톤이므로, 한 번 생성된 Bean은 컨테이너 종료 전까지 재사용된다(7장 참고).

3) @Autowired가 의존성을 주입하는 원리

@Autowired가 붙으면 Spring 컨테이너는 해당 필드/생성자 파라미터의 타입을 기준으로 컨테이너 안에서 일치하는 Bean을 찾아 연결해줘요. 이 과정을 타입에 의한 자동 매칭(byType)이라고 부른다.

타입이 여러 개일 때 — @Qualifier로 구분
public interface BookRepository {
    Optional<Book> findById(Long id);
}

@Repository
public class JpaBookRepository implements BookRepository { ... }

@Repository
public class InMemoryBookRepository implements BookRepository { ... }

// BookRepository 타입 Bean이 2개 존재 → 타입만으로는 어떤 걸 주입할지 모호(ambiguous)
@Service
public class BookService {
    private final BookRepository bookRepository;

    public BookService(@Qualifier("jpaBookRepository") BookRepository bookRepository) {
        this.bookRepository = bookRepository; // 이름을 지정해서 명확히 구분
    }
}
🔑 같은 타입의 Bean이 하나뿐이면 이름을 신경 쓸 필요 없이 타입만으로 주입돼요. 여러 개일 때만 @Qualifier(이름 지정) 또는 @Primary(우선순위 지정)로 모호함을 해소해줘야 한다. 컴포넌트 스캔으로 등록된 Bean의 기본 이름은 클래스명의 첫 글자를 소문자로 바꾼 값(JpaBookRepository → jpaBookRepository)이에요.

4) 컴포넌트 스캔 대상에서 제외/포함하기

기본 스캔 범위를 벗어나는 패키지를 포함시키거나, 특정 클래스를 스캔에서 제외하고 싶을 때는 @ComponentScan을 직접 지정할 수 있어요.

스캔 범위 커스터마이징
@SpringBootApplication
@ComponentScan(basePackages = {"com.example.bookapi", "com.example.common"})
public class BookApplication {
    public static void main(String[] args) {
        SpringApplication.run(BookApplication.class, args);
    }
}
✔ 10장 핵심 요약
  • @SpringBootApplication에 포함된 @ComponentScan이 메인 클래스 기준 하위 패키지를 스캔한다.
  • ApplicationContext는 스캔 → BeanDefinition 등록 → 의존관계 분석 → Bean 생성·주입 순서로 동작한다.
  • @Autowired는 기본적으로 타입 기준(byType)으로 주입 대상을 찾고, 후보가 여러 개면 @Qualifier/@Primary로 구분한다.

11. Controller와 HTTP 요청 처리

@RestController·@RequestMapping 계열 · @PathVariable·@RequestParam·@RequestBody 차이 · ResponseEntity로 상태코드 제어

💡
쉽게 말하면: Controller는 클라이언트 요청을 가장 먼저 받는 계층이에요. URL 경로의 일부(/books/1의 1)는 @PathVariable, 쿼리 파라미터(?author=김)는 @RequestParam, JSON 요청 바디는 @RequestBody로 각각 받는 방법이 정해져 있어요. 그리고 응답의 상태 코드까지 세밀하게 제어하고 싶을 땐 ResponseEntity를 사용한다.

1) @RestController와 매핑 애노테이션

@RestController는 @Controller와 @ResponseBody를 합쳐놓은 애노테이션이에요. 이 애노테이션이 붙은 클래스의 메서드가 반환하는 객체는 View를 거치지 않고 그대로 JSON으로 변환되어 응답 바디에 담긴다.

BookController — 매핑 애노테이션 기본형
@RestController
@RequestMapping("/api/books")   // 이 컨트롤러의 공통 URL 접두어
public class BookController {

    private final BookService bookService;

    public BookController(BookService bookService) {
        this.bookService = bookService;
    }

    @GetMapping                 // GET /api/books
    public List<Book> findAll() {
        return bookService.findAll();
    }

    @GetMapping("/{id}")        // GET /api/books/{id}
    public Book findById(@PathVariable Long id) {
        return bookService.findById(id);
    }

    @PostMapping                // POST /api/books
    public Book create(@RequestBody Book book) {
        return bookService.create(book);
    }

    @PutMapping("/{id}")        // PUT /api/books/{id}
    public Book update(@PathVariable Long id, @RequestBody Book book) {
        return bookService.update(id, book);
    }

    @DeleteMapping("/{id}")     // DELETE /api/books/{id}
    public void delete(@PathVariable Long id) {
        bookService.delete(id);
    }
}

@GetMapping, @PostMapping, @PutMapping, @PatchMapping, @DeleteMapping은 각각 @RequestMapping(method = RequestMethod.GET) 등을 축약한 표현이에요. 클래스 레벨의 @RequestMapping("/api/books")과 메서드 레벨의 매핑이 합쳐져 최종 URL이 결정된다.

2) @PathVariable vs @RequestParam vs @RequestBody

애노테이션가져오는 위치예시
@PathVariableURL 경로 자체의 일부/api/books/{id} → @PathVariable Long id
@RequestParam쿼리 스트링(?key=value)/api/books?author=김민준 → @RequestParam String author
@RequestBodyHTTP 요청 바디(주로 JSON)POST/PUT 시 전달된 JSON → @RequestBody Book book
@RequestParam 활용 — 검색/페이징 예시
// GET /api/books/search?author=김민준&page=0&size=10
@GetMapping("/search")
public List<Book> search(
        @RequestParam String author,
        @RequestParam(defaultValue = "0") int page,
        @RequestParam(defaultValue = "10") int size) {
    return bookService.searchByAuthor(author, page, size);
}
🔑 @RequestParam은 기본적으로 필수 파라미터예요. 없어도 되는 값이면 required = false 또는 defaultValue를 지정해야 400 에러 없이 동작한다. 이 페이지 우측 하단의 REST API 연습장에서 쿼리 파라미터를 바꿔가며 요청을 보내보면 차이가 더 잘 와닿는다.

3) ResponseEntity로 상태 코드와 바디 함께 제어하기

지금까지 예시는 객체를 그대로 반환했는데, 이 경우 상태 코드는 항상 200(또는 예외 발생 시 500)으로 고정돼요. 생성 성공 시 201을, 삭제 성공 시 204를 명시적으로 응답하려면 ResponseEntity로 감싸서 반환해야 한다.

ResponseEntity 활용
@PostMapping
public ResponseEntity<Book> create(@RequestBody Book book) {
    Book saved = bookService.create(book);
    return ResponseEntity
            .status(HttpStatus.CREATED)   // 201 Created
            .body(saved);
}

@GetMapping("/{id}")
public ResponseEntity<Book> findById(@PathVariable Long id) {
    return bookService.findByIdOptional(id)
            .map(ResponseEntity::ok)                    // 200 OK + 바디
            .orElse(ResponseEntity.notFound().build());  // 404 Not Found, 바디 없음
}

@DeleteMapping("/{id}")
public ResponseEntity<Void> delete(@PathVariable Long id) {
    bookService.delete(id);
    return ResponseEntity.noContent().build(); // 204 No Content
}
✔ ResponseEntity를 쓰면 좋은 상황
  • 생성 성공 시 200이 아닌 201을 명시적으로 응답하고 싶을 때.
  • 자원이 없을 때 예외 대신 404 응답을 직접 구성하고 싶을 때(다음 장의 예외 처리와도 비교해볼 것).
  • 응답 헤더(예: Location)를 함께 담아 보내고 싶을 때 — ResponseEntity.created(uri).body(saved).
✔ 11장 핵심 요약
  • @RestController = @Controller + @ResponseBody, 매핑 애노테이션으로 URL·메서드를 지정한다.
  • 경로 값은 @PathVariable, 쿼리 파라미터는 @RequestParam, 요청 바디는 @RequestBody로 받는다.
  • 상태 코드까지 세밀하게 제어하려면 ResponseEntity로 감싸서 반환한다.

12. Lombok과 입력값 검증

Lombok 주요 애노테이션(@Getter·@Setter·@Builder 등) · Bean Validation(@NotNull·@NotBlank·@Size 등)과 @Valid

💡
쉽게 말하면: Lombok은 getter/setter/생성자처럼 자바에서 매번 반복해서 써야 하는 코드를 애노테이션 하나로 자동 생성해주는 라이브러리예요. Bean Validation은 "제목은 비어있으면 안 된다", "가격은 0 이상이어야 한다" 같은 입력값 규칙을 애노테이션으로 선언해두면, Spring이 요청을 처리하기 전에 자동으로 검증해주는 기능이에요. 둘 다 "반복 작업을 줄여준다"는 공통점이 있다.

1) Lombok 주요 애노테이션

Lombok은 컴파일 시점에 애노테이션을 분석해서 getter/setter, 생성자, toString() 같은 코드를 자동으로 만들어 넣어줘요. 클래스 파일에는 손으로 친 코드가 안 보이지만, 컴파일된 바이트코드에는 실제로 포함된다.

애노테이션생성해주는 것
@Getter / @Setter모든 필드의 getter / setter 메서드
@NoArgsConstructor파라미터 없는 기본 생성자
@AllArgsConstructor모든 필드를 파라미터로 받는 생성자
@Builder빌더 패턴으로 객체를 생성하는 메서드 체인
@ToString필드 값을 보기 좋게 출력하는 toString()
@EqualsAndHashCode필드 기반 equals()/hashCode()
@Data@Getter+@Setter+@ToString+@EqualsAndHashCode+생성자를 한 번에 (남용 주의)
Lombok 적용 전 vs 적용 후 — Book 클래스
// Lombok 없이 — getter/setter/생성자를 모두 직접 작성
public class Book {
    private Long id;
    private String title;
    private String author;
    private int price;

    public Book() {}
    public Book(Long id, String title, String author, int price) {
        this.id = id; this.title = title; this.author = author; this.price = price;
    }
    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    // ... author, price도 반복 ...
}

// Lombok 적용 후 — 애노테이션 몇 줄로 대체
@Getter @Setter
@NoArgsConstructor
@AllArgsConstructor
@Builder
public class Book {
    private Long id;
    private String title;
    private String author;
    private int price;
}

// @Builder 사용 예
Book book = Book.builder()
        .title("객체지향의 사실과 오해")
        .author("조영호")
        .price(22000)
        .build();
⚠️ @Builder를 클래스에 붙일 때는 @NoArgsConstructor와 @AllArgsConstructor를 함께 붙여주는 게 안전해요. @Builder가 내부적으로 모든 필드를 받는 생성자를 필요로 하는데, 다른 생성자 애노테이션과 충돌하는 경우가 있기 때문이에요. 그리고 JPA 엔티티는 프록시 생성을 위해 기본 생성자가 필수라, @NoArgsConstructor는 특히 자주 함께 쓰인다(16장 참고).

2) Bean Validation — 검증 애노테이션

클라이언트가 보낸 요청 데이터가 올바른지(제목이 비어있지 않은지, 가격이 음수가 아닌지 등)를 매번 if문으로 검사하는 대신, 필드에 검증 규칙을 애노테이션으로 선언해둘 수 있어요.

애노테이션검증 내용
@NotNullnull이 아니어야 함
@NotBlanknull·빈 문자열·공백만 있는 문자열이 아니어야 함(String 전용)
@NotEmptynull이거나 비어있지 않아야 함(문자열·컬렉션 등)
@Size(min=, max=)문자열 길이·컬렉션 크기 범위 제한
@Min / @Max숫자 값의 최소/최대 범위
@Positive / @PositiveOrZero양수 / 0 이상
@Email이메일 형식 검증
BookRequest DTO에 검증 규칙 선언
@Getter @Setter
@NoArgsConstructor
public class BookRequest {

    @NotBlank(message = "제목은 비어있을 수 없습니다.")
    @Size(max = 100, message = "제목은 100자를 넘을 수 없습니다.")
    private String title;

    @NotBlank(message = "저자는 비어있을 수 없습니다.")
    private String author;

    @NotNull(message = "가격은 필수입니다.")
    @Min(value = 0, message = "가격은 0원 이상이어야 합니다.")
    private Integer price;
}

3) @Valid로 검증 트리거하기

DTO에 검증 규칙을 선언해도, 컨트롤러에서 @Valid(또는 @Validated)를 붙여야 실제로 검증이 실행돼요. 검증에 실패하면 컨트롤러 메서드가 실행되기도 전에 MethodArgumentNotValidException이 발생하며 요청이 차단된다(13장에서 이 예외를 다루는 방법을 배운다).

@Valid를 붙인 컨트롤러
@PostMapping
public ResponseEntity<Book> create(@Valid @RequestBody BookRequest request) {
    // @Valid가 없으면 검증 애노테이션이 있어도 무시된 채 이 메서드가 그대로 실행된다
    Book saved = bookService.create(request);
    return ResponseEntity.status(HttpStatus.CREATED).body(saved);
}
🔑 @Valid를 빠뜨리는 실수가 은근히 잦아요. DTO에 @NotBlank 등을 붙여놓고도 컨트롤러 파라미터에 @Valid를 안 붙이면 검증이 조용히 통과되어 버리니, 요청 바디를 받는 DTO에는 항상 @Valid를 붙이는 습관을 들이는 게 좋다.
✔ 12장 핵심 요약
  • Lombok은 getter/setter/생성자/빌더 같은 반복 코드를 애노테이션으로 자동 생성한다.
  • Bean Validation 애노테이션(@NotBlank, @Size, @Min 등)으로 입력값 규칙을 선언할 수 있다.
  • 실제 검증이 실행되려면 컨트롤러에서 @Valid(또는 @Validated)를 붙여야 한다.

13. 예외 처리(ExceptionHandler)

@ExceptionHandler로 컨트롤러별 예외 처리 · @RestControllerAdvice로 전역 예외 처리 · 커스텀 예외와 일관된 에러 응답 형식

💡
쉽게 말하면: 존재하지 않는 도서를 조회하거나, 검증에 실패한 요청이 들어오면 예외가 발생해요. 이걸 그냥 두면 스택 트레이스가 그대로 노출된 500 에러가 나가버려요. @ExceptionHandler와 @RestControllerAdvice는 이런 예외를 붙잡아서, 클라이언트가 이해할 수 있는 일관된 형식의 JSON 에러 응답으로 바꿔서 돌려주는 장치예요.

1) 커스텀 예외 클래스 설계

자바 표준 예외(RuntimeException 등) 대신, 상황에 맞는 의미를 담은 커스텀 예외를 만들어 쓰는 게 좋아요. "무엇이 왜 잘못됐는지"가 예외 이름만 봐도 드러나기 때문이에요.

BookNotFoundException
public class BookNotFoundException extends RuntimeException {
    public BookNotFoundException(Long id) {
        super("도서를 찾을 수 없습니다. id=" + id);
    }
}

// Service 계층에서 발생시키는 지점
@Service
public class BookService {
    private final BookRepository bookRepository;
    // ... 생성자 생략 ...

    public Book findById(Long id) {
        return bookRepository.findById(id)
                .orElseThrow(() -> new BookNotFoundException(id));
    }
}
🔑 RuntimeException(비검사 예외)을 상속하면 메서드 시그니처마다 throws를 선언하지 않아도 돼서, Spring 기반 코드에서는 대부분 비검사 예외로 커스텀 예외를 설계한다.

2) @ExceptionHandler — 컨트롤러 단위 예외 처리

@ExceptionHandler는 같은 컨트롤러 클래스 안에서 특정 예외가 발생했을 때 실행될 메서드를 지정해요. 컨트롤러 범위에 국한된다는 게 특징이에요.

컨트롤러 내부 예외 처리
@RestController
@RequestMapping("/api/books")
public class BookController {

    private final BookService bookService;
    // ... 생성자 생략 ...

    @GetMapping("/{id}")
    public Book findById(@PathVariable Long id) {
        return bookService.findById(id); // 못 찾으면 BookNotFoundException
    }

    @ExceptionHandler(BookNotFoundException.class)
    public ResponseEntity<String> handleNotFound(BookNotFoundException e) {
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(e.getMessage());
    }
}

이 방식은 해당 컨트롤러에서만 적용되기 때문에, 컨트롤러가 여러 개면 같은 처리 코드를 계속 복사해야 하는 단점이 있어요. 이 문제를 해결하는 게 다음의 전역 예외 처리예요.

3) @RestControllerAdvice — 전역 예외 처리

@RestControllerAdvice(@ControllerAdvice + @ResponseBody)가 붙은 클래스는 애플리케이션 전체의 컨트롤러에서 발생하는 예외를 한곳에서 처리할 수 있게 해줘요. 컨트롤러마다 @ExceptionHandler를 반복하지 않아도 된다.

전역 예외 처리기 — GlobalExceptionHandler
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler(BookNotFoundException.class)
    public ResponseEntity<ErrorResponse> handleBookNotFound(BookNotFoundException e) {
        ErrorResponse body = new ErrorResponse("BOOK_NOT_FOUND", e.getMessage());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(body);
    }

    @ExceptionHandler(MethodArgumentNotValidException.class) // @Valid 검증 실패 시 발생
    public ResponseEntity<ErrorResponse> handleValidation(MethodArgumentNotValidException e) {
        String message = e.getBindingResult().getFieldErrors().stream()
                .map(f -> f.getField() + ": " + f.getDefaultMessage())
                .collect(Collectors.joining(", "));
        ErrorResponse body = new ErrorResponse("VALIDATION_FAILED", message);
        return ResponseEntity.badRequest().body(body);
    }

    @ExceptionHandler(Exception.class) // 나머지 예상치 못한 예외의 최종 방어선
    public ResponseEntity<ErrorResponse> handleUnexpected(Exception e) {
        ErrorResponse body = new ErrorResponse("INTERNAL_ERROR", "서버 내부 오류가 발생했습니다.");
        return ResponseEntity.status(HttpStatus.INTERNAL_SERVER_ERROR).body(body);
    }
}
🔑 예외 처리 메서드는 더 구체적인 예외가 우선 적용돼요. BookNotFoundException 전용 핸들러와 Exception 전체를 받는 핸들러가 함께 있으면, BookNotFoundException이 발생했을 때는 더 구체적인 핸들러가 먼저 매칭된다. 가장 포괄적인 Exception.class 핸들러는 "예상치 못한 예외를 500으로라도 일관되게 응답하기 위한 최종 방어선" 역할을 한다.

4) 일관된 에러 응답 형식 설계

클라이언트(프론트엔드)가 에러를 일관되게 처리하려면, 어떤 예외든 같은 구조의 JSON으로 응답하는 게 중요해요.

ErrorResponse DTO와 응답 예시
@Getter
@AllArgsConstructor
public class ErrorResponse {
    private String code;      // 클라이언트가 분기 처리할 수 있는 에러 코드
    private String message;   // 사람이 읽을 수 있는 메시지
}

// GET /api/books/999 → 404 응답 바디 예시
{
  "code": "BOOK_NOT_FOUND",
  "message": "도서를 찾을 수 없습니다. id=999"
}

// POST /api/books (제목 누락) → 400 응답 바디 예시
{
  "code": "VALIDATION_FAILED",
  "message": "title: 제목은 비어있을 수 없습니다."
}
✔ 실무에서 흔히 추가하는 필드
  • timestamp — 에러 발생 시각(로그 추적에 유용).
  • path — 에러가 발생한 요청 경로.
  • status — HTTP 상태 코드 숫자(응답 헤더와 별개로 바디에도 담아두면 클라이언트가 파싱하기 편함).
🔎 심화 — @ExceptionHandler vs @RestControllerAdvice, 언제 뭘 쓰나

특정 컨트롤러에서만 특별하게 처리해야 하는 예외라면 그 컨트롤러 안에 @ExceptionHandler를 두는 게 맞지만, 대부분의 경우(공통 검증 실패, 리소스 없음, 서버 오류 등)는 @RestControllerAdvice 하나로 애플리케이션 전역을 통일해서 관리하는 게 유지보수에 유리해요. 실무에서는 @RestControllerAdvice를 기본으로 두고, 정말 예외적인 경우에만 컨트롤러 로컬 핸들러를 추가하는 경우가 많다.

✔ 13장 핵심 요약
  • 커스텀 예외 클래스로 "무엇이 왜 잘못됐는지"를 명확히 표현한다.
  • @ExceptionHandler는 컨트롤러 단위, @RestControllerAdvice는 애플리케이션 전역 예외 처리를 담당한다.
  • 모든 예외를 code/message 같은 일관된 JSON 구조로 응답하도록 설계하는 것이 중요하다.

14. 자동 설정과 로그 관리

Auto Configuration이 조건에 따라 Bean을 구성하는 원리 · SLF4J+Logback 기본 사용법 · 로그 레벨

💡
쉽게 말하면: 6장에서 Spring Boot가 "관례 기반 자동 설정"으로 설정 지옥을 해결했다고 배웠는데, 그 자동 설정을 실제로 실행하는 메커니즘이 Auto Configuration이에요. "classpath에 이 라이브러리가 있으면 이 Bean을 등록해라" 같은 조건을 판단해서 동작한다. 그리고 개발 중 무슨 일이 일어나는지 파악하려면 System.out.println 대신 SLF4J+Logback 기반의 로그를 남기는 게 표준이에요.

1) Auto Configuration 동작 원리 개요

Spring Boot는 프로젝트의 classpath에 어떤 라이브러리가 올라와 있는지를 보고, 그에 맞는 Bean들을 자동으로 등록해요. 예를 들어 spring-boot-starter-web이 있으면 내장 톰캣과 DispatcherServlet 관련 Bean들을, JDBC 드라이버와 spring-boot-starter-data-jpa가 있으면 DataSource와 EntityManagerFactory 관련 Bean들을 자동으로 구성해준다. 이 판단은 @Conditional 계열 애노테이션으로 이루어져요.

애노테이션조건
@ConditionalOnClass지정한 클래스가 classpath에 존재할 때만 설정을 활성화
@ConditionalOnMissingBean같은 타입의 Bean이 아직 등록되어 있지 않을 때만 기본 Bean을 등록(개발자가 직접 등록한 Bean이 있으면 그걸 우선시)
@ConditionalOnPropertyapplication.yml의 특정 프로퍼티 값에 따라 설정을 활성화/비활성화
Auto Configuration 개념 예시(Spring Boot 내부 구현을 단순화한 형태)
@Configuration
@ConditionalOnClass(DataSource.class)          // JDBC DataSource 클래스가 classpath에 있을 때만
public class DataSourceAutoConfiguration {

    @Bean
    @ConditionalOnMissingBean                  // 개발자가 직접 DataSource Bean을 등록하지 않았을 때만
    public DataSource dataSource() {
        return new HikariDataSource(); // 기본 커넥션 풀
    }
}
🔑 핵심은 "덮어쓸 수 있는 기본값"이라는 점이에요. 자동 설정이 만들어주는 Bean은 어디까지나 기본값이고, 개발자가 직접 같은 타입의 Bean을 등록하면(@ConditionalOnMissingBean 조건에 의해) 자동 설정 쪽이 조용히 비활성화되고 개발자가 등록한 Bean이 우선 사용된다.

2) SLF4J + Logback — 로그를 남기는 이유

System.out.println은 로그 레벨 구분도 없고, 파일로 저장하거나 끄고 켜는 것도 쉽지 않아요. Spring Boot는 SLF4J(Simple Logging Facade for Java, 로깅 API의 "인터페이스")와 Logback(실제 구현체)을 기본 조합으로 사용한다. spring-boot-starter-web 같은 스타터에 이미 포함되어 있어서 별도 의존성 추가 없이 바로 쓸 수 있다.

Logger 사용 예시 — BookService
@Service
public class BookService {
    private static final Logger log = LoggerFactory.getLogger(BookService.class);
    // Lombok의 @Slf4j 애노테이션을 쓰면 위 한 줄을 자동 생성해준다

    private final BookRepository bookRepository;

    public Book findById(Long id) {
        log.debug("도서 조회 시작 - id: {}", id);   // {} 는 파라미터 자리표시자(placeholder)
        Book book = bookRepository.findById(id)
                .orElseThrow(() -> {
                    log.warn("도서를 찾을 수 없음 - id: {}", id);
                    return new BookNotFoundException(id);
                });
        log.info("도서 조회 완료 - id: {}, title: {}", id, book.getTitle());
        return book;
    }
}
🔑 문자열을 +로 이어붙이는 대신 {} 자리표시자를 쓰는 이유: 로그 레벨이 꺼져 있을 때(예: DEBUG 비활성화 상태에서 log.debug(...) 호출) 문자열 연결 연산 자체가 실행되지 않아 성능 낭비가 없기 때문이에요.

3) 로그 레벨(TRACE / DEBUG / INFO / WARN / ERROR)

로그 레벨은 심각도 순서로 나열돼요. 특정 레벨을 설정하면, 그 레벨 이상의 로그만 출력된다.

TRACE < DEBUG < INFO < WARN < ERROR
심각도가 낮은 순 → 높은 순. 예를 들어 INFO로 설정하면 TRACE·DEBUG는 무시되고 INFO 이상만 출력된다.
레벨용도
TRACE가장 상세한 추적 정보. 메서드 진입/파라미터 값 등 (거의 개발 중 디버깅 전용)
DEBUG개발 단계에서 흐름을 파악하기 위한 상세 정보
INFO정상적인 애플리케이션 동작 정보(요청 처리 완료, 서버 시작 등)
WARN당장 오류는 아니지만 주의가 필요한 상황(재시도, 폴백 처리 등)
ERROR예외 발생 등 실제 오류 상황
application.yml에서 로그 레벨 설정
logging:
  level:
    root: INFO                          # 기본 로그 레벨
    com.example.bookapi: DEBUG          # 우리 패키지만 더 상세하게
    org.hibernate.SQL: DEBUG            # JPA가 실행하는 SQL을 보고 싶을 때
⚠️ 운영 환경에서 DEBUG/TRACE를 켜두면 로그 양이 폭증해서 디스크·성능에 부담을 줄 수 있어요. 보통 운영(prod) 프로필은 INFO 이상, 개발(dev) 프로필은 DEBUG로 Profile별로 다르게 설정한다(8장의 Profile 분리와 연결).
✔ 14장 핵심 요약
  • Auto Configuration은 @ConditionalOnClass 등으로 classpath·설정 상태를 판단해 기본 Bean을 자동 등록한다.
  • 개발자가 직접 같은 타입 Bean을 등록하면 자동 설정보다 우선한다(@ConditionalOnMissingBean).
  • SLF4J+Logback으로 로그를 남기고, TRACE<DEBUG<INFO<WARN<ERROR 순서로 레벨을 구분해 관리한다.

15. AOP(Aspect Oriented Programming)

관점 지향 프로그래밍(횡단 관심사 분리) · @Aspect·@Before·@After·@Around · 프록시 기반 동작 원리 · 로깅·트랜잭션 활용

💡
쉽게 말하면: "메서드 실행 시간을 로그로 남기고 싶다"는 요구가 BookService, BookController 등 수십 개 클래스에 다 있다고 해봐요. 매번 로깅 코드를 복사해 넣으면 지저분하고, 나중에 로그 형식을 바꿀 때 모든 곳을 수정해야 해요. AOP는 이런 "여기저기 흩어진 공통 관심사"를 핵심 비즈니스 로직과 분리해서 한 곳에 모아두고, 필요한 지점에 자동으로 "끼워 넣는" 방법이에요.

1) 횡단 관심사(Cross-Cutting Concern)란

애플리케이션의 관심사는 크게 두 가지로 나눌 수 있어요.

  • 핵심 관심사(Core Concern) — 도서를 조회하고, 등록하고, 삭제하는 것처럼 그 기능이 존재하는 이유 자체가 되는 로직.
  • 횡단 관심사(Cross-Cutting Concern) — 로깅, 트랜잭션 관리, 보안 검사, 성능 측정처럼 여러 핵심 로직에 공통적으로 걸쳐 있는(가로지르는) 관심사.

횡단 관심사를 각 클래스에 직접 섞어 넣으면 핵심 로직이 무엇인지 알아보기 어려워지고, 코드 중복도 심해져요. AOP(관점 지향 프로그래밍)는 이 횡단 관심사를 "관점(Aspect)"이라는 별도 모듈로 분리해서, 핵심 로직 코드는 건드리지 않은 채 필요한 지점에 자동으로 적용되게 하는 프로그래밍 패러다임이에요.

2) @Aspect와 주요 어드바이스(Advice)

Spring AOP에서 관점은 @Aspect가 붙은 클래스로 정의해요. 그 안에서 "언제(Before/After/Around) · 어디에(Pointcut) 적용할지"를 애노테이션으로 지정한다.

애노테이션실행 시점
@Before대상 메서드 실행 전
@After대상 메서드 실행 후(정상 종료든 예외든 항상)
@AfterReturning대상 메서드가 정상적으로 값을 반환한 후
@AfterThrowing대상 메서드에서 예외가 발생한 후
@Around대상 메서드 실행 전·후를 모두 감싸서 제어(가장 강력, 실행 여부·반환값까지 조작 가능)
LoggingAspect — 메서드 실행 시간 로깅
@Aspect
@Component
public class LoggingAspect {

    private static final Logger log = LoggerFactory.getLogger(LoggingAspect.class);

    // Pointcut: service 패키지 아래 모든 클래스의 모든 public 메서드
    @Around("execution(* com.example.bookapi.service..*(..))")
    public Object logExecutionTime(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.currentTimeMillis();

        Object result = joinPoint.proceed(); // 실제 대상 메서드(핵심 로직) 실행

        long elapsed = System.currentTimeMillis() - start;
        log.info("{} 실행 시간: {}ms", joinPoint.getSignature(), elapsed);
        return result;
    }
}

execution(* com.example.bookapi.service..*(..))는 포인트컷(Pointcut) 표현식이에요 — "어떤 메서드에 이 관점을 적용할지"를 지정하는 패턴이에요. service 패키지와 그 하위 패키지의 모든 반환 타입(*), 모든 메서드(*(..))를 의미한다.

3) 프록시 기반 동작 원리

Spring AOP는 프록시(Proxy) 객체를 통해 동작해요. BookService Bean을 컨테이너에서 꺼내 쓸 때, 실제로는 원본 BookService가 아니라 그것을 감싼 프록시 객체가 대신 주입된다.

호출부 → 프록시 객체(부가 기능 실행: 로깅 시작) → 원본 BookService.findById() 실행 → 프록시로 복귀(부가 기능 실행: 로깅 종료) → 호출부로 결과 반환
Spring AOP는 실제 객체를 감싼 프록시가 부가 기능을 끼워 넣는 방식으로 동작한다
⚠️ 프록시 기반이기 때문에 생기는 대표적인 제약이 있어요 — 같은 클래스 내부에서 자기 자신의 메서드를 호출하면(this.methodA()가 내부에서 this.methodB()를 호출) 프록시를 거치지 않고 원본 객체가 직접 호출되므로 AOP(예: @Transactional)가 적용되지 않아요. 이런 경우 메서드를 별도 Bean으로 분리하는 등의 우회가 필요하다.

4) 실전 활용 — 로깅과 트랜잭션

AOP는 개념 설명용 예제뿐 아니라 실무에서도 널리 쓰여요. 대표적인 두 가지 예시가 로깅과 트랜잭션이에요.

사실 @Transactional도 AOP 기반이다
@Service
public class BookService {

    @Transactional // 이 애노테이션 자체가 Spring AOP의 프록시로 동작한다
    public Book create(BookRequest request) {
        Book book = Book.builder()
                .title(request.getTitle())
                .author(request.getAuthor())
                .price(request.getPrice())
                .build();
        return bookRepository.save(book);
        // 메서드가 정상 종료되면 프록시가 자동으로 커밋(commit),
        // 예외가 발생하면 자동으로 롤백(rollback)한다 — 이 커밋/롤백 로직이 바로 AOP로 "끼워 넣어진" 부분
    }
}
✔ AOP가 실무에서 쓰이는 대표적인 곳
  • 로깅 — 메서드 호출·실행 시간·파라미터를 자동으로 기록.
  • 트랜잭션 관리 — @Transactional (17장에서 자세히 다룸)
  • 보안 검사 — 메서드 실행 전 권한이 있는지 확인.
  • 성능 모니터링 — 특정 메서드의 응답 시간을 측정해 통계로 수집.
✔ 15장 핵심 요약
  • AOP는 로깅·트랜잭션 같은 횡단 관심사를 핵심 로직과 분리해서 관리하는 프로그래밍 패러다임이다.
  • @Aspect 클래스 안에서 @Before/@After/@Around 등으로 언제 실행할지, 포인트컷 표현식으로 어디에 적용할지를 지정한다.
  • Spring AOP는 프록시 객체를 통해 동작하며, 내부 자기 호출에는 적용되지 않는다는 제약이 있다.

16. JPA 기초 — 엔티티와 연관관계 매핑

@Entity·@Id·@GeneratedValue · @OneToMany·@ManyToOne·@ManyToMany 연관관계 매핑 · 지연 로딩(LAZY) vs 즉시 로딩(EAGER)

💡
쉽게 말하면: JPA(Java Persistence API)는 자바 객체와 관계형 DB 테이블을 자동으로 연결해주는 표준 인터페이스예요. Book 클래스에 @Entity를 붙이면 그게 곧 book 테이블과 매핑되고, SQL을 직접 쓰지 않아도 객체를 저장·조회할 수 있게 돼요. "책 한 권에는 여러 리뷰가 달릴 수 있다" 같은 테이블 간 관계도 애노테이션 하나로 표현할 수 있다.

1) @Entity, @Id, @GeneratedValue — 기본 매핑

@Entity가 붙은 클래스는 JPA가 관리하는 대상이 되고, DB의 한 테이블에 대응돼요. 기본 키 필드에는 @Id를, 자동 증가시킬 값이라면 @GeneratedValue를 함께 붙인다.

Book 엔티티
@Entity
@Table(name = "book")
@Getter @Setter
@NoArgsConstructor
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY) // DB의 auto_increment에 위임
    private Long id;

    @Column(nullable = false, length = 100)
    private String title;

    @Column(nullable = false)
    private String author;

    private int price;
}
🔑 @Entity 클래스는 JPA가 프록시를 생성하고 리플렉션으로 다루기 때문에, 파라미터 없는 기본 생성자(@NoArgsConstructor)가 반드시 필요해요. 12장에서 배운 Lombok의 @NoArgsConstructor가 여기서 실질적으로 쓰인다.

2) 연관관계 매핑 — @ManyToOne, @OneToMany

"도서 한 권에는 여러 개의 리뷰(Review)가 달릴 수 있다"는 관계를 예로 들어볼게요. 리뷰 입장에서는 도서 하나를 참조하고(다대일, N:1), 도서 입장에서는 여러 리뷰를 가진다(일대다, 1:N).

Review(N) ↔ Book(1) 양방향 매핑
@Entity
@Getter @Setter
@NoArgsConstructor
public class Review {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String content;
    private int rating;

    @ManyToOne(fetch = FetchType.LAZY)   // 리뷰 여러 개가 도서 하나를 가리킴 (연관관계의 주인)
    @JoinColumn(name = "book_id")        // 외래 키(FK) 컬럼 이름
    private Book book;
}

@Entity
@Getter @Setter
@NoArgsConstructor
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private String author;
    private int price;

    @OneToMany(mappedBy = "book", cascade = CascadeType.ALL) // "book" = Review 쪽 필드 이름
    private List<Review> reviews = new ArrayList<>();
}
🔑 연관관계의 주인(owner)은 외래 키(FK)를 관리하는 쪽, 즉 @JoinColumn이 있는 Review.book이에요. 주인이 아닌 쪽(Book.reviews)은 mappedBy로 "나는 상대방의 어떤 필드에 의해 매핑된 거울일 뿐"이라고 표시만 하고, 실제 FK 값 변경에는 관여하지 않는다. FK를 변경하려면 반드시 주인 쪽 필드(review.setBook(book))를 통해야 한다.

3) @ManyToMany 연관관계

"도서 하나가 여러 태그(Tag)를 가질 수 있고, 태그 하나도 여러 도서에 붙을 수 있다"처럼 양쪽 모두 여러 개를 가질 수 있는 관계는 다대다(N:M)예요. 관계형 DB는 다대다를 직접 표현할 수 없어서, 중간에 연결 테이블이 필요하다.

@ManyToMany 매핑
@Entity
@Getter @Setter
@NoArgsConstructor
public class Book {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;

    @ManyToMany
    @JoinTable(
        name = "book_tag",                                   // 중간 연결 테이블
        joinColumns = @JoinColumn(name = "book_id"),
        inverseJoinColumns = @JoinColumn(name = "tag_id"))
    private List<Tag> tags = new ArrayList<>();
}
⚠️ 실무에서는 @ManyToMany를 직접 쓰기보다, 연결 테이블 자체를 BookTag라는 별도 엔티티로 만들어 @OneToMany + @ManyToOne 두 개의 관계로 풀어내는 방식을 더 선호해요. 연결 테이블에 "태그를 등록한 날짜" 같은 추가 컬럼이 필요해지는 경우가 많고, 그때 @ManyToMany로는 대응이 어렵기 때문이에요.

4) 지연 로딩(LAZY) vs 즉시 로딩(EAGER)

연관된 엔티티(예: Book을 조회할 때 딸려오는 Review 목록)를 언제 실제로 DB에서 가져올지를 결정하는 옵션이에요.

전략동작기본값이 적용되는 곳
LAZY(지연 로딩)연관 엔티티를 실제로 사용하는 시점(book.getReviews() 호출 시)에 DB 조회@OneToMany, @ManyToMany
EAGER(즉시 로딩)대상 엔티티를 조회할 때 연관 엔티티까지 함께 즉시 조회@ManyToOne, @OneToOne
🔑 실무에서는 거의 항상 모든 연관관계를 LAZY로 명시하는 게 권장돼요. EAGER는 예상치 못한 시점에 불필요한 연관 데이터까지 한꺼번에 조회해버려서(특히 연관관계가 여러 단계로 얽혀 있으면) 성능 문제(N+1 문제 등)를 진단하기 어렵게 만들기 때문이에요. 필요한 데이터는 다음 장에서 배울 @Query(fetch join)로 필요한 시점에 명시적으로 가져오는 게 더 안전하다.
✔ 16장 핵심 요약
  • @Entity+@Id(+@GeneratedValue)로 자바 클래스를 DB 테이블에 매핑한다.
  • @ManyToOne/@OneToMany로 1:N, @ManyToMany로 N:M 관계를 표현하며, FK를 관리하는 쪽이 연관관계의 주인이다.
  • 연관관계 로딩 전략은 실무에서 기본적으로 LAZY를 명시하는 것이 권장된다.

17. JPA Repository — 조회와 트랜잭션

JpaRepository<T,ID> 상속만으로 CRUD가 되는 원리 · 쿼리 메서드 네이밍 규칙 · @Query로 JPQL 작성 · @Transactional

💡
쉽게 말하면: 지금까지는 BookRepository를 직접 구현했지만, Spring Data JPA를 쓰면 인터페이스 하나만 선언해도 저장·조회·삭제 같은 기본 CRUD가 전부 자동으로 동작해요. 심지어 메서드 이름을 findByTitleContaining처럼 규칙에 맞게 짓기만 해도, Spring이 이름을 해석해서 알맞은 SQL을 자동으로 만들어준다. 정말 복잡한 조회는 @Query로 직접 JPQL을 쓸 수도 있어요.

1) JpaRepository<T, ID> 상속만으로 CRUD가 되는 원리

Spring Data JPA가 제공하는 JpaRepository<Book, Long>을 상속하는 인터페이스를 하나 선언하기만 하면, 구현 클래스를 직접 작성하지 않아도 기본적인 CRUD 메서드를 즉시 사용할 수 있어요.

BookRepository — 인터페이스 선언만으로 끝
public interface BookRepository extends JpaRepository<Book, Long> {
    // 아무 메서드도 추가하지 않아도 아래가 전부 기본 제공된다
}

// 사용 예 — BookService
@Service
public class BookService {
    private final BookRepository bookRepository;

    public List<Book> findAll() {
        return bookRepository.findAll();          // 전체 조회
    }
    public Optional<Book> findById(Long id) {
        return bookRepository.findById(id);        // id로 단건 조회
    }
    public Book save(Book book) {
        return bookRepository.save(book);           // 저장(insert) 또는 수정(update)
    }
    public void delete(Long id) {
        bookRepository.deleteById(id);              // 삭제
    }
}
🔑 Spring Data JPA는 애플리케이션이 시작될 때 JpaRepository를 상속한 인터페이스를 찾아서, 런타임에 프록시 구현체를 자동으로 만들어 Bean으로 등록해줘요. 그래서 개발자는 구현 클래스를 직접 작성할 필요 없이 인터페이스만 정의하면 된다. save()는 id가 없으면 insert, 있으면 update로 동작한다는 점도 기억해두면 좋다.

2) 쿼리 메서드 네이밍 규칙

메서드 이름을 정해진 규칙대로 지으면, Spring Data JPA가 그 이름을 분석해서 자동으로 쿼리를 생성해줘요. SQL을 한 줄도 쓰지 않고 조건 조회가 가능한 이유예요.

메서드 이름생성되는 조건
findByTitle(String title)WHERE title = ?
findByTitleContaining(String keyword)WHERE title LIKE %?%
findByAuthorAndPriceLessThan(String author, int price)WHERE author = ? AND price < ?
findByPriceBetween(int min, int max)WHERE price BETWEEN ? AND ?
findByOrderByPriceDesc()ORDER BY price DESC(전체 조회 + 정렬)
countByAuthor(String author)SELECT COUNT(*) WHERE author = ?
existsByTitle(String title)WHERE title = ?의 존재 여부(boolean 반환)
BookRepository에 쿼리 메서드 추가
public interface BookRepository extends JpaRepository<Book, Long> {
    List<Book> findByTitleContaining(String keyword);
    List<Book> findByAuthorAndPriceLessThan(String author, int price);
    List<Book> findByOrderByPriceDesc();
}
⚠️ 조건이 많아질수록 메서드 이름이 길고 복잡해져요(예: findByAuthorAndPriceLessThanAndTitleContaining). 조건이 3~4개를 넘어가거나 통계성 집계가 필요하면, 다음에 배울 @Query로 직접 JPQL을 작성하는 편이 오히려 가독성이 좋다.

3) @Query로 직접 JPQL 작성하기

메서드 이름만으로 표현하기 어려운 복잡한 조건은 @Query 애노테이션에 JPQL(SQL과 비슷하지만 테이블이 아닌 엔티티·필드를 기준으로 쓰는 객체지향 쿼리 언어)을 직접 작성할 수 있어요.

@Query 사용 예시
public interface BookRepository extends JpaRepository<Book, Long> {

    @Query("SELECT b FROM Book b WHERE b.price >= :minPrice ORDER BY b.price ASC")
    List<Book> findExpensiveBooks(@Param("minPrice") int minPrice);

    // 네이티브 SQL이 꼭 필요할 때는 nativeQuery = true
    @Query(value = "SELECT * FROM book WHERE author = :author LIMIT 5", nativeQuery = true)
    List<Book> findTop5ByAuthorNative(@Param("author") String author);
}
🔑 JPQL은 FROM Book b처럼 테이블명이 아니라 엔티티 클래스명을 기준으로 쓴다는 점이 SQL과 다른 핵심 차이예요. JPQL은 특정 DB 벤더에 종속되지 않는 반면, nativeQuery = true로 쓰는 순수 SQL은 DB마다 문법이 조금씩 달라질 수 있다.

4) @Transactional — 트랜잭션 관리

여러 DB 작업을 하나의 단위로 묶어서 "전부 성공 또는 전부 취소(원자성)"를 보장하고 싶을 때 @Transactional을 사용해요. 15장에서 배운 AOP 기반으로 동작한다 — 메서드 실행 전 트랜잭션을 시작하고, 정상 종료되면 커밋, 예외가 발생하면 롤백한다.

@Transactional 사용 예시
@Service
public class BookService {

    private final BookRepository bookRepository;

    @Transactional
    public void updatePrice(Long id, int newPrice) {
        Book book = bookRepository.findById(id)
                .orElseThrow(() -> new BookNotFoundException(id));
        book.setPrice(newPrice);
        // 트랜잭션 안에서 엔티티 필드만 바꿔도, 트랜잭션 종료 시점에 JPA가 변경을 감지해
        // 자동으로 UPDATE 쿼리를 실행한다 — 이를 '변경 감지(Dirty Checking)'라고 부른다.
        // 별도로 save()를 호출하지 않아도 된다.
    }

    @Transactional(readOnly = true) // 조회 전용 — 성능 최적화(변경 감지 생략 등) 힌트
    public List<Book> findAll() {
        return bookRepository.findAll();
    }
}
🔑 조회만 하는 메서드에는 @Transactional(readOnly = true)를 붙여주는 게 좋은 습관이에요. JPA가 변경 감지를 위한 스냅샷 비교를 생략하는 등 내부적으로 최적화를 할 수 있어서 성능에 도움이 된다.
✔ 17장 핵심 요약
  • JpaRepository를 상속하기만 해도 기본 CRUD 메서드가 자동으로 제공된다.
  • 쿼리 메서드 네이밍 규칙(findBy...)으로 SQL 없이 조건 조회를 만들 수 있고, 복잡한 조건은 @Query(JPQL)로 작성한다.
  • @Transactional로 원자성을 보장하며, 변경 감지(Dirty Checking)로 save() 호출 없이도 엔티티 변경이 반영된다.
Day 4

18. SQL Mapper(MyBatis)

MyBatis가 JPA와 다른 접근 방식(SQL 직접 제어) · Mapper 인터페이스 + XML/애노테이션 쿼리 매핑 · 통계·리포트 쿼리에 유리한 이유

💡
쉽게 말하면: JPA는 "객체를 다루면 SQL은 알아서 생성된다"는 철학이라면, MyBatis는 반대로 "SQL은 내가 직접 쓰고, 그 결과를 객체에 매핑하는 반복 작업만 자동화해준다"는 철학이에요. 두 기술은 대립 관계가 아니라, 한 프로젝트 안에서 일반 CRUD는 JPA, 복잡한 통계·리포트 쿼리는 MyBatis로 역할을 나눠서 함께 쓰는 경우가 많다.

1) MyBatis vs JPA — 접근 방식의 차이

구분JPA(Hibernate)MyBatis
패러다임객체 중심 — 엔티티를 다루면 SQL은 프레임워크가 생성(ORM)SQL 중심 — 개발자가 SQL을 직접 작성, 결과 매핑만 자동화
SQL 제어권추상화되어 개발자가 직접 손대기 어려움SQL을 한 글자까지 원하는 대로 튜닝 가능
학습 곡선영속성 컨텍스트, 연관관계, 로딩 전략 등 개념이 많음SQL만 알면 비교적 빠르게 익힐 수 있음
적합한 상황단건 CRUD, 연관관계가 있는 도메인 모델 조작복잡한 조인·집계, DB 벤더 특화 기능이 필요한 조회
🔑 MyBatis는 ORM이 아니라 SQL Mapper예요. "객체와 테이블을 자동으로 매핑"하는 게 목표가 아니라, "SQL 실행 결과(ResultSet)를 자바 객체로 옮겨 담는 반복 코드(JDBC의 PreparedStatement, ResultSet 처리 등)를 대신 해주는" 역할에 집중한다는 점이 JPA와의 근본적인 차이예요.

2) Mapper 인터페이스 + XML 쿼리 매핑

MyBatis는 Java 인터페이스와 SQL을 담은 XML 파일을 연결하는 방식이 전통적으로 널리 쓰여요. 인터페이스의 메서드 시그니처와 XML의 id가 서로 매칭된다.

BookMapper 인터페이스
@Mapper
public interface BookMapper {
    List<BookStatDto> findAuthorStatistics();
    List<Book> searchBooks(@Param("keyword") String keyword, @Param("minPrice") int minPrice);
}
BookMapper.xml — 실제 SQL 정의
<?xml version="1.0" encoding="UTF-8" ?>
<!DOCTYPE mapper PUBLIC "-//mybatis.org//DTD Mapper 3.0//EN"
        "http://mybatis.org/dtd/mybatis-3-mapper.dtd">
<mapper namespace="com.example.bookapi.mapper.BookMapper">

    <select id="findAuthorStatistics" resultType="com.example.bookapi.dto.BookStatDto">
        SELECT author,
               COUNT(*)      AS bookCount,
               AVG(price)    AS avgPrice,
               MAX(price)    AS maxPrice
        FROM book
        GROUP BY author
        ORDER BY bookCount DESC
    </select>

    <select id="searchBooks" resultType="com.example.bookapi.entity.Book">
        SELECT * FROM book
        WHERE title LIKE CONCAT('%', #{keyword}, '%')
          AND price >= #{minPrice}
    </select>

</mapper>
🔑 #{keyword} 문법은 내부적으로 PreparedStatement의 ? 자리표시자로 변환돼요(SQL Injection에 안전). 반면 ${ } 문법은 값을 문자열 그대로 SQL에 끼워 넣기 때문에 SQL Injection에 취약하니, 컬럼명·테이블명처럼 바인딩이 불가능한 경우가 아니면 항상 #{ }를 사용해야 한다.

3) 애노테이션 방식 — 간단한 쿼리는 XML 없이

쿼리가 짧고 단순하다면, XML 파일 없이 인터페이스 메서드에 애노테이션으로 SQL을 바로 붙일 수도 있어요.

애노테이션 기반 Mapper
@Mapper
public interface BookMapper {

    @Select("SELECT * FROM book WHERE id = #{id}")
    Optional<Book> findById(@Param("id") Long id);

    @Insert("INSERT INTO book (title, author, price) VALUES (#{title}, #{author}, #{price})")
    @Options(useGeneratedKeys = true, keyProperty = "id") // insert 후 생성된 id를 book.id에 채워줌
    void insert(Book book);

    @Update("UPDATE book SET price = #{price} WHERE id = #{id}")
    void updatePrice(@Param("id") Long id, @Param("price") int price);
}
⚠️ 실무에서는 짧은 단건 쿼리는 애노테이션으로, 조인이 여러 개거나 조건에 따라 SQL이 동적으로 바뀌는(<if>, <where> 같은 동적 SQL 태그가 필요한) 복잡한 쿼리는 XML로 작성하는 식으로 섞어 쓰는 경우가 많다.

4) 복잡한 통계·리포트 쿼리에 MyBatis가 유리한 이유

위 findAuthorStatistics() 예시처럼 여러 테이블을 조인하고, GROUP BY·집계 함수·서브쿼리가 뒤섞인 리포트성 쿼리는 JPQL이나 엔티티 그래프로 표현하려면 오히려 부자연스럽고 성능도 예측하기 어려운 경우가 많아요.

✔ 이런 상황에서는 MyBatis가 더 유리하다
  • 여러 테이블을 조인한 뒤 GROUP BY·집계 함수로 통계를 뽑아야 할 때 — 엔티티 하나에 대응되지 않는 결과(DTO)를 자유롭게 매핑할 수 있다.
  • DB 벤더 전용 SQL 문법(윈도우 함수, 특정 힌트 등)을 그대로 활용해야 할 때.
  • 실행 계획(explain)을 보고 쿼리를 세밀하게 튜닝해야 하는 성능 크리티컬한 조회.
  • 동적 조건이 많은 대시보드·검색 필터 화면(<if> 태그로 조건별 SQL 분기를 명확하게 표현).
🔎 심화 — JPA와 MyBatis를 함께 쓰는 실무 패턴

많은 실무 프로젝트가 두 기술을 배타적으로 선택하지 않고 함께 사용해요. 도서 등록·수정·삭제 같은 일반적인 CRUD와 연관관계 조작은 JPA(BookRepository)로 처리하고, 저자별 판매 통계 같은 리포트성 조회는 MyBatis(BookMapper)로 별도 계층을 두는 식이에요. "무엇을 다루는가"보다 "어떤 종류의 쿼리인가"를 기준으로 도구를 선택하는 것이 핵심이다.

✔ 18장 핵심 요약
  • JPA는 객체 중심 ORM, MyBatis는 SQL을 직접 제어하는 SQL Mapper라는 점이 근본적인 차이다.
  • Mapper 인터페이스 + XML(또는 애노테이션)으로 SQL과 자바 메서드를 연결한다.
  • 복잡한 조인·통계·리포트 쿼리는 SQL을 직접 튜닝할 수 있는 MyBatis가 유리하며, 실무에서는 JPA와 병행하는 경우가 많다.

19. REST API 문서화 — OpenAPI/Swagger

OpenAPI 스펙이란 무엇인가 · springdoc-openapi로 문서 자동 생성 · Swagger UI로 API 직접 테스트 · @Operation/@Schema/@Parameter로 문서 보강

💡
쉽게 말하면: API를 만들었어도 그 사용법을 팀원이나 프론트엔드 개발자에게 말로 설명하기는 번거로워요. OpenAPI는 "이 API는 어떤 요청을 받고 어떤 응답을 주는지"를 정해진 형식으로 정리한 명세이고, springdoc-openapi 라이브러리를 추가하기만 하면 컨트롤러 코드를 스캔해서 이 명세를 자동으로 만들어줘요. 그리고 Swagger UI라는 웹 화면에서 그 명세를 보기 좋게 보여주는 동시에, 브라우저에서 버튼 클릭만으로 API를 직접 호출해볼 수도 있다.

1) OpenAPI 스펙이란 무엇인가

OpenAPI Specification(OAS)은 REST API의 엔드포인트, 요청 파라미터, 요청/응답 본문의 구조, 상태 코드 등을 사람과 기계가 모두 읽을 수 있는 JSON/YAML 형식으로 표현하기로 약속한 표준 규격이에요. 예전에는 "Swagger 스펙"이라고 불렸는데, 지금은 OpenAPI라는 이름으로 표준화되어 있고 Swagger는 그 스펙을 다루는 도구 모음(Swagger UI, Swagger Editor 등)의 브랜드 이름으로 남아있다.

✔ OpenAPI 문서가 있으면 좋은 점
  • 프론트엔드 개발자가 백엔드 코드를 보지 않아도 요청/응답 형식을 정확히 알 수 있다.
  • 문서를 기반으로 클라이언트 코드(SDK)를 자동 생성하는 도구를 쓸 수 있다.
  • Swagger UI 같은 도구로 문서를 웹 화면에서 바로 렌더링하고, 그 자리에서 테스트도 가능하다.
  • API 명세와 실제 코드가 어긋나는 것을 방지하기 쉽다(코드에서 자동 생성하기 때문).

2) springdoc-openapi로 문서 자동 생성하기

의존성 하나만 추가하면, 애플리케이션이 뜰 때 @RestController로 등록된 컨트롤러들을 스캔해서 OpenAPI 문서(JSON)와 Swagger UI 화면을 자동으로 만들어줘요. 별도의 설정 파일을 직접 작성할 필요가 거의 없다는 게 큰 장점이다.

build.gradle — 의존성 추가
dependencies {
    implementation 'org.springdoc:springdoc-openapi-starter-webmvc-ui:2.5.0'
}
BookController — 기존 코드 그대로, 애노테이션만 없어도 기본 문서는 만들어진다
@RestController
@RequestMapping("/api/books")
public class BookController {

    @GetMapping
    public List<Book> findAll() {
        return bookService.findAll();
    }

    @GetMapping("/{id}")
    public Book findById(@PathVariable Long id) {
        return bookService.findById(id);
    }

    @PostMapping
    public Book create(@RequestBody Book book) {
        return bookService.save(book);
    }
}

애플리케이션을 실행한 뒤 아래 두 경로로 접속하면 각각 원본 명세(JSON)와 사람이 보기 좋은 화면을 확인할 수 있어요.

🔑 springdoc-openapi는 컨트롤러의 @GetMapping/@PostMapping 같은 매핑 애노테이션과 메서드 파라미터 타입을 리플렉션으로 분석해서 기본적인 문서를 만들어줘요. 그래서 애노테이션을 하나도 추가하지 않아도 "어떤 경로가 있고 어떤 타입을 주고받는지" 정도는 이미 문서화된다. 다만 설명이나 예시값처럼 코드만으로는 알 수 없는 정보는 다음 절의 애노테이션으로 직접 보강해야 한다.

3) Swagger UI로 API 직접 테스트해보기

Swagger UI는 단순히 문서를 보여주기만 하는 게 아니라, 각 엔드포인트마다 "Try it out" 버튼을 눌러 파라미터 값을 입력하고 바로 요청을 보내볼 수 있는 화면을 제공해요. 이 페이지의 "REST API 연습장"과 비슷한 역할을, 실제 Swagger UI는 서버가 자동으로 만들어주는 문서와 함께 제공하는 셈이다.

엔드포인트 목록 확인 → Try it out 클릭 → 파라미터/요청 본문 입력 → Execute → 실제 서버에 요청 전송 → 응답(상태 코드·본문) 확인
Swagger UI는 문서 열람과 실제 API 호출 테스트를 한 화면에서 처리한다
⚠️ Swagger UI에서 "Try it out"으로 보낸 요청은 문서 열람용 가짜 요청이 아니라, 실제로 서버에 도달하는 진짜 HTTP 요청이에요. 그래서 운영 환경에 그대로 노출하면 외부인이 실제 데이터를 조작할 수 있는 통로가 될 수 있어, 실무에서는 운영(prod) 환경에서 Swagger UI 접근을 막거나 인증을 요구하는 경우가 많다.

4) @Operation / @Schema / @Parameter로 문서 내용 보강하기

기본 생성된 문서는 "경로와 타입"만 알려줄 뿐, "이 API가 정확히 무슨 의미인지"는 설명하지 못해요. 애노테이션을 추가하면 Swagger UI에 사람이 읽을 설명·예시값·필수 여부 같은 정보를 덧붙일 수 있다.

애노테이션으로 문서 보강하기
@RestController
@RequestMapping("/api/books")
@Tag(name = "Book API", description = "도서 등록·조회·수정·삭제를 담당하는 API")
public class BookController {

    @Operation(summary = "id로 도서 단건 조회", description = "존재하지 않는 id면 404를 반환한다.")
    @GetMapping("/{id}")
    public Book findById(
            @Parameter(description = "조회할 도서의 id", example = "1")
            @PathVariable Long id) {
        return bookService.findById(id);
    }

    @Operation(summary = "새 도서 등록")
    @PostMapping
    public Book create(@RequestBody Book book) {
        return bookService.save(book);
    }
}

@Schema(description = "도서 정보")
public class Book {

    @Schema(description = "도서 고유 id", example = "1")
    private Long id;

    @Schema(description = "제목", example = "객체지향의 사실과 오해")
    private String title;

    @Schema(description = "저자", example = "조영호")
    private String author;

    @Schema(description = "가격(원)", example = "18000")
    private int price;
}

@SchemaDTO/엔티티 클래스 및 필드요청/응답 본문 필드에 대한 설명과 예시값
🔎 심화 — 문서는 코드와 함께 살아있어야 한다

API 문서를 별도의 워드/노션 페이지로 따로 관리하면, 코드가 바뀌어도 문서를 갱신하는 걸 잊어버려 금방 실제와 어긋나는 "죽은 문서"가 되기 쉬워요. springdoc-openapi처럼 코드(애노테이션)에서 문서를 생성하는 방식은 코드가 바뀌면 문서도 자동으로 함께 바뀌기 때문에, 문서와 실제 동작이 어긋나는 문제를 근본적으로 줄여준다는 점이 핵심 장점이다.

✔ 19장 핵심 요약
  • OpenAPI는 REST API의 구조를 표준 형식으로 표현한 명세이고, Swagger는 그 명세를 다루는 도구 모음이다.
  • springdoc-openapi 의존성만 추가해도 컨트롤러를 스캔해 문서(JSON)와 Swagger UI 화면이 자동 생성된다.
  • Swagger UI는 문서 열람뿐 아니라 Try it out으로 실제 API 호출 테스트까지 지원하며, 운영 환경 노출에는 주의가 필요하다.
  • @Operation/@Schema/@Parameter로 요약·설명·예시값을 추가해 문서를 사람이 이해하기 쉽게 보강할 수 있다.

20. JWT와 Spring Security

JWT 구조(Header.Payload.Signature) · 로그인→토큰 발급→요청마다 검증하는 인증 흐름 · Spring Security 필터 체인 · @PreAuthorize로 메서드 단위 권한 제어

💡
쉽게 말하면: 세션 방식은 서버가 "누가 로그인했는지"를 메모리나 DB에 기억해둬야 하지만, JWT(JSON Web Token) 방식은 로그인 성공 시 서버가 "이 사람이 누구인지"를 담은 토큰을 발급하고, 그 이후에는 클라이언트가 요청마다 그 토큰을 들고 오면 서버가 서명만 검증해서 신원을 확인해요. 서버가 상태를 따로 기억하지 않아도 된다는 뜻에서 무상태(stateless) 인증 방식이라고 부른다. Spring Security는 이 인증·인가 과정을 요청이 컨트롤러에 도달하기 전 여러 개의 필터를 거치게 해서 처리한다.

1) JWT의 구조 — Header.Payload.Signature

JWT는 점(.)으로 구분된 3개의 부분이 이어붙은 하나의 문자열이에요. 각 부분은 Base64Url로 인코딩되어 있어서, 디코딩하면 내용을 바로 읽을 수 있다(암호화된 것이 아니라 인코딩된 것이라는 점에 유의).

구성 요소담는 내용예시(디코딩 후)
Header토큰 타입, 서명 알고리즘{"alg":"HS256","typ":"JWT"}
Payload클레임(claim) — 사용자 정보, 만료 시간 등{"sub":"user1","role":"USER","exp":1735689600}
SignatureHeader+Payload를 서버만 아는 비밀키로 서명한 값 — 위변조 검증용HMACSHA256(base64(header)+"."+base64(payload), secretKey)
Header(Base64Url) + "." + Payload(Base64Url) + "." + Signature(Base64Url)
예: eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJ1c2VyMSJ9.SflKxwRJSMeKKF2QT4fw...
⚠️ Payload는 암호화되어 있지 않고 단순히 인코딩만 된 상태라서, 토큰을 가진 사람이면 누구나 디코딩해서 내용을 읽을 수 있어요. 그래서 비밀번호나 주민번호 같은 민감한 정보는 절대 Payload에 담으면 안 된다. Signature는 내용을 숨기는 게 아니라, "이 토큰이 서버가 발급한 뒤 중간에 조작되지 않았는지"를 검증하는 용도다.

2) 로그인 → 토큰 발급 → 요청마다 검증하는 인증 흐름

JWT 기반 인증은 최초 로그인 시 한 번 토큰을 발급받고, 이후에는 매 요청의 헤더에 그 토큰을 실어 보내는 방식으로 동작해요. 서버는 요청이 올 때마다 토큰의 서명을 검증하기만 하면 되므로, 로그인 상태를 별도로 저장해둘 필요가 없다.

① POST /api/auth/login(id/pw) → ② 서버가 검증 후 JWT 발급 → ③ 클라이언트가 토큰을 저장(예: localStorage) → ④ 이후 요청마다 Authorization: Bearer <token> 헤더로 전송 → ⑤ 서버가 매 요청마다 서명·만료시간 검증 → ⑥ 유효하면 요청 처리, 무효면 401 응답
로그인 요청/응답 예시
POST /api/auth/login
Content-Type: application/json

{ "username": "reader1", "password": "p@ssw0rd" }

--- 응답 ---
200 OK
{ "accessToken": "eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJyZWFkZXIxIn0.abc123..." }

--- 이후 도서 API 요청 시 ---
GET /api/books/1
Authorization: Bearer eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJyZWFkZXIxIn0.abc123...
JwtTokenProvider — 발급과 검증(개념 예시)
@Component
public class JwtTokenProvider {

    private final SecretKey secretKey; // 서버만 아는 비밀키

    public String createToken(String username, String role) {
        return Jwts.builder()
                .subject(username)
                .claim("role", role)
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + 3600_000)) // 1시간
                .signWith(secretKey)
                .compact();
    }

    public boolean validateToken(String token) {
        try {
            Jwts.parser().verifyWith(secretKey).build().parseSignedClaims(token);
            return true; // 서명이 유효하고, 만료되지 않았음
        } catch (JwtException | IllegalArgumentException e) {
            return false; // 위변조되었거나 만료된 토큰
        }
    }
}
🔑 JWT는 만료 시간이 짧은 Access Token과, 그것을 재발급받는 데 쓰는 만료 시간이 긴 Refresh Token을 함께 쓰는 경우가 많아요. Access Token이 탈취되어도 금방 만료되도록 짧게 두고, 사용자가 매번 재로그인하지 않도록 Refresh Token으로 Access Token만 갱신하는 구조다.

3) Spring Security 필터 체인

Spring Security는 클라이언트의 요청이 컨트롤러에 도달하기 전에, 여러 개의 필터(Filter)가 순서대로 요청을 가로채서 인증·인가 처리를 하는 구조로 동작해요. 이 필터들이 이어진 것을 필터 체인(Filter Chain)이라고 부른다.

요청 → ... → JwtAuthenticationFilter(토큰 꺼내 검증, 인증 정보 등록) → ... → AuthorizationFilter(권한 확인) → DispatcherServlet → Controller
JWT를 직접 다루는 프로젝트에서는 보통 커스텀 필터를 필터 체인 중간에 끼워 넣는다
SecurityConfig — 필터 체인 설정 예시
@Configuration
@EnableWebSecurity
public class SecurityConfig {

    @Bean
    public SecurityFilterChain filterChain(HttpSecurity http, JwtAuthenticationFilter jwtFilter) throws Exception {
        http
            .csrf(csrf -> csrf.disable())          // 토큰 기반 API는 보통 CSRF 보호가 불필요
            .sessionManagement(sm ->
                sm.sessionCreationPolicy(SessionCreationPolicy.STATELESS)) // 세션 사용 안 함
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/login").permitAll()   // 로그인은 누구나 접근 가능
                .requestMatchers("/api/books/**").authenticated() // 도서 API는 인증 필요
                .anyRequest().authenticated())
            .addFilterBefore(jwtFilter, UsernamePasswordAuthenticationFilter.class); // 커스텀 필터 등록

        return http.build();
    }
}
🔑 JwtAuthenticationFilter는 요청 헤더에서 토큰을 꺼내 JwtTokenProvider로 검증하고, 유효하면 SecurityContextHolder에 "이 요청은 이 사용자가 인증된 상태"라는 정보를 등록해요. 이후 필터들과 컨트롤러는 이 정보를 참조해서 "누가 요청했는지"를 알 수 있게 된다.

4) @PreAuthorize — 메서드 단위 권한 제어

필터 체인 설정이 URL 경로 단위로 접근을 막는 것이었다면, @PreAuthorize는 메서드 단위로 더 세밀하게 "이 역할(role)을 가진 사용자만 이 메서드를 실행할 수 있다"는 조건을 걸 수 있어요.

@PreAuthorize 사용 예시
@RestController
@RequestMapping("/api/books")
public class BookController {

    @GetMapping
    public List<Book> findAll() { // 인증만 되어 있으면 누구나 조회 가능
        return bookService.findAll();
    }

    @PreAuthorize("hasRole('ADMIN')")
    @PostMapping
    public Book create(@RequestBody Book book) { // ADMIN 권한을 가진 사용자만 등록 가능
        return bookService.save(book);
    }

    @PreAuthorize("hasRole('ADMIN')")
    @DeleteMapping("/{id}")
    public void delete(@PathVariable Long id) { // ADMIN 권한을 가진 사용자만 삭제 가능
        bookService.delete(id);
    }
}
⚠️ @PreAuthorize가 동작하려면 @EnableMethodSecurity를 설정 클래스에 붙여야 하고, 필터 체인 단계에서 이미 SecurityContextHolder에 인증 정보(역할 포함)가 등록되어 있어야 해요. 즉 20장에서 다룬 "토큰 검증 → 인증 정보 등록" 흐름이 먼저 성립해야, 그 정보를 바탕으로 메서드 단위 권한 검사가 가능해진다.
🔎 오해 — JWT를 쓰면 로그아웃이 저절로 처리된다?

세션 방식은 서버가 세션을 삭제하면 즉시 로그아웃되지만, JWT는 서버가 토큰 자체를 "기억"하지 않기 때문에 이미 발급된 토큰을 서버가 강제로 무효화하기 어렵다는 특징이 있어요. 그래서 실무에서는 만료 시간을 짧게 유지하거나, 무효화해야 할 토큰 목록(블랙리스트)을 별도로 관리하는 방식을 함께 쓰는 경우가 많다. "무상태"라는 장점이 곧 "로그아웃 처리가 간단하다"는 뜻은 아니다.

✔ 20장 핵심 요약
  • JWT는 Header.Payload.Signature 3부분으로 구성되며, Payload는 암호화가 아니라 인코딩만 되어 있어 민감 정보를 담으면 안 된다.
  • 로그인 시 토큰을 한 번 발급받고, 이후 요청마다 헤더에 담아 보내면 서버가 서명을 검증하는 무상태 인증 흐름이다.
  • Spring Security는 요청이 컨트롤러에 도달하기 전 필터 체인을 거치며, JWT 검증도 보통 커스텀 필터로 이 체인에 끼워 넣는다.
  • @PreAuthorize로 URL 단위보다 더 세밀한 메서드 단위 권한 제어가 가능하다.

21. 컨테이너 이해 — Docker와 Kubernetes

컨테이너와 가상머신(VM)의 차이 · Dockerfile로 Spring Boot 앱 이미지 빌드 · docker-compose로 앱+DB 함께 띄우기 · Kubernetes 기본 개념(Pod/Deployment/Service) 개요

💡
쉽게 말하면: "내 컴퓨터에서는 되는데 서버에서는 안 돼요"라는 문제는, 개발 환경과 운영 환경의 설정(자바 버전, 라이브러리 등)이 미묘하게 다를 때 자주 생겨요. 컨테이너는 애플리케이션과 그 실행에 필요한 모든 것(런타임, 라이브러리, 설정)을 하나의 "상자"에 통째로 담아, 어느 환경에서 실행하든 똑같이 동작하도록 보장하는 기술이다. Docker는 이 컨테이너를 만들고 실행하는 도구이고, Kubernetes는 이런 컨테이너들을 수십·수백 개 규모로 자동으로 관리해주는 도구예요.

1) 컨테이너와 가상머신(VM)의 차이

가상머신(VM)은 하드웨어를 통째로 가상화해서 그 위에 운영체제(OS) 전체를 새로 설치하는 방식이라 무겁고 느려요. 반면 컨테이너는 호스트 OS의 커널을 그대로 공유하면서 프로세스 수준에서만 격리하기 때문에 훨씬 가볍고 빠르게 뜬다.

구분가상머신(VM)컨테이너
격리 단위하드웨어 가상화 + OS 전체프로세스(호스트 OS 커널 공유)
크기보통 수 GB(OS 이미지 포함)보통 수백 MB 이하

🔑 이런 가벼움 덕분에 "빌드한 이미지를 어디서 실행하든 똑같이 동작한다"는 점이 컨테이너의 핵심 가치예요. 개발자 로컬 환경, 테스트 서버, 운영 서버가 모두 같은 이미지를 실행하므로 환경 차이로 인한 장애를 크게 줄일 수 있다.

2) Dockerfile로 Spring Boot 앱을 이미지로 빌드하기

Dockerfile은 "어떤 재료로, 어떤 순서로 이미지를 만들지"를 적어둔 설계도예요. Spring Boot 프로젝트를 빌드한 jar 파일을 컨테이너 이미지 안에 넣고, 그 jar를 실행하도록 지시하는 식으로 작성한다.

Dockerfile — 도서 관리 API 이미지 빌드
# 1단계: 자바 실행 환경이 담긴 베이스 이미지에서 시작
FROM eclipse-temurin:21-jre

# 2단계: 컨테이너 안에서 작업할 디렉터리 지정
WORKDIR /app

# 3단계: 로컬에서 빌드해 둔 jar 파일을 이미지 안으로 복사
COPY build/libs/book-api-0.0.1-SNAPSHOT.jar app.jar

# 4단계: 이 컨테이너가 외부에 노출할 포트를 명시(문서화 목적)
EXPOSE 8080

# 5단계: 컨테이너가 시작될 때 실행할 명령
ENTRYPOINT ["java", "-jar", "app.jar"]
이미지 빌드 & 실행 명령
# 이미지 빌드 (Dockerfile이 있는 위치에서 실행)
docker build -t book-api:1.0 .

# 컨테이너 실행 — 호스트의 8080 포트를 컨테이너의 8080 포트에 연결
docker run -p 8080:8080 book-api:1.0
⚠️ 실무에서는 빌드 도구(Gradle 등)까지 포함한 무거운 이미지를 그대로 배포하지 않도록, 빌드 단계와 실행 단계를 분리하는 멀티 스테이지 빌드를 자주 사용해요. 빌드에 필요한 도구는 중간 단계에만 두고, 최종 이미지에는 실행에 꼭 필요한 jar 파일만 남겨서 이미지 크기를 줄이는 방식이다.

3) docker-compose로 앱+DB를 함께 띄우기

도서 관리 API처럼 애플리케이션이 DB와 함께 동작해야 하는 경우, 컨테이너를 하나씩 docker run으로 실행하고 서로 연결하는 건 번거로워요. docker-compose는 여러 컨테이너의 구성을 YAML 파일 하나로 정의하고, 명령 한 번으로 한꺼번에 띄우고 내릴 수 있게 해준다.

docker-compose.yml — book-api + MySQL
version: "3.8"
services:
  book-api:
    build: .
    ports:
      - "8080:8080"
    environment:
      SPRING_DATASOURCE_URL: jdbc:mysql://db:3306/bookdb
      SPRING_DATASOURCE_USERNAME: bookuser
      SPRING_DATASOURCE_PASSWORD: bookpass
    depends_on:
      - db

  db:
    image: mysql:8.0
    environment:
      MYSQL_DATABASE: bookdb
      MYSQL_USER: bookuser
      MYSQL_PASSWORD: bookpass
      MYSQL_ROOT_PASSWORD: rootpass
    ports:
      - "3306:3306"
    volumes:
      - book-db-data:/var/lib/mysql

volumes:
  book-db-data:
실행 명령
docker compose up -d    # 백그라운드로 book-api, db 컨테이너를 함께 실행
docker compose down     # 실행 중인 컨테이너들을 한 번에 정지 및 제거
🔑 book-api 서비스에서 DB 접속 주소를 jdbc:mysql://db:3306/...처럼 서비스 이름(db)으로 지정할 수 있는 이유는, docker-compose가 같은 네트워크 안의 컨테이너들을 서비스 이름으로 서로 찾을 수 있게(DNS처럼) 연결해주기 때문이에요. IP 주소를 몰라도 서비스 이름만으로 통신할 수 있다.

4) Kubernetes 기본 개념 — Pod / Deployment / Service (개요)

docker-compose는 보통 한 대의 서버 안에서 여러 컨테이너를 관리하는 데 적합해요. 하지만 트래픽이 늘어나 서버를 여러 대로 늘리고, 컨테이너가 죽으면 자동으로 재시작하고, 트래픽을 여러 컨테이너에 고르게 분산해야 하는 규모가 되면 Kubernetes(K8s)라는 컨테이너 오케스트레이션 도구를 쓰게 된다. 여기서는 핵심 개념 3가지만 아주 개요 수준으로 짚어본다.

개념역할
PodKubernetes에서 컨테이너를 실행하는 가장 작은 단위. 보통 컨테이너 1개(가끔 여러 개)를 감싼다.
Deployment"Pod를 몇 개 유지할지"를 선언해두면, Pod가 죽었을 때 자동으로 다시 만들어 개수를 유지해준다(자가 치유).
Service여러 개로 늘어난 Pod들 앞에서 고정된 접속 주소 역할을 하며, 요청을 여러 Pod에 고르게 분산(로드밸런싱)한다.
Deployment(원하는 Pod 개수 = 3 선언) → Pod, Pod, Pod(각각 book-api 컨테이너 실행) → Service(고정 주소로 요청을 3개 Pod에 분산)
Pod 하나가 죽으면 Deployment가 감지해 자동으로 새 Pod를 만들어 개수를 다시 3개로 맞춘다
🔎 심화 — docker-compose와 Kubernetes, 무엇이 다른가

docker-compose는 "이 컨테이너들을 이렇게 구성해서 띄워줘"라는 정적인 구성을 다루는 데 강점이 있고, 보통 로컬 개발 환경이나 작은 규모에 적합해요. Kubernetes는 여기서 한 걸음 더 나아가 "몇 개의 Pod를 항상 유지할지, 트래픽이 늘면 몇 개까지 자동으로 늘릴지(오토스케일링), 장애가 나면 어떻게 복구할지"까지 지속적으로 관리해주는 오케스트레이션 도구라는 점이 근본적인 차이다. 이 강의에서는 개념만 소개하며, 실제 운영은 별도의 심화 학습이 필요하다.

✔ 21장 핵심 요약
  • 컨테이너는 호스트 OS 커널을 공유해 VM보다 훨씬 가볍고 빠르며, 어디서든 동일하게 동작하는 이식성을 제공한다.
  • Dockerfile로 Spring Boot jar를 이미지로 빌드하고, docker build/docker run(또는 docker compose)으로 실행한다.
  • docker-compose는 앱과 DB처럼 여러 컨테이너의 구성을 YAML 하나로 정의해 한 번에 띄우고 내릴 수 있게 해준다.
  • Kubernetes는 Pod(최소 실행 단위)·Deployment(개수 유지·자가 치유)·Service(고정 주소·로드밸런싱)로 대규모 컨테이너 운영을 자동화한다.

22. MSA와 최신 트렌드

모놀리식 vs 마이크로서비스 아키텍처 · MSA의 장점(독립 배포/확장)과 단점(운영 복잡도/분산 트랜잭션) · 동기 REST vs 비동기 메시지 큐 · API Gateway 역할

💡
쉽게 말하면: 지금까지 이 강의에서 만든 도서 관리 API는 도서 등록·조회·리뷰·통계 기능이 하나의 애플리케이션 안에 모두 들어있는 구조예요(모놀리식). 마이크로서비스 아키텍처(MSA)는 이걸 "도서 서비스", "리뷰 서비스", "통계 서비스"처럼 독립적으로 배포·운영 가능한 여러 개의 작은 서비스로 쪼개는 방식이다. 서비스가 늘어나면 그만큼 서비스끼리 어떻게 통신하고, 요청을 어디로 보낼지 정리해줄 장치도 함께 필요해진다.

1) 모놀리식 아키텍처 vs 마이크로서비스 아키텍처(MSA)

모놀리식(Monolithic)은 하나의 애플리케이션, 하나의 코드베이스, 하나의 배포 단위 안에 모든 기능이 들어있는 전통적인 구조예요. 반면 MSA는 기능(도메인)별로 애플리케이션 자체를 여러 개로 쪼개서, 각자 독립적인 코드베이스·배포·DB를 갖게 한다.

구분모놀리식MSA
배포 단위애플리케이션 전체를 하나로 배포서비스별로 독립적으로 배포
도서 API 예시도서·리뷰·통계 기능이 한 프로젝트, 한 jar 안에 함께 존재book-service, review-service, stat-service로 완전히 분리된 프로젝트
DB보통 하나의 DB를 여러 기능이 공유서비스마다 자신만의 DB를 갖는 경우가 많음
기술 스택보통 프로젝트 전체가 동일한 언어/프레임워크서비스마다 다른 언어/프레임워크 선택 가능
🔑 MSA로 전환한다는 것은 단순히 "코드를 여러 폴더로 나누는 것"이 아니라, 배포 단위와 DB까지 독립적으로 분리한다는 뜻이에요. book-service를 재배포해도 review-service는 전혀 영향을 받지 않아야 진짜 MSA라고 할 수 있다.

2) MSA의 장점 — 독립 배포와 확장

서비스를 잘게 쪼개면 각 서비스를 독립적으로 다룰 수 있다는 게 가장 큰 장점이에요.

✔ MSA의 대표적인 장점
  • 독립 배포 — 리뷰 기능에 버그를 고쳤을 때 review-service만 재배포하면 되고, 도서 등록 기능은 중단 없이 계속 돌아간다.
  • 독립 확장(스케일링) — 통계 조회 요청이 몰릴 때 stat-service의 인스턴스 개수만 늘리면 되고, 상대적으로 트래픽이 적은 book-service까지 함께 늘릴 필요가 없다.
  • 기술 선택의 자유 — 통계 서비스는 데이터 분석에 유리한 다른 언어를 쓰는 식으로, 서비스별로 적합한 기술을 고를 수 있다.
  • 장애 격리 — 리뷰 서비스에 장애가 나도, 잘 설계되어 있다면 도서 조회 자체는 영향을 받지 않을 수 있다.

3) MSA의 단점 — 운영 복잡도와 분산 트랜잭션

장점이 있는 만큼, 서비스가 여러 개로 나뉘는 순간부터 모놀리식에는 없던 새로운 어려움이 생긴다.

⚠ MSA의 대표적인 단점
  • 운영 복잡도 증가 — 서비스가 10개면 배포 파이프라인, 모니터링, 로그 수집도 10곳에서 따로 관리해야 한다.
  • 서비스 간 통신 오버헤드 — 같은 프로세스 안에서 메서드를 호출하던 것을, 이제는 네트워크를 통한 API 호출로 바꿔야 하니 지연 시간과 실패 가능성이 늘어난다.
  • 분산 트랜잭션 문제 — "도서 주문 생성"과 "재고 차감"이 서로 다른 서비스, 다른 DB에 있다면, 하나의 @Transactional로 두 작업을 함께 묶어 원자성을 보장할 수 없다.
  • 디버깅 난이도 증가 — 하나의 사용자 요청이 여러 서비스를 거치면서 처리되기 때문에, 어느 서비스에서 문제가 생겼는지 추적하기가 모놀리식보다 훨씬 어렵다.
⚠️ 분산 트랜잭션 문제는 실무에서 보통 "여러 서비스에 걸친 작업을 하나의 트랜잭션으로 묶는다"가 아니라, 실패했을 때 이전 작업을 취소하는 보상(compensation) 로직을 순차적으로 실행하는 사가(Saga) 패턴 같은 방식으로 다뤄요. 완벽한 원자성 대신, 최종적으로는 일관된 상태에 도달하는 것(최종 일관성, eventual consistency)을 목표로 설계하는 경우가 많다.

4) 서비스 간 통신 — 동기 REST 호출 vs 비동기 메시지 큐

서비스가 여러 개로 나뉘면, 그 서비스들이 서로 정보를 주고받는 방법을 선택해야 해요. 크게 두 가지 방식이 있다.

방식동작 방식특징
동기(Synchronous) — REST 호출book-service가 review-service의 API를 직접 호출하고, 응답이 올 때까지 기다린다.구현이 직관적이지만, review-service가 느리거나 죽으면 book-service 요청도 함께 지연·실패한다.
비동기(Asynchronous) — 메시지 큐book-service가 "도서가 등록됨"이라는 이벤트를 메시지 큐에 발행만 하고 응답을 기다리지 않으며, review-service는 큐를 구독해 나중에 처리한다.서비스 간 결합도가 낮아지고 한쪽이 잠시 죽어도 메시지가 큐에 남아있어 안정적이지만, 즉시 결과가 필요한 경우엔 맞지 않는다.
동기: book-service → (REST 호출, 응답 대기) → review-service → 응답 반환 vs 비동기: book-service → (이벤트 발행) → 메시지 큐 → review-service(나중에 구독·처리, 즉시 응답 없음)
🔑 "지금 당장 응답 결과가 필요한가?"가 선택의 기준이 되는 경우가 많아요. 예를 들어 "도서 상세 조회"처럼 즉시 화면에 결과를 보여줘야 하면 동기 REST 호출이, "도서가 등록되면 알림을 보낸다"처럼 결과를 그 자리에서 기다릴 필요가 없는 작업은 비동기 메시지 큐가 더 적합한 경우가 많다.

5) API Gateway의 역할

서비스가 여러 개로 나뉘면, 클라이언트 입장에서는 "도서 조회는 어느 주소로, 리뷰 조회는 또 다른 어느 주소로 보내야 하는지"를 일일이 알아야 하는 불편함이 생겨요. API Gateway는 여러 서비스 앞에 놓인 단일 진입점 역할을 하며, 클라이언트의 모든 요청을 받아 적절한 내부 서비스로 전달해준다.

Client → API Gateway(단일 진입점) → 요청 경로에 따라 라우팅 → book-service / review-service / stat-service
클라이언트는 내부에 서비스가 몇 개인지, 어디에 있는지 몰라도 Gateway 주소 하나만 알면 된다
✔ API Gateway가 흔히 함께 담당하는 역할
  • 라우팅 — 요청 경로(예: /api/books/**, /api/reviews/**)에 따라 알맞은 내부 서비스로 전달.
  • 인증/인가 공통 처리 — 20장에서 다룬 JWT 검증 같은 공통 로직을 각 서비스마다 중복 구현하지 않고 Gateway에서 한 번에 처리.
  • 로드밸런싱 — 같은 서비스의 여러 인스턴스(Pod) 중 하나로 요청을 분산.
  • 공통 정책 적용 — 요청 속도 제한(rate limiting), 로깅, CORS 같은 공통 관심사를 한곳에서 관리.
🎯 정리 — 언제 MSA를 고려해야 할까

MSA는 무조건 더 좋은 구조가 아니라, 팀 규모가 커지고 기능 단위로 독립 배포·확장이 자주 필요해질 때 그 복잡도를 감수할 가치가 생기는 선택이에요. 이 강의에서 계속 다룬 도서 관리 API처럼 작은 규모의 프로젝트라면 모놀리식으로 시작해서 필요할 때 서비스를 점진적으로 분리해나가는 방식이 실무에서도 흔히 권장되는 접근이다. "작게 시작해서 필요할 때 나눈다"는 원칙을 기억해두면 좋다.

✔ 22장 핵심 요약
  • 모놀리식은 하나의 배포 단위로 모든 기능을 담고, MSA는 기능별로 독립 배포·독립 DB를 갖는 서비스로 나눈다.
  • MSA는 독립 배포·독립 확장·장애 격리라는 장점이 있지만, 운영 복잡도 증가와 분산 트랜잭션 같은 새로운 어려움이 따른다.
  • 서비스 간 통신은 즉시 응답이 필요하면 동기 REST 호출을, 결합도를 낮추고 싶으면 비동기 메시지 큐를 선택한다.
  • API Gateway는 여러 서비스 앞의 단일 진입점으로 라우팅, 공통 인증, 로드밸런싱 등을 담당한다.
