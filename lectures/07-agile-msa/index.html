1. Agile 개요와 필요성

Waterfall vs Agile · Agile이 적합한 상황 · Agile 선언문과 12원칙 · 조직 도입 프로세스

💡
쉽게 말하면: Waterfall은 "설계도를 완벽히 그린 뒤 한 번에 짓는" 방식이고, Agile은 "작게 지어보고, 써보고, 고쳐가며 짓는" 방식이에요. 요구사항이 자주 바뀌고 시장 반응을 빨리 확인해야 하는 프로젝트일수록 Agile이 유리해요. 이번 장은 두 방법론의 차이와, 조직이 실제로 Agile을 어떻게 도입하는지를 정리합니다.

1) Waterfall과 Agile — 순차적 vs 반복적

Waterfall(폭포수 모델)은 요구분석 → 설계 → 구현 → 테스트 → 배포 단계를 순서대로, 앞 단계가 끝나야 다음 단계로 넘어가는 방식이에요. 반면 Agile은 이 전체 사이클을 1~4주짜리 짧은 주기(Iteration/Sprint)로 잘게 쪼개, 매 주기마다 "동작하는 결과물"을 반복해서 내놓아요.

구분WaterfallAgile
진행 방식순차적(단계별로 한 번씩)반복적(짧은 주기를 여러 번 순환)
요구사항초기에 완전히 확정한다고 가정변할 수 있음을 전제로 매 주기마다 재확인
고객 피드백프로젝트 막바지(배포 직전)에 확인매 Sprint 종료 시점마다 확인
산출물단계별 문서(요구정의서, 설계서 등)동작하는 소프트웨어(Increment)
위험 대응후반부에 문제 발견 시 수정 비용이 큼매 주기마다 조기에 문제를 발견·수정

2) Agile 선언문의 핵심 가치

2001년 발표된 Agile 소프트웨어 개발 선언문(Agile Manifesto)은 4가지 핵심 가치를 제시해요. "왼쪽 것도 가치 있지만, 오른쪽 것을 더 중요하게 여긴다"는 상대적 우선순위 표현이라는 점이 포인트예요.

  • 공정과 도구보다 개인과 상호작용(Individuals and interactions)을
  • 포괄적인 문서보다 동작하는 소프트웨어(Working software)를
  • 계약 협상보다 고객과의 협력(Customer collaboration)을
  • 계획을 따르기보다 변화에 대응하기(Responding to change)를
🔑 "문서를 아예 안 쓴다"는 뜻이 아니에요. 문서 자체보다 "실제로 동작하는 결과물로 가치를 증명하는 것"에 더 무게를 둔다는 의미입니다.

3) Agile이 적합한 상황

모든 프로젝트에 Agile이 정답은 아니에요. 아래처럼 불확실성이 크고, 빠른 검증이 필요한 프로젝트일수록 Agile의 효과가 커요.

✔ Agile이 특히 유리한 상황
  • 요구사항이 초기에 명확히 확정되지 않고, 시장·사용자 반응에 따라 계속 바뀔 것으로 예상될 때
  • 신규 서비스처럼 "무엇을 만들어야 성공할지" 자체가 불확실할 때(가설 검증이 필요)
  • 경쟁이 치열해 빠른 출시와 잦은 개선 주기가 중요한 도메인일 때
  • 고객·이해관계자와 자주 소통하며 방향을 조율할 수 있는 환경일 때

반대로 요구사항이 법·규제로 이미 고정되어 있거나(예: 항공기 제어 소프트웨어), 초기에 전체 범위를 정확히 계약해야 하는 프로젝트라면 Waterfall식 접근이 더 안전할 수 있어요.

4) 조직의 Agile 도입 프로세스 개요

조직이 처음부터 전사적으로 Agile을 도입하는 경우는 드물어요. 보통 아래처럼 단계적으로 확산시켜요.

① 현황 진단(현재 개발 프로세스·조직 문화 파악) → ② 파일럿 팀 선정 → ③ Sprint 0(환경 세팅·백로그 초안 작성) → ④ 실제 Sprint 실행·반복 → ⑤ 회고 기반 정착·확산
한 팀에서 검증한 뒤 성공 사례를 조직 전체로 확산하는 것이 일반적인 흐름
  • 현황 진단 — 기존 개발 방식의 병목(느린 피드백, 잦은 재작업 등)을 파악하고 Agile 도입 목표를 명확히 한다.
  • 파일럿 팀 선정 — 조직 전체가 아니라 소규모 팀 하나를 먼저 선정해 시범 적용하고 학습한다.
  • Sprint 0 — 본격적인 기능 개발에 앞서 팀 구성, 개발 환경 세팅, 초기 Product Backlog 작성 등 준비 작업을 수행하는 짧은 준비 기간.
  • 실행 — Sprint를 반복하며 실제로 동작하는 결과물을 지속적으로 산출한다.
  • 정착 — Retrospective에서 얻은 개선점을 반영하며 팀의 프로세스를 다듬고, 성공 경험을 다른 팀으로 확산한다.
🔎 심화 — Agile은 "방법론"이지 "특정 프레임워크"가 아니다

흔히 Agile=Scrum으로 오해하기 쉬운데, Scrum은 Agile 가치를 구현하는 여러 프레임워크 중 하나예요. Kanban, XP(Extreme Programming) 등도 Agile 가치를 따르는 다른 프레임워크입니다. 이 강의에서는 실무에서 가장 널리 쓰이는 Scrum을 중심으로 다뤄요.

5) 왜 AI 서비스 개발에 특히 Agile이 잘 맞는가

전통적인 소프트웨어(제조·금융 시스템 등)는 업무 규칙이 이미 명확하고 안정적이라 요구사항을 초기에 확정하기 쉬워요. 반면 AI 서비스는 출발점 자체가 다르다는 점을 짚어볼게요.

구분전통적 개발AI 서비스 개발
요구사항명확하고 변경이 적음모델 성능·사용자 반응에 따라 계속 바뀜
개발 방식전체 범위를 먼저 설계(Waterfall과 궁합이 좋음)최소 핵심 기능(MVP)부터 만들어 검증 후 확장
데이터이미 정련된 업무 데이터를 활용데이터 자체가 "업무를 수행한 결과물" — 실제로 서비스를 돌려봐야 쌓인다
🔑 AI 서비스는 "무엇이 사용자에게 가치가 있는지"를 미리 100% 확정하기 어렵기 때문에, 작게 나눠(Sprint) 자주 검증하는 Agile 방식이 특히 유리해요. 그리고 이 "빠르고 잦은 변경"을 기술적으로 뒷받침하는 것이 다음 장부터 다룰 MSA입니다 — Agile이 "어떻게 일할 것인가"의 방법론이라면, MSA는 "그 일하는 방식이 가능하도록 뒷받침하는 기술 구조"라고 볼 수 있어요.

  • "우리의 본질은 데이터센터 운영이 아니라 고객에게 최고의 콘텐츠 경험을 주는 것"이라는 핵심 역량 재정의 후, 인프라 운영은 클라우드에 맡기고 자사는 서비스 고도화에 집중했어요.
  • 이후 대규모 장애를 계기로 단일 시스템을 수백 개의 마이크로서비스로 점진적으로 분할했고, 이는 "비즈니스 방향(스트리밍 확장)에 기술 구조(MSA)를 맞춘" 사례로 자주 인용돼요 — 장애 대응이 목적이 아니라, 비즈니스 가치 실현을 위해 분할했더니 결과적으로 장애에도 강해진 것이라는 순서로 이해하는 게 중요해요.
✔ 1장 핵심 요약

  • Agile 선언문은 문서보다 동작하는 결과물, 계획보다 변화 대응을 더 중시한다.
  • 요구사항 변동성이 크고 빠른 피드백이 중요한 프로젝트일수록 Agile이 유리하다.
  • 조직 도입은 보통 현황진단 → 파일럿팀 → Sprint 0 → 실행 → 정착의 단계적 흐름을 따른다.

2. Scrum 핵심 요소

3가지 역할(PO·SM·개발팀) · 5가지 이벤트(Sprint·Planning·Daily·Review·Retro) · 3가지 산출물(Backlog·Increment)

💡
쉽게 말하면: Scrum은 "누가(역할) 언제(이벤트) 무엇을 만드는가(산출물)"를 정의한 뼈대예요. 역할 3개, 이벤트 5개, 산출물 3개 — 이 "3-5-3" 구조만 기억하면 Scrum의 큰 그림이 잡혀요.

1) 3가지 역할(Roles)

역할책임
Product Owner(PO)제품의 가치를 극대화할 책임자. Product Backlog를 관리하고 "무엇을, 어떤 순서로" 만들지 우선순위를 결정한다.
Scrum Master(SM)팀이 Scrum 프로세스를 잘 지키도록 돕는 퍼실리테이터. 장애물(Impediment)을 제거하고 팀을 보호하는 역할이지, 팀의 관리자가 아니다.
Development Team(개발팀)실제로 Increment를 만드는 사람들. 특정 역할(백엔드/프론트/QA)로 나뉘어도 결과에 대해서는 팀 전체가 공동 책임을 진다(Cross-functional).
🔑 Scrum Master는 "팀장"이 아니에요. 지시하는 사람이 아니라, 팀이 스스로 일할 수 있도록 방해 요소를 치워주는 역할에 가깝습니다.

2) 5가지 이벤트(Events)

Scrum의 모든 활동은 Sprint라는 하나의 컨테이너 이벤트 안에서 일어나요. Sprint는 보통 1~4주(팀에 따라 2주가 흔함)의 고정된 기간이고, 그 안에 나머지 4개 이벤트가 순서대로 포함돼요.

Sprint(전체 기간) 시작 시 → Sprint Planning → (기간 중 매일) Daily Scrum → 종료 시 → Sprint Review → Sprint Retrospective
하나의 Sprint 안에 Planning·Daily·Review·Retro 4개 이벤트가 모두 포함된다
  • Sprint Planning — 이번 Sprint에서 무엇을(What), 어떻게(How) 만들지 계획하는 회의. Product Backlog에서 항목을 골라 Sprint Backlog를 구성한다.
  • Daily Scrum — 매일 15분 내외로 진행하는 짧은 동기화 미팅. "어제 한 일 / 오늘 할 일 / 장애물"을 공유해 계획 대비 진행 상황을 점검한다.
  • Sprint Review — Sprint 종료 시점에 완성된 Increment를 이해관계자에게 시연하고 피드백을 받는 자리.
  • Sprint Retrospective — 이번 Sprint에서 "팀의 일하는 방식" 자체를 되돌아보고 다음 Sprint에서 개선할 점을 찾는 회고.
⚠️ Daily Scrum은 "상태 보고" 자리가 아니다

Scrum Master나 PO에게 진행 상황을 보고하는 자리로 오해하기 쉬운데, 본래 목적은 개발팀 스스로가 오늘 할 일을 조율하기 위한 자리예요. 보고 회의처럼 운영되면 팀원들이 형식적으로만 참여하게 되기 쉽습니다.

3) 3가지 산출물(Artifacts)

산출물설명
Product Backlog제품에 필요한 모든 작업(기능·개선·버그 수정 등)을 우선순위 순으로 정렬한 전체 목록. PO가 관리하며, 끝없이 진화하는 살아있는 문서다.
Sprint Backlog이번 Sprint에서 완료하기로 약속한 Product Backlog 항목 + 이를 완료하기 위한 실행 계획. 개발팀이 소유한다.
IncrementSprint 종료 시점까지 완성된, 이전 Increment들과 통합되어 실제로 동작 가능한 결과물. "Done"의 정의를 만족해야 한다.

4) 역할·이벤트·산출물의 관계

세 요소는 서로 맞물려 돌아가요. PO가 Product Backlog의 우선순위를 정하면 → Sprint Planning에서 개발팀이 그중 일부를 골라 Sprint Backlog로 만들고 → Daily Scrum으로 매일 진행을 조율하며 → Sprint Review에서 Increment를 검증받고 → Retrospective로 다음 Sprint의 일하는 방식을 개선해요.

✔ 2장 핵심 요약
  • Scrum은 "3(역할) - 5(이벤트) - 3(산출물)" 구조로 이루어진다.
  • PO=우선순위 결정, SM=프로세스 퍼실리테이터, 개발팀=Increment 제작 및 공동 책임.
  • Sprint라는 큰 이벤트 안에 Planning·Daily·Review·Retro가 순서대로 포함된다.
  • Product Backlog(전체) → Sprint Backlog(이번 주기) → Increment(결과물) 순으로 구체화된다.

쉽게 말하면: User Story는 "누가, 무엇을, 왜 원하는가"를 한 문장으로 요약한 요구사항 표현 방식이에요. Product Backlog는 이런 User Story들을 우선순위대로 쌓아놓은 To-Do 목록이고요. 이번 장은 좋은 User Story를 쓰는 기준(INVEST)과, Backlog를 계속 다듬어가는 과정(Grooming)을 정리해요.

1) User Story 작성 형식

User Story는 기능 명세서처럼 세세하게 쓰지 않아요. 대신 사용자 관점에서 "왜 필요한지"가 드러나도록 짧은 문장으로 표현해요. 가장 널리 쓰이는 형식은 다음과 같아요.

User Story 기본 템플릿
As a <역할/사용자>,
I want <하고 싶은 행동>,
so that <그것을 원하는 이유/얻는 가치>.
예시 — 티켓 예매 플랫폼
As a 회원,
I want 관심있는 공연을 찜(위시리스트)해두고 싶다,
so that 예매 오픈 시간에 놓치지 않고 빠르게 예매할 수 있다.

As a 비회원 방문자,
I want 회원가입 없이도 공연 목록과 상세 정보를 볼 수 있어야 한다,
so that 가입 여부를 결정하기 전에 서비스를 먼저 둘러볼 수 있다.

User Story만으로는 세부 조건이 부족할 수 있어, 보통 인수 조건(Acceptance Criteria)을 함께 덧붙여 "이 조건을 만족하면 완료"라는 기준을 명확히 해요.

2) INVEST 원칙 — 좋은 User Story의 조건

모든 User Story가 똑같이 좋은 건 아니에요. Bill Wake가 제안한 INVEST 원칙은 좋은 User Story가 갖춰야 할 6가지 특성의 앞글자를 딴 것이에요.

글자의미설명
IIndependent(독립적)다른 Story에 대한 의존성이 적어 순서에 상관없이 개발 가능해야 한다.
NNegotiable(협상 가능)세부 구현은 고정된 계약이 아니라, 팀과 대화를 통해 조율될 여지가 있어야 한다.
VValuable(가치 있음)사용자나 고객에게 실제 가치를 전달해야 한다("내부 리팩토링"만으로는 Story가 되기 어렵다).
EEstimable(추정 가능)팀이 대략적인 작업량을 가늠할 수 있을 만큼 충분히 이해 가능해야 한다.
SSmall(작음)한 Sprint 안에 충분히 끝낼 수 있는 크기로 작아야 한다.
TTestable(테스트 가능)"완료됐는지 아닌지"를 명확히 검증할 수 있는 기준이 있어야 한다.
⚠️ Story가 너무 크면(Epic) 쪼개야 한다

"결제 시스템을 만든다"처럼 범위가 큰 요구사항은 하나의 Sprint에 담기 어려워요. 이런 큰 단위를 Epic이라고 부르고, 실제 Sprint에 담기 전에 "신용카드 결제", "간편결제 연동", "결제 실패 처리"처럼 더 작은 User Story로 쪼개는 작업이 필요해요.

3) Backlog Grooming(Refinement)

Product Backlog는 한 번 작성하고 끝나는 문서가 아니라 계속 다듬어지는 살아있는 목록이에요. 이 다듬는 활동을 Backlog Grooming(또는 Refinement)이라고 불러요. 보통 다음 Sprint Planning 전에 미리 진행해요.

  • 정리(Ordering) — 우선순위를 다시 검토하고 필요 없어진 항목은 제거한다.
  • 구체화(Elaboration) — 상위 우선순위 항목일수록 인수 조건을 더 상세하게 다듬는다("점점 자세해지는 것"이 자연스럽다).
  • 추정(Estimation) — Story Point 등으로 작업량을 가늠해, Sprint Planning 때 얼마나 담을 수 있을지 판단할 근거를 만든다.
  • 분할(Splitting) — 너무 큰 항목(Epic)을 실행 가능한 크기의 Story로 나눈다.

4) Definition of Done(DoD)

"완료됐다"는 기준이 팀원마다 다르면 Sprint Review에서 갈등이 생겨요. Definition of Done은 팀 전체가 합의한, "이 조건을 만족해야 진짜로 완료된 것"이라는 공통 체크리스트예요.

Definition of Done 예시 — BookingService "예매하기" 기능
- 기능 코드가 작성되고 로컬에서 정상 동작 확인됨
- 단위 테스트 작성 및 통과
- 코드 리뷰 승인 완료
- 개발/스테이징 환경에 배포 완료
- Product Owner의 인수 조건(Acceptance Criteria) 검토 통과
🔑 DoD는 Sprint마다 새로 정하는 게 아니라, 팀 차원에서 한 번 합의하면 여러 Sprint에 걸쳐 일관되게 적용돼요. User Story 하나하나의 "인수 조건"과는 별개로, 모든 Story에 공통 적용되는 최소 기준이라고 보면 됩니다.
✔ 3장 핵심 요약
  • User Story는 "As a ~, I want ~, so that ~" 형식으로 사용자 가치를 중심에 두고 작성한다.
  • INVEST(독립적·협상가능·가치있음·추정가능·작음·테스트가능)는 좋은 Story의 기준이다.
  • Backlog Grooming은 정리·구체화·추정·분할을 통해 Backlog를 계속 다듬는 활동이다.
  • Definition of Done은 팀이 합의한 "완료"의 공통 기준으로, Story별 인수 조건과는 별개다.

2) Product Backlog 작성 예시

이 기능들을 User Story로 풀어 Product Backlog에 쌓으면 아래와 같은 모습이 돼요. 우선순위가 높은 항목일수록 더 구체적으로 다듬어져 있는 것에 주목하세요.

Product Backlog (우선순위 순, 일부 발췌)
#1  As a 신규 방문자, I want 이메일로 회원가입하고 싶다,
    so that 서비스를 이용할 수 있는 계정을 만들 수 있다.        [3 pt]
#2  As a 회원, I want 이메일/비밀번호로 로그인하고 싶다,
    so that 내 예매 내역에 접근할 수 있다.                      [2 pt]
#3  As a 방문자, I want 공연 목록을 검색·조회하고 싶다,
    so that 원하는 공연을 빠르게 찾을 수 있다.                  [5 pt]
#4  As a 회원, I want 원하는 좌석을 선택해 예매하고 싶다,
    so that 보고 싶은 공연을 확보할 수 있다.                    [8 pt]
#5  As a 회원, I want 신용카드로 결제하고 싶다,
    so that 예매를 확정할 수 있다.                              [8 pt]
#6  As a 회원, I want 예매 완료 시 알림을 받고 싶다,
    so that 예매가 성공했는지 바로 확인할 수 있다.               [3 pt]
#7  As a 회원, I want 예매를 취소하고 환불받고 싶다,
    so that 일정이 바뀌어도 손해를 최소화할 수 있다.             [5 pt]

3) Sprint 단위로 쪼개기 — 점진적 확장

이 모든 기능을 한 번에 만들지 않아요. 가장 가치 있고 기반이 되는 기능부터 순서대로 Sprint에 담아, 매 Sprint마다 "실제로 써볼 수 있는" 결과물을 늘려가요.

Sprint 1: 회원가입·로그인 → Sprint 2: 공연 검색·조회 → Sprint 3: 좌석 선택·예매 → Sprint 4: 결제 연동 → Sprint 5: 알림·취소/환불
기반 기능(인증) → 탐색(조회) → 핵심 가치(예매) → 부가 기능(결제·알림) 순으로 점진적으로 확장
  • Sprint 1 — 회원가입/로그인만으로도 "계정을 만들고 로그인할 수 있는" 최소 동작 결과물이 나온다.
  • Sprint 2 — 공연 검색/조회 기능이 추가되어, 로그인 후 무엇을 예매할지 탐색할 수 있게 된다.
  • Sprint 3 — 좌석 선택과 예매 요청이 추가되어 비로소 서비스의 핵심 가치(예매)가 동작한다.
  • Sprint 4~5 — 결제, 알림, 취소/환불처럼 예매 흐름을 완성하는 기능들이 순차적으로 붙는다.
🔑 이렇게 쌓아가면 Sprint 3만 끝나도 "회원가입 → 검색 → 예매"까지의 핵심 흐름을 이해관계자에게 시연할 수 있어요. 전체 기능이 다 끝날 때까지 기다리지 않고도 조기에 피드백을 받을 수 있다는 게 Agile의 핵심 이점이에요.

4) Story Point와 Planning Poker

Backlog 항목 옆에 붙은 [3 pt], [8 pt] 같은 숫자가 Story Point예요. 시간(시간/일)이 아니라 상대적인 작업 규모(복잡도·불확실성·작업량)를 나타내는 단위로, 보통 피보나치 수열(1, 2, 3, 5, 8, 13...)을 사용해요. 숫자가 클수록 "더 복잡하거나 불확실하다"는 뜻이에요.

Planning Poker는 팀원들이 각자 Story Point를 카드로 동시에 제시해 추정하는 기법이에요. 한 사람의 의견에 휩쓸리지 않고, 팀 전체의 의견 차이를 드러내 논의를 유도하는 것이 목적이에요.

✔ Planning Poker 진행 순서
  • ① PO가 하나의 User Story를 소개하고 팀이 질문/논의한다.
  • ② 각 팀원이 동시에 자신이 생각하는 Story Point 카드를 낸다(눈치 보지 않도록 동시 공개가 핵심).
  • ③ 의견이 크게 갈리면(예: 누구는 2, 누구는 13) 왜 그렇게 생각했는지 짧게 논의한다.
  • ④ 합의된 값으로 수렴할 때까지 반복하고, 최종 Story Point를 기록한다.

이렇게 추정한 Story Point가 쌓이면, 팀은 "한 Sprint에 평균적으로 몇 포인트를 처리할 수 있는지(Velocity)"를 알게 되고, 이를 기반으로 다음 Sprint에 얼마나 많은 Backlog 항목을 담을 수 있을지 계획할 수 있어요.

✔ 4장 핵심 요약
  • Product Backlog는 User Story 단위로 우선순위대로 쌓이며, 상위 항목일수록 더 구체적이다.
  • Sprint는 기반 기능(인증) → 탐색(조회) → 핵심 가치(예매) → 부가 기능(결제·알림) 순으로 점진적으로 기능을 확장해간다.
  • Story Point는 절대적 시간이 아닌 상대적 작업 규모를 나타내며, Planning Poker로 팀 합의를 통해 추정한다.
  • 누적된 Story Point(Velocity)는 다음 Sprint의 계획 수립 근거가 된다.

5. MSA 개요 — 모놀리식과의 차이

Monolithic vs Microservice · 서비스 분리 기준(Bounded Context) · MSA의 장단점

💡
쉽게 말하면: 모놀리식은 모든 기능을 하나의 애플리케이션으로 묶어 한 번에 배포하는 방식이고, MSA(Microservice Architecture)는 기능별로 독립된 작은 서비스로 쪼개 각자 따로 배포·확장하는 방식이에요. Day 1에서 배운 "작게 나눠 반복한다"는 Agile 정신이, 이제 소프트웨어의 물리적 구조 자체에도 적용된다고 볼 수 있어요.

1) 모놀리식(Monolithic) 아키텍처

하나의 애플리케이션 안에 회원, 공연 정보, 예매, 결제, 알림 기능이 모두 한 코드베이스, 한 프로세스로 들어있는 구조예요. 하나의 WAR/JAR로 빌드되고, 하나의 서버(또는 서버군)에 배포돼요.

  • 장점 — 초기 개발이 단순하고, 기능 간 호출이 인메모리 함수 호출이라 빠르며, 배포·모니터링 대상이 하나뿐이라 운영이 단순하다.
  • 단점 — 코드베이스가 커질수록 기능 간 결합도가 높아져 "결제 로직 하나 고쳤는데 알림 기능이 깨지는" 부작용이 생기기 쉽고, 서비스 전체를 매번 다시 빌드·배포해야 하며, 특정 기능(예: 예매)만 트래픽이 몰려도 애플리케이션 전체를 스케일 아웃해야 한다.

2) MSA(Microservice Architecture)

MSA는 하나의 큰 애플리케이션을 독립적으로 배포 가능한 여러 개의 작은 서비스로 쪼개는 아키텍처예요. 각 서비스는 자신만의 코드베이스, 자신만의 데이터베이스를 갖고, 네트워크를 통해(주로 REST API나 메시징으로) 서로 통신해요.

티켓 예매 플랫폼을 MSA로 분리한 예
MemberService       - 회원가입, 로그인, 인증
EventService        - 공연/행사 정보 조회, 검색
BookingService       - 좌석 선택, 예매 처리
PaymentService       - 결제 처리, 환불
NotificationService  - 예매/결제 알림 발송

→ 각 서비스는 독립된 코드베이스 + 독립된 DB + 독립된 배포 파이프라인을 가진다

3) 서비스 분리 기준

"어디를 기준으로 서비스를 쪼갤 것인가"는 MSA 설계에서 가장 어려운 질문이에요. 단순히 화면 단위나 팀 조직도로 나누기보다, 아래 기준을 함께 고려해요.

기준설명
Bounded Context도메인 주도 설계(DDD)에서 나온 개념으로, "같은 용어가 같은 의미로 통하는 범위"를 하나의 경계로 삼는다. 예를 들어 "회원"이라는 개념은 MemberService 안에서는 인증 정보 중심이지만, BookingService 관점에서는 단순히 "예매자 ID" 정도로만 필요하다.
데이터 소유권하나의 데이터(예: 예매 정보)는 하나의 서비스만 직접 쓰기 권한을 가져야 한다. 다른 서비스는 API를 통해서만 접근한다.
변경 빈도·이유함께 자주 바뀌는 기능은 한 서비스로, 서로 다른 이유·주기로 바뀌는 기능은 분리한다(결제 정책 변경과 알림 문구 변경은 서로 독립적으로 배포될 수 있어야 한다).
🔑 Bounded Context는 Day 1에서 배운 SRP(단일 책임 원칙)의 서비스 버전이라고 볼 수 있어요 — "하나의 서비스는 하나의 명확한 책임(도메인)만 가져야 한다"는 관점이 그대로 이어져요.

4) MSA의 장단점

✔ MSA의 장점
  • 서비스별 독립 배포 — BookingService만 수정해도 다른 서비스는 재배포할 필요가 없다.
  • 서비스별 독립 확장 — 예매 오픈 시간처럼 트래픽이 몰리는 BookingService만 인스턴스를 늘릴 수 있다.
  • 기술 스택 자유도 — 서비스마다 필요에 맞는 언어·DB를 선택할 수 있다(Polyglot).
  • 장애 격리 — NotificationService에 장애가 나도 예매·결제 자체는 계속 동작하도록 설계할 수 있다.
⚠️ MSA가 "공짜"는 아니다 — 늘어나는 운영 복잡도

서비스가 여러 개로 나뉘면 배포·모니터링 대상도 그만큼 늘어나고, 서비스 간 네트워크 호출이 늘면서 지연·장애 지점도 늘어나요. 특히 여러 서비스에 걸친 데이터 정합성을 하나의 DB 트랜잭션으로 묶을 수 없다는 분산 트랜잭션 문제가 대표적인 난제예요(예: 예매 확정과 결제 처리가 서로 다른 서비스·DB에 걸쳐 있을 때 "둘 다 성공" 또는 "둘 다 실패"를 보장하기 어렵다). 이 강의 뒷부분(API Gateway, Kafka)은 이런 복잡도를 다루기 위한 도구들이에요.

5) 서비스 분리의 진짜 기준 — "데이터가 나뉠 수 있는가"

MSA가 항상 정답은 아니에요. 판단의 핵심은 "업무를 얼마나 잘게 쪼갤 수 있는가"가 아니라, "그 업무를 뒷받침하는 데이터가 실제로 분리될 수 있는가"예요.

⚠️ 데이터가 촘촘히 얽혀 있으면 억지로 나누면 안 된다

예를 들어 인사 시스템에서 "승진 처리"와 "직급별 인센티브 지급"을 서로 다른 서비스로 분리한다고 해볼게요. 두 기능이 같은 트랜잭션 안에서 같은 데이터(직원의 직급 정보)를 동시에 다뤄야 한다면, 서비스를 나누는 순간 "승진은 반영됐는데 인센티브 계산은 옛 직급 기준으로 됐다"처럼 데이터 정합성이 깨지는 트랜잭션 충돌이 발생하기 쉬워요. 제조 공정 관리(MES)처럼 여러 단계가 촘촘한 선후관계로 얽힌 업무 영역에 MSA를 무리하게 적용했다가 어려움을 겪는 사례도 이런 이유 때문이에요. 반대로 전자상거래·추천·개인화처럼 사용자 접점에서 개별적으로 가치를 주는 서비스는 데이터도 자연스럽게 분리되는 경우가 많아 MSA와 궁합이 좋아요.

🔑 정리하면: 데이터가 서로 다른 트랜잭션·소유권으로 분리될 수 있어야 서비스도 분리할 수 있어요. 데이터가 강하게 결합되어 있는데 서비스만 억지로 쪼개면, 서비스 경계를 넘나드는 분산 트랜잭션 문제(바로 위에서 다룬 문제)가 오히려 더 심해질 뿐이에요.

6) 언제 MSA를 고려할까

모든 프로젝트가 처음부터 MSA로 시작할 필요는 없어요. 팀 규모가 작고 도메인이 아직 불확실한 초기 단계에는 모놀리식으로 빠르게 시작하고, 서비스가 커지고 팀이 나뉘며 배포 주기가 달라질 필요가 생길 때 MSA로 전환하는 것이 실무에서 흔한 흐름이에요.

✔ 5장 핵심 요약
  • 모놀리식은 단일 배포 단위, MSA는 독립 배포 가능한 여러 서비스 단위로 구성된다.
  • 서비스 분리는 Bounded Context, 데이터 소유권, 변경 빈도를 기준으로 판단한다.
  • MSA는 독립 배포·확장·장애 격리라는 장점이 있지만, 운영 복잡도와 분산 트랜잭션이라는 비용을 동반한다.

6. 인증서버와 API Gateway

JWT 기반 인증 흐름 · API Gateway의 역할 · OAuth2 개념 소개

💡
쉽게 말하면: 서비스가 5개로 쪼개졌다고 클라이언트가 5개 주소를 다 알아야 하는 건 비효율적이에요. API Gateway가 모든 요청을 받는 단일 창구 역할을 하고, 그 뒤에서 인증서버가 발급한 JWT로 "이 요청이 누구의 것인지"를 검증해요.

1) JWT 기반 인증 흐름

JWT(JSON Web Token)는 사용자 정보(클레임)를 담아 서명한 토큰이에요. 로그인에 성공하면 서버가 JWT를 발급하고, 이후 클라이언트는 매 요청마다 이 토큰을 헤더에 실어 보내요. 서버는 DB를 매번 조회하지 않고도 토큰의 서명만 검증하면 "누구의 요청인지"를 알 수 있어요.

① 로그인(ID/PW) → MemberService가 검증 → ② JWT 발급(Access Token) → ③ 클라이언트가 이후 요청마다 Authorization: Bearer <token> 헤더로 전송 → ④ 서버는 토큰 서명 검증만으로 사용자 식별
세션을 서버에 저장하지 않고(Stateless), 토큰 자체에 정보를 담아 검증하는 방식
JWT 구조 — Header.Payload.Signature
// Header (토큰 타입, 서명 알고리즘)
{ "alg": "HS256", "typ": "JWT" }

// Payload (클레임 — 사용자 정보, 만료 시간 등)
{ "sub": "member-1024", "role": "USER", "exp": 1755504000 }

// Signature (Header+Payload를 비밀키로 서명 — 위변조 검증용)
HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secretKey)
🔑 JWT는 암호화된 게 아니라 서명(Signature)된 거예요. Payload는 누구나 디코딩해서 내용을 볼 수 있으니, 비밀번호 같은 민감 정보를 Payload에 담으면 안 돼요. 서명 덕분에 "내용이 변조되지 않았다"는 것만 보장됩니다.

2) API Gateway의 역할

클라이언트가 MemberService, EventService, BookingService 등 5개 서비스의 주소를 각각 알고 직접 호출한다면 관리가 매우 번거로워져요. API Gateway는 모든 외부 요청이 거치는 단일 진입점(Single Entry Point) 역할을 해요.

역할설명
단일 진입점클라이언트는 Gateway 주소 하나만 알면 되고, 내부 서비스 구조를 몰라도 된다.
라우팅(Routing)요청 경로(예: /bookings/**)에 따라 알맞은 내부 서비스(BookingService)로 전달한다.
인증 위임JWT 검증을 Gateway 단에서 먼저 수행해, 내부 서비스들이 각자 인증 로직을 중복 구현하지 않아도 되게 한다.
Rate Limiting사용자·IP별 요청 횟수를 제한해 특정 클라이언트가 시스템을 과도하게 사용하는 것을 막는다.
API Gateway 라우팅 설정 예시 (application.yml)
spring:
  cloud:
    gateway:
      routes:
        - id: booking-service
          uri: lb://BOOKING-SERVICE
          predicates:
            - Path=/api/bookings/**
        - id: event-service
          uri: lb://EVENT-SERVICE
          predicates:
            - Path=/api/events/**

3) OAuth2 개념 간단 소개

OAuth2는 "제3자 애플리케이션이 사용자를 대신해 리소스에 접근할 수 있는 권한을 위임받는" 표준 프로토콜이에요. 예를 들어 "카카오 계정으로 로그인"이 대표적인 사례예요 — 우리 서비스가 사용자의 카카오 비밀번호를 직접 알 필요 없이, 카카오가 발급한 토큰으로 사용자를 대신 인증할 수 있어요.

  • Resource Owner — 리소스의 주인, 즉 사용자.
  • Client — 사용자를 대신해 리소스에 접근하려는 애플리케이션(예: 티켓 예매 플랫폼).
  • Authorization Server — 인증을 수행하고 토큰을 발급하는 서버.
  • Resource Server — 실제 보호된 데이터를 갖고 있는 서버.
🔎 심화 — JWT와 OAuth2는 다른 층위의 개념이다

JWT는 "정보를 담아 서명하는 토큰의 형식(포맷)"이고, OAuth2는 "권한을 위임하는 절차(프로토콜)"예요. OAuth2 흐름에서 발급되는 Access Token이 JWT 형식으로 구현되는 경우가 많을 뿐, 둘은 서로 다른 목적을 가진 개념이라는 점을 구분해두면 좋아요.

🔑 API Gateway와 헷갈리기 쉬운 개념으로 BFF(Backend For Frontend)가 있어요. API Gateway가 "라우팅·인증 위임"처럼 범용적인 중개 역할에 집중한다면, BFF는 프론트엔드(웹/모바일 등) 화면별로 필요한 형태에 맞춰 여러 서비스의 응답을 조합·가공해서 돌려주는 전용 계층이에요. 예를 들어 예매 상세 화면 하나를 그리려면 EventService·BookingService·MemberService 응답을 모아야 하는데, 이 조합 로직을 프론트가 직접 하지 않고 BFF가 대신 처리해주는 식이에요.
✔ 6장 핵심 요약
  • JWT는 서명된 토큰으로, 서버가 세션을 저장하지 않고도(Stateless) 요청자를 식별할 수 있게 한다.
  • API Gateway는 단일 진입점 역할을 하며 라우팅, 인증 위임, Rate Limiting을 담당한다.
  • OAuth2는 제3자에게 접근 권한을 위임하는 표준 프로토콜로, JWT는 그 안에서 토큰 형식으로 자주 쓰인다.

7. 서비스 디스커버리(Eureka)

동적 인스턴스 환경의 문제 · Eureka Server/Client · Client-side Load Balancing

💡
쉽게 말하면: MSA 환경에서는 서비스 인스턴스가 트래픽에 따라 늘었다 줄었다 해요. IP 주소를 하드코딩해두면 인스턴스가 바뀔 때마다 설정을 고쳐야 하죠. 서비스 디스커버리는 "지금 이 서비스가 어디에 몇 개 떠 있는지"를 자동으로 등록·조회할 수 있게 해주는 장치예요.

1) 왜 서비스 디스커버리가 필요한가

전통적인 방식이라면 BookingService가 EventService를 호출할 때 http://192.168.0.12:8082처럼 고정된 주소를 코드에 박아둘 거예요. 그런데 MSA·클라우드 환경에서는 다음과 같은 문제가 생겨요.

  • 트래픽에 따라 EventService 인스턴스가 2개에서 5개로 늘어나거나 줄어들 수 있다(오토 스케일링).
  • 배포할 때마다 컨테이너가 재시작되며 IP가 바뀔 수 있다.
  • 이런 상황마다 호출하는 쪽 코드를 일일이 고치는 건 현실적이지 않다.

이 문제를 해결하기 위해 "서비스 이름"으로만 호출하고, 실제 IP·포트는 별도의 레지스트리가 관리하도록 하는 것이 서비스 디스커버리예요.

2) Eureka Server와 Eureka Client

구성 요소역할
Eureka Server(레지스트리)모든 서비스 인스턴스의 "이름 → 현재 위치(IP·포트) 목록"을 저장하고 관리하는 중앙 저장소.
Eureka Client(등록·조회)각 서비스(MemberService, EventService 등)에 포함되는 라이브러리. 시작 시 자신의 위치를 Eureka Server에 등록하고, 주기적으로 살아있음을 알리며(Heartbeat), 다른 서비스를 호출할 때는 Eureka Server에 위치를 물어본다.
① BookingService 인스턴스 기동 → ② Eureka Server에 자신을 등록(이름: BOOKING-SERVICE, IP:Port) → ③ 주기적 Heartbeat로 생존 신고 → ④ EventService 호출 필요 시 Eureka Server에 "EVENT-SERVICE 인스턴스 목록" 조회 → ⑤ 받은 목록 중 하나를 골라 직접 호출
레지스트리는 "주소록"만 관리하고, 실제 요청은 클라이언트가 직접 목적지로 보낸다
🔑 인스턴스가 갑자기 죽으면(Heartbeat가 끊기면) Eureka Server는 일정 시간 후 해당 인스턴스를 목록에서 제거해요. 그래서 호출하는 쪽은 항상 "현재 살아있는" 인스턴스 목록만 받아볼 수 있어요.

3) Client-side Load Balancing과의 관계

EventService가 인스턴스 3개로 떠 있다고 해볼게요. BookingService가 EventService를 호출할 때 Eureka Server는 "3개의 주소 목록"을 돌려줄 뿐, 그중 어떤 걸 쓸지는 호출하는 쪽(Client)이 스스로 결정해요. 이걸 Client-side Load Balancing이라고 해요.

  • 서버 앞단에 별도의 로드밸런서 장비를 두지 않고, 호출하는 서비스 내부의 라이브러리(Spring Cloud LoadBalancer 등)가 라운드로빈 같은 규칙으로 분산 호출한다.
  • Eureka(레지스트리) + Client-side Load Balancer 조합으로 "어디에 몇 개가 떠 있는지"와 "그중 뭘 호출할지"를 모두 클라이언트 쪽에서 동적으로 처리한다.
서비스 이름으로 호출하기 (의사 코드)
// IP:Port를 직접 쓰지 않고 Eureka에 등록된 서비스 이름(BOOKING-SERVICE 등)으로 호출
restTemplate.getForObject("http://EVENT-SERVICE/api/events/{id}", Event.class, eventId);
// 실제로는 Eureka에서 조회한 인스턴스 목록 중 하나로 자동 라우팅된다

4) API Gateway와 Eureka의 조합

앞 장에서 배운 API Gateway도 사실 내부적으로 Eureka를 함께 써요. Gateway가 lb://BOOKING-SERVICE처럼 서비스 이름으로 라우팅 규칙을 정의해두면, 실제 어떤 인스턴스로 보낼지는 Eureka에서 조회한 목록을 바탕으로 Gateway가 결정해요. 즉 Gateway는 "무엇을 어디로 보낼지 규칙"을, Eureka는 "그 대상이 실제로 지금 어디에 떠 있는지"를 책임진다고 정리할 수 있어요.

5) 상대 서비스가 응답하지 않을 때 — Circuit Breaker

서비스 디스커버리로 EventService의 위치를 잘 찾았더라도, 그 EventService 자체가 느려지거나 응답을 멈춘 상태라면 어떻게 될까요? BookingService가 이를 마냥 기다리면, 장애가 BookingService까지 전파(연쇄 장애)될 수 있어요. Circuit Breaker(회로 차단기)는 이런 상황에서 일정 시간 이상 실패가 반복되면 아예 호출 자체를 중단하고, 미리 정해둔 대체 응답(Fallback)을 즉시 돌려주는 패턴이에요.

🔑 예를 들어 추천 서비스가 응답하지 않으면 개인화 추천 대신 "인기 콘텐츠 목록" 같은 대체 결과를 보여주는 식이에요. 실패를 무한정 기다리지 않고 빠르게 포기(Fail Fast)한 뒤 대체 경로로 넘어감으로써, 한 서비스의 장애가 전체 시스템으로 번지는 것을 막아준다는 점에서 5장에서 배운 "장애 격리"를 실제로 구현하는 기술 중 하나예요.
✔ 7장 핵심 요약
  • 서비스 디스커버리는 동적으로 늘고 줄어드는 인스턴스 환경에서 "서비스가 어디 있는지"를 자동으로 추적하는 장치다.
  • Eureka Server는 레지스트리(주소록), Eureka Client는 각 서비스에 붙어 등록·Heartbeat·조회를 담당한다.
  • 조회한 인스턴스 목록 중 실제로 어디를 호출할지는 Client-side Load Balancing이 결정한다.

8. Kafka와 비동기 메시징

동기(REST) vs 비동기(메시지 큐) · Producer/Consumer/Topic/Partition · 이벤트 기반 통신

💡
쉽게 말하면: BookingService가 결제를 완료했다고 NotificationService에 REST로 직접 알리면, NotificationService가 잠깐이라도 느리거나 죽어있으면 결제 처리 자체가 지연·실패할 수 있어요. Kafka를 쓰면 "결제 완료" 이벤트를 큐에 던져놓기만 하면 되고, NotificationService는 자기 페이스대로 가져가 처리해요 — 두 서비스가 느슨하게 연결(Decoupling)돼요.

1) 동기(REST) 호출 vs 비동기(메시지 큐) 통신

구분동기(REST 직접 호출)비동기(메시지 큐)
호출 방식요청 후 응답이 올 때까지 대기메시지를 큐에 발행하고 즉시 다음 작업 진행
결합도호출자가 상대 서비스의 주소·가용성에 직접 의존발행자는 누가 구독하는지 몰라도 됨(느슨한 결합)
장애 전파상대 서비스가 느리거나 죽으면 호출자도 영향받음구독자가 잠시 죽어도 메시지는 큐에 남아있다가 복구 후 처리 가능
적합한 경우즉시 응답 결과가 필요한 요청(예: 로그인)결과를 바로 알 필요 없는 후속 처리(예: 알림 발송, 통계 집계)

2) Kafka 기본 개념 — Producer / Consumer / Topic / Partition

  • Producer — 메시지(이벤트)를 생성해 Kafka로 보내는 쪽. 예: 결제가 완료되면 PaymentService가 Producer가 된다.
  • Consumer — Kafka에서 메시지를 가져가 처리하는 쪽. 예: NotificationService가 Consumer가 되어 결제 완료 메시지를 받아 알림을 보낸다.
  • Topic — 메시지가 쌓이는 논리적인 채널(카테고리). 예: payment-completed라는 Topic에 결제 완료 이벤트들이 쌓인다.
  • Partition — 하나의 Topic을 여러 조각으로 나눈 것. 여러 Consumer가 나눠서 병렬로 처리할 수 있게 해 처리량(Throughput)을 높인다.
PaymentService(Producer) → Topic: payment-completed(여러 Partition으로 분산) → NotificationService(Consumer)가 구독해 메시지 소비
Producer와 Consumer는 서로를 직접 모르고, Topic을 매개로만 연결된다
결제 완료 이벤트 발행 (의사 코드 — Producer)
// PaymentService: 결제 성공 시 이벤트를 Kafka Topic에 발행
PaymentCompletedEvent event = new PaymentCompletedEvent(bookingId, memberId, amount);
kafkaTemplate.send("payment-completed", event);
// 여기서 PaymentService는 NotificationService의 존재 자체를 몰라도 된다
결제 완료 이벤트 구독 (의사 코드 — Consumer)
// NotificationService: "payment-completed" Topic을 구독해 알림 발송
@KafkaListener(topics = "payment-completed", groupId = "notification-group")
public void handlePaymentCompleted(PaymentCompletedEvent event) {
    notificationSender.sendPushNotification(event.getMemberId(), "결제가 완료되었습니다.");
}

3) MSA에서 이벤트 기반 통신이 유리한 이유

서비스 개수가 늘어날수록 서비스 간 REST 호출을 촘촘하게 엮으면 장애가 연쇄적으로 퍼지기 쉬워요(하나가 느려지면 그걸 호출하는 서비스도 줄줄이 느려짐). Kafka 기반 이벤트 통신은 이런 문제를 줄여줘요.

✔ 이벤트 기반 통신의 이점
  • 느슨한 결합 — PaymentService는 "결제 완료" 이벤트만 발행하면 끝. 이후 어떤 서비스가 이 이벤트를 구독해서 무엇을 하는지 알 필요가 없다(나중에 "쿠폰 지급 서비스"가 새로 추가돼 같은 이벤트를 구독해도 PaymentService 코드는 변경할 필요가 없다).
  • 장애 격리 — NotificationService가 일시적으로 다운되어도, 메시지는 Kafka에 그대로 쌓여있다가 복구되면 이어서 처리된다(REST 직접 호출이었다면 그 시점 요청은 실패했을 것).
  • 처리량 분산 — Partition을 여러 Consumer 인스턴스가 나눠 처리해, 트래픽이 몰려도 병렬로 소화할 수 있다.
⚠️ 모든 통신을 비동기로 바꿔야 하는 건 아니다

"로그인 성공 여부"처럼 클라이언트가 즉시 결과를 알아야 하는 요청까지 메시지 큐로 처리하면 오히려 응답이 지연되고 설계가 복잡해져요. 즉각적인 응답이 필요한 요청-응답형 흐름은 REST(동기)로, 결과를 바로 알 필요 없는 후속 처리(알림, 로그 적재, 통계 집계 등)는 Kafka(비동기)로 — 상황에 맞게 섞어 쓰는 것이 실무 패턴이에요.

✔ 8장 핵심 요약
  • 동기(REST)는 즉시 응답이 필요한 요청에, 비동기(Kafka)는 후속 처리와 느슨한 결합이 필요한 곳에 적합하다.
  • Producer가 Topic에 메시지를 발행하면, 구독 중인 Consumer가 이를 가져가 처리한다. Partition은 병렬 처리 단위다.
  • MSA에서 이벤트 기반 통신은 서비스 간 결합도를 낮추고 장애 전파를 줄이는 데 유리하다.

9. 컨테이너와 Docker 핵심 개념

컨테이너 vs VM · 이미지 vs 컨테이너 · Dockerfile 기본 명령어 · 포트 매핑

💡
쉽게 말하면: MSA로 서비스를 5개로 쪼갰다면, 배포도 5개를 각자 독립적으로 할 수 있어야 의미가 있어요. 컨테이너는 "이 서비스가 어떤 환경에서든 항상 똑같이 동작하도록 포장하는 상자"예요. Docker는 이 상자를 만들고 실행하는 가장 널리 쓰이는 도구고요.

1) 컨테이너와 VM의 차이 — 격리 방식

둘 다 "격리된 실행 환경을 여러 개 만든다"는 목적은 같지만, 격리하는 방식이 달라요.

구분가상머신(VM)컨테이너
격리 단위하이퍼바이저 위에서 Guest OS 전체를 각각 구동호스트 OS의 커널을 공유하며 프로세스 단위로 격리
무게무겁다(OS 하나만큼의 용량, 수 GB)가볍다(필요한 라이브러리만, 수십~수백 MB)
기동 속도OS 부팅 시간 필요(수십 초~분 단위)프로세스 시작 수준(수 초 이내)
이식성하이퍼바이저 환경에 따라 다를 수 있음"이미지"만 있으면 어디서든 동일하게 실행
🔑 컨테이너는 VM보다 가볍고 빠르기 때문에, 서비스 하나당 인스턴스를 여러 개 띄우고 내리는 MSA·오토스케일링 환경에 훨씬 잘 맞아요.

2) Docker 이미지 vs 컨테이너

  • 이미지(Image) — 애플리케이션 실행에 필요한 모든 것(코드, 런타임, 라이브러리, 설정)을 담은 불변(immutable)의 설계도/템플릿. 한 번 빌드하면 내용이 바뀌지 않는다.
  • 컨테이너(Container) — 이미지를 실제로 실행한 인스턴스. 같은 이미지로 컨테이너를 여러 개 띄울 수 있고(예: BookingService 이미지로 3개 컨테이너 실행), 각 컨테이너는 독립된 프로세스로 동작한다.

비유하자면 이미지는 "클래스", 컨테이너는 "그 클래스로 만든 객체(인스턴스)"에 가까워요 — 같은 설계도로 여러 개의 독립된 실체를 찍어낼 수 있다는 점에서요.

3) Dockerfile 기본 명령어

Dockerfile은 이미지를 어떻게 빌드할지 정의하는 스크립트예요. BookingService를 컨테이너 이미지로 만드는 예시를 볼게요.

Dockerfile — BookingService 예시
FROM eclipse-temurin:17-jre
WORKDIR /app
COPY build/libs/booking-service-0.0.1.jar app.jar
RUN mkdir -p /app/logs
EXPOSE 8082
CMD ["java", "-jar", "app.jar"]
명령어역할
FROM베이스 이미지를 지정한다(여기서는 자바 17 실행 환경).
WORKDIR컨테이너 내부에서 이후 명령어들이 실행될 작업 디렉터리를 지정한다.
COPY호스트(빌드 환경)의 파일을 컨테이너 이미지 안으로 복사한다.
RUN이미지를 빌드하는 동안 실행할 명령(패키지 설치, 디렉터리 생성 등).
EXPOSE컨테이너가 사용할 포트를 문서화한다(실제로 열어주는 것은 아니고, 정보 제공 목적에 가깝다).
CMD컨테이너가 시작될 때 실행할 기본 명령(여기서는 애플리케이션 실행).

4) 포트 매핑 — 호스트와 컨테이너

컨테이너는 자기만의 격리된 네트워크 환경을 가져요. 컨테이너 내부의 8082 포트로 애플리케이션이 떠 있어도, 호스트(외부)에서 바로 접근할 수는 없어요. 포트 매핑으로 "호스트의 어떤 포트를 컨테이너의 어떤 포트로 연결할지"를 지정해야 해요.

docker run — 포트 매핑 예시
docker run -d -p 8082:8082 --name booking-service booking-service:1.0
#              호스트포트:컨테이너포트

docker run -d -p 8082:8082 -p 8083:8082 --name booking-service-2 booking-service:1.0
# 같은 이미지를 다른 호스트 포트로 여러 인스턴스 실행 가능
🔑 -p 8082:8082에서 앞이 호스트(내 컴퓨터/서버) 포트, 뒤가 컨테이너 내부 포트예요. 같은 이미지로 컨테이너를 여러 개 띄울 때는 호스트 포트가 겹치지 않게 각각 다르게 지정해야 해요.

5) MSA 환경에서 서비스별로 컨테이너를 분리하는 이유

MemberService, EventService, BookingService, PaymentService, NotificationService를 각각 별도의 컨테이너로 배포하면 다음과 같은 이점이 생겨요.

✔ 서비스별 컨테이너 분리의 이점
  • 독립 배포 — BookingService 이미지만 새로 빌드·재배포하면 되고, 다른 서비스는 그대로 유지된다.
  • 독립 확장 — 트래픽이 몰리는 BookingService 컨테이너만 인스턴스 수를 늘릴 수 있다.
  • 일관된 실행 환경 — "내 컴퓨터에서는 됐는데 서버에서는 안 된다"는 문제를 이미지가 실행 환경(라이브러리 버전 등)까지 통째로 포함해 해결한다.
  • 오케스트레이션과의 연계 — Kubernetes 같은 컨테이너 오케스트레이션 도구가 각 서비스 컨테이너를 독립적으로 관리(재시작, 스케일링, 롤링 업데이트)할 수 있게 되는 기반이 된다.

6) 여러 컨테이너 함께 실행하기 — Docker Compose vs Kubernetes

서비스가 5개면 컨테이너도 5개(+API Gateway, Eureka 등 인프라까지 더하면 그 이상)를 매번 개별 명령으로 띄우는 건 번거로워요. 여러 컨테이너를 한 번에 정의하고 실행하는 도구가 필요한데, 규모에 따라 흔히 두 가지를 씁니다.

구분Docker ComposeKubernetes
적합 규모서비스 수십 개 이하, 개발·소규모 운영서비스가 매우 많고 운영 요구가 높은 대규모 환경
설정 방식YAML 파일 하나로 여러 컨테이너·네트워크 정의Pod/Deployment/Service 등 더 세분화된 리소스로 정의
자동 복구·스케일링제한적(직접 재시작 정책 정도)컨테이너가 죽어도 자동으로 다시 띄우고, 트래픽에 따라 자동 확장
학습·운영 부담가볍다강력하지만 개념이 많고 자원 소비도 크다
🔑 Kubernetes는 "웬만해선 안 죽는" 자동 복구·확장 능력이 강력한 대신, 그만큼 배우고 운영하는 데 드는 비용(양날의 검)도 커요. 이 강의의 실습 규모(서비스 5개 안팎)에서는 Docker Compose로도 충분히 MSA를 구현·실습할 수 있고, 서비스 수가 크게 늘어나 사람이 일일이 관리하기 어려워지는 시점(대략 수십~백 개 단위)부터 Kubernetes 도입을 본격적으로 고려하는 것이 실무에서 흔한 흐름이에요.
✔ 9장 핵심 요약
  • 컨테이너는 OS 커널을 공유하는 가벼운 격리 방식으로, VM보다 빠르고 이식성이 높다.
  • 이미지는 불변의 실행 템플릿, 컨테이너는 이미지를 실제로 실행한 인스턴스다.
  • Dockerfile은 FROM/WORKDIR/COPY/RUN/EXPOSE/CMD 등의 명령어로 이미지 빌드 과정을 정의한다.

10. 요구사항 분석과 도메인 분리

주체별 기능 요구사항 정리 · 서비스 경계 도출 · 응집도는 높게, 결합도는 낮게

💡
쉽게 말하면: 실습의 첫 단계는 화면이나 코드가 아니라 "누가 무엇을 원하는가"를 정리하는 것부터예요. Day 1에서 배운 "주체 관점에서 요구사항을 바라보는" User Story식 접근을, 이번엔 MSA의 서비스 경계(Bounded Context)를 도출하는 데 그대로 활용해봐요.

1) 주체별 기능 요구사항 정리

티켓 예매 플랫폼에는 크게 세 종류의 주체가 있어요. 각 주체가 "무엇을 하고 싶은지"를 먼저 표로 정리하면, 뒤에서 서비스 경계를 나눌 때 기준이 흐트러지지 않아요.

주체주요 기능 요구사항
회원(예매자)회원가입/로그인, 공연·행사 검색 및 상세 조회, 좌석 선택 및 예매, 결제, 예매 내역 조회/취소, 예매·결제 알림 수신
주최자(운영자)공연·행사 등록/수정, 좌석·회차 관리, 예매 현황 통계 조회, 정산 내역 확인
시스템(관리자·운영)회원 계정 관리, 결제 이상거래 모니터링, 알림 발송 이력 관리, 서비스 상태(인스턴스 등록·헬스체크) 모니터링
🔑 이 표는 Day 1의 User Story("As a 회원, I want ~") 형식을 요약해놓은 것과 같아요. 다만 여기서는 문장 하나하나가 아니라, 주체 단위로 기능을 묶어 전체 그림을 먼저 조망하는 게 목적이에요.

2) 기능을 서비스 경계로 묶기

위 요구사항들을 Day 2에서 배운 서비스 분리 기준(Bounded Context·데이터 소유권·변경 빈도)에 따라 묶으면, 이미 여러 장에서 예시로 등장했던 5개 서비스로 자연스럽게 정리돼요.

서비스명담당 기능핵심 데이터포트
MemberService회원가입, 로그인/인증(JWT 발급), 회원정보 관리, 권한(USER/HOST/ADMIN) 관리member, credential8081
EventService공연·행사 등록/수정, 검색/상세 조회, 좌석·회차 관리event, seat, schedule8082
BookingService좌석 선택, 예매 요청/확정, 예매 내역 조회, 예매 취소booking8083
PaymentService결제 처리, 환불, 주최자 정산 집계payment, settlement8084
NotificationService예매/결제/취소 알림 발송, 발송 이력 관리notification_log8085
🔑 표에는 없지만 이 5개 서비스를 감싸는 인프라 요소로 API Gateway(8080)와 Eureka Server(8761)가 별도로 필요해요 — 이 둘은 특정 도메인 기능이 아니라 서비스들을 연결·중개하는 공통 인프라라서 "서비스 경계" 표에는 포함하지 않아요. 자세한 배치는 11장에서 다룰게요.

3) 도메인 분리 시 고려사항 — 응집도는 높게, 결합도는 낮게

  • 응집도(Cohesion)를 높게 — 서로 관련 깊은 기능은 한 서비스에 모은다. "좌석 선택 → 예매 요청 → 예매 확정 → 예매 취소"는 모두 하나의 예매 라이프사이클이므로 BookingService 하나로 묶어야, 이 흐름을 처리하는 로직이 여러 서비스에 흩어지지 않는다.
  • 결합도(Coupling)를 낮게 — 서비스 간에는 최소한으로만 의존한다. 예를 들어 EventService가 "공연별 예매 현황 통계"를 보여주려면 BookingService의 데이터가 필요하지만, EventService가 BookingService의 DB를 직접 조회하는 대신 API 호출이나 이벤트 구독을 통해서만 데이터를 받아와야 한다(12장에서 이어서 다룸).
⚠️ 주체가 다르다고 서비스를 무조건 더 쪼갤 필요는 없다

회원과 주최자는 서로 다른 이해관계자이지만, "인증된 계정"이라는 개념 자체는 공유돼요. 그래서 주최자 전용 서비스를 따로 만들기보다, MemberService 안에서 role(USER/HOST/ADMIN) 값으로 구분하는 편이 응집도 측면에서 더 합리적이에요. 서비스를 지나치게 잘게 쪼개면(Over-decomposition) 오히려 서비스 간 호출과 운영 부담만 늘어나요 — MSA의 목적은 "잘게 쪼개는 것" 자체가 아니라 "독립적으로 변경·배포 가능한 경계를 찾는 것"이라는 점을 기억해야 해요.

4) 서비스 경계 검증 — "이 기능은 어디에 속하는가?" 질문해보기

경계가 애매한 기능이 나오면 아래 질문을 스스로 던져보면 판단에 도움이 돼요.

  • 이 데이터를 누가 직접 쓰기(write) 권한을 가져야 하는가? — "정산 내역"은 결제 결과를 계산해야 하므로 PaymentService가 소유한다.
  • 이 기능이 다른 기능과 같은 이유로, 같은 주기로 바뀌는가? — "알림 문구 변경"은 결제 로직 변경과 무관하게 일어나므로 NotificationService로 분리한다.
  • 이 기능이 없어도 다른 서비스가 핵심 흐름을 유지할 수 있는가? — 알림 발송이 잠깐 실패해도 예매·결제 자체는 성립해야 하므로, NotificationService는 장애 격리가 되도록 분리한다.
✔ 10장 핵심 요약
  • 주체별(회원/주최자/시스템)로 기능 요구사항을 먼저 정리한 뒤, Bounded Context·데이터 소유권 기준으로 서비스 경계를 도출한다.
  • 티켓 예매 플랫폼은 MemberService(8081)·EventService(8082)·BookingService(8083)·PaymentService(8084)·NotificationService(8085) 5개 서비스로 분리한다.
  • 도메인 분리는 응집도는 높게(관련 기능은 한 서비스로), 결합도는 낮게(서비스 간 직접 의존 최소화)라는 원칙을 따른다.
  • 주체가 다르다고 무조건 서비스를 쪼개는 것이 아니라, 권한(role) 구분처럼 한 서비스 안에서 처리하는 편이 나은 경우도 있다.

11. 인프라 구성과 서비스간 통신 설계

6~9장 요소를 조합한 인프라 배치 · 동기(REST) vs 비동기(Kafka) 판단 기준 · 통신 흐름도

💡
쉽게 말하면: 10장에서 나눈 5개 서비스를 실제로 동작하게 하려면, 앞서 배운 API Gateway·Eureka·Kafka·서비스별 DB를 어떻게 배치할지 정해야 해요. 그리고 서비스끼리 대화할 때 "바로 답을 들어야 하는가(동기)" 아니면 "결과를 나중에 알아도 되는가(비동기)"를 매 호출마다 판단해야 해요.

1) 서비스를 감싸는 인프라 요소 조합

인프라 요소역할이 프로젝트에서의 적용
API Gateway단일 진입점, 라우팅, JWT 인증 위임클라이언트는 Gateway(8080) 하나만 알면 되고, /api/bookings/** 같은 경로로 각 서비스에 라우팅한다.
Eureka Server서비스 인스턴스 등록·조회MemberService~NotificationService 5개 서비스가 모두 Eureka Client로 등록되고(8761), Gateway와 서비스 간 호출 모두 서비스 이름으로 이뤄진다.
Kafka비동기 이벤트 브로커결제 완료 → 알림 발송, 예매 취소 → 환불 트리거 등 "즉시 응답이 필요 없는" 흐름을 담당한다.
서비스별 DBDatabase per Service5개 서비스가 각자 독립된 DB 스키마를 소유한다(자세한 내용은 12장).
인증(JWT 발급)로그인 시 토큰 발급MemberService가 로그인 요청을 검증하고 JWT를 발급하며, 이후 모든 요청은 Gateway 단에서 이 토큰을 검증한다.
🔑 6~9장에서 배운 요소들은 각자 독립된 지식이 아니라, 실제로는 이렇게 하나의 시스템 안에서 함께 동작해요. Gateway는 Eureka에서 조회한 위치로 라우팅하고, 서비스 간 무거운 동기 호출은 최소화하며 Kafka로 흐름을 분산시키는 식이에요.

2) 동기(REST) vs 비동기(Kafka) — 무엇을 기준으로 판단할까

"이 호출은 동기로 할까, 비동기로 할까?"는 매번 새로 판단해야 해요. 핵심 기준은 "호출한 쪽이 결과를 즉시 알아야 하는가"예요.

상황판단이유
예매 확정 시 결제 서비스 호출동기(REST)결제 성공/실패를 즉시 알아야 "예매가 확정되었습니다"라는 응답을 사용자에게 바로 줄 수 있다.
결제 완료 후 알림 발송비동기(Kafka)알림이 몇 초 늦게 가도 예매·결제 흐름에는 영향이 없다. NotificationService 장애가 결제 처리를 막아서는 안 된다.
좌석 선택 시 실시간 잔여 좌석 확인동기(REST)사용자가 좌석을 고르는 순간 가장 최신 상태를 즉시 반영해야 중복 예매를 막을 수 있다.
예매 취소 시 정산·통계 데이터 갱신비동기(Kafka)정산 집계는 실시간일 필요가 없고, 여러 서비스(PaymentService, EventService)가 같은 취소 이벤트를 각자의 속도로 구독해 처리하면 된다.

3) 통신 흐름도 예시 — 예매 확정 플로우

① 클라이언트 → API Gateway(8080, JWT 검증) → ② BookingService(8083) 예매 요청 접수 → ③ BookingService → PaymentService(8084) 동기 REST 호출(결제 처리) → ④ 결제 성공 시 BookingService가 예매 상태를 CONFIRMED로 확정, 클라이언트에 즉시 응답 → ⑤ PaymentService가 Kafka Topic payment-completed에 이벤트 발행(비동기) → ⑥ NotificationService가 구독해 알림 발송
③~④는 사용자가 결과를 기다려야 하므로 동기, ⑤~⑥은 후속 처리이므로 비동기로 분리한다
예매 확정 API 호출 흐름 (의사 코드 — BookingService)
// BookingService: 예매 확정 처리
@PostMapping("/api/bookings/{bookingId}/confirm")
public BookingResponse confirmBooking(@PathVariable Long bookingId) {
    Booking booking = bookingRepository.findById(bookingId);

    // 결제는 즉시 결과를 알아야 하므로 동기(REST) 호출
    PaymentResult result = paymentClient.requestPayment(booking.getMemberId(), booking.getAmount());

    if (result.isSuccess()) {
        booking.confirm();
        // 알림은 즉시 필요 없으므로 여기서 직접 호출하지 않는다
        // → PaymentService가 결제 완료 이벤트를 Kafka에 발행하면 NotificationService가 알아서 구독한다
        return BookingResponse.confirmed(booking);
    }
    booking.fail();
    return BookingResponse.failed(booking);
}

4) 서비스 간 직접 호출을 줄이는 설계 습관

  • BookingService가 EventService의 공연 상세정보를 매번 REST로 조회하기보다, 예매 시점에 필요한 최소 정보(공연명, 좌석번호 등)만 예매 스냅샷으로 BookingService에 함께 저장해두면 EventService 장애 시에도 예매 내역 조회가 가능하다.
  • 여러 서비스가 같은 이벤트에 반응해야 한다면(예: 예매 취소 → 알림 발송 + 정산 조정 + 좌석 재오픈), Kafka Topic 하나에 각 서비스가 독립적으로 구독하게 하면 새로운 구독 서비스가 추가돼도 발행자(BookingService) 코드는 변경할 필요가 없다.
🔎 심화 — 동기 호출이 늘어나면 장애가 전파된다

BookingService → PaymentService처럼 동기 호출 체인이 길어질수록, 체인 끝에 있는 서비스 하나가 느려지면 그 앞의 모든 서비스가 함께 느려지는 장애 전파(Cascading Failure) 위험이 커져요. 그래서 실무에서는 꼭 필요한 곳(즉시 응답이 필요한 흐름)에만 동기 호출을 남기고, 나머지는 최대한 이벤트 기반으로 분리하는 것이 MSA 통신 설계의 기본 원칙이에요.

✔ 11장 핵심 요약
  • API Gateway·Eureka·Kafka·서비스별 DB는 각 서비스를 감싸는 공통 인프라로서 함께 배치된다.
  • 동기(REST)는 "즉시 응답이 필요한 흐름"에, 비동기(Kafka)는 "결과를 바로 몰라도 되는 후속 처리"에 사용한다.
  • 예매 확정은 결제까지는 동기, 결제 완료 이후의 알림·정산은 비동기로 분리하는 것이 대표적인 설계 패턴이다.
  • 동기 호출 체인이 길어질수록 장애 전파 위험이 커지므로, 꼭 필요한 곳에만 동기 호출을 남긴다.

쉽게 말하면: MSA에서는 서비스마다 자기만의 DB를 가져요. 그래서 BookingService의 booking 테이블에는 EventService·MemberService의 데이터를 직접 join할 수 없고, ID 참조값만 저장해요. 그리고 서비스끼리는 DB가 아니라 REST API로만 대화하기 때문에, API 명세를 먼저 표로 정리해두는 게 실습의 핵심이에요.

1) Database per Service 원칙과 그 이유

MSA에서는 "서비스마다 자신만의 데이터베이스(또는 최소한 스키마)를 소유한다"는 원칙을 따라요. 다른 서비스의 테이블을 직접 조회하거나 join하지 않고, 반드시 그 서비스의 API를 거쳐야 해요.

  • 느슨한 결합 — EventService가 event 테이블 스키마를 바꿔도, 직접 그 테이블을 참조하는 다른 서비스가 없으므로 EventService만 재배포하면 된다.
  • 독립 배포·확장 — BookingService의 트래픽이 몰려 DB 인스턴스를 늘려야 할 때, 다른 서비스의 DB에는 영향을 주지 않는다.
  • 기술 선택의 자유(Polyglot Persistence) — 정형 데이터가 많은 PaymentService는 RDB를, 발송 이력처럼 쓰기가 잦은 NotificationService는 필요하면 다른 저장소를 선택할 수 있다.
🔑 대신 대가도 있어요 — 5장에서 배운 것처럼, 여러 서비스에 걸친 데이터 정합성을 하나의 DB 트랜잭션으로 묶을 수 없다는 분산 트랜잭션 문제가 여기서 그대로 이어져요. 이 실습에서는 "예매 확정 + 결제 처리"를 동기 호출로 순서대로 묶어(11장) 이 문제를 단순화했지만, 실무에서는 Saga 패턴 같은 더 정교한 기법을 쓰기도 해요.

2) 서비스별 간단 ERD 예시

핵심은 "내 서비스가 소유하지 않은 데이터는 ID 참조값만 저장한다"는 것이에요. BookingService의 booking 테이블을 예로 볼게요.

BookingService — booking 테이블
CREATE TABLE booking (
    booking_id   BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_id     BIGINT NOT NULL,   -- EventService 소유 데이터의 참조값(ID)만 저장, FK 아님
    member_id    BIGINT NOT NULL,   -- MemberService 소유 데이터의 참조값(ID)만 저장, FK 아님
    seat_no      VARCHAR(10) NOT NULL,
    status       VARCHAR(20) NOT NULL,  -- REQUESTED, CONFIRMED, CANCELLED
    event_name_snapshot VARCHAR(100),   -- 조회 편의를 위한 스냅샷(EventService 장애 시에도 표시 가능)
    created_at   TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);
PaymentService — payment 테이블
CREATE TABLE payment (
    payment_id   BIGINT PRIMARY KEY AUTO_INCREMENT,
    booking_id   BIGINT NOT NULL,   -- BookingService 소유 데이터의 참조값(ID)만 저장
    amount       INT NOT NULL,
    status       VARCHAR(20) NOT NULL,  -- SUCCESS, FAILED, REFUNDED
    paid_at      TIMESTAMP
);
⚠️ event_id, member_id에 FK(외래키)를 걸 수 없다

일반적인 단일 DB 설계라면 event_id에 REFERENCES event(event_id) 같은 외래키 제약을 걸겠지만, MSA에서는 event 테이블이 아예 다른 DB(EventService 소유)에 있어서 물리적으로 FK를 걸 수 없어요. 데이터 정합성은 DB 제약이 아니라 애플리케이션 로직과 이벤트(Kafka)로 보장해야 한다는 점이 모놀리식 DB 설계와 가장 크게 다른 부분이에요.

3) REST API 명세 설계 예시

서비스끼리는 DB가 아니라 API로 대화하므로, 각 서비스가 무엇을 주고받는지 표로 먼저 정리해두면 다른 서비스를 만드는 팀(또는 미래의 나)이 구현 세부사항을 몰라도 연동할 수 있어요.

서비스메서드/엔드포인트설명요청응답
MemberServicePOST /api/members/login로그인, JWT 발급{email, password}{accessToken, memberId}
EventServiceGET /api/events/{eventId}공연 상세 조회경로변수 eventId{eventId, name, seats[]}
BookingServicePOST /api/bookings예매 요청 생성{eventId, memberId, seatNo}{bookingId, status}
BookingServicePOST /api/bookings/{bookingId}/confirm예매 확정(결제 연동)경로변수 bookingId{bookingId, status: CONFIRMED}
PaymentServicePOST /api/payments결제 처리(BookingService가 동기 호출){bookingId, memberId, amount}{paymentId, success}
🔑 이렇게 표로 먼저 정리하는 걸 API 설계 실무에서는 API 명세(Spec)라고 불러요. 실제 프로젝트에서는 이 표를 Swagger/OpenAPI 문서로 옮겨 자동으로 문서화·검증하는 경우가 많지만, 실습에서는 표 형태만으로도 "이 서비스가 무엇을 주고받는지"를 명확히 하는 데 충분해요.

4) API 명세를 먼저 정하면 좋은 점

  • 서비스를 병렬로 개발할 수 있다 — BookingService 개발자가 PaymentService의 구현이 끝나지 않아도, API 명세만 합의되면 Mock 응답으로 먼저 개발을 진행할 수 있다.
  • 서비스 경계가 다시 한번 검증된다 — API 명세를 쓰다 보면 "이 데이터는 어느 서비스가 응답해야 하지?"라는 질문에 부딪히게 되는데, 이 과정에서 10장의 서비스 경계가 실제로 타당한지 재점검하게 된다.
✔ 12장 핵심 요약
  • MSA는 Database per Service 원칙에 따라 서비스마다 독립된 DB를 가지며, 다른 서비스 데이터는 API로만 접근한다.
  • 서비스 간 참조는 FK가 아니라 ID 값(참조값)만 저장하고, 필요하면 조회 편의를 위한 스냅샷을 함께 둔다.
  • REST API 명세는 엔드포인트·메서드·요청/응답 형식을 표로 정리해, 서비스 간 계약(Contract)을 먼저 합의하는 데 쓰인다.
  • API 명세를 먼저 정하면 병렬 개발이 가능해지고, 서비스 경계의 타당성도 함께 검증된다.

13. 컨테이너 구성·배포와 Sprint Review

서비스별 Docker 이미지 빌드 · docker-compose로 5개 서비스 통합 실행 · 실습에 적용하는 Sprint Review·Retrospective

💡
쉽게 말하면: 10~12장에서 설계만 하던 5개 서비스를 이제 실제로 띄워볼 차례예요. 9장에서 배운 Dockerfile로 서비스마다 이미지를 만들고, docker-compose로 5개 서비스 + DB + 메시지 브로커를 한 번에 실행해요. 그리고 이 실습 자체를 하나의 작은 Sprint로 보고, Day 1의 Scrum 이벤트(Review·Retrospective)로 마무리해봐요.

1) 서비스별 Docker 이미지 빌드

9장에서 배운 방식 그대로, 5개 서비스 각각에 Dockerfile을 두고 독립적으로 이미지를 빌드해요. 서비스마다 이미지가 분리되어 있어야 "BookingService만 새로 빌드·배포"가 가능해져요.

서비스별 이미지 빌드 명령 예시
docker build -t member-service:1.0       ./member-service
docker build -t event-service:1.0        ./event-service
docker build -t booking-service:1.0      ./booking-service
docker build -t payment-service:1.0      ./payment-service
docker build -t notification-service:1.0 ./notification-service

2) docker-compose.yml로 전체 시스템 한 번에 실행

docker run으로 컨테이너를 하나씩 띄우면 5개 서비스 + DB + 메시지 브로커까지 매번 순서를 챙겨 실행해야 해서 번거로워요. Docker Compose는 여러 컨테이너의 구성을 파일 하나로 정의하고, 한 번의 명령으로 전체를 기동·종료할 수 있게 해줘요.

docker-compose.yml — 티켓 예매 플랫폼 전체 구성
version: "3.8"
services:
  eureka-server:
    image: eureka-server:1.0
    ports:
      - "8761:8761"

  api-gateway:
    image: api-gateway:1.0
    ports:
      - "8080:8080"
    depends_on:
      - eureka-server

  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: rootpass
      MYSQL_DATABASE: ticketing
    ports:
      - "3306:3306"

  zookeeper:
    image: confluentinc/cp-zookeeper:7.5.0
    environment:
      ZOOKEEPER_CLIENT_PORT: 2181

  kafka:
    image: confluentinc/cp-kafka:7.5.0
    depends_on:
      - zookeeper
    environment:
      KAFKA_ZOOKEEPER_CONNECT: zookeeper:2181
      KAFKA_ADVERTISED_LISTENERS: PLAINTEXT://kafka:9092
    ports:
      - "9092:9092"

  member-service:
    image: member-service:1.0
    ports:
      - "8081:8081"
    depends_on:
      - eureka-server
      - mysql

  event-service:
    image: event-service:1.0
    ports:
      - "8082:8082"
    depends_on:
      - eureka-server
      - mysql

  booking-service:
    image: booking-service:1.0
    ports:
      - "8083:8083"
    depends_on:
      - eureka-server
      - mysql

  payment-service:
    image: payment-service:1.0
    ports:
      - "8084:8084"
    depends_on:
      - eureka-server
      - mysql
      - kafka

  notification-service:
    image: notification-service:1.0
    ports:
      - "8085:8085"
    depends_on:
      - eureka-server
      - kafka
🔑 depends_on은 컨테이너의 시작 순서만 보장할 뿐, 그 서비스가 "완전히 준비될 때까지" 기다려주지는 않아요. 예를 들어 MySQL 컨테이너가 뜨기 시작했어도 실제로 접속 가능해지기까지는 시간이 걸릴 수 있어서, 각 서비스에는 재시도(Retry) 로직이나 헬스체크를 함께 넣어주는 게 안전해요.
전체 시스템 기동 / 종료 명령
docker compose up -d      # 전체 서비스 백그라운드로 기동
docker compose ps         # 컨테이너 상태 확인
docker compose logs -f booking-service   # 특정 서비스 로그만 확인
docker compose down       # 전체 종료 및 컨테이너 제거

3) 실습 프로젝트에 적용하는 Sprint Review

Day 1에서 배운 Sprint Review는 "완성된 Increment를 이해관계자에게 시연하고 피드백을 받는 자리"였어요. 이 실습을 하나의 Sprint로 본다면, 아래와 같은 것들이 Increment이자 Sprint Review에서 보여줄 결과물이에요.

✔ Sprint Review에서 시연할 것
  • docker compose up 한 번으로 5개 서비스 + Gateway + Eureka + DB + Kafka가 모두 정상 기동되는지.
  • Eureka 대시보드(http://localhost:8761)에서 5개 서비스가 모두 등록되어 있는지.
  • Postman 등으로 "회원가입 → 로그인(JWT 발급) → 공연 검색 → 좌석 선택 → 예매 확정(결제 동기 호출) → 알림 발송(Kafka 비동기)"까지 이어지는 핵심 흐름이 실제로 동작하는지.
  • API Gateway를 통해서만 접근해도 각 서비스로 올바르게 라우팅되는지.

4) 실습 프로젝트에 적용하는 Sprint Retrospective

Retrospective는 "결과물"이 아니라 "일하는 방식"을 되돌아보는 자리였죠. 이 실습을 마치며 스스로에게(또는 팀과 함께) 던져볼 수 있는 회고 질문 예시예요.

  • 10장에서 서비스 경계를 정할 때, 처음 계획과 실제 구현 과정에서 바뀐 부분이 있었는가? 있었다면 왜 바뀌었는가?
  • 11장에서 동기/비동기를 판단한 기준이 실제로 구현해보니 맞았는가, 아니면 다시 바꾸고 싶은 부분이 있는가?
  • 12장의 API 명세를 먼저 정해두고 개발한 것이 실제로 도움이 되었는가?
  • 다음 Sprint(다음 실습)에서는 무엇을 다르게 해보고 싶은가?(예: 처음부터 API 명세를 Swagger로 관리해보기, Saga 패턴으로 분산 트랜잭션을 다뤄보기 등)
🎯 Day 1의 이론이 Day 3의 실습으로 완성되는 지점

Day 1에서 배운 Agile/Scrum은 "어떻게 일할 것인가"에 대한 답이었고, Day 2에서 배운 MSA 요소들은 "무엇으로 만들 것인가"에 대한 답이었어요. Day 3는 이 둘을 하나로 연결하는 자리예요 — 요구사항을 User Story처럼 정리하고(10장), Sprint를 계획하듯 서비스 간 통신과 인프라를 설계하고(11장), 계약을 맺듯 API 명세를 합의하고(12장), 마지막으로 Sprint Review·Retrospective로 결과를 점검하고 개선점을 찾는 것(13장)까지 — 이 전체 흐름 자체가 "Agile하게 MSA를 설계·구축한다"는 것이 실제로 어떤 모습인지를 보여줘요.

✔ 13장 핵심 요약
  • 서비스별로 Dockerfile을 두어 독립된 이미지를 빌드하고, docker-compose.yml로 5개 서비스 + DB + Kafka를 한 번에 정의·기동한다.
  • depends_on은 시작 순서만 보장하므로, 실제 준비 여부는 재시도·헬스체크로 보완해야 한다.
  • Sprint Review에서는 실제로 동작하는 예매 흐름 전체를 시연하고, Retrospective에서는 설계·구현 과정에서 배운 점과 다음에 개선할 점을 되돌아본다.
  • Day 1의 Agile/Scrum과 Day 2의 MSA 요소는 Day 3의 설계·구현·배포 실습을 통해 하나의 흐름으로 연결된다.
