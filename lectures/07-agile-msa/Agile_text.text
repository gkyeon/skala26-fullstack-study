## 2. 왜 Agile과 MSA를 함께 배우는가

### 2.1 전통적 소프트웨어 개발 vs AI 서비스 개발

| 구분 | 전통적 개발(제조·금융 등) | AI 서비스 개발 |
|---|---|---|
| 요구사항 | 명확하고 변경 거의 없음 | 모델 성능·사용자 반응에 따라 계속 변함 |
| 개발 방식 | 요구사항 분석 → 설계 → 구현 → 테스트 → 배포 (Waterfall) | 최소 핵심 기능(MVP)부터 만들고 검증 후 확장 |
| 데이터 | 이미 업무가 셋업되어 정련됨 | 시작점 자체가 "업무의 결과인 데이터" |

- **AI 서비스의 본질**: 데이터는 업무의 결과 → AI는 결국 "사람들의 업무에 어떤 가치를 줄 수 있는가"가 방향성
- 이 특성 때문에 요구사항을 한 번에 완벽히 정의할 수 없고, **작게 나눠(Sprint) 자주 검증**하는 Agile 방식이 잘 맞음
- MSA는 이 Agile 방식(빠르고 잦은 변경)을 **기술적으로 뒷받침하는 아키텍처**
  - Agile = 어떻게 일할 것인가(방법론)
  - MSA = 그 방식이 가능하게 하는 기술 구조

### 2.2 MSA가 항상 정답은 아니다

- **MSA에 안 맞는 경우**: 반도체 공정(수율), 금융 여신·수신처럼 데이터·업무가 촘촘하게 선후관계로 얽힌 영역
  - 예: 삼성전자가 반도체 비즈니스(지원)영역 MES에 MSA를 적용했다가 곤란을 겪은 사례
  - 예: 인사 테이블에서 '승진 처리'와 '직급별 인센티브 지급' 업무를 분리하면 트랜잭션 충돌 발생 → **업무가 분리될 수 있어야만 MSA로 나눌 수 있음**
- **MSA에 잘 맞는 경우**: 사용자 접점에서 개별적으로 가치를 주는 서비스 (전자상거래, 추천, 개인화 등)
- **핵심 기준**: "데이터를 어떻게 나눌 수 있는가"의 문제 — 데이터가 분리되지 않으면 서비스도 분리하면 안 됨 (분리 시 트랜잭션 격리 문제 발생)
- AI 서비스는 대부분 **기존 업무 시스템을 건드리지 않고 별도로 가치를 추가하는 방식**이라 MSA와 궁합이 좋음 (에이전틱 AI가 기존 플로우에 개입하지 않고 별도 동작하는 것도 같은 맥락)

### 2.3 사례 연구

**① FBI Virtual Case File (실패 사례)**
- 2001년 9·11 테러 이후, 노후 수사기록 시스템을 대체하기 위해 방대한 요구사항 명세서를 먼저 확정하고 통째로(모노리식) 개발
- 4년 이상 개발 → 완성 시점엔 현장 요구사항이 이미 바뀌어 무가치 → **약 1.7억 달러 손실, 시스템 폐기**
- 교훈: 현장 요구사항이 계속 바뀌는 영역에서 한 번에 큰 설계로 밀어붙이면 실패

**② Netflix (성공 사례)**
- 원래는 DVD/CD 우편 대여 회사 → 2007년 스트리밍으로 전환하며 트래픽 폭증(약 1000배) 예상
- **핵심 역량 재정의**: "우리의 본질은 데이터센터 운영이 아니라 고객에게 최고의 콘텐츠 경험을 주는 것" → 인프라는 AWS에 위임, 자사는 서비스 고도화·추천 알고리즘에 집중
- 2008년 DB 손상으로 전체 서비스 중단 장애 발생 → 이를 계기로 **700개 이상의 마이크로서비스**로 분할, 현재 일 API 호출 150억 건, 190개국 서비스
- **카오스 몽키(Chaos Monkey)**: 일부러 장애를 유발해도 전체가 죽지 않는지 검증하는 문화 → 분리된 만큼 장애 격리 가능
- 교훈: 비즈니스 전략(스트리밍 확장)과 기술 구조(MSA 분할)를 연결했기 때문에 성공. "장애가 나서 MSA를 했다"가 아니라 "비즈니스 가치 실현을 위해 분할했더니 장애에도 강해졌다"는 순서로 이해해야 함

**③ Spotify류 — 모듈러 모노리식(Modular Monolithic)**
- MSA로 과도하게 분할했다가, 서비스 간 호출·데이터 전달 비용이 너무 커져 다시 일부를 모듈 단위로 재통합한 사례
- MSA의 이점 vs 분할·통신 비용을 항상 저울질해야 함 — **무조건 잘게 쪼개는 것이 정답은 아님**
- 판단 기준 예: 팀 인원 5명 이하 + 기능 단순 + 배포를 팀 전체가 한 번에 해도 무방하면 굳이 분리할 필요 없음

## 3. Agile 핵심 개념

| 용어 | 설명 |
|---|---|
| **Sprint** | 업무 범위를 나눠 달려나가는 구간(럭비의 스크럼에서 유래). 통상 2주~3개월, AI 서비스는 보통 1개월 이내 |
| **Backlog** | 요구사항을 우선순위에 따라 누적해 놓은 목록. 사용자가 제시한 것뿐 아니라 "이러면 가치가 있을 것 같다"는 것도 포함 가능 |
| **Scrum** | 스프린트 안에서 매일(또는 스프린트 기간에 따라 주 단위) 진행 상황을 논의·협의하는 미팅/조직 |
| **Scrum Team 구성** | Product Owner(PO), Scrum Master(SM), 개발팀 |
| **MVP (Minimum Viable Product)** | 최소 생존 가능한 핵심 기능. 먼저 만들어 가치를 입증한 뒤 확산할지 판단 |
| **DoD (Definition of Done)** | 해당 구간에서 하기로 한 것을 "완료했다"고 판단하는 기준 |

- Agile은 상위 개념(방법론)이라 구체적 지시를 하지 않음 — 이번 과정도 **깊게 파는 것이 아니라 적용 경험**에 초점
- 실전에서 요구사항이 도중에 바뀌면 리워크(Man-Month 비용 증가) 발생 → 이를 수용할지/추가 비용을 받을지의 **프로젝트 관리(협상·타협)** 문제로 이어짐

## 4. MSA 핵심 개념

### 4.1 배경 — 왜 지금 MSA가 가능해졌나

- 전통 컴퓨터 구조(폰노이만: CPU–메모리–디스크)는 관련 있든 없든 통합해서 메모리에 올려야 속도가 났음 → **모놀리식(Monolithic)**의 기원
- 2000년대 전후 클라우드/클러스터링 기술 등장 → 여러 컴퓨터를 하나처럼 묶어 사용 가능 → 사람 수준 학습(딥러닝) 실현, 그리고 **굳이 통합할 필요 없이 분할 가능**해짐

### 4.2 MSA란

- 관련 없는 업무를 굳이 하나로 묶지 않고 **분할해서 독립 서비스로 운영**하는 컨셉 ("작다"의 기준이 중요한 게 아니라 "분할" 자체가 핵심)
- 예: SK텔레콤 월말 "선물하기" 트래픽 폭증이 "빌링/정산" 기능에 영향을 주던 문제 → 서비스 분리로 해결(트래픽 몰리는 서비스만 자원 확장)

### 4.3 Spring Boot(SRP) vs MSA

- Spring Boot 안에서도 SOLID의 SRP(단일 책임 원칙)에 따라 역할·책임을 나누지만, **빌드/배포는 하나로 묶여 있음** (진짜 분리는 아님)
- MSA는 각 서비스를 **컨테이너 단위로 완전히 분리**하여 배포 → 한 서비스만 고쳐 배포해도 다른 서비스에 영향 없음

### 4.4 클라우드 레이어링 참고

- IaaS → PaaS → SaaS(→ "Anything as a Service") 순으로 인프라 관심사를 클라우드에 위임하는 흐름
- Kubernetes: 공통 인프라 기능을 대부분 커버, 매우 강력하지만 자원 소비가 큼(양날의 검) — "절대 안 죽는" 대신 비용이 큼
- Docker Compose로도 MSA 구현 가능(실습 과정에서 사용) — 다만 100개 이상 서비스 규모부터는 사람이 관리하기 어려워 Kubernetes 필요
- BFF(Backend For Frontend): 백엔드가 여러 서비스로 쪼개져 있어 프론트가 이를 찾고 연결하기 위한 추가 계층. API Gateway는 라우팅만 담당

## 5. 실습 프로젝트 구조

### 5.1 배포된 서비스(온라인 교육 플랫폼 도메인)

| 서비스 | 역할 | 실습생 매핑 예시 |
|---|---|---|
| User Service | 회원가입/로그인 | 인증 필요 없이 요청 형식/토큰 응답만 알면 됨 |
| Course Service | 과목(=상품) 등록/조회 | 강의 등록 = 상품 등록 |
| Enrollment Service | 수강 신청(=구매) | 결제 완료 시 Kafka 이벤트로 상태 변경 |
| Payment Service | 결제 처리 | 결제 완료 → Enrollment로 이벤트 전달 |
| Recommend Service | 추천(FastAPI, 룰베이스) | 구매하지 않은 상품 추천 |
| 공통 인프라 | Eureka(서비스 디스커버리), API Gateway, 인증서버(서비스 간 인증), Kafka | **블랙박스로 취급, 이해 X, 사용 O** |

- 강사=판매자, 수강생=사용자 구도. "강의 등록"이 아니라 "상품 등록"으로 치환해서 이해하면 됨

### 5.2 스프린트 구분

- **Sprint 1 (워킹 스켈레톤)**: User, Course, Enrollment — 핵심 뼈대. "이 기능 없이 시연 가능한가?"로 판단
- **Sprint 2 (확장)**: Kafka, Payment, Recommend — 서비스 간 협업(결제 → Enrollment 이벤트 반영 → 사용자 화면 표시)

### 5.3 "알아야 할 것" vs "몰라도 되는 것"

| 서비스 | 알아야 할 것 | 몰라도 되는 것 |
|---|---|---|
| User | 요청 형식, 응답 토큰 | 비밀번호 암호화 로직, DB 내부 구조 |
| Course | API 형식(등록/조회) | JPA 매핑, 내부 쿼리 |
| Enrollment | 신청 → 이벤트 발생 → 결제 후 상태 자동 변경 | Kafka Producer/Consumer 내부 동작 |
| Payment | 결제 완료 호출 → Enrollment 상태 변화 확인 | 내부 처리 로직 |
| Eureka/API Gateway/인증서버 | 로그인 → 토큰 발급 → 헤더에 포함해 다른 API 호출 가능 | 내부 설정, 서명 알고리즘, 서비스 등록 방식 |

- 이유: 실전에서도 신입 개발자가 인프라팀 구축물을 처음부터 다 이해하고 시작하지 않음 — **주어진 것을 활용하는 능력**이 이번 실습의 범위
- Circuit Breaker(회로 차단) 개념도 이미 구현되어 있음 — 장애 시 fallback 처리 (예: 넷플릭스 추천 서비스 장애 시 "인기 콘텐츠"로 대체)

### 5.4 실습 방법

1. Swagger UI(각 서비스 포트 + `/swagger-ui/index.html`)에서 엔드포인트 확인
2. "Try it out"으로 직접 호출 → 인증 필요 시 토큰 먼저 발급
3. 프론트엔드는 HTML/CSS + JavaScript `fetch` 방식으로 백엔드 REST API 연동 (로그인 → 토큰 저장 → 이후 요청 헤더에 포함)
4. **목업(Mock) 금지**: 데이터만 하드코딩해 화면만 만드는 것은 구현이 아님 — 실제 MSA 서비스와 연결해야 함
5. 아키텍처 다이어그램은 Mermaid 코드로 간단히 확인 가능(실전에서는 draw.io 등을 더 많이 사용)

## 6. 조별 과제 제출 가이드

### 6.1 기획서(PPT) 목차

1. **이해관계자 가치**: 팀이 정의한 이해관계자(사용자/강사/판매자/운영자 등)의 실제 불편함(Pain Point) 정의
2. **AI 솔루션**: Pain Point를 해결할 핵심 기능 + AI가 담당하는 역할
3. **스프린트 구분**: MVP(Sprint1) → 확장 기능(Sprint2) 우선순위 및 일정
4. **아키텍처 구성도**: 제공된 MSA 구조 + 각 서비스 역할 + API 명세(엔드포인트 목록, Swagger 요약 매핑)
5. **동작 화면 스냅샷**: 시나리오 순서대로 캡처 + 설명 (GIF 불필요, 스냅샷으로 충분)

### 6.2 제출 규칙

- 프론트엔드 코드 + (백엔드 수정 시) 수정한 파일만 경로 포함해 제출 — 전체 200MB 압축 금지
- 조별 발표 15분, PPT + 동작 코드 데모
- **B2C 지양, B2B/B2B2C/B2G 권장**: 신입/커리어 초기 포트폴리오로는 개인향(B2C) 서비스보다 기업/정부 대상 서비스가 설득력 있음

### 6.3 AI(예: Claude) 활용 시 주의사항

- PPT 작성 등에 AI 활용은 권장하나, **"AI가 만든 티가 나면 아마추어처럼 보임"** — 본인만의 템플릿/스타일로 다듬어야 함
- AI가 생성한 내용을 검증 없이 그대로 사용하는 것은 위험 — 본인이 이미 아는 것을 확장하는 방향으로 활용해야 신뢰할 수 있음
- 개발 경험이 없는 사람이 AI에게 지시하고 결과를 검증할 수 없는 것은 실전에서 통하지 않음 → 이번 실습으로 "AI에게 검증 가능한 수준의 최소 역량"을 갖추는 것이 목적

## 7. 강사가 강조한 핵심 태도(Attitude)

- 실전 상황에 던져졌을 때 "이해가 안 되는 게 정상" — 다만 **스스로 답을 찾으려는 노력**이 성장의 핵심 (서브노트를 쓰는 이유)
- 커리어 인터뷰에서 필요한 것: ① 어떤 이해관계자의 Pain Point를 AI로 해결했는지(비즈니스 가치), ② 실제 동작하는 코드, ③ **협업 능력**(팀 내 역할 분담) — 이 세 가지가 합쳐져야 완성된 포트폴리오
- "실력 좋음"은 최대 50점, 나머지 50점은 **협업** — 두 가지가 합쳐져야 100점
- 스칼라 커리큘럼 판단 기준: "현장 기준" — 방대한 내용 중 무엇을 깊게 팔지는 "이 AI 서비스가 어떤 이해관계자에게 어떤 가치를 주는가"를 중심으로 스스로 우선순위를 판단해야 함
