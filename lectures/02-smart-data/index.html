1. 데이터베이스 개요

왜 파일 대신 DB인가 · 발전 과정 · 트랜잭션과 ACID · WAL · Consensus · Isolation Level

💡
쉽게 말하면: 파일로 데이터 관리하다 한계(중복, 동시접속, 중간에 죽음)를 느껴서 DB가 나왔어요. ACID는 '계좌이체 같은 거래가 중간에 끊기거나 꼬이지 않게 보장하는 4가지 약속'. WAL은 '실제 잔고를 바꾸기 전에 통장 여백에 먼저 메모해두는 것', Consensus는 '서버가 여러 대일 때 다수결로 진짜 기록을 정하는 것', Isolation Level은 '남의 작업이 얼마나 보이게 할지 고르는 등급'이라고 생각하면 쉬워요.
🎯 이 장의 목표

데이터베이스가 무엇을 해결하려고 태어났는지 이해하고, 트랜잭션의 ACID 네 속성을 각각 설명할 수 있게 된다. 그리고 그 위에 얹히는 세 가지를 ACID와 연결해서 볼 수 있게 된다.

  • WAL — ACID의 D(지속성)를 실제로 구현하는 장치
  • Consensus — 서버가 여러 대인 분산 환경에서 그 역할을 대신하는 알고리즘
  • Isolation Level — ACID의 I(격리성)를 등급으로 나눈 것

1) 왜 이게 필요한가 — 파일로 시작하면 어디서 터지는가

프로그램이 데이터를 다루는 가장 소박한 방법은 파일이다. sales.csv를 열고, 읽고, 고치고, 닫는다. Python으로 CSV·JSON을 다뤘던 것이 정확히 그 방식이다. 혼자 쓸 때는 아무 문제가 없다. 문제는 다음 세 가지가 동시에 일어날 때 터진다.

  • 여러 프로그램이 같은 데이터를 쓴다 — 주문 시스템과 재고 시스템이 각각 자기 파일을 들고 있으면, 같은 상품의 재고 수량이 두 파일에서 서로 달라진다.
  • 여러 사람이 동시에 고친다 — A와 B가 동시에 같은 파일을 읽어 각자 수정하고 저장하면, 나중에 저장한 쪽이 앞사람의 수정을 덮어쓴다. 앞사람의 작업은 흔적도 없이 사라진다.
  • 중간에 죽는다 — 계좌 A에서 1만 원을 빼고 계좌 B에 넣는 도중에 정전이 나면, 1만 원이 세상에서 증발한다.

데이터베이스는 이 세 가지를 해결하려고 만들어진 소프트웨어다. "데이터를 저장하는 곳"이라는 설명은 절반만 맞다. 정확히는 여러 주체가 동시에 접근해도 데이터가 깨지지 않도록 보장해 주는 소프트웨어이고, 저장은 그 보장을 하기 위한 부수 작업에 가깝다.

DB와 DBMS는 다른 말이다

  • 데이터베이스(DB): 저장된 데이터 자체, 또는 그 데이터의 집합
  • DBMS(DataBase Management System): 그 데이터를 관리해 주는 소프트웨어 — PostgreSQL, MySQL, Oracle이 여기에 해당

DB 발전은 단순한 저장 방식의 변화가 아니라 데이터 무결성·일관성 vs 확장성 사이의 균형 싸움이다. 무결성/일관성은 "데이터가 틀리지 않게"이고, 확장성은 "많이·빨리 처리되게"다. 둘은 근본적으로 상충한다 — 데이터가 틀리지 않도록 확인하는 절차 자체가 시간이 걸리고, 여러 서버로 나눠 놓을수록 그 확인이 비싸지기 때문이다. 그래서 DB의 역사는 "이번엔 어느 쪽을 얼마나 포기할까"의 역사다.

3) 트랜잭션과 ACID

트랜잭션(transaction)은 "하나로 취급되어야 하는 작업 묶음"이다. 계좌 이체가 교과서적인 예다.

트랜잭션의 기본형 — 계좌 이체
BEGIN;                                                        -- 트랜잭션 시작
UPDATE account SET balance = balance - 10000 WHERE id = 'A';  -- 출금
UPDATE account SET balance = balance + 10000 WHERE id = 'B';  -- 입금
COMMIT;                                                       -- 확정
  • BEGIN — 여기서부터 트랜잭션이 시작된다는 선언. 표준은 START TRANSACTION이고 PostgreSQL/MySQL 모두 BEGIN도 받는다.
  • COMMIT — 지금까지의 변경을 확정한다. 이 시점 이후로는 되돌릴 수 없다.
  • ROLLBACK — 지금까지의 변경을 전부 취소하고 트랜잭션 시작 전 상태로 되돌린다.

두 UPDATE는 반드시 둘 다 되거나 둘 다 안 돼야 한다. 하나만 되면 돈이 사라지거나 생겨난다. 이 "둘 다 아니면 아무것도"를 보장하는 단위가 트랜잭션이다.

ACID 네 속성 — 무엇으로부터 지켜 주는가

속성설명무엇으로부터 지켜 주는가
Atomicity
(원자성)		트랜잭션의 모든 작업이 완전히 수행되거나 전혀 수행되지 않아야 함 (송금 = 출금 + 입금 → 둘 다 성공 or 둘 다 취소)중간에 죽는 것으로부터. 출금만 되고 입금 전에 서버가 꺼져도, 재기동하면 출금이 취소되어 있다.
Consistency
(일관성)		트랜잭션 수행 전후에 DB는 일관된 상태를 유지규칙 위반으로부터. "잔액은 음수 불가", "주문의 회원번호는 실재하는 회원" 같은 제약이 트랜잭션 끝에 깨져 있으면 그 트랜잭션을 무효로 만든다.
Isolation
(격리성)		트랜잭션이 동시에 실행될 때 서로 간섭하지 않도록 보장남으로부터. 내가 이체하는 도중의 중간 상태(출금은 됐고 입금은 안 된 상태)를 남이 보지 못하게 한다.
Durability
(지속성)		트랜잭션이 성공적으로 완료되면 그 결과는 영구적으로 반영전원이 나가는 것으로부터. COMMIT 응답을 받았다면 그 직후 정전이 나도 결과는 남아 있다.
⚠️ 자주 하는 착각 — A와 C는 같은 말이 아니다

A는 "전부 아니면 전무"라는 실행 단위에 대한 약속이고, C는 "규칙을 어긴 상태로 끝나지 않는다"는 결과 상태에 대한 약속이다. 출금·입금이 둘 다 성공했는데(A는 지켜짐) 그 결과 잔액이 -5,000원이 됐다면 C가 깨진 것이고, DB는 그 트랜잭션을 롤백한다.

🔎 심화 — ACID 중 C만 성격이 다르다

A·I·D는 DBMS가 알아서 보장해 주지만, C는 개발자가 제약조건과 애플리케이션 로직으로 정의한 규칙을 DBMS가 대신 검사해 주는 것에 가깝다. 내가 "잔액은 음수 불가"라는 CHECK 제약을 걸어 두지 않았으면 DBMS는 잔액이 음수가 되는 것을 막아 주지 않는다. (제약조건은 6장 DDL에서 다룬다.)

4) DBMS별 ACID 지원 차이

ACID는 모든 DBMS에서 "교과서적으로는 지원" — 엔진/설정/클라우드 옵션에 따라 실제 보장 수준이 다르다. 제품 소개서에 "ACID 지원"이라고 적혀 있다고 해서 내가 쓰는 설정에서 실제로 보장된다는 뜻이 아니다.

  • MySQL InnoDB 엔진: 완전한 ACID 지원 (Redo/Undo Log, MVCC)
  • MySQL MyISAM 엔진: Rollback 불가, FK 없음 → 사실상 ACID 미지원 (현재는 InnoDB가 기본 엔진)
  • PostgreSQL: MVCC 기반, WAL, SSI(Serializable Snapshot Isolation). 모든 격리 수준 지원 — 가장 표준에 가까운 구현
  • Oracle: Read Committed 기본, 매우 안정적인 상용 ACID 구현
  • Cloud DB (Aurora/RDS): 분산 환경에서 ACID + 수평 확장. 특히 Aurora는 스토리지 레벨 6방향 복제로 장애 시 빠른 복구
  • 핵심: DB 선택 시 ACID 보장 수준과 성능 트레이드오프를 반드시 확인할 것

  • 모든 주요 DBMS가 MVCC를 쓴다 — MVCC(다중 버전 동시성 제어)는 데이터를 덮어쓰는 대신 여러 버전을 남겨 두는 방식. 읽는 사람은 자기 시점의 버전을 보므로 쓰는 사람과 부딪히지 않는다 → 읽기가 쓰기를 막지 않는다. (20장에서 다시 다룸)
  • Durability의 구현체가 로그다 — PostgreSQL의 WAL, Oracle의 Redo/Undo, SQL Server의 Transaction Log, MySQL의 Double-write Buffer는 모두 "데이터 파일보다 먼저 기록해 두는 장치"라는 같은 아이디어의 제품별 이름이다.

5) WAL — 지속성(Durability)의 구현 원리

왜 필요한가

"COMMIT하면 영구히 남는다"를 곧이곧대로 구현하려면, COMMIT할 때마다 데이터 파일의 해당 위치를 찾아가 고치고 디스크에 확실히 기록해야 한다. 문제는 이게 너무 느리다는 것이다. 고쳐야 할 행이 파일 여기저기에 흩어져 있으면 디스크가 이리저리 움직이는 랜덤 I/O가 되고, 랜덤 I/O는 순차 I/O보다 훨씬 느리다.

핵심 메커니즘

  • DBMS는 데이터 파일은 나중에 고치고, "무엇을 고칠 것인지"를 적은 로그를 먼저 디스크에 쓴다.
  • 로그는 파일 끝에 계속 덧붙이기만 하므로 순차 I/O다 → 빠르다.
  • 장애가 나도 로그만 있으면 재현할 수 있으므로 안전하다.
  • 이 메커니즘이 WAL(Write-Ahead Logging) — 변경 사항을 실제 데이터 파일에 쓰기 전에 로그(저널)에 먼저 기록하는 방식이다.

동작 과정과 장점

  • ① 클라이언트가 UPDATE 실행 → ② DB는 즉시 데이터 파일을 고치지 않고 먼저 WAL 로그에 기록 → ③ 로그가 디스크에 안전하게 기록되면 "COMMIT 성공" 응답 → ④ 실제 데이터 파일 반영은 나중에 배치/버퍼 관리자가 수행
  • 장애 발생 시 로그를 기반으로 Redo(다시 적용) / Undo(취소) 가능
  • 쓰기 성능 개선 (순차 기록 → 랜덤 I/O 최소화)
  • PostgreSQL, Oracle, SQL Server, MySQL(InnoDB) 등 대부분의 DBMS가 사용
🔑 "COMMIT 성공"의 근거는 데이터 파일이 아니라 로그다

사용자가 커밋 완료를 확인한 그 순간, 데이터 파일에는 아직 아무것도 안 쓰여 있을 수 있다. 그래도 괜찮은 이유는 로그가 디스크에 있기 때문이다.

PostgreSQL WAL — 단계별 흐름
BEGIN;
UPDATE account SET balance = balance - 10000 WHERE id = 'A';
-- 1단계: WAL 버퍼에 변경 내용 기록 (로그 우선 원칙)
-- 2단계: Shared Buffer(메모리)에 페이지 변경 반영
-- 3단계: 아직 디스크 데이터 파일에는 미기록 (dirty page)

UPDATE account SET balance = balance + 10000 WHERE id = 'B';
COMMIT;
-- COMMIT 로그를 WAL에 기록 후 fsync(디스크 동기화)
-- 이후 Checkpoint 시점에 데이터 파일에 반영

-- 장애 복구 시:
--   pg_wal/ 디렉토리의 로그를 순서대로 재실행 (Redo)
--   COMMIT되지 않은 트랜잭션은 Undo 처리
  • Shared Buffer — PostgreSQL이 디스크 페이지를 캐싱해 두는 공유 메모리 영역. 모든 읽기/쓰기는 일단 여기를 거친다.
  • dirty page — 메모리에서는 고쳐졌는데 아직 디스크 데이터 파일에는 반영 안 된 페이지. "더럽다"는 건 메모리와 디스크의 내용이 어긋나 있다는 뜻.
  • fsync — OS에게 "버퍼에 들고 있지 말고 지금 물리 디스크에 확실히 써라"라고 강제하는 시스템 호출. OS도 자체 캐시가 있어서 이걸 호출하지 않으면 "썼다"고 해도 전원이 나가면 날아간다. COMMIT의 안전성은 결국 이 fsync 한 번에 달려 있다.
  • Checkpoint — 쌓인 dirty page를 데이터 파일에 몰아서 반영하고 "여기까지 반영 완료"라고 표시하는 시점. 이 표시가 있어야 복구 시 로그를 처음부터가 아니라 마지막 체크포인트부터만 재생하면 된다.
  • pg_wal/ — PostgreSQL 데이터 디렉터리 안에서 WAL 파일이 쌓이는 실제 디렉터리 (9.6 이전에는 pg_xlog/).
postgresql.conf — WAL 관련 설정
wal_level = replica            -- 복제 레벨
synchronous_commit = on        -- on: 안전 / off: 성능↑, 최대 200ms 손실 가능
checkpoint_timeout = 5min      -- 체크포인트 주기
  • wal_level — WAL에 얼마나 상세히 기록할지. replica면 복제 서버를 붙일 수 있을 만큼 기록한다.
  • synchronous_commit — 이 값이 D를 켜고 끄는 스위치다. on이면 COMMIT 시 fsync가 끝날 때까지 기다렸다 응답(안전·느림). off면 fsync를 기다리지 않고 먼저 응답(빠름·직후 정전 시 최근 커밋 일부 유실). "최대 200ms 손실 가능"이 이 창(window)이다.
  • checkpoint_timeout — 짧게 잡으면 복구가 빠르지만 평소 디스크 쓰기가 잦아지고, 길게 잡으면 그 반대가 된다.
짚어 둘 것 — synchronous_commit = off는 데이터가 깨지지는 않고 최근 것 일부가 없어질 뿐이다. 트랜잭션이 반쪽만 반영되는 일은 없다(A는 지켜진다). 잃어도 되는 로그성 데이터라면 실무에서 실제로 쓰는 옵션이지만, 돈이 오가는 테이블에는 쓰면 안 된다.

6) Consensus — 분산 환경의 안전장치

왜 필요한가

WAL은 서버 한 대 안에서의 장애를 막아 준다. 그런데 서버가 여러 대라면? 데이터를 3대에 복제해 두었는데 그중 한 대가 네트워크에서 끊긴 사이에 나머지 두 대에만 반영되었다면, 끊겼던 서버가 돌아왔을 때 세 대의 내용이 다르다. 이때 "누구 말이 맞는가"를 정해 주는 장치가 필요하다. 즉, 분산 DB에서는 여러 노드가 동일한 데이터를 가진 상태여야 하고, 네트워크 지연/장애가 발생해도 모든 노드가 같은 결과(합의)를 갖도록 하는 알고리즘을 쓴다.

대표 알고리즘과 동작

  • Paxos — 이론적으로 가장 유명한 분산 합의 알고리즘
  • Raft — 구현이 단순해 실제 제품(AWS Aurora, etcd, CockroachDB 등)에서 널리 활용
  • Google Spanner — Paxos + TrueTime API(전역 시계 동기화) 활용
  • 동작 과정: 클라이언트가 트랜잭션 요청 → Leader 노드가 로그에 기록(→ 여기서도 WAL!) → Follower 노드들과 "투표"를 통해 과반수가 같은 로그에 동의해야 Commit 확정 → 모든 노드에 같은 순서의 로그가 쌓이므로 Strong Consistency 보장
🔗 Consensus는 WAL을 대체하지 않고 그 위에 얹힌다

리더가 로그를 쓰는 것까지는 단일 서버 WAL과 똑같고, 거기에 "과반수 노드가 같은 로그를 받았는지 확인" 단계가 추가된 것이다.

왜 하필 과반수인가? 5대 중 3대가 동의했다면, 어떤 두 "과반수 집합"을 잡아도 반드시 겹치는 노드가 하나 이상 있다(3+3 > 5). 그 겹치는 노드가 최신 로그를 갖고 있으므로, 옛 리더가 죽고 새 리더를 뽑아도 확정된 내용이 유실되지 않는다. 과반수는 임의로 고른 수가 아니라 이 겹침을 보장하는 최소값이다.

  • 장점: 분산 환경에서도 데이터 일관성 유지 · 장애 시 Leader 재선출 가능 → 고가용성
  • 단점: 네트워크 지연이 늘어나면 성능 저하(특히 글로벌 DB에서 latency 증가) · 쓰기가 항상 과반수 왕복을 기다려야 해서 단일 노드보다 쓰기 지연이 길다

7) Isolation Level — 격리성을 등급으로 나누기

왜 등급이 있는가

ACID의 I를 완벽하게 지키는 방법은 사실 간단하다. 트랜잭션을 한 번에 하나씩만 실행하면 된다. 그러면 서로 간섭할 여지가 아예 없다. 문제는 그러면 동시 사용자가 1명인 시스템이 된다는 것이다. 그래서 실제 DBMS는 "완벽한 격리"와 "빠른 동시 처리" 사이에서 얼마나 격리할지를 등급으로 골라 쓰게 한다. 등급을 낮출수록 빨라지지만 이상한 현상을 보게 되고, 등급은 "그 현상 중 무엇까지 참을 것인가"로 정의된다.

세 가지 이상 현상 — 무엇이 달라졌는가로 구분한다

현상무엇이 문제인가언제 깨지나
Dirty Read확정되지 않은 값을 봤다상대가 아직 COMMIT 안 했는데 읽음
Non-Repeatable Read같은 행의 값이 바뀌었다상대가 UPDATE/DELETE 후 COMMIT
Phantom Read결과의 행 개수가 바뀌었다상대가 INSERT 후 COMMIT

Dirty Read가 특히 위험한 이유는 상대가 롤백해 버릴 수 있기 때문이다. 존재한 적이 없는 값을 근거로 내 계산이 진행된다.

Phantom Read 예제 — 두 세션
-- 【 Session 1 】
BEGIN;
SELECT COUNT(*) FROM orders WHERE amount >= 100;   -- 결과: 5

-- 【 Session 2 (동시 처리 트랜잭션) 】
BEGIN;
INSERT INTO orders(id, amount) VALUES (999, 150);
COMMIT;

-- 【 다시 Session 1 】
SELECT COUNT(*) FROM orders WHERE amount >= 100;   -- 결과가?

-- READ COMMITTED  : 5 → 6 으로 증가 → 팬텀 발생
-- REPEATABLE READ : 5 → 5 유지 (같은 트랜잭션 = 같은 스냅샷; InnoDB/PostgreSQL)
--   단, Session 1이 SELECT ... FOR UPDATE를 하거나 같은 범위를 UPDATE/DELETE로
--   잡으면 범위 잠금이 걸려 Session 2의 INSERT가 대기/차단 → 팬텀 사전 차단
-- SERIALIZABLE    : 팬텀 원천 차단 (범위/프레디킷 잠금 또는 SSI)
--   Session 2의 INSERT는 대기하거나 충돌로 롤백된다
팬텀의 정확한 정의 — "값이 변해서"가 아니라 "조건에 맞는 새 행이 생겨서 결과 개수가 바뀌는 현상"
  • SELECT ... FOR UPDATE — 읽으면서 동시에 그 행에 쓰기 잠금을 거는 문법. "지금 읽는 이 행을 곧 고칠 거니까 아무도 건드리지 마라"라는 선언 (21장 비관적 Lock이 이걸로 구현된다).
  • 프레디킷 잠금(predicate lock) — 행 하나가 아니라 amount >= 100이라는 조건 자체에 거는 잠금. 아직 존재하지 않는 행까지 막아야 팬텀을 진짜로 막을 수 있기 때문에 필요하다.
  • Gap Lock — MySQL InnoDB가 쓰는 잠금으로, 인덱스의 레코드와 레코드 사이의 빈 구간을 잠근다. 행이 아니라 틈을 잠그므로 그 틈에 새 행이 INSERT되는 것을 막아 팬텀을 방지한다. next-key lock은 "레코드 잠금 + 갭 잠금"을 합친 것.

✔ 이 표에서 실무적으로 뽑아 갈 것
  • PostgreSQL·Oracle의 기본값은 RC, MySQL의 기본값은 RR — 같은 코드를 두 DB에 올리면 동작이 달라질 수 있다.
  • SQL Server만 락 기반이 기본 — 나머지는 MVCC라 "읽기가 쓰기를 막지 않는다"가 성립하지만, SQL Server의 기본 RC는 읽기가 쓰기를 기다릴 수 있다. READ_COMMITTED_SNAPSHOT을 켜면 MVCC처럼 동작.
  • SERIALIZABLE은 공짜가 아니다 — Oracle은 충돌 시 ORA-08177로 죽이고, PostgreSQL SSI도 직렬성이 깨질 것 같으면 롤백한다. 즉 애플리케이션에 재시도 로직이 있어야 한다. "가장 안전하니까 그냥 SERIALIZABLE"이 안 되는 이유.

재무나 대출처럼 금액이 걸린 도메인은 트랜잭션 요건을 강하게 잡아야 하므로 가장 엄격한 SERIALIZABLE을 쓴다. 한 트랜잭션이 끝날 때까지 다른 작업의 접근을 막고, 끝난 뒤에야 반영을 허용하는 등급이다. 반면 이 DBMS별 비교표 자체는 외울 대상이 아니다. "데이터베이스마다 허용 범위가 다르다"는 사실만 기억해 두었다가, 같은 코드인데 조회 결과가 달라 보이는 상황을 만났을 때 이 표를 찾아보면 된다.

🔎 심화 — PostgreSQL의 RR은 표준보다 강하다

표준상 RR은 팬텀을 허용하지만, PostgreSQL의 RR은 트랜잭션 시작 시점의 스냅샷을 끝까지 보기 때문에 새로 INSERT된 행이 아예 보이지 않는다. 그래서 읽기만 하는 한 팬텀이 발생하지 않는다. 그럼에도 PostgreSQL이 SERIALIZABLE을 따로 두는 이유는, 읽은 값을 근거로 쓰는 패턴(write skew)까지 막으려면 스냅샷만으로는 부족하기 때문이다.

따라 치기 ① — 내 DB의 기본 격리 수준 확인 (psql)
SHOW default_transaction_isolation;

--  default_transaction_isolation
-- -------------------------------
--  read committed
-- (1 row)
따라 치기 ② — 한 트랜잭션에만 다른 수준 적용
BEGIN;
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM orders WHERE amount >= 100;
-- ... 다른 세션에서 INSERT 후 COMMIT 해도 ...
SELECT COUNT(*) FROM orders WHERE amount >= 100;   -- 개수 그대로
COMMIT;

-- 주의: SET TRANSACTION ISOLATION LEVEL 은 반드시 트랜잭션의 첫 문장이어야 한다.
--       이 설정은 해당 트랜잭션에만 적용되고 COMMIT 후엔 기본값으로 돌아간다.
막히면 여기 — ERROR: SET TRANSACTION ISOLATION LEVEL must be called before any query가 뜬다면 BEGIN 다음에 이미 SELECT 같은 걸 실행한 상태다. ROLLBACK; 후 BEGIN; → SET TRANSACTION ... 순서로 다시 치면 된다.

8) 짚고 넘어가기

데이터를 파일에 저장하면 되는데 왜 굳이 DB를 쓰나요? CSV로도 충분하지 않나요?
혼자 쓰고, 동시에 안 고치고, 중간에 죽어도 상관없는 데이터라면 충분합니다. 실제로 Python 실습에서는 CSV로 다 했지요. DB가 필요해지는 지점은 데이터 양이 아니라 동시성과 무결성입니다. 두 사람이 같은 파일을 동시에 고치는 순간, 또는 작업 도중 중단되면 안 되는 순간부터 파일로는 감당이 안 됩니다. "데이터가 많아지면 DB"가 아니라 "여럿이 건드리면 DB"라고 기억하는 편이 정확합니다.
격리 수준은 무조건 SERIALIZABLE로 두는 게 가장 안전한 것 아닌가요?
안전하지만 권장하지 않습니다. 첫째, 사실상 트랜잭션을 줄 세우는 것이라 동시 처리량이 급격히 떨어집니다. 둘째, 더 중요한데 SERIALIZABLE은 조용히 성공시켜 주는 게 아니라 충돌하면 트랜잭션을 죽입니다. Oracle은 ORA-08177, PostgreSQL SSI는 serialization failure로 롤백합니다. 애플리케이션에 "실패하면 다시 시도한다"는 코드가 없으면 안전해지기는커녕 사용자에게 에러가 그대로 노출됩니다. 대부분의 서비스는 기본값(RC 또는 RR)을 쓰고, 정말 필요한 몇몇 트랜잭션에만 수준을 올리거나 명시적 잠금을 씁니다.
MySQL이 REPEATABLE READ가 기본이면 MySQL이 PostgreSQL보다 더 안전한 건가요?
그렇게 단정할 수 없습니다. 등급 이름만 보면 RR이 RC보다 위지만, 두 DBMS의 구현이 다르기 때문에 이름 비교가 곧 안전성 비교가 되지 않습니다. PostgreSQL의 RC도 문장 단위로는 일관된 스냅샷을 보고, PostgreSQL에서 RR을 켜면 표준 RR보다 오히려 강한 스냅샷 격리가 됩니다. 등급 이름은 표준이 정한 라벨이고, 실제 보장은 그 DBMS가 어떻게 구현했는지로 결정됩니다.
COMMIT을 했는데 데이터 파일에 아직 안 쓰였다면, 그건 지속성이 깨진 것 아닌가요?
아닙니다. 지속성의 기준은 "데이터 파일에 반영되었는가"가 아니라 "다시 살아났을 때 복원할 수 있는가"입니다. WAL 로그가 fsync로 디스크에 확실히 기록되었다면, 지금 당장 전원이 나가도 재기동 시 그 로그를 재생(Redo)해서 같은 상태로 복원할 수 있습니다. 그래서 로그만 안전하면 데이터 파일 반영은 미뤄도 되고, 이 "미룰 수 있다"가 WAL이 빠른 이유이기도 합니다.
WAL이 있으면 Consensus는 필요 없는 것 아닌가요? 둘 다 로그를 쓰잖아요.
둘은 층이 다릅니다. WAL은 한 노드 안에서 "이 노드가 죽었다 살아나도 상태를 복원한다"를 보장하고, Consensus는 노드들 사이에서 "여러 노드가 같은 순서의 같은 로그를 갖는다"를 보장합니다. 노드가 통째로 죽어서 안 돌아오는 상황은 WAL로 해결이 안 됩니다. 그래서 분산 DB는 두 개를 겹쳐서 씁니다 — Consensus 동작 과정의 "Leader 노드가 로그에 기록"이 그 겹침을 가리킵니다.
Dirty Read는 실제로 언제 일어나나요? 요즘 DB에서도 발생하나요?
거의 안 일어납니다. Dirty Read를 허용하는 유일한 등급인 READ UNCOMMITTED가 현대 DBMS에서 사실상 안 쓰이기 때문입니다. PostgreSQL은 READ UNCOMMITTED를 요청해도 내부적으로 READ COMMITTED로 처리합니다. 그래서 Dirty Read는 격리 수준을 이해하기 위한 기준점으로서 의미가 있지, 실무에서 만나는 버그는 아닙니다. 실무에서 실제로 만나는 건 Non-Repeatable Read와 Phantom, 그리고 그보다 훨씬 흔한 Lost Update(둘이 동시에 읽고 각자 고쳐서 한쪽이 덮어써지는 것)입니다. Lost Update는 21장 낙관적/비관적 Lock에서 다룹니다.

2. 관계형 모델 핵심 개념

테이블(Relation) · 키(PK/FK/UK)와 FK 옵션 · 관계(1:1/1:N/N:M) · 정규화(1NF~BCNF)와 반정규화

💡
쉽게 말하면: 엑셀 시트 여러 개를 만들고 '학번' 같은 공통 열로 서로 연결(참조)해서 중복 없이 관리하는 방식이에요. PK=그 행을 딱 특정하는 값, FK=다른 시트를 가리키는 화살표, UK=중복은 안 되지만 비워둘 수는 있는 값. 정규화는 '한 표에 여러 주제를 섞어 넣지 말고 주제별로 표를 쪼개기'라고 생각하면 쉬워요.
🎯 이 장의 목표

현실의 데이터를 테이블로 바꾸는 규칙을 익힌다. 구체적으로는 다음 세 가지를 스스로 설명할 수 있게 된다.

  • 키 — PK·FK·UK를 구분해서 쓸 수 있다 (특히 "FK는 어느 쪽 테이블에 두는가")
  • 관계 — 1:1·1:N·N:M을 테이블로 어떻게 표현하는지 안다
  • 정규화 — 1NF~3NF를 "무엇을 제거하는 단계인지"로 설명할 수 있다

1) 왜 이게 필요한가 — 현실의 문장을 표로 쪼개는 작업

1장에서 DB가 무엇을 해 주는지 봤다. 이제 실제로 데이터를 넣으려면 어떤 모양으로 넣을지를 정해야 한다.

현실의 데이터는 문장으로 되어 있다. "3학년 홍길동은 컴퓨터공학과 학생이고, 이번 학기에 데이터베이스와 알고리즘을 수강한다." 이걸 그대로 저장할 수는 없다. 표 몇 개로 쪼개야 한다. 이 쪼개는 작업이 관계형 데이터 모델링 — 현실 세계의 데이터를 관계형 포맷으로 변환하는 과정이다.

이 "변환"은 단계를 따라가 보면 잡힌다. 개념 수준의 「종목」이 속성을 갖춘 논리 모델로 늘어나고, 다시 컬럼명·타입이 확정된 물리 테이블과 실제 행 데이터로 내려간다. 이 세 단계가 4장의 개념적→논리적→물리적 모델 설계 그대로다.

이걸 대충 하면 무슨 일이 벌어지는지가 이 장의 후반부(정규화)다. 결론부터 말하면 같은 사실이 여러 곳에 중복 저장되고, 그중 일부만 고쳐져서 데이터가 서로 모순되기 시작한다. 모델링은 그 모순의 여지를 설계 단계에서 없애는 작업이다.

🔎 출발점은 1970년 논문 하나

Codd, E. F. (1970). A Relational Model of Data for Large Shared Data Banks. Communications of the ACM, 13(6), 377–387. 지금 우리가 쓰는 테이블·키·JOIN·정규화가 전부 이 논문에서 나왔다.

2) 테이블 (Table / Relation)

  • 데이터를 행(Row, Tuple)과 열(Column, Attribute)로 구성한 2차원 구조
  • 각 행(Row): 하나의 레코드(데이터 인스턴스)를 의미
  • 각 열(Column): 특정 속성(Attribute)을 의미 — 동일한 데이터 타입을 가진 값들이 한 컬럼

엑셀 시트와 생김새가 같다. 다만 결정적 차이가 하나 있다. 엑셀은 한 열에 숫자와 글자를 섞어 넣을 수 있지만, DB 테이블의 한 컬럼에는 정해진 타입의 값만 들어간다. 이 제약 덕분에 DB는 그 컬럼을 어떻게 정렬하고 비교하고 인덱싱할지 미리 알 수 있다.

2024002이순신경영학2
2024003강감찬컴퓨터공학3

🎓 교수님의 코멘트 — 테이블은 어제 배운 pandas DataFrame과 같다

"테이블은 행과 열로 된 2차원 구조인데, 어제 배운 파이썬 판다스랑 연결됩니다. 각 행은 데이터 인스턴스이고 각 열은 특정 속성과 데이터 타입을 갖죠. 엑셀에 쓰던 표가 그대로 DB 테이블로 들어간다고 보시면 돼요. 헤더가 컬럼이 되고, 그 밑의 값들이 밸류가 됩니다."

파이썬에서 다룬 표와 데이터베이스의 테이블을 같은 그림으로 붙여 놓고 보면, 뒤에 나오는 GROUP BY나 JOIN도 이미 pandas에서 해 본 것과 대응된다.

⚠️ 자주 하는 착각 — "관계형"은 테이블 사이의 관계 때문이 아니다

"관계형"이라는 이름이 테이블 간의 관계 때문에 붙었다고 오해하기 쉬운데, 원래는 Relation(릴레이션) 즉 테이블 자체를 가리키는 말에서 왔다. 테이블 사이의 연결은 Relationship이고 다른 단어다.

3) 키 (Key) — PK · FK · UK

키는 관계형 데이터베이스에서 데이터 무결성과 식별성을 보장하기 위한 제약 조건이다. 기본키·외래키·고유키 세 가지를 구분해서 쓴다.

기본키 (PK, Primary Key)

  • 각 행을 고유하게 식별할 수 있는 컬럼(혹은 컬럼 조합)
  • NULL 불가, 중복 불가 — 자동으로 인덱스가 생성됨
  • 예: 학생 테이블의 "학번". PK는 "이 테이블에서 한 행을 콕 집어 가리키는 방법"이다. 이름은 동명이인이 있을 수 있으므로 PK가 될 수 없다.
  • WHERE id = 5가 빠른 이유는 DB가 PK에 알아서 인덱스를 만들어 두었기 때문이다. (인덱스는 17장)
🎓 교수님의 코멘트 — 개인정보를 기본키로 쓰지 마라

"기본키로 주민번호나 이메일 같은 개인정보를 잡지 마세요. PK는 항상 공개돼서 유지되는 값인데 개인정보는 암호화를 해야 하잖아요. 그러면 PK를 암호화하게 되고, 작업할 때마다 복호화했다가 다시 암호화하는 번거로움이 계속 생깁니다. 개인정보는 별도 컬럼을 두고 거기서 암호화하는 게 효율적이에요."

초심자가 "자연스러운 식별자"라는 이유로 가장 흔히 저지르는 실수다. 개인정보를 PK로 삼으면 그 PK가 FK로 여러 테이블에 퍼지면서 민감정보가 곳곳에 복제되고, 암호화·복호화 비용이 그 값을 참조하는 모든 조인에 따라붙는다. 참고로 학번·사번도 엄밀히는 개인 식별 정보다. 원칙을 엄격히 지킨다면 학번조차 PK에서 빼고 의미 없는 대체키를 따로 두는 편이 낫다.

외래키 (FK, Foreign Key)

  • 다른 테이블의 기본키를 참조하는 컬럼
  • 테이블 간 관계(relationship)를 표현하고, 참조 무결성을 보장
  • 예: 성적 테이블의 "학번" → 학생 테이블의 "학번(PK)"을 참조

참조 무결성(referential integrity)은 존재하지 않는 것을 가리킬 수 없다는 규칙이다. 성적 테이블에 학번 9999999짜리 행을 넣으려 하면, 학생 테이블에 그런 학번이 없으므로 DB가 INSERT를 거부한다. 이 거부가 FK의 존재 이유다. FK가 없으면 어느 학생 것인지 알 수 없는 유령 성적이 쌓인다.

고유키 (UK, Unique Key)

  • 중복은 허용하지 않지만, PK와 달리 NULL은 허용 가능
  • 예: 이메일 주소, 직원코드
구분PKUK

NULL불가허용

이메일이 좋은 예다. 이메일은 중복되면 안 되지만(UK), 아직 이메일을 등록 안 한 회원이 있을 수 있으므로 NULL이 허용돼야 한다. 그래서 PK가 아니라 UK다. UK는 SQL의 UNIQUE 제약이다 — 같은 것을 층마다 다르게 부를 뿐이다. 모델링에서는 UK(고유키)·대체키, SQL 문법에서는 UNIQUE, 실제 DB 안에서는 자동 생성된 unique 인덱스.

PK 하나 + UK 여러 개가 정상적인 모양
CREATE TABLE member (
  member_id  SERIAL PRIMARY KEY,   -- PK
  email      VARCHAR(100) UNIQUE,  -- UK
  phone      VARCHAR(20)  UNIQUE   -- UK는 여러 개 가능
);

엄밀히는 "UK 컬럼"보다 "UK 제약"이 맞는 말이다. 여러 컬럼을 묶어서 걸 수 있기 때문이다. UNIQUE (student_id, course_id)는 UK 두 개가 아니라 컬럼 두 개짜리 UK 하나이고, "이 학생이 이 과목을 두 번 신청할 수 없다"는 뜻이다. 컬럼 각각은 얼마든지 중복돼도 된다. 복합 PK도 같은 구조다.

🔎 심화 — 두 가지 세부 사항
  • UK 컬럼의 NULL 허용 개수는 DBMS마다 다르다 — 표준과 PostgreSQL/MySQL/Oracle은 NULL을 여러 개 허용한다(NULL은 서로 같지 않다고 보므로 중복이 아니다). 반면 SQL Server는 NULL을 하나만 허용한다. PostgreSQL 15부터는 UNIQUE NULLS NOT DISTINCT 옵션으로 SQL Server처럼 바꿀 수도 있다.
  • 후보키(Candidate Key)와 대체키(Alternate Key) — 한 행을 유일하게 식별할 수 있는 컬럼 조합이 여러 개일 때 그것들을 모두 후보키라 하고, 그중 하나를 골라 PK로 삼는다. 선택받지 못한 나머지가 대체키이고, 실무에서는 UK 제약으로 구현된다.

고르는 기준 — "자식이 부모 없이 의미가 있는가"

  • 주문항목은 주문 없이는 아무 의미가 없다 → CASCADE
  • 고객은 담당 직원이 없어도 여전히 고객이다 → SET NULL
  • 카테고리를 지우려는데 그 안에 상품이 있다면 실수일 가능성이 높다 → RESTRICT
🔎 RESTRICT와 NO ACTION의 차이는 "금지 여부"가 아니라 "체크 시점"

RESTRICT는 그 DELETE 문이 실행되는 즉시 검사하고, NO ACTION은 트랜잭션이 커밋(또는 문장이 끝)될 때까지 검사를 미룰 수 있다. 미룰 수 있다는 게 왜 유용하냐면, 부모를 지우고 곧바로 자식도 지우는 식으로 한 트랜잭션 안에서 결국 정리되는 경우 NO ACTION은 통과시켜 주기 때문이다. 실무에서는 거의 같게 취급해도 무방하다.

🎓 교수님의 코멘트 — 삭제는 자식부터 치우고 부모를 지운다

"ON DELETE RESTRICT는 자식이 있으면 부모를 못 지우게 막는 건데, 실무에서 제일 많이 씁니다. 그래서 상품 카테고리 밑에 상품이 있으면, 상품을 다 지운 다음에 카테고리를 지우게 하는 거죠."

옵션에만 기대지 않고 삭제 순서를 직접 통제하는 것이 실무의 기본이다. 옵션(RESTRICT)은 잘못된 삭제를 막아 주는 안전장치로 두고, 실제 정리 순서는 자식부터 치우고 부모를 지우는 업무 규칙대로 밟는다.

짚어 둘 것 — ON UPDATE CASCADE가 필요한 상황 자체가 설계가 잘못되었다는 신호다. 학번처럼 현실의 의미를 담은 값(자연키)을 PK로 쓰면, 학번 체계가 바뀔 때 그 값을 참조하는 모든 테이블이 연쇄 수정되어야 한다. 실무 권장은 의미 없는 일련번호(대체키, surrogate key)를 PK로 쓰고, 학번은 UK로 따로 두는 것이다. 참고로 Oracle은 ON UPDATE를 아예 지원하지 않는다.

5) 관계 (Relationship) — 1:1 · 1:N · N:M

1:1 관계 (One-to-One)

  • 한 레코드가 다른 테이블의 하나의 레코드와만 연결 — 예: [학생] ↔ [학생증]
  • 구현은 한쪽 테이블에 FK를 두고 그 FK에 UNIQUE를 건다. UNIQUE가 없으면 1:N이 되어 버린다.
  • 1:1은 실제로는 드물다. "한 명당 하나"라면 그냥 같은 테이블의 컬럼으로 두면 되기 때문이다. 굳이 쪼개는 경우는 조회 빈도가 크게 다르거나(자주 쓰는 컬럼과 거의 안 쓰는 큰 컬럼 분리), 보안 등급이 다를 때(민감정보만 별도 테이블로 빼서 접근 권한을 따로 줌)다.

1:N 관계 (One-to-Many) — 가장 흔한 관계

  • 한 레코드가 다른 테이블의 여러 레코드와 연결 — 예: [학생] 1명 ↔ [성적] 여러 개
  • 구현은 "N쪽"에 FK를 둔다. 학생 1명에 성적 여러 개이므로, FK(학번)는 성적 테이블에 있다. 이 방향을 헷갈리면 모델이 통째로 틀어지므로 규칙으로 외워 두자.
  • 거꾸로 학생 테이블에 성적의 FK를 두면 한 컬럼에 값 여러 개를 넣어야 하는데, 그게 바로 뒤에 나올 1NF 위반이다. 관계형 모델에서 "여러 개"를 표현하는 유일한 방법은 행을 여러 개 만드는 것이다.

N:M 관계 (Many-to-Many)

  • 여러 레코드가 다른 테이블의 여러 레코드와 연결 — 예: [학생] ↔ [강좌] → "수강" 테이블 필요
  • 학생 한 명이 여러 강좌를 듣고, 한 강좌를 여러 학생이 듣는다. 이건 어느 쪽에 FK를 둬도 표현이 안 된다. 따라서 연결 자체를 담는 세 번째 테이블(중간 테이블 / 교차 엔티티)을 만든다.
N:M은 1:N 두 개로 분해된다
students          enrollments              courses
  id (PK)  ◄───   student_id (FK)
  name            course_id  (FK)   ───►     id (PK)
                  score                      title
                  enrolled_at
                  PK(student_id, course_id)
  • 핵심은 N:M은 물리적으로 존재할 수 없고, 1:N 두 개로 분해된다는 것이다. students → enrollments가 1:N이고, courses → enrollments도 1:N이다. 교차 테이블은 그 둘의 교차점이다.
  • 교차 테이블의 또 다른 이점은 관계 자체에 속성을 붙일 수 있다는 점이다. "이 학생이 이 강좌를 언제 신청했고 점수가 몇 점인가"는 학생의 속성도 강좌의 속성도 아니라 관계의 속성이다. 교차 테이블에 enrolled_at, score가 들어가는 이유다. (4장에서 다시 다룸)
따라 치기 ① — 교차 테이블이 실제로 어떻게 쓰이는지 (연습장 실행 가능)
-- N:M을 1:N 두 개로 풀었기 때문에 이렇게 이어 붙일 수 있다
SELECT s.name AS 학생, c.title AS 강좌, e.score AS 점수, e.enrolled_at AS 신청일
FROM students s
JOIN enrollments e ON e.student_id = s.id   -- students 1 : enrollments N
JOIN courses     c ON c.id = e.course_id    -- courses  1 : enrollments N
ORDER BY s.name, c.title;
막히면 여기 — 결과가 비어 있다면 JOIN 조건의 방향(e.student_id = s.id)을 확인하자. FK는 언제나 N쪽 테이블인 enrollments에 있다.

6) 정규화 (Normalization)

왜 필요한가 — 이상 현상 세 가지

  • 삽입 이상 (Insertion Anomaly) — 일부 데이터 저장 시 불필요한 데이터도 함께 저장해야 함
  • 삭제 이상 (Deletion Anomaly) — 데이터 삭제 시 다른 중요 정보까지 삭제됨
  • 갱신 이상 (Update Anomaly) — 중복 저장된 데이터 중 일부만 수정 → 불일치 발생

말로만 보면 안 와닿으니 예로 보자. 학생과 학과를 한 테이블에 몰아넣었다고 하자.

학번이름학과코드학과명학과사무실
2024001홍길동CS컴퓨터공학공학관 301
2024002이순신BA경영학상경관 105

  • 삽입 이상: 새 학과 "인공지능(AI)"이 신설됐는데 아직 소속 학생이 없다. 학생 없이는 학과를 등록할 수 없다. 학번이 PK인데 넣을 학번이 없기 때문이다.
  • 삭제 이상: 경영학과 학생이 이순신 한 명뿐인데 그가 자퇴했다. 그 행을 지우면 경영학과라는 학과가 존재했다는 사실 자체가 사라진다.
  • 갱신 이상: 컴퓨터공학과 사무실이 공학관 405로 이사했다. 2개 행을 고쳐야 하는데 하나만 고치면, 같은 학과의 사무실이 두 개가 된다.
✔ 세 이상 현상의 뿌리는 하나다
  • "학과에 대한 사실"과 "학생에 대한 사실"이 한 테이블에 섞여 있다. 정규화는 이걸 분리하는 작업이고, 학과 테이블을 따로 만들면 셋 다 사라진다.

정규화 단계

정규형조건제거 대상예시
1NF각 컬럼은 원자값(Atomic Value)만반복 그룹, 다중값 속성"과목 = DB, 네트워크" → 별도 행으로 분리
2NF1NF + 부분 함수 종속 제거복합키 일부에만 종속된 속성(학번+과목코드)가 PK인데 학생이름은 학번에만 종속
3NF2NF + 이행적 종속 제거비-키 속성이 다른 비-키 속성에 종속학번→학과코드→학과명 이행 종속 제거
BCNF3NF + 결정자는 반드시 후보키비후보키 결정자 제거모든 함수 종속의 결정자가 후보키여야 함
  • 1NF — 한 칸에 값이 여러 개면 애초에 종속을 따질 수 없다. 칸을 원자값으로 만든다.
  • 2NF — PK가 (학번, 과목코드) 복합키인데 학생이름은 학번만 알면 정해진다. PK의 일부에만 종속된 것을 떼어낸다. (부분 종속)
  • 3NF — 학번 → 학과코드 → 학과명. 학과명은 PK(학번)에 직접 종속된 게 아니라 학과코드를 거쳐서 종속된다. 이 우회 경로를 떼어낸다. (이행 종속)
  • BCNF — 결정자인데 후보키가 아닌 것을 떼어낸다. 3NF까지 왔는데도 남는 드문 경우를 처리한다.

용어 정리 — 함수 종속과 결정자

  • 함수 종속 (Functional Dependency): "A를 알면 B가 하나로 정해진다"는 관계. A → B로 쓰고 "B는 A에 종속된다"고 읽는다. 학번을 알면 이름이 하나로 정해지므로 학번 → 이름이다. 반대로 이름을 안다고 학번이 정해지지는 않는다.
  • 결정자 (Determinant): 화살표 왼쪽. 학번 → 이름에서 학번이 결정자다.
  • 즉 정규화란 "모든 컬럼이 오직 PK 전체에만 종속되도록 테이블을 쪼개는 것"이고, 각 단계는 그걸 깨는 서로 다른 유형을 하나씩 없앤다.
💡 한 줄로 외우기

모든 컬럼은 키에, 오직 키에만, 키 전체에 의존해야 한다.
(the key, the whole key, and nothing but the key)
— "the whole key"가 2NF(부분 종속 제거), "nothing but the key"가 3NF(이행 종속 제거)다.

🔎 심화 — 두 가지 실전 감각
  • 2NF는 PK가 복합키일 때만 문제가 된다. PK가 단일 컬럼이면 "PK의 일부"라는 게 존재하지 않으므로 1NF를 만족하면 자동으로 2NF다. 실무에서 대체키(일련번호) 단일 PK를 주로 쓰는 것도 2NF 문제를 원천적으로 없애는 효과가 있다.
  • BCNF와 3NF가 갈리는 경우는 드물다. 후보키가 여러 개이고 그것들이 서로 겹칠 때만 차이가 생긴다.

정규화 전/후 비교 — SQL

비정규화 (1NF 위반: 다중값 컬럼)
CREATE TABLE student_bad (
  student_id INT PRIMARY KEY,
  name       VARCHAR(50),
  subjects   VARCHAR(200)   -- "DB, 네트워크, OS" ← 원자값 아님!
);

subjects에 콤마로 이어 붙인 문자열을 넣은 것이 1NF 위반이다. 왜 나쁜가 — "네트워크를 듣는 학생을 모두 찾아라"를 하려면 LIKE '%네트워크%'로 문자열을 뒤져야 하는데, 인덱스를 못 쓰고, "네트워크보안"까지 걸리는 오탐이 생기고, 과목이 하나 추가되면 문자열 전체를 다시 조립해야 한다.

1NF + 2NF + 3NF 적용 후 (분리된 테이블)
CREATE TABLE students (
  id       INT PRIMARY KEY,
  name     VARCHAR(50) NOT NULL,
  major_id INT REFERENCES majors(id)   -- 3NF: 학과명 분리
);

CREATE TABLE majors (
  id   INT PRIMARY KEY,
  code VARCHAR(20) UNIQUE,
  name VARCHAR(100)                    -- major_id → name (이행종속 제거)
);

CREATE TABLE enrollments (
  -- 1NF: 과목 분리 + 2NF 교차테이블
  student_id INT REFERENCES students(id),
  course_id  INT REFERENCES courses(id),
  score      DECIMAL(5,2),
  PRIMARY KEY (student_id, course_id)   -- 복합 PK
);
  • REFERENCES majors(id) — FK를 선언하는 축약 문법. 컬럼 정의 뒤에 바로 붙이는 이 형태를 컬럼 레벨 제약이라 하고, FOREIGN KEY (major_id) REFERENCES majors(id)라고 따로 쓰는 테이블 레벨 제약과 결과는 같다. 복합키를 참조할 때는 테이블 레벨로만 쓸 수 있다.
  • PRIMARY KEY (student_id, course_id) — 두 컬럼을 묶어 PK로 삼는 복합 PK. 이게 있으면 같은 학생이 같은 강좌를 두 번 신청하는 것이 자동으로 막힌다. 별도 중복 체크 코드가 필요 없다는 것이 제약조건의 힘이다.
  • DECIMAL(5,2) — 전체 5자리, 소수점 아래 2자리(즉 999.99까지). 점수·금액에 FLOAT이 아니라 DECIMAL/NUMERIC을 쓰는 이유는 4장에서 다룬다.

  • 결과적으로 인사정보 / 전공정보 / 직위정보 / 회사정보 네 테이블로 나뉘고, 이것으로 관계형 데이터 모델링이 완성된다.

반정규화 (Denormalization)

  • 정규화는 중복을 없애는 대신 테이블 개수를 늘린다. 학생 정보 하나 보려고 students, majors, enrollments, courses를 다 JOIN해야 하면 조회가 느려진다.
  • 그래서 성능이 문제가 되는 지점에 한해 의도적으로 중복을 다시 넣는 것이 반정규화다.
  • 주의 — 순서가 전부다. 정규화를 먼저 하고, 성능 문제가 실제로 측정된 다음에 반정규화한다. 처음부터 "JOIN이 느릴 것 같으니까" 중복을 넣는 것은 반정규화가 아니라 그냥 설계 실수다.
🎓 교수님의 코멘트 — 실무 정규화는 3NF까지

"보통 1·2·3정규화에 BCNF까지 하는데, 실무에서는 3정규화까지만 해도 크게 무리는 없어요. 다만 과도하게 정규화를 하면 한 줄 데이터를 찾으려고 테이블을 열 개 이상 조인해야 해서 조회 시간이 과하게 늘어납니다."

"정규화가 과도해서 조인 부하가 커지면 반정규화를 합니다. 여러 테이블을 조인하는 대신, 한 테이블에 필요한 데이터를 넣어 두고 그것만 가져오면 성능이 빨라지는 거죠." — BCNF는 개념으로 알아 두되 실제 설계의 목표선은 3NF다. 설계는 한 번 하고 끝나는 것이 아니라, 운영하면서 더 쪼갤지 다시 합칠지를 계속 판단해야 한다. (반정규화는 22장에서 다시 다룬다.)

7) 모델링과 SQL의 관계

  • 완료된 데이터 모델링을 토대로 DBMS에 테이블을 생성하고 데이터를 입력/조회/삭제/수정한다 ⇒ SQL(Structured Query Language) 언어 사용
  • 모델링 없이 바로 테이블을 생성할 수는 있으나, 데이터 양이 많아지거나 복잡해지면 데이터 중복 및 오류 등 품질 문제가 발생한다
앞에서 분리한 전공정보 테이블을 실제 SQL로
CREATE TABLE 전공정보 (
    전공코드 Varchar(10) Primary Key,
    역할상세 Varchar(40)
);

INSERT INTO 전공정보 (전공코드, 역할상세)
VALUES ('SNIPER', '저격');
  • 테이블명·컬럼명에 한글을 쓰는 것은 문법상 가능하지만 권장하지 않는다. DBMS·클라이언트·드라이버마다 인코딩 처리가 달라 깨질 수 있다. majors, major_code 같은 영문 소문자 스네이크케이스로 간다.
  • Varchar(10)처럼 대소문자를 섞어 써도 SQL 키워드는 대소문자를 구분하지 않으므로 동작에는 문제가 없다. 관례는 키워드 대문자, 식별자 소문자다.
✔ 여기가 2장과 6장을 잇는 지점
  • 모델링(무엇을 어떻게 나눌지)이 끝나야 DDL(그걸 실제로 만드는 SQL)을 쓸 수 있다. 순서를 뒤집어서 일단 테이블부터 만들고 나중에 고치려 하면, 이미 들어간 데이터 때문에 고치기가 훨씬 어려워진다.

8) 짚고 넘어가기

PK를 여러 개 만들면 안 되나요? 학번도 유일하고 이메일도 유일한데요.
안 됩니다. PK는 테이블당 하나입니다. 다만 이건 제약이 아니라 정의에 가깝습니다. PK는 "이 테이블에서 행을 가리키는 대표 방법"을 하나로 못 박아 두는 것이고, 그래야 다른 테이블이 FK로 참조할 때 무엇을 가리킬지가 명확해집니다. 유일해야 하는 컬럼이 더 있다면 UNIQUE 제약(UK)으로 얼마든지 추가할 수 있습니다. PK 하나 + UK 여러 개가 정상적인 모양입니다. 참고로 PRIMARY KEY (student_id, course_id)처럼 여러 컬럼을 묶은 PK 하나는 가능합니다 — 이건 PK가 여러 개인 게 아니라 컬럼이 여러 개인 PK 하나입니다.
NULL이 허용되니까 UK가 PK보다 유연한 것 아닌가요? 그냥 다 UK로 쓰면 안 되나요?
권장하지 않습니다. PK가 하는 일이 "유일성 보장" 하나가 아니기 때문입니다. PK는 (1) 유일성 보장, (2) NULL 금지, (3) 자동 인덱스 생성, (4) 다른 테이블의 FK가 참조할 대상 지정 네 가지를 합니다. 특히 (4)가 중요합니다. FK가 NULL이 있을 수 있는 컬럼을 참조하면 "무엇을 가리키는지 모르는 참조"가 생겨 참조 무결성이 흐려집니다. 표준은 FK가 PK 또는 UNIQUE 컬럼을 참조하도록 하되, 실무에서는 PK를 참조하는 것이 기본입니다.
1:1 관계면 그냥 한 테이블로 합치면 되지 않나요?
대부분의 경우 맞습니다. 실제로 1:1이 보이면 "합칠 수 있는데 왜 나눴지?"를 먼저 의심하는 게 좋습니다. 나누는 게 정당한 경우는 이유가 따로 있을 때입니다. (1) 한쪽 컬럼이 아주 크고 거의 조회되지 않을 때(프로필 사진 바이너리 등) — 매번 읽어 오는 데이터 양을 줄이려고, (2) 보안 등급이 다를 때 — 주민등록번호만 별도 테이블로 빼서 접근 권한을 다르게 주려고, (3) 한쪽이 선택적일 때 — 회원 중 일부만 사업자 정보를 갖는 경우, 합치면 NULL 컬럼이 잔뜩 생깁니다. 이런 이유가 없으면 합치는 게 맞습니다.
3NF까지 하면 되는데 왜 BCNF를 배우나요?
3NF로 못 잡는 경우가 존재하기 때문입니다. 3NF는 "비-키 속성이 다른 비-키 속성에 종속되는 것"을 막는데, 결정자가 키의 일부인 경우는 걸러내지 못합니다. 후보키가 여러 개이고 서로 겹칠 때 이런 상황이 생깁니다. BCNF는 "모든 결정자는 후보키여야 한다"는 한 줄로 이 구멍까지 막습니다. 다만 실무에서 이런 스키마가 나오는 일은 드물어서, 이름과 한 줄 정의만 알아 두고 실제 설계는 3NF를 목표로 잡으면 충분합니다.
subjects VARCHAR(200)에 "DB, 네트워크, OS"를 넣는 게 왜 그렇게 나쁜가요? 파이썬에서 split(',')으로 나누면 되잖아요.
애플리케이션에서 나눌 수 있다는 것과 DB가 그 값을 다룰 수 있다는 것은 다른 문제입니다. 구체적으로 네 가지가 막힙니다. (1) 검색: "네트워크 수강생 찾기"가 LIKE '%네트워크%'가 되어 인덱스를 못 쓰고, "네트워크보안"까지 잡히는 오탐이 생깁니다. (2) 집계: "과목별 수강 인원"을 SQL로 셀 수 없습니다. (3) 무결성: 존재하지 않는 과목명 오타를 DB가 막아 줄 수 없습니다 — FK를 걸 대상이 없으니까요. (4) 수정: 과목 하나를 빼려면 문자열을 읽어서 파싱하고 다시 조립해 UPDATE해야 하는데, 그 사이에 다른 사람이 같은 작업을 하면 한쪽이 날아갑니다. 별도 행으로 분리하면 넷 다 SQL 한 줄로 해결됩니다.
FK를 걸면 성능이 느려진다던데, 그냥 안 걸고 애플리케이션에서 체크하면 안 되나요?
INSERT/UPDATE/DELETE 때 부모 존재 여부를 확인하는 비용이 있는 건 사실입니다. 하지만 애플리케이션 체크로 대체하는 것은 위험합니다. (1) 애플리케이션이 하나가 아닙니다 — 배치 스크립트, 관리자 도구, 데이터 마이그레이션에서 직접 INSERT하면 그 체크를 안 거칩니다. (2) 동시성 문제가 있습니다 — "부모가 있는지 SELECT로 확인 → INSERT" 사이에 다른 트랜잭션이 부모를 지울 수 있습니다. DB 안에서 하는 FK 체크는 이 틈이 없습니다. 실무에서 FK를 빼는 경우가 없지는 않지만(초대용량 테이블, 샤딩 환경), 그건 다른 방법으로 무결성을 보장할 준비가 되어 있을 때의 선택이지 기본값이 아닙니다.
정규화를 하면 항상 좋은가요?
아닙니다. 정규화는 중복을 테이블 개수와 맞바꾸는 것이고, 테이블이 늘어나면 JOIN이 늘어납니다. 한 줄의 데이터를 얻으려고 열 개 넘는 테이블을 조인하게 되면 그 자체가 부하가 됩니다. 그래서 실무 목표선은 3NF이고, 그 뒤에 성능이 실제로 문제가 된 지점만 골라 반정규화합니다. 중요한 건 순서입니다 — 먼저 정규화하고, 측정하고, 그 다음에 되돌립니다.

1) 왜 이게 필요한가 — 설계의 출발점은 규칙이 아니라 '말'

2장에서 배운 테이블·키·관계는 "무엇을 어떻게 나눌지"에 대한 규칙이었다. 그런데 실제 설계는 규칙을 안다고 바로 되지 않는다. 출발점이 규칙이 아니라 말이기 때문이다.

📋 요구 사항 — 학사 관리 시스템

"학사 관리 시스템을 만들어 주세요. 학생이 강의를 수강하고, 교수가 강의를 담당하고, 학생마다 학과가 있고, 성적을 조회할 수 있어야 합니다."

이 문장 뭉치에서 테이블 몇 개를 뽑아야 하는가? 어떤 게 테이블이고 어떤 게 컬럼인가? 이걸 혼자 머릿속으로 하면 반드시 빠뜨린다. 그래서 그림으로 그려 놓고 다른 사람과 같이 보는 도구가 필요하다. 그것이 ERD다.

ERD(Entity-Relationship Diagram)는 개체–관계 다이어그램이고, 세 가지 요소로 이루어진다.

  • Entity (엔티티) — 관리할 대상. 대체로 테이블이 된다.
  • Attribute (속성) — 엔티티가 가진 특성. 대체로 컬럼이 된다.
  • Relationship (관계) — 엔티티들이 어떻게 연결되는지. FK가 된다.
✔ ERD의 진짜 값어치
  • 그림이 예뻐서가 아니라 비개발자와 대화할 수 있는 형식이라는 데 있다. "학생 한 명이 여러 강의를 듣는 게 맞나요?"를 SQL로 물어볼 수는 없지만 ERD를 보여 주면서는 물어볼 수 있다. 작성 절차의 마지막이 "팀원과 함께 검토"인 이유가 이것이다.

3) Entity (엔티티, 개체)

데이터베이스에서 관리하고자 하는 대상 객체다.

  • 유형 엔티티: 사람, 사물, 장소 (학생, 교수, 강의실)
  • 무형 엔티티: 개념, 사건, 행위 (수강신청, 주문)
  • 엔티티 집합(Entity Set): 동일한 특성을 가진 엔티티들의 모임. 엄밀히는 학생 홍길동 한 명이 엔티티(인스턴스)이고 테이블에 해당하는 것은 엔티티 집합이지만, 실무에서는 둘 다 그냥 "엔티티"라고 부른다.
⚠️ 초보자가 가장 흔히 놓치는 것 — 무형 엔티티

"수강신청"은 손에 잡히지 않으니 테이블이 아닐 것 같지만, 언제 신청했고 몇 점을 받았는지를 저장해야 하므로 반드시 테이블이 되어야 한다. "명사인데 저장할 사실이 딸려 있으면 엔티티"라고 보면 놓치지 않는다.

🎓 실무 이야기 — 엔티티는 요구사항 문장에서 뽑는다

고객사가 "이런 시스템을 만들어 달라"고 말한 시나리오를 읽으면 관리해야 할 대상이 드러난다. 회계 시스템이라면 월별 매출을 관리해야 하므로 매출액, 매출이 발생한 카테고리, 연·월, 날짜 같은 항목이 나온다. 이 단계에서 엔티티를 제대로 뽑지 못하면 정보 자체가 누락되므로, 엔티티 도출은 설계 전체에서 비중이 가장 큰 작업 중 하나다.

강한 엔티티 vs 약한 엔티티

강한 엔티티 (Strong Entity)약한 엔티티 (Weak Entity)
PK독자적인 PK 존재, 혼자서도 식별 가능독자적 PK 없음, 다른 강한 엔티티에 의존해야 식별 가능
예학생(학번), 강좌(강좌코드), 교수(교수번호)OrderItem — OrderID + ItemNo 복합키 (Order 없이 존재 불가)
ERD 표기사각형이중 사각형, 식별 관계는 굵은 선
삭제—부모 엔티티 삭제 시 자식도 삭제 (ON DELETE CASCADE)

약한 엔티티를 이해하는 열쇠는 "3번 항목"이라는 말이 성립하지 않는다는 데 있다. 주문항목 번호 3번은 그 자체로 아무것도 가리키지 못한다. "12345번 주문의 3번 항목"이라고 해야 비로소 하나가 특정된다. 그래서 PK가 (order_id, item_no) 복합키가 되고, item_no 혼자서는 부분키(partial key)라고 부른다.

⚠️ 약한 엔티티와 "FK를 가진 엔티티"는 다르다

성적 테이블은 학생 FK를 갖지만 약한 엔티티가 아니다. 성적에 자체 id(PK)를 주면 학생 없이도 행을 식별할 수 있기 때문이다. 판단 기준은 FK가 PK에 포함되는가다. 포함되면 약한 엔티티(식별 관계), 안 되면 강한 엔티티(비식별 관계)다.

4) Attribute (속성) — 네 쌍으로 나눠 보기

엔티티가 가지는 고유한 특성이나 성질. 학생 엔티티의 속성: 학번, 이름, 이메일, 학과, 학년, 입학일 등.

① 단순 속성 vs 복합 속성

  • 단순 속성 (Simple) — 더 이상 나눌 수 없는 원자값. 전화번호, 성별, 생년월일
  • 복합 속성 (Composite) — 여러 단순 속성으로 구성. 주소 = 시 + 구 + 동 + 상세주소
  • 복합 속성은 쪼갤지 말지를 결정해야 한다. 기준은 "그 부분만 따로 쓸 일이 있는가". 지역별 통계를 낼 거라면 city, district를 따로 두어야 하고, 그냥 배송지로 출력만 할 거라면 address 한 컬럼으로 둬도 된다. 나중에 쪼개려면 이미 쌓인 문자열을 파싱해야 하므로 훨씬 비싸진다.

② 단일값 속성 vs 다중값 속성

  • 단일값 (Single-valued) — 하나의 값만 가짐. 주민등록번호 → 한 사람당 하나
  • 다중값 (Multi-valued) — 여러 값을 가질 수 있음(이메일 여러 개, 취미 여러 개) → 별도 테이블로 분리(1NF)
✔ 2장과의 연결 고리
  • 다중값 속성은 관계형 테이블에 그대로 담을 수 없다. subjects = "DB, 네트워크, OS"가 1NF 위반이었던 그 문제다. 다중값 속성을 발견하면 그건 곧 새 테이블이 하나 필요하다는 신호다.

③ 유도 속성 vs ④ 기본키 속성

  • 유도 속성 (Derived) — 다른 속성으로부터 계산 가능 → DB에 직접 저장 불필요. 나이 = 현재연도 − 출생연도(생년월일에서 유도)
  • 기본키 속성 (Key) — 엔티티를 고유하게 식별 → ERD에서 밑줄로 표시

유도 속성을 저장하지 말라는 원칙은 실제로 사고를 막아 준다. 나이를 컬럼으로 저장해 두면 매년 전 회원의 나이를 갱신하는 배치가 필요하고, 그 배치가 하루라도 실패하면 데이터가 틀린다. 생년월일만 저장하고 나이는 조회 시점에 계산하면 틀릴 수가 없다.

나이를 저장하지 않고 계산 (PostgreSQL)
SELECT name,
       EXTRACT(YEAR FROM AGE(birth_date)) AS age
FROM students;
  • AGE(birth_date) — 오늘과 인자 사이의 간격을 interval 타입("21 years 3 mons 5 days" 같은 값)으로 돌려준다.
  • EXTRACT(YEAR FROM ...) — 그 interval에서 연 부분만 뽑는다. 결과적으로 만 나이가 나온다.
  • 단순히 현재연도 - 출생연도로 계산하면 생일이 안 지난 사람의 나이가 1살 많게 나온다. 실제로는 생일 경과 여부를 따져야 한다.
🔎 심화 — 유도 속성을 저장해도 되는 경우와 생성 컬럼

계산이 매우 비싸고 조회는 잦은 경우(예: 게시글마다 댓글 수), 계산값을 컬럼에 들고 있는 것이 정당할 때가 있다. 이게 22장에서 다룰 반정규화의 한 형태다. 다만 그러면 "원본이 바뀔 때 이 값도 반드시 같이 갱신된다"를 트리거(25장)나 애플리케이션 로직으로 보장해야 한다.

PostgreSQL 12+에는 생성 컬럼(generated column)이 있어서 유도 속성을 안전하게 저장할 수 있다. total NUMERIC GENERATED ALWAYS AS (price * qty) STORED처럼 선언하면 DB가 자동으로 계산해서 유지하므로 사람이 갱신을 잊을 여지가 없다.

5) ERD 작성 — 7단계

단계하는 일예
1. 요구사항 수집시스템에서 관리해야 할 정보, 업무 흐름을 파악학생 관리 시스템에서는 학생, 강의, 교수, 과제 등
2. 엔티티 도출관리 대상의 주요 객체를 추출해 엔티티로 정의 (주로 명사)학생(Student), 강의(Course), 교수(Professor)
3. 속성 정의각 엔티티가 가져야 할 특징(속성)을 정리학생 → 학번, 이름, 전공 / 강의 → 강의코드, 강의명
4. 관계 설정엔티티 간의 연관성 파악, 관계 정의학생–강의는 '수강한다' / 교수–강의는 '담당한다'
5. 카디널리티관계의 수(1:1, 1:N, N:M)를 명확히 표시한 학생은 여러 강의를 수강, 한 강의는 여러 학생이 수강 → N:M
6. ERD 시각화도형으로 표현 후 검토사각형: 엔티티 / 타원: 속성 / 마름모: 관계 · dbdiagram, Lucidchart 등
7. 검토 및 수정팀원과 함께 검토, 데이터 무결성 및 요구사항 반영 여부 확인—
💡 2단계 "주로 명사"가 실전 요령

"학생이 강의를 수강한다. 교수가 강의를 담당한다."

명사 셋 → 엔티티 셋(학생, 강의, 교수). 동사 둘 → 관계 둘(수강, 담당). 그리고 "수강"은 N:M이므로 교차 테이블이 되어 결국 엔티티가 하나 더 늘어난다.

🎓 실무 이야기 — 요구사항부터 훑고, 범례를 반드시 넣는다

요구사항을 받으면 곧바로 엔티티를 뽑지 말고, 이 시스템을 누가 쓸지 페르소나를 먼저 정하고 그 사용자가 어떤 흐름으로 시스템을 쓰는지 비즈니스 프로세스를 그려 본다. 그 흐름 위에서 대상을 골라내야 누락이 줄어든다. ERD도 한 번 그리고 끝내지 말고 반복해서 리뷰한 뒤 마무리한다.

그리고 ERD에는 범례를 반드시 넣는다. "이 정도는 다 알겠지" 하고 범례를 빼는 경우가 많은데, 이 문서는 개발자만 보는 것이 아니라 고객사와 현업 담당자도 본다. 산출물은 커뮤니케이션 도구다.

짚어 둘 것 — 6단계의 "사각형/타원/마름모"는 Chen 표기법의 기호다. 그런데 뒤에서 실제로 쓰는 것은 IE 표기법이고, IE에서는 속성을 타원으로 그리지 않고 엔티티 상자 안에 목록으로 적는다. 두 표기법이 한 자료에 섞여 있는 셈인데, 이 과정에서 실제로 그릴 것은 IE 쪽이다.

6) IE 표기법 (까마귀발, Crow's Foot)

이름이 두 개다. IE는 Information Engineering의 약자이고, 관계선 끝이 새 발자국처럼 세 갈래로 갈라져서 까마귀발(Crow's Foot)이라고도 부른다.

기호의미
│하나 (One)
< (까마귀발)여럿 (Many)
○없거나 하나 (Zero or One)
‖반드시 하나 (One and Only One)

읽는 법에 규칙이 하나 있다. 기호는 선의 반대쪽 끝에 붙는다. 학생과 성적을 잇는 선에서 성적 쪽 끝에 까마귀발이 있다면, "학생 하나에 성적이 여럿"이라는 뜻이다. 그리고 기호는 대개 두 개가 짝으로 붙는다 — 바깥쪽(선 끝에서 먼 쪽)이 최소 개수(참여도), 안쪽이 최대 개수(카디널리티)다.

모양최소/최대읽는 법예
─○<최소 0, 최대 다Zero or many학생은 강의를 하나도 안 들을 수도, 여러 개 들을 수도 있다
─│<최소 1, 최대 다One or many주문에는 주문항목이 최소 하나는 있어야 한다
─○│최소 0, 최대 1Zero or one학생은 학생증이 없을 수도 있다
─‖최소 1, 최대 1One and only one성적은 반드시 한 학생의 것이다
✔ 그림과 스키마가 맞물리는 지점
  • 이 "최소 0이냐 1이냐"가 실제 DDL에서 FK 컬럼의 NULL 허용 여부로 번역된다. 최소 0이면 FK가 NULL 가능, 최소 1이면 NOT NULL이다.

관계선 종류 — 식별 관계와 비식별 관계

식별 관계 (실선)비식별 관계 (점선)
FK의 위치FK가 자식의 PK 일부FK가 자식의 일반 컬럼
존재 의존성부모 없이 자식 존재 불가 (약한 엔티티)부모 없이도 자식 존재 가능
셋은 같은 사실의 세 가지 표현 — 하나만 정하면 나머지는 따라온다
약한 엔티티  =  식별 관계   =  실선  =  FK가 PK에 포함됨   (order_items)
강한 엔티티  =  비식별 관계 =  점선  =  FK가 일반 컬럼      (students → majors)

7) dbdiagram.io와 DBML

DBML (Database Markup Language)은 ERD를 그림 도구로 끌어다 그리는 대신 텍스트로 쓰는 언어다. 왼쪽에 코드를 치면 오른쪽에 ERD가 자동으로 그려지고, SQL DDL로 내보낼 수도 있다. 마우스로 상자를 옮겨 가며 그리는 것보다 훨씬 빠르고, 무엇보다 텍스트라서 Git으로 버전 관리가 된다.

DBML 예제 — 네 테이블을 통째로 붙여 넣어 보자
// dbdiagram.io (DBML) — SQL 없이 빠르게 ERD 작성 → SQL DDL 자동 생성

Table students {
  id          bigint       [pk, increment, note: 'PK']
  student_no  varchar(20)  [unique, not null, note: '학번']
  name        varchar(100) [not null]
  email       varchar(200) [unique, not null]
  major_id    int          [ref: > majors.id, note: 'FK → 학과']
  grade       smallint     [not null, note: '1~4학년']
  created_at  timestamp    [default: 'now()']
}

Table majors {
  id   int          [pk, increment]
  code varchar(20)  [unique, not null]
  name varchar(100) [not null]
}

Table courses {
  id      int          [pk, increment]
  code    varchar(20)  [unique, not null]
  title   varchar(200) [not null]
  credits smallint     [not null]
}

Table enrollments {          // N:M 교차 테이블
  student_id  bigint [ref: > students.id]
  course_id   int    [ref: > courses.id]
  score       decimal(5,2)
  enrolled_at date   [not null]

  Indexes {
    (student_id, course_id) [pk]   // 복합 PK
  }
}

// 관계 방향: > 다대일, < 일대다, - 일대일, <> 다대다

문법 해설

  • [pk, increment] — PK이면서 자동 증가. SQL로 내보내면 PostgreSQL은 SERIAL/IDENTITY, MySQL은 AUTO_INCREMENT로 변환된다.
  • [ref: > majors.id] — 이 컬럼이 majors.id를 참조하는 FK라는 선언. 화살표 방향이 중요하다. >는 "이쪽이 다(多), 저쪽이 일(一)". 방향을 뒤집어 <로 쓰면 ERD의 까마귀발이 반대쪽에 붙어 완전히 다른 모델이 된다.
  • [note: '...'] — 그 컬럼에 붙는 주석. ERD 그림과 내보낸 SQL에 코멘트로 남는다. 채점자가 읽으므로 한글 설명을 적어 두면 좋다.
  • [default: 'now()'] — 기본값. DBML에서 함수 호출 기본값은 따옴표 안에 쓴다.
  • Indexes { (student_id, course_id) [pk] } — 복합 PK는 컬럼 옆이 아니라 Indexes 블록 안에서 선언한다. 이걸 몰라서 두 컬럼에 각각 [pk]를 붙이면 PK가 두 개 생겨 에러가 난다.

따라 하기 — DBML로 ERD를 그리고 SQL까지 뽑아 보기

  • ① dbdiagram.io에 접속한다(로그인 없이도 쓸 수 있다).
  • ② 왼쪽 편집기에 위 네 테이블(students, majors, courses, enrollments)을 모두 붙여 넣는다.
  • ③ 오른쪽에 ERD가 그려지는지 확인한다. students와 majors 사이 선의 까마귀발이 students 쪽에 붙어 있어야 맞다.
  • ④ 상단 Export → PostgreSQL을 눌러 SQL을 받아 본다.
내보내면 나오는 DDL (발췌)
CREATE TABLE "students" (
  "id" bigserial PRIMARY KEY,
  "student_no" varchar(20) UNIQUE NOT NULL,
  "name" varchar(100) NOT NULL,
  "email" varchar(200) UNIQUE NOT NULL,
  "major_id" int,
  "grade" smallint NOT NULL,
  "created_at" timestamp DEFAULT (now())
);

ALTER TABLE "students" ADD FOREIGN KEY ("major_id") REFERENCES "majors" ("id");
  • 내보낸 SQL은 식별자를 전부 큰따옴표로 감싼다. PostgreSQL에서 큰따옴표로 감싼 식별자는 대소문자가 고정된다. 소문자로만 쓴 경우에는 문제되지 않지만, 6장에서 따옴표를 지양하라고 하는 이유가 이것이다.
  • FK가 CREATE TABLE 안이 아니라 별도 ALTER TABLE로 나온다. 테이블 생성 순서에 상관없이 동작하게 하려는 것이다. 손으로 DDL을 쓸 때 참조 대상 테이블을 먼저 만들어야 하는 문제를 이 방식으로 피할 수 있다.
자동 생성 DDL을 그대로 제출하지 말자. CHECK 제약, ON DELETE 옵션, 코멘트가 빠져 있다. 8장 실습이 "제약조건 포함 DDL 작성"을 요구하므로, 내보낸 SQL을 출발점으로 삼고 제약조건을 직접 얹어야 한다.

8) 함정 / 감점 포인트

  • ERD에 범례를 안 넣기 — 제출 조건에 "ERD 내 범례 추가할 것(설명문)"이 명시되어 있다. 실선/점선/까마귀발이 무엇을 뜻하는지 그림 옆에 적자.
  • 관계선이 겹치게 그리기 — "각 연결관계가 잘 보이도록 할 것(선 겹침 금지)". 엔티티 배치를 몇 번 옮겨서라도 선이 교차하지 않게 정리하자.
  • 카디널리티 기호를 안 붙이기 — 선만 그어 놓고 1:N인지 N:M인지 표시하지 않으면 ERD로서 정보가 절반이다.
  • 관계 방향 뒤집기 — DBML의 >와 <를 헷갈리면 ERD가 통째로 틀린다. 그린 뒤 "까마귀발이 N쪽에 붙었는가"를 눈으로 확인하자.
  • 다중값 속성을 컬럼 하나로 두기 — "취미", "자격증"처럼 여러 개일 수 있는 것을 콤마 문자열로 두면 1NF 위반. ERD 단계에서 별도 엔티티로 뽑아야 한다.
  • 유도 속성을 저장하기 — 나이·합계 금액처럼 계산 가능한 것을 컬럼으로 만들면 지적받는다. 정당한 이유(성능)가 있다면 그 이유를 리포트에 적자.

9) 짚고 넘어가기

엔티티와 테이블은 같은 말 아닌가요?
거의 같지만 정확히는 다릅니다. 엔티티는 개념 수준의 용어이고, 테이블은 구현 수준의 용어입니다. 대부분의 엔티티는 테이블 하나가 되지만 예외가 있습니다. N:M 관계는 엔티티가 둘인데 테이블은 셋이 되고(교차 테이블 추가), 상속 관계(정규직/계약직이 모두 직원)는 설계 전략에 따라 엔티티 셋이 테이블 하나가 되기도 합니다(4장의 Single Table vs Class Table). 그래서 4장에서 개념 → 논리 → 물리 3단계를 따로 배웁니다. 그 단계 구분이 곧 "엔티티가 테이블로 굳어지는 과정"입니다.
요구사항의 명사를 전부 엔티티로 만들면 되나요?
아닙니다. 명사 추출은 후보를 빠짐없이 모으는 단계이지 최종 답이 아닙니다. 걸러내야 할 것이 두 종류입니다. 첫째, 다른 엔티티의 속성인 명사 — "학생의 이름"에서 이름은 엔티티가 아니라 속성입니다. 둘째, 시스템 자체나 화면을 가리키는 명사 — "학사 관리 시스템", "조회 화면"은 저장할 데이터가 아닙니다. 판별 기준은 "이것에 대해 저장할 사실이 두 개 이상 있는가"입니다. 이름은 그 자체가 값 하나이므로 속성이고, 학과는 코드·명칭·사무실 등 여러 사실을 갖고 있으므로 엔티티입니다.
나이를 컬럼으로 저장하면 조회할 때 계산 안 해도 되니까 더 빠르지 않나요?
조회는 빨라지지만 틀릴 위험을 사는 것입니다. 저장해 두면 매일 자정에 생일 지난 사람의 나이를 올려 주는 작업이 필요하고, 그 작업이 한 번이라도 실패하거나 누락되면 DB의 나이가 현실과 어긋납니다. 그리고 그 어긋남은 조용히 일어나서 한참 뒤에 발견됩니다. 반면 생년월일만 저장하고 계산하면 틀릴 방법 자체가 없습니다. 계산 비용이 문제가 될 만큼 큰 경우에만 저장을 고려하고, 그때도 PostgreSQL의 생성 컬럼처럼 DB가 자동으로 유지해 주는 장치를 쓰는 게 안전합니다.
약한 엔티티는 그냥 자체 id를 PK로 주면 강한 엔티티가 되는 것 아닌가요?
물리적으로는 그렇게 만들 수 있고, 실무에서 실제로 그렇게 하기도 합니다. order_items에 id BIGSERIAL PRIMARY KEY를 주고 order_id는 일반 FK로 두면 됩니다. 다만 그렇게 하면 "한 주문 안에서 항목 번호가 1, 2, 3으로 이어진다"는 업무 규칙이 스키마에서 사라집니다. 복합 PK (order_id, item_no)는 그 규칙을 DB가 강제해 주지만, 대체키 PK는 그러지 않으므로 별도 UNIQUE 제약을 걸어야 같은 효과가 납니다. 어느 쪽이 옳다기보다 "이 데이터가 부모 없이 의미가 없다"는 사실을 인식하는 것이 핵심이고, PK를 어떻게 줄지는 그다음 선택입니다. 어떻게 하든 ON DELETE CASCADE는 걸어야 합니다.
실선/점선 구분은 그냥 그림 취향 아닌가요? 꼭 지켜야 하나요?
지켜야 합니다. 실선/점선은 장식이 아니라 FK가 PK에 들어가는지 아닌지를 나타내는 정보입니다. ERD를 보는 사람은 선 모양만으로 "이 자식은 부모 없이 존재할 수 있는가"를 판단합니다. 아무 데나 실선을 쓰면 읽는 사람이 잘못된 스키마를 상상하게 됩니다. 게다가 대부분의 ERD 도구는 실선/점선 선택이 곧 PK 구성에 반영되므로, 잘못 그으면 내보낸 DDL도 잘못 나옵니다.
dbdiagram.io로 SQL을 뽑을 수 있으면 6장의 DDL은 왜 배우나요?
세 가지 이유입니다. 첫째, 자동 생성 SQL은 불완전합니다 — CHECK 제약, ON DELETE 옵션, 인덱스, 코멘트, 타입 세부 선택은 손으로 넣어야 합니다. 둘째, 읽을 줄 알아야 검증할 수 있습니다 — 도구가 뽑아 준 DDL이 내 의도대로인지 확인하려면 DDL을 읽을 줄 알아야 합니다. 셋째, 운영 중 변경은 도구가 못 해 줍니다 — 이미 데이터가 들어 있는 테이블에 컬럼을 추가하는 ALTER TABLE은 처음부터 다시 만드는 것과 전혀 다른 문제이고, 이건 손으로 써야 합니다.

ALTER TABLE students DROP COLUMN IF EXISTS phone CASCADE;

10. SQL 중급 — 집계 & 그룹화

집계함수, GROUP BY, HAVING, ROLLUP, CUBE, FILTER

💡
쉽게 말하면: GROUP BY는 '학과별로 묶어서 평균 내줘' 같은 명령이에요. 엑셀 피벗테이블이랑 비슷하다고 생각하면 편해요.

집계 함수 핵심 5가지

  • COUNT(*): NULL포함 전체 / COUNT(col): NULL제외 / COUNT(DISTINCT col): 고유값 개수
  • SUM/AVG: NULL 자동 제외. AVG(NULL)=NULL (0이 아님에 주의!)
  • MIN/MAX: 문자열도 가능(알파벳/유니코드 순)
  • FILTER(PostgreSQL 전용): COUNT(*) FILTER (WHERE score>=80) — 다른 DBMS는 SUM(CASE WHEN...THEN 1 ELSE 0 END)
GROUP BY / HAVING
SELECT department_id, COUNT(*) AS emp_count, ROUND(AVG(salary),0) AS avg_salary
FROM employees
WHERE hire_date >= '2020-01-01'   -- 집계 전 행 필터 (WHERE)
GROUP BY department_id
HAVING COUNT(*) >= 3 AND AVG(salary) >= 5000   -- 집계 후 그룹 필터 (HAVING)
ORDER BY avg_salary DESC;
-- FILTER 절
SELECT COUNT(*) AS total,
 COUNT(*) FILTER (WHERE true_label = pred_label) AS correct,
 ROUND(COUNT(*) FILTER (WHERE true_label=pred_label)::NUMERIC / COUNT(*), 3) AS accuracy
FROM prediction_results;
ROLLUP / CUBE — 다차원 소계
-- ROLLUP: 계층적 소계 (지역별 → 전체합), 빠름
SELECT region, product, SUM(amount) AS total FROM sales_summary GROUP BY ROLLUP(region, product);
-- 결과: (East,A,100),(East,B,150),(East,NULL,250)... ,(NULL,NULL,500)
-- CUBE: 모든 조합 소계 (지역+상품+전체), 느림
SELECT region, product, SUM(amount) FROM sales_summary GROUP BY CUBE(region, product);
-- GROUPING 함수로 소계행에 라벨 부여
SELECT CASE WHEN GROUPING(region)=1 THEN '전체' ELSE region END AS region_label,
 SUM(amount) FROM sales_summary GROUP BY ROLLUP(region, product);

집계 쿼리 성능 최적화 포인트

  • SELECT에 GROUP BY 키 이외 컬럼 포함 금지 (MySQL ONLY_FULL_GROUP_BY 모드에서 에러)
  • OFFSET 페이지네이션 함정: LIMIT 10 OFFSET 990 → DB가 990개 읽고 버림 = O(N). 해결: Cursor/Keyset 방식 WHERE id > :last_id
  • ORDER BY + 인덱스: INDEX(dept_id, salary DESC)면 Sort 노드 제거 가능
  • 통계 테이블 전략: 자주 쓰는 집계값을 별도 테이블에 미리 계산(트리거 갱신) 또는 Materialized View + 주기적 REFRESH

11. SQL 고급 — JOIN 알고리즘

NL·Hash·Merge·BNL/BKA · DBMS별 엔진 비교

💡
쉽게 말하면: JOIN을 DB가 내부적으로 어떻게 처리하는지예요. 몰라도 쿼리는 짤 수 있지만, 알면 '왜 이 쿼리가 느린지' 이해하는 데 도움돼요.
알고리즘 동작 방식 적합한 경우
Nested Loop Join(NLJ)외부 테이블 행마다 내부 테이블 탐색외부 집합 작을 때 / 내부 인덱스 있을 때
Hash Join(HJ)작은쪽 해시테이블, 큰쪽 프로브탐색대용량 등가 조인, 인덱스 없을 때
Sort-Merge Join(SMJ)양쪽 정렬 후 병합 매칭이미 정렬된 대용량, 범위/비등가 조인
BNL/BKA(MySQL)여러 행을 버퍼에 모아 배치 조회join_buffer_size로 튜닝
실행계획으로 JOIN 알고리즘 확인
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT s.name, c.title, e.score FROM students s
 JOIN enrollments e ON e.student_id = s.id
 JOIN courses c ON c.id = e.course_id
WHERE s.grade = 3;
-- Hash Join (cost=12.5..45.8 rows=200) (actual time=0.5..2.3 rows=185)
-- Buffers: shared hit=12 read=5   ← hit=메모리(빠름), read=디스크(느림)
-- -> Seq Scan on enrollments  ← Full Scan, 인덱스 검토 필요
-- -> Index Scan on students   ← 인덱스 사용 중
-- MySQL 8.0.18+: Hash Batches > 1 → work_mem 부족 신호(Spill 발생)

JOIN 성능 튜닝 체크리스트

  • FK 컬럼에 반드시 인덱스! (ON DELETE CASCADE 대상 포함)
  • 작은×큰 테이블+인덱스 → Nested Loop / 대형×대형 → Hash
  • ON 조건 누락 주의 → 카르테시안 곱(N×M행) 발생
  • PostgreSQL: work_mem·hash_mem_multiplier 확인, Hash Batches>1 → Spill 신호
  • MySQL: join_buffer_size 설정, 8.0.18+ Hash Join 후보
  • SQL Server: tempdb Spill 감지 → 통계 갱신, Adaptive Join(2017+) 활용

12. JOIN 종류 상세

INNER · OUTER · SELF · CROSS · Anti-Join · Semi-Join

💡
쉽게 말하면: 여러 테이블을 합쳐 보는 여러 방법이에요. INNER=둘 다 있는 것만, LEFT=왼쪽 기준으로 다 보여주고 없으면 빈칸(NULL).
종류 설명
INNER JOIN두 테이블 모두 매칭되는 행만(교집합) — JOIN만 쓰면 기본값
LEFT OUTER JOIN왼쪽 전체 + 오른쪽 없으면 NULL
RIGHT OUTER JOIN오른쪽 전체 + 왼쪽 없으면 NULL (실무에선 LEFT로 방향 바꿔쓰는게 관례)
FULL OUTER JOIN양쪽 모두 보존. MySQL 미지원 → LEFT UNION RIGHT로 우회
SELF JOIN같은 테이블 2개처럼 조인 (직원-상사 계층)
CROSS JOIN카르테시안 곱(N×M) — 의도적으로만 사용
Anti-Join 패턴
-- Anti-Join: 한 번도 수강하지 않은 학생 (3가지 방법)
-- 1) LEFT JOIN + IS NULL (직관적)
SELECT s.name FROM student s LEFT JOIN enroll e ON e.student_id=s.id WHERE e.student_id IS NULL;
-- 2) NOT EXISTS (성능 우수, NULL 안전 - 권장!)
SELECT s.name FROM student s WHERE NOT EXISTS (SELECT 1 FROM enroll e WHERE e.student_id=s.id);
-- 3) NOT IN (NULL 함정 주의! 서브쿼리에 NULL 있으면 전체 결과가 빈 집합)
SELECT s.name FROM student s WHERE s.id NOT IN (SELECT student_id FROM enroll);
✔ Checkpoint
  • NOT IN vs NOT EXISTS: NULL 안전성·성능 모두 NOT EXISTS가 우수 → NOT EXISTS 선호
실무 활용 패턴
-- SELF JOIN: 직원-상사 계층
SELECT e.name AS employee, m.name AS manager
FROM employees e LEFT JOIN employees m ON m.id = e.manager_id;
-- 고객별 주문통계 (LEFT JOIN + COALESCE)
SELECT c.customer_name, COUNT(o.order_id) AS order_count, COALESCE(SUM(o.amount),0) AS total_spent
FROM customers c LEFT JOIN orders o ON o.customer_id=c.customer_id
GROUP BY c.customer_id, c.customer_name ORDER BY total_spent DESC;

💡
쉽게 말하면: 쿼리 안에 또 쿼리(서브쿼리)를 넣거나, 두 쿼리 결과를 더하고·빼고·겹치는 부분만 찾는(집합연산) 방법이에요.
유형 위치 특징
스칼라 서브쿼리SELECT 절단일값 하나 반환, 행마다 실행 → 성능주의, JOIN 대체 검토

WHERE절 서브쿼리WHERE비교조건, 단일값(=)/다중행(IN/ANY/ALL/EXISTS)
상관 서브쿼리WHERE 등바깥쿼리 컬럼 참조 → 행마다 독립실행, JOIN/CTE로 대체 권장
EXISTS / IN / ANY / ALL
-- EXISTS(효율적, 존재만 확인) vs IN vs NOT EXISTS(권장)
SELECT name FROM students s WHERE EXISTS (SELECT 1 FROM enrollments e WHERE e.student_id=s.id);
SELECT name FROM students s WHERE NOT EXISTS (SELECT 1 FROM enrollments e WHERE e.student_id=s.id);
-- NOT IN의 NULL 함정: 서브쿼리에 NULL 하나라도 있으면 전체 결과가 빈 집합!
-- ANY: 하나이상 만족(=,>MIN과 동일) / ALL: 모두 만족(=,>MAX와 동일)
WHERE salary > ANY (SELECT salary FROM employees WHERE dept='HR')
WHERE salary > ALL (SELECT salary FROM employees WHERE dept='HR')

SELECT ... UNION ALL SELECT ...; -- 합집합(중복포함, 더 빠름 - 정렬/비교 불필요)
SELECT customer_id FROM orders WHERE ... 2024 INTERSECT SELECT customer_id FROM orders WHERE ... 2025; -- 교집합
SELECT student_id FROM enrollments WHERE course='DB' EXCEPT SELECT student_id ... WHERE course='Algorithm'; -- 차집합(Oracle: MINUS)

14. CTE · View · Materialized View

WITH · 재귀 CTE · 뷰 활용 전략

💡
쉽게 말하면: CTE(WITH절)는 복잡한 쿼리에 임시로 이름 붙여서 마치 테이블처럼 재사용하는 것, View는 자주 쓰는 쿼리를 아예 저장해두고 테이블처럼 불러쓰는 것이에요.
CTE(Common Table Expression) — WITH 절
WITH dept_avg AS (
  SELECT dept_id, AVG(salary) AS avg_sal FROM employees GROUP BY dept_id )
SELECT e.emp_name, e.salary, d.avg_sal, e.salary-d.avg_sal AS diff
FROM employees e JOIN dept_avg d ON d.dept_id=e.dept_id
WHERE e.salary > d.avg_sal ORDER BY diff DESC;
재귀 CTE — 계층형 데이터 탐색 (조직도, 카테고리 트리)
WITH RECURSIVE org_tree AS (
  -- 기저 단계(Anchor)
  SELECT id, emp_name, manager_id, 1 AS depth, emp_name::TEXT AS path
  FROM employees WHERE manager_id IS NULL
  UNION ALL
  -- 재귀 단계
  SELECT e.id, e.emp_name, e.manager_id, t.depth+1, t.path || ' > ' || e.emp_name
  FROM employees e JOIN org_tree t ON t.id = e.manager_id
  WHERE t.depth < 10   -- ← 무한재귀 방지! 항상 필요
)
SELECT depth, REPEAT(' ', depth-1) || emp_name AS indented_name, path FROM org_tree ORDER BY path;
View / Materialized View
-- 일반 View: 조회할 때마다 쿼리 실행(항상 최신)
CREATE OR REPLACE VIEW v_student_dashboard AS
SELECT s.id, COUNT(e.id) AS course_count, ROUND(AVG(e.score),2) AS avg_score
FROM students s LEFT JOIN enrollments e ON e.student_id=s.id GROUP BY s.id;
-- Materialized View(PostgreSQL): 결과를 디스크에 저장 → 빠른 조회, 인덱스 생성 가능
CREATE MATERIALIZED VIEW mv_monthly_sales AS
SELECT DATE_TRUNC('month', order_date) AS month, SUM(amount) AS total_sales FROM orders GROUP BY 1;
CREATE INDEX ON mv_monthly_sales (month);
REFRESH MATERIALIZED VIEW CONCURRENTLY mv_monthly_sales; -- 잠금 없이 갱신 (자동 아님! pg_cron 등 필요)

15. Windows Function – 분석 함수

ROW_NUMBER · RANK · DENSE_RANK · NTILE · LAG · LEAD · 누적합 · 이동평균 (+부록: LATERAL, UPSERT, JSONB, RAG 등)

💡
쉽게 말하면: GROUP BY랑 비슷한데 그룹으로 묶어도 원래 행이 사라지지 않는 것이 핵심 차이예요. 순위 매기기(RANK), 전월 대비(LAG) 같은 데 씁니다. 이 세션은 분량이 많은데 뒤쪽 '[참고]'는 실무 심화 부록이라 처음엔 앞부분(순위/LAG/누적합)만 확실히 이해해도 충분해요.
GROUP BY Window Function
동작그룹으로 집계 → 행 수 줄어듦(개별행 소실)집계하면서도 원래 행 유지 → 행별결과+집계값 동시
기본 문법 — PARTITION BY(분석단위구분) · ORDER BY(윈도우내정렬) · ROWS/RANGE(집계범위 프레임)
함수명() OVER ([PARTITION BY 컬럼] [ORDER BY 컬럼] [ROWS/RANGE 프레임])

핵심 함수 분류

  • 순위함수: ROW_NUMBER(고유번호 1,2,3,4) / RANK(동점시 같은순위,건너뜀 1,2,2,4) / DENSE_RANK(동점시 같은순위,연속 1,2,2,3) / NTILE(n)(n개그룹균등분할)
  • 이동/비교함수: LAG(col,n) / LEAD(col,n) / FIRST_VALUE / LAST_VALUE
  • 집계Window: SUM/AVG/COUNT/MIN/MAX OVER() — 누적합, 이동평균
ROW_NUMBER / RANK / DENSE_RANK 비교
SELECT region, month, revenue,
 ROW_NUMBER() OVER (PARTITION BY region ORDER BY revenue DESC) AS row_num,
 RANK()       OVER (PARTITION BY region ORDER BY revenue DESC) AS rank_r,
 DENSE_RANK() OVER (PARTITION BY region ORDER BY revenue DESC) AS d_rank,
 NTILE(3)     OVER (PARTITION BY region ORDER BY revenue DESC) AS tier
FROM sales;
LAG/LEAD — 전월 대비 증감 (NULLIF로 0나누기 방지)
SELECT region, month, revenue,
 LAG(revenue,1) OVER (PARTITION BY region ORDER BY month) AS prev_month_sales,
 ROUND((revenue - LAG(revenue,1) OVER (PARTITION BY region ORDER BY month))
   / NULLIF(LAG(revenue,1) OVER (PARTITION BY region ORDER BY month),0) * 100, 1) AS mom_growth_pct,
 LEAD(revenue,1) OVER (PARTITION BY region ORDER BY month) AS next_month_sales
FROM sales;
-- 활용: MoM/YoY(LAG 12개월전) 성장률, 연속 이벤트 감지, 대기시간 계산
누적합 / 이동평균 — ROWS vs RANGE 프레임
-- 누적합
SUM(revenue) OVER (PARTITION BY region ORDER BY month
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS cumulative_revenue
-- 3개월 이동평균
AVG(revenue) OVER (PARTITION BY region ORDER BY month
  ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS ma_3month
-- ROWS: 물리적 행 개수 기준(정확) / RANGE: 논리적 값(ORDER BY 값 같으면 모두 포함) 기준
-- 프레임 키워드: UNBOUNDED PRECEDING / N PRECEDING / CURRENT ROW / N FOLLOWING / UNBOUNDED FOLLOWING
실무 패턴 — TOP-N per Group / LATERAL JOIN / Gap&Island
-- TOP-N per Group (학과별 성적 상위 3명) — 3가지 방법
-- 1) Window Function (가장 추천)
SELECT * FROM ( SELECT s.name, e.score,
  ROW_NUMBER() OVER (PARTITION BY s.major_id ORDER BY e.score DESC) AS rn
  FROM students s JOIN enrollments e ON e.student_id=s.id ) ranked WHERE rn<=3;
-- 2) LATERAL JOIN (PostgreSQL, 행별 독립 서브쿼리)
SELECT m.name, top3.name, top3.score FROM majors m
CROSS JOIN LATERAL ( SELECT s.name, e.score FROM students s JOIN enrollments e ON e.student_id=s.id
  WHERE s.major_id=m.id ORDER BY e.score DESC LIMIT 3 ) top3;
-- Gap & Island: 연속 구간 찾기 (연속 로그인 등)
SELECT MIN(login_date), MAX(login_date), COUNT(*) FROM (
  SELECT login_date, login_date - ROW_NUMBER() OVER (ORDER BY login_date)*INTERVAL '1 day' AS grp
  FROM user_logins ) t GROUP BY grp;

17. 인덱스 설계 및 최적화

B-Tree · Hash · GIN · GiST · BRIN · 복합 인덱스 · 커버링 인덱스

💡
쉽게 말하면: 책의 '찾아보기(색인)'와 완전히 같은 개념이에요. 인덱스가 없으면 처음부터 끝까지 다 뒤지고(Full Scan), 있으면 바로 찾아갑니다.

인덱스 개념 및 트레이드오프

  • 인덱스 없음: Table Full Scan = O(N) / 인덱스: B-Tree 탐색 O(log N) — 수백만 행에서 수십ms 차이
  • 트레이드오프: 읽기 성능↑ vs 쓰기 비용↑(INSERT/UPDATE/DELETE시 재정렬) vs 저장공간 증가
  • 설계원칙: WHERE 자주 등장 컬럼 우선, 선택도(Selectivity) 높은 컬럼, FK 컬럼 필수, 미사용 인덱스 제거
B-Tree 인덱스 성능 비교 실습
-- Before: 인덱스 없이 (100만건)
EXPLAIN ANALYZE SELECT * FROM query_logs WHERE user_id='u123';
-- Seq Scan (actual time=120..1850)  ← 1850ms
CREATE INDEX idx_query_logs_user ON query_logs(user_id);
-- After: 인덱스 적용 후
-- Index Scan (actual time=0.05..0.8) ← 0.8ms (약 2,300배 향상)
인덱스 생성 명령어 모음
-- 복합 인덱스: 선두 컬럼 원칙(leftmost prefix rule)
CREATE INDEX idx_orders_cust_date ON orders (customer_id, order_date DESC);
-- 커버링 인덱스: SELECT 컬럼이 모두 인덱스에 있으면 테이블접근 불필요 → Index Only Scan
CREATE INDEX idx_customer_cover ON customers (customer_id) INCLUDE (name, email);
-- 부분 인덱스(Partial Index): 특정 조건 행만 인덱싱 → 크기↓속도↑
CREATE INDEX idx_orders_pending ON orders (created_at) WHERE status='PENDING';
-- 함수 기반 인덱스
CREATE INDEX idx_users_email_lower ON users (LOWER(email));
-- CONCURRENTLY: 운영 중 잠금 없이 생성
CREATE INDEX CONCURRENTLY idx_products_category ON products (category_id);
✔ Checkpoint
  • 복합 인덱스 설계: 등호(=) 조건 컬럼 먼저 → 범위(<,>) 조건 나중, 선택도 높은 컬럼 우선
  • 선두 컬럼 포함 시 사용 가능 (customer_id=5 / customer_id=5 AND order_date>.. / customer_id=5 ORDER BY order_date)
  • 선두 컬럼 없이 order_date만 조건이면 사용 불가

인덱스 심화 — B-Tree 내부구조 & 커버링 인덱스

  • B-Tree = Balanced Tree: 모든 리프노드가 같은 깊이 → O(log N) 탐색 보장
  • 키가 작을수록 노드당 항목 많음 → 트리 깊이 감소 → 빠름 (UUID 16바이트 vs BIGINT 8바이트 → UUID가 더 큰 트리)
  • Fill Factor(기본 90%): UPDATE 많은 테이블은 낮추면(예:70%) 페이지 분할(Split) 감소
  • Index Only Scan: 커버링 인덱스로 Heap Fetches=0 달성 → 테이블 접근 없이 인덱스만으로 응답 (가장 빠름)

명령 동작
EXPLAIN추정 실행계획만 표시(쿼리 실행 안 함)

실행계획을 읽어야 하는 상황

  • 쿼리가 갑자기 느려졌을 때 / 인덱스 만들었는데 안 쓰이는 것 같을 때
  • JOIN 방식이 이상할 때(Hash vs Nested Loop) / rows 예측값과 actual rows 크게 다를 때(통계 갱신 필요)
  • 시각화 도구: explain.dalibo.com (PostgreSQL JSON 플랜 붙여넣기)
PostgreSQL EXPLAIN ANALYZE — 플랜 읽기
BEGIN;
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT)
SELECT s.name, c.title, e.score FROM students s
 JOIN enrollments e ON e.student_id=s.id JOIN courses c ON c.id=e.course_id
WHERE s.major_id=1;
ROLLBACK; -- DML이면 롤백
-- Hash Join (cost=12.5..45.8 rows=200) (actual time=0.5..2.3 rows=185)
-- Buffers: shared hit=12 read=5  (hit=메모리, read=디스크)
-- Seq Scan on enrollments ← 인덱스 없음! 추가 검토
-- Planning Time: 0.2ms / Execution Time: 2.5ms
✔ Checkpoint
  • Hash Batches > 1 → 메모리 Spill 발생 → work_mem 증가 검토
  • 예측 rows와 실제 rows 차이 크면 → ANALYZE 필요

타 DBMS 실행계획 확인

  • MySQL: EXPLAIN FORMAT=JSON — access_type:'ALL'=Full Scan(나쁨), 'range'=범위 인덱스(좋음). 8.0.18+ EXPLAIN ANALYZE 지원
  • SQL Server: SET SHOWPLAN_ALL ON / Oracle: SET AUTOTRACE ON

19. SQL 튜닝 & 느린 쿼리 식별

안티패턴 · Slow Query · pg_stat_statements · 파티셔닝

💡
쉽게 말하면: 느린 쿼리를 빠르게 고치는 노하우 모음이에요. 대표적인 8가지 실수 패턴만 기억해도 절반은 해결돼요.
SQL 튜닝 8대 안티패턴
-- 1) 인덱스 컬럼에 함수 적용 → 인덱스 무력화
-- X: WHERE YEAR(order_date)=2024   /  O: WHERE order_date>='2024-01-01' AND order_date<'2025-01-01'
-- 2) SELECT * → 불필요한 데이터 + 커버링 인덱스 불가.  O: 필요한 컬럼만 명시
-- 3) 암묵적 타입변환 → 인덱스 무력화.  X: WHERE user_id='12345' (INT 컬럼)  O: WHERE user_id=12345
-- 4) LIKE 앞 와일드카드 → 전체스캔.  X: LIKE '%길동%'  O: LIKE '홍%' 또는 GIN+pg_trgm
-- 5) N+1 문제: 루프 안에서 개별쿼리(1+N번) → 한번의 JOIN으로 처리
-- 6) NOT IN + NULL 함정 → NOT EXISTS로 변경
-- 7) DISTINCT 남용(원인 파악없이 제거) → EXISTS로 존재여부만 확인

20. MVCC & 트랜잭션 격리 수준

다중버전 동시성 제어 · Isolation Level · DBMS별 실습

💡
쉽게 말하면: 여러 사람이 동시에 DB를 봐도 서로 안 꼬이게 하는 방법이에요. 핵심은 '수정해도 옛날 버전을 잠깐 남겨둔다(다중버전)'는 것.

MVCC(Multi-Version Concurrency Control) 심화

  • 데이터 수정 시 In-place 덮어쓰기 대신 새 버전 레코드 생성. 각 트랜잭션은 시작시점 스냅샷 보유 → 읽기가 쓰기를 차단하지 않음
  • PostgreSQL: 각 행에 xmin/xmax 시스템컬럼, UPDATE=새버전 INSERT+구버전 xmax 갱신. Dead tuple은 VACUUM이 회수. 장수 트랜잭션은 VACUUM 차단→Table Bloat 주의
  • MySQL InnoDB: Undo Log(변경전 데이터 별도 저장), Read View(TX시작시 스냅샷), Purge Thread(불필요 undo 자동정리)
Isolation Level 실습 — RC vs RR vs Serializable
-- Read Committed(기본): 커밋된 최신 데이터 읽음 → Non-Repeatable Read 발생 가능
BEGIN ISOLATION LEVEL READ COMMITTED;
SELECT balance FROM bank WHERE name='Alice'; -- 1000
-- (다른 세션이 800으로 UPDATE+COMMIT)
SELECT balance FROM bank WHERE name='Alice'; -- 800 (바뀜!)
-- Repeatable Read: 트랜잭션 내 항상 같은 값(스냅샷 유지)
BEGIN ISOLATION LEVEL REPEATABLE READ;
SELECT balance ...; -- 1000
-- (다른 세션 UPDATE+COMMIT 해도)
SELECT balance ...; -- 여전히 1000
-- Serializable: 가장 엄격, 충돌 시 강제 실패
-- ERROR: could not serialize access due to concurrent update (에러코드 40001, 앱에서 재시도 필요)

21. Lock & Deadlock 관리

Row Lock · Advisory Lock · 감지 · 해소 · 모니터링

💡
쉽게 말하면: 두 작업이 서로 상대방이 가진 걸 기다리다 영원히 멈추는 상황(교착상태, Deadlock)과 그 해결법이에요.

Lock 종류 및 PostgreSQL Lock 구조

  • Row-Level Lock(Tuple Lock): 행단위 충돌방지(UPDATE/DELETE) / Table-Level Lock: ACCESS SHARE~ACCESS EXCLUSIVE / Advisory Lock: 사용자정의 논리락
  • FOR UPDATE(배타적 락, 대기) / FOR UPDATE NOWAIT(즉시 ERROR) / FOR UPDATE SKIP LOCKED(잠긴행 건너뜀 — 작업큐 처리에 유용)
SKIP LOCKED 패턴 (분산 작업큐/배치처리 필수 패턴)
-- SKIP LOCKED: 여러 Worker가 중복없이 작업 큐 분배 (경쟁 소비자 패턴)
WITH picked AS (
  SELECT id FROM job_queue WHERE status='READY' ORDER BY id
  FOR UPDATE SKIP LOCKED LIMIT 10 )
UPDATE job_queue SET status='RUNNING' FROM picked WHERE job_queue.id=picked.id
RETURNING job_queue.*;
Deadlock 발생 구조와 해소법
-- Deadlock: 교차대기 (Session1: row1잠금→row2요청 / Session2: row2잠금→row1요청)
-- → 순환대기! PostgreSQL이 자동감지 → ERROR: deadlock detected → 한쪽 자동 ROLLBACK
-- 해결1: 항상 동일 순서로 Lock 획득(ORDER BY id) — 핵심!
WITH targets AS (SELECT id FROM items WHERE id=ANY(ARRAY[1,2]) ORDER BY id FOR UPDATE)
UPDATE items SET stock=stock-1 FROM targets WHERE items.id=targets.id;
-- 해결2: 트랜잭션 짧게 유지 (HTTP호출/파일I/O는 트랜잭션 밖에서)
-- 해결3: Advisory Lock으로 업무단위 직렬화: SELECT pg_advisory_xact_lock(42);
-- 해결4: 재시도 전략(에러코드 40P01) — 지수 백오프 + Jitter
Deadlock 모니터링
-- 대기 중인 세션 확인 (blocking/waiting)
SELECT bl.pid AS waiting_pid, wl.pid AS blocking_pid, bl.query AS waiting_query
FROM pg_catalog.pg_locks l1 JOIN pg_catalog.pg_stat_activity bl ON bl.pid=l1.pid
JOIN pg_catalog.pg_locks l2 ON l1.locktype=l2.locktype AND l1.pid<>l2.pid
JOIN pg_catalog.pg_stat_activity wl ON wl.pid=l2.pid WHERE NOT l1.granted AND l2.granted;
-- 세션 강제 종료
SELECT pg_cancel_backend(pid);    -- 쿼리만 취소(graceful)
SELECT pg_terminate_backend(pid); -- 연결 자체 종료(강제)

22. 고급 DB 설계

💡
쉽게 말하면: 정규화를 더 깐깐하게(BCNF) 하거나, 반대로 성능을 위해 일부러 중복을 허용(반정규화)하거나, 데이터가 너무 많을 때 여러 서버로 쪼개는 것(샤딩)까지 다루는 심화 설계예요.

BCNF (Boyce-Codd Normal Form)

  • 조건: 모든 결정자(Determinant)가 후보키(Candidate Key)여야 함
  • 예: 학습지원(교수,과목,강의실) — 교수→강의실 함수종속(교수는 항상 같은 강의실) → 교수는 후보키 아닌데 강의실을 결정 = BCNF 위반
  • 해결: 교수강의실(교수,강의실) + 강의배정(교수,과목) 두 테이블로 분리
  • 3NF: 함수종속 보존 우선(비후보 결정자 허용 가능) vs BCNF: 정합성 우선(엄격). 실무는 3NF까지 적용(JOIN비용·복잡도 고려)

정규화 vs 반정규화 선택

정규화 유지(OLTP) 반정규화 허용(OLAP)

함수 예시 — 4개 DBMS (부가세 계산)
-- PostgreSQL: IMMUTABLE이면 함수기반 인덱스에도 사용 가능

CREATE FUNCTION fn_vat(amount DECIMAL(10,2)) RETURNS DECIMAL(10,2) DETERMINISTIC
BEGIN RETURN amount * 0.1; END;
-- Oracle: RESULT_CACHE(결과 메모리 캐시)
CREATE OR REPLACE FUNCTION fn_vat(p_amount NUMBER) RETURN NUMBER RESULT_CACHE DETERMINISTIC
IS BEGIN RETURN p_amount * 0.1; END;

  • 앱 코드가 나은 경우: 자주 바뀌는 비즈니스 로직, 외부 API 연동, 복잡한 조건분기
  • 예외처리: PostgreSQL EXCEPTION 블록 / MySQL DECLARE HANDLER / Oracle EXCEPTION WHEN / SQL Server TRY...CATCH
PostgreSQL SP 실전 예 — 주문 생성 (재고부족 시 자동 ROLLBACK)
CREATE OR REPLACE PROCEDURE sp_create_order(p_customer_id BIGINT, p_items JSONB)
LANGUAGE plpgsql AS $$
DECLARE v_order_id BIGINT; v_item JSONB; v_stock INT;
BEGIN
  INSERT INTO orders (customer_id, status) VALUES (p_customer_id,'created') RETURNING id INTO v_order_id;
  FOR v_item IN SELECT * FROM jsonb_array_elements(p_items) LOOP
    SELECT stock_qty INTO v_stock FROM products WHERE id=(v_item->>'product_id')::INT FOR UPDATE; -- 동시성 처리
    IF v_stock < (v_item->>'qty')::INT THEN
      RAISE EXCEPTION '재고 부족: product_id=%', (v_item->>'product_id');  -- EXCEPTION시 자동 ROLLBACK
    END IF;
    UPDATE products SET stock_qty = stock_qty - (v_item->>'qty')::INT WHERE id=(v_item->>'product_id')::INT;
  END LOOP;
  UPDATE orders SET status='paid' WHERE id=v_order_id;
END;$$;

-- Row-level Trigger
CREATE OR REPLACE FUNCTION trg_sales_ai() RETURNS trigger AS $$
BEGIN INSERT INTO audit_log(table_name,op,row_json) VALUES ('sales', TG_OP, to_jsonb(NEW)); RETURN NEW; END$$ LANGUAGE plpgsql;
CREATE TRIGGER sales_ai AFTER INSERT ON sales FOR EACH ROW EXECUTE FUNCTION trg_sales_ai();
-- Statement-level + Transition table (대량 DML에 효율적)
CREATE TRIGGER sales_stmt_ai AFTER INSERT ON sales REFERENCING NEW TABLE AS new_table
FOR EACH STATEMENT EXECUTE FUNCTION trg_sales_stmt_ai();

  INSERT INTO ddl_history(event_tag, object) VALUES (r.command_tag, r.object_identity); END LOOP; END$$ LANGUAGE plpgsql;

28. 데이터 웨어하우스 & 분석 DB

OLTP vs OLAP · 파티션 프루닝 · 벡터화 실행 · Redshift · BigQuery · Snowflake · ClickHouse

💡
쉽게 말하면: 우리가 지금까지 배운 DB(OLTP, 실시간 거래처리용)와 분석·보고서 전용 DB(OLAP)는 애초에 설계 목적이 다르다는 걸 짚고 가는 파트예요.

분석 DB 핵심 기술 3가지

  • 파티션 프루닝: 필요한 날짜/범위 파티션만 읽음 (BigQuery PARTITION BY DATE, Snowflake 마이크로파티션, ClickHouse PARTITION BY)
  • 컬럼 프루닝: SELECT한 컬럼만 읽음 — SELECT * 절대 금지! (스캔 바이트=과금 기준)
  • 벡터화 실행: 컬럼단위 벡터(1000개씩)로 SIMD 처리 — BigQuery/Snowflake/DuckDB/ClickHouse 모두 채택

스타 스키마 & DW 설계 원칙

  • 스타 스키마: 팩트테이블(거래·이벤트, append-only, 시간파티션) + 디멘전테이블(사용자/상품/시간, SCD Type2)이 별모양으로 둘러쌈
  • Surrogate Key(디멘전 대체키), 역할차원(Role-Playing: 날짜 하나로 order_date/ship_date 별칭), Junk Dimension, Conformed Dimension(여러 마트 공용)
  • 스노우플레이크 스키마: 디멘전을 다시 정규화(계층 자주 바뀔 때) / 3NF DW: 원천레이어는 3NF, 소비레이어(mart)는 스타
BigQuery 파티션·클러스터 + ClickHouse MergeTree
-- BigQuery: 파티션+클러스터
CREATE TABLE mart.fact_sales PARTITION BY DATE(event_ts) CLUSTER BY user_id, item_id AS
SELECT event_ts, user_id, item_id, qty, amount FROM stg.sales_cleaned;
-- ClickHouse: MergeTree 엔진 (초고속 실시간 OLAP)
CREATE TABLE fact_events (event_time DateTime, user_id UInt64, amount Decimal(12,2))
ENGINE=MergeTree PARTITION BY toDate(event_time) ORDER BY (user_id, event_time)
TTL event_time + INTERVAL 90 DAY;

pg_basebackup -U replicator -D /backup/base -Ft -z -P --wal-method=stream
-- postgresql.conf: wal_level=replica, archive_mode=on, archive_command='cp %p /backup/wal/%f'
-- 복구 시점 지정: recovery_target_time = '2024-12-15 14:30:00'
